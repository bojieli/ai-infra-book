# 算子与运行时分析

适用：有算子 trace、kernel 计时或编译方案，想解释局部优化能否缩短完整请求。依据 `manuscripts/05-算子与运行时.md` 第 5.1—5.6 节。

1. 记录张量形状、精度、布局、tile、寄存器或片上存储占用、有效带宽和 kernel 启动次数；确认优化前后工作量是否相同。
2. 追踪数据被读写和复用的次数。融合/预计算节省的外部访存，要与额外片上空间、占用率下降、重算或准备开销比较。
3. 按依赖检查分块、流水、事件与缓冲区复用；数据未就绪前不可读取，消费者完成前不可释放。
4. 在完整请求 trace 中定位该阶段的关键路径占比，区分可重叠的传输与必须等待的同步。用相同输入和预热条件复测总时间。

输出瓶颈证据、预期节省与实际端到端变化。单个 kernel 加速而任务无明显变化时，先检查是否被其他阶段遮蔽，不直接归因于测量错误。

## 可执行练习：在访问预算内选择 CPU 矩阵乘内核

从仓库根目录运行 `python3 skills/kernel-runtime-analysis/examples/tune_matmul.py --slice-budget-bytes 256`。需要 Python 3 和 C 编译器。基线按单个输出点做点积，候选内核改变循环顺序并把输出列分块。预算按同一次内层扫描覆盖的 B 行片段和 C 行片段字节计，不代表整个工作集或实测缓存占用。

脚本先排除超预算的候选，用独立 Python 参考结果逐元素检查单点、非整块边界及计时形状，再打散顺序测量 11 轮。只有候选中位耗时比基线低至少 5% 才采用；否则保留基线。JSON 记录每个候选、拒绝原因、实测时间和最终 tile。把预算降到 8 可验证保留基线的路径。要试验新的遍历方式，修改同目录的 matmul.c 并重新运行相同门槛。此练习测量本机 CPU 上的整数算子，不推算 GPU 或整条请求的收益。
