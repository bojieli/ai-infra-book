# 优化结果与 Agent 执行记录

2026-09-08 核对。由[第四批面试资料](../references/interviews/2026-09-08/fourth-pass/README.md)检验第 5、12、13 章的回答能力：优化改变了什么、任务到底完成了什么、哪些记录足以支持这个判断。这里只做源码阅读与教学计算，没有执行考核程序、模型或云端服务。

## 固定机器之后，才有可比较的加速

Anthropic 在 2026 年公开的是历史性能考核的改编版本，官方说明已经更换限时考核的基础题。固定仓库 `5452f74bd977807ac2e74f3d29432b9df6f25197` 的 [README](../references/interviews/2026-09-08/fourth-pass/takehome-readme.md)和[提交测试](../references/interviews/2026-09-08/fourth-pass/takehome-tests.py)需一起读：公开慢基线为 147,734 个模拟周期，后来两小时考核的起点为 18,532；官方模型成绩使用后一个起点，不能拿不同准备条件排列人和模型的能力。

[机器定义](../references/interviews/2026-09-08/fourth-pass/takehome-problem.py)是自定义单核 VLIW／SIMD 模型，向量宽度 8，scratch 为 1,536 个 32-bit word，即 6 KiB；各执行部件有每周期发射槽位限制。每束指令先读旧值，写入在周期末生效。它没有真实 GPU 的缓存、HBM 延迟和并发干扰模型，因此模拟周期不能换算为 GPU 毫秒。

沿[未优化基线](../references/interviews/2026-09-08/fourth-pass/takehome-kernel.py)做一次静态计数。256 个输入、16 轮，共 4,096 次节点处理；每次有 29 条标量 ALU、3 条 load、2 条 store、2 条 flow，未计 debug。基线每束只放一条，循环共 `4096×36=147456` 周期；加初始化和两条 pause 的 278，恰为 147,734。正式测试虽不暂停，flow 指令仍占模拟周期；debug 单独一束则不计周期。

如果**保持这份指令集合不变，只重新安排发射**，各部件给出的循环下界分别为 `ceil(118784/12)=9899`、`12288/2=6144`、`8192/2=4096`、`8192/1=8192` 周期。取最大值只得到资源下界，依赖仍可能使它不可达到；指令数减少、向量化或复用改变之后，必须重新计数。另一个有用反问是：若每次节点处理坚持发一条标量节点 load，仅它就至少需 2,048 周期，已经高于 README 中 1,363 的历史成绩。这只能否定“每次都要发这条 load”的限制，不能宣布成绩违反物理下界。

回到 Qwen3 算子优化，采用的是这个检查过程，不把树遍历增设为全书主实验。固定参考实现、形状、精度、设备数及验证入口；Agent 可以提出扩大资源或改变语义的方案，但要另列为新条件。静态字节与指令预算排除不可能的宣传，再用真实 trace 检查关键路径。官方提交测试从 frozen copy 导入机器，随机生成输入，主要比较最终输出 values；这是特定题目的契约，不保证任何 GPU 算子、输入形状或业务状态都正确。没有运行这些测试，也没有把公开旧阈值写成当前录用标准。

## 诊断 trace 与可恢复的任务记录

MiniMax 平台研发的一位候选人分别记录数据采集可靠性、Agent 反馈与生命周期观测的追问。这是一名候选人的两轮经历，未经本书独立核实；不能推成 MiniMax 的 GPU 内核考题。它暴露的教学缺口是：第 12 章已经讲工具重试，却还应说明用什么记录判断一次逻辑操作完成、哪些尝试真的花了资源。

沿代码 Agent 的测试工具安排三种记录。任务结果记录保存任务、步骤、逻辑操作与尝试身份、输入／文件版本、结果及持久化位置，服务于续接和计费；诊断 trace 关联模型、排队、环境与工具 span，用于定位延迟，可以按目标采样；训练反馈引用满足准入条件的完整轨迹，并保留行为版本、验证器与奖励来源。三者可以共享基础存储和身份，所需完整性及保留策略却不同，不能仅凭 trace 中没有错误推断任务成功。

[OpenTelemetry 的采样指南](../references/interviews/2026-09-08/fourth-pass/otel-sampling.html)区分早期决定保留与根据结果选择的 tail sampling。前者可能错过稀有错误，后者需要缓冲并改变保留分布；二者叠加也不能找回上游已经丢弃的数据。本书的推论是：采样 trace 不适合作为完整费用账本；偏向保留错误的 trace 集合也不能据此声称保持了自然请求或既定 RL 采样分布。有意选择难例是另一个训练决定，需按相应目标验证。

网络恢复并不自动消除数据缺口。[Collector 韧性指南](../references/interviews/2026-09-08/fourth-pass/otel-resiliency.html)明确列出队列满、重试到期、进程崩溃和持久化存储故障等丢失条件。WAL 与消息队列增加可承受故障的范围，但应用尚未发出的事件、到期和磁盘问题仍要另查；配置中的 queue size 还可能按请求／batch 计，不能直接填入下面算出的字节数。

## 先算积压，再讨论重试保证

教学输入沿第 12.1 节的 **10 tasks/s**：每任务 20 条必须保留的结果／状态事件，平均每条序列化载荷 2 KiB，折合 **200 events/s、400 KiB/s**。假定这一到达流在故障期间稳定，后端中断 120 s，入口仍接受事件，则新增 **24,000 条、46.875 MiB** 载荷。若可用于这些载荷的缓冲只有 32 MiB，约 **81.92 s** 后耗尽；若为 64 MiB，载荷预算可容纳本次积压，尚需为索引、WAL、批次和进程开销另留容量。这不是任何产品默认配置的保证。

恢复后给定有效排出能力 1 MiB/s，新的 400 KiB/s 仍继续到达，所以净排空速度为 **624 KiB/s**，约需 **76.92 s**。不能把 `46.875 MiB / 1 MiB/s` 的 46.875 s 当作恢复完成时间；若有效排出速度不超过到达速度，积压不会消退。若把这条必需记录流采样到 1%，平均只剩 4 KiB/s，却同时改变了完整记录的要求，不是免费修复容量问题。

再把故障放到“工具已经完成、确认丢失”这个具体位置。区分同一操作结果的重传与真正重新执行的尝试：前者应去重，后者的 CPU／API 成本仍要保留。为外部操作使用稳定的逻辑操作身份，核对结果是否已提交，再选择查询、续接或重新执行；不能仅凭客户端超时判定没有副作用。

[Kafka 4.2 的交付语义](../references/interviews/2026-09-08/fourth-pass/kafka-delivery.html)将生产重试去重、消费位置与输出的一致提交分开。其事务能力在相应 Kafka 读写范围内成立；写外部系统仍需对方配合。对 Agent 来说，队列中只有一条工具消息，并不能证明外部操作只发生一次；对 E2B 来说，恢复 VM 快照也不会回滚环境外的操作。实验通过固定故障点核对状态，而不是测试几次没重复就声称 exactly-once。
