# 训练卸载中的转换、传输与更新位置

> 当前落点：10.1.2、实验 10-1、图 10-1；承接 5.2.3 的主机缓冲与生命周期。配套研究笔记，尚非书稿或实测报告。

## 从同一条梯度路径比较

卸载省下显存后，仍要问 CPU 是否来得及更新参数。SuperOffload 的价值是把卸载重新画成计算与传输图：类型转换在哪一端执行、哪些更新留在 GPU、哪些全局检查会阻止下一步开始。这里选取其中一个能独立推算的决定，不将整套系统展开为功能列表。

使用本书固定 [Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)的一层 gate 投影，矩阵为 `[12288,4096]`，共 50,331,648 个元素。假定 GPU 已产生 BF16 梯度，CPU Adam 消费 FP32 梯度；本例只计梯度从就绪到 CPU 可消费的路径，主权重、Adam 两项状态、参数返回和其他层另算。

BF16 梯度为 **96 MiB**，FP32 为 **192 MiB**。比较两种执行顺序：

- 先传 96 MiB，再由 CPU 转为 FP32。
- 先由 GPU 转为 FP32，再传 192 MiB。

两侧转换都至少读入 2 字节、写出 4 字节，共访问 `6N` 字节。令 `C_CPU`、`C_GPU` 为这次转换的有效读写吞吐，`B` 为所用方向的有效链路吞吐：

`T_CPU = 2N/B + 6N/C_CPU`

`T_GPU = 6N/C_GPU + 4N/B`

两条路径内部有先后依赖，本例串行相加。双方都预先分配锁页主机缓冲，不借未锁页基线制造差距。启动、分配、资源争用和多个块之间的重叠暂不计。

取教学输入 `C_CPU=100 GB/s`、`C_GPU=1500 GB/s`，不是 GH200 测量值。转换分别约 3.020 ms、0.201 ms：

| 有效单向链路 | 传 BF16 后 CPU 转换 | GPU 转换后传 FP32 | 本条件下较快的选择 |
|---|---:|---:|---|
| 32 GB/s | 6.166 ms | 6.493 ms | CPU 转换 |
| 300 GB/s | 3.355 ms | 0.872 ms | GPU 转换 |

交点约为 **35.714 GB/s**，来自 `2N/B = 6N/C_CPU − 6N/C_GPU`。在这个忽略固定开销的模型里 N 消去；实际小张量有启动与吞吐爬升，交点还会随尺寸变化。减少链路字节与减少这段完成时间因此可能给出不同选择。

再检查容量：不计两条路径共有的 GPU BF16 梯度，CPU 转换需要主机 96 MiB 暂存和 192 MiB 输出；GPU 转换需要额外 192 MiB GPU 暂存，主机只存 192 MiB 输出。后一条路径虽可能更快，也可能因 HBM 不足而不可行。分块可以降低暂存，却增加启动并改变吞吐；回到第 5 章的缓冲时序继续算。[脚本](../research/2026-infra-survey/calculate_superoffload.py)和[数值结果](../research/2026-infra-survey/superoffload-arithmetic.json)保留单位和全部假设。

## 论文能支持的判断

选读 [SuperOffload 的 2025-09-25 arXiv v1](../references/proceedings/ASPLOS/2026/paper-023.pdf)物理页 3–12、16，涵盖设计、评估和模型／基线附录；正式 ASPLOS 2026 身份另由日程 DOI 核对，不能把早期稿当成正式版本全文。页级记录见[阅读范围](../references/proceedings/ASPLOS/2026/superoffload-reading.json)。

§4.5 与图 9 比较转换连同传输的耗时。作者的旧路径还产生了未锁页临时缓冲，故其性能差距同时包含转换放置和实现路径的影响。上面的教学例刻意让双方使用锁页缓冲；后续实测应先分离这两个原因，不能直接套用论文倍率。

§4.3 将最后就绪的若干梯度桶及其更新留在 GPU，目的是缩短下一次前向之前的尾部。CPU 更新和参数回传必须落在尚余的反向／GPU 更新窗口内；链路再快也不能消除优化器计算。每增加一个 GPU 桶，还须补算 FP32 主权重、动量、方差与暂存。图 7 的约 64 MB 是该测量中吞吐趋于饱和的尺寸，不是所有互联的最佳桶大小。

§4.4 的推测更新是在全局梯度检查完成前先做工作，验证失败后撤销或重做。其收益取决于正常路径省时与失败概率乘恢复代价；需要保留权重、优化器状态、步数及受影响前向的正确语义。§5.7 给出的 93 次／79,000 次及约 2 秒恢复只覆盖该报告的训练区间，不证明新模型 warmup、Muon 或全部随机状态可以照搬。正文暂不展开另一套推测执行流程。

评估采用特定 GPT／LLaMA 风格配置；附录中的“13B”为 65 层、宽度 4096，不能当成 Qwen3 或通用 Llama-13B。单芯片与多芯片分别使用 96 GB HBM 搭配 480 GB／240 GB 主机内存；§5.1 的双芯片节点与 §5.4 的四芯片节点描述不同，未将其作为统一拓扑复算。§2.2 的“H100 96GB”字样不作为产品规格。900 GB/s 的双向总量与 §4.2 的 450 GB/s 单向上限也不能混用。

表 2 的五项吞吐为 116.20、128.23、144.49、209.36、238.92 TFLOPS，是按固定次序逐项启用后的结果；它们说明组合后的变化，不提供任意组合的独立收益。算法 FLOPs 排除了重计算，GPU 忙碌时间不等于 MFU。所有型号上限和长序列结果继续限定在论文的配方与测量范围。

## 接回真实系统实验

[官方实现与教程快照](../references/framework-history/2026-09-08/training-superchip/README.md)将这个问题接到 DeepSpeed ZeRO-3。v0.18.0 的配置包含 `super_offload`、优化器卸载比例和 CPU 核比例；当前固定示例使用 Qwen3-14B。先用本书 8B 的矩阵完成纸笔推算，再用受支持的 GH200 配置或同一配置的配套记录分析真实更新过程，不能声称 8B 纸笔算例已经运行。

实验 10-1 的延伸按转换、传输、CPU Adam、GPU 更新和全局检查分别记录时间与峰值容量。先核对两组生成配置：示例的 SuperOffload 模式同时设置 `ratio=0.90`，对照模式未显式给 ratio，不能把整个差距归于一个开关。示例虽建议 NUMA 绑定，所选启动脚本未加对应参数；执行前需固定亲和性。依赖表只要求 `deepspeed>=0.17.0`，而发布文章说明 SuperOffload 在 0.18.0 起可用，正式实验应锁定已核对版本，不能照抄宽松依赖便视为可复现。
