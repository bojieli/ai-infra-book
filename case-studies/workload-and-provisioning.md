# 请求分布与推理资源配置

这份扩写笔记连接第 3.1 节的负载、第 9.2 节的 PD 配比和第 11.3 节的资源准备。先按具体请求算需求，再检查混合比例在时间上怎样变化。ServeGen 是负载生成工具，vLLM／SGLang 是论文中被评估的推理引擎；两者的角色分开说明。

## 生产负载提供的依据

已读 [ServeGen，NSDI 2026](../references/proceedings/NSDI/2026/selected/nsdi26-xiang-servegen.pdf)物理页 2–13（正文印刷页 1845–1856），逐页文本与官方整卷一致。研究来自阿里云 Model Studio 的 12 个模型，合计约 35.4 亿请求；收集横跨四个月，但表 1 中各模型的分析窗口分别为一周或一个月，不能写成每个模型均连续观察四个月。

采用其客户分解思路：同一个客户的请求形状较稳定，不同客户的速率变化会改变整体长度分布。保留“请求何时来、来自哪类客户、输入输出多长”的关联，再检查短时间窗中的资源需求。生成器用于补充真实记录，不能以均值和边际直方图相同认定两个负载等价。

§6.3 用 Qwen2.5-14B、每实例两张 A100 80GB、PP 的 vLLM 服务检验实例规划。论文在 P99 TTFT 2.25 秒、TBT 0.5 秒的一个设置中，真实负载需要 24 个实例，ServeGen 估计为 25，NAIVE 为 12。§6.4 则用 Qwen2.5-72B、四台八卡 H20、TP4 的 SGLang PD 服务；部分 SLO 下，两种生成方式选出的池配比不同。这里只引用论文报告，未复现实测；已读正文没有定位精确引擎提交。历史模型、硬件与 SLO 保留，不能将其配比移作 Qwen3 或 V4 的结论。

§7 明确留下工具调用和前缀缓存两项限制。公开的是参数化、脱敏的数据及选择性哈希化的对话，不能从中直接推断 Agent 工具依赖、真实缓存命中率或语义正确性。第 3.1.3 的 Agent 轨迹和第 9.5 节的缓存实验继续使用各自的记录。图像预处理与 reasoning 输出只作为已有负载的补充，不展开新的背景章节。

## 同样四个请求每秒，哪一池会积压

给 Qwen3-8B 构造两类教学请求：A 输入 8,192、输出 256 token，B 输入 1,024、输出 2,048 token。假定无前缀命中，先不计 KV 交接和批处理效率变化。每个 P 实例有效处理 16,384 输入 token/s，每个 D 实例有效处理 2,048 个序列-token decode 步/s；这些速率是教学假设，不是 GPU 规格或框架测量。与第 9 章逐请求算例统一：P 产生首个输出 token，A／B 随后分别需要 255／2,047 个 decode 步。一次批执行按参与的各序列 token 计量，不能把该速率理解为 kernel 调用次数。

两份记录都持续 120 秒，以 4 requests/s 到达，共 480 个请求，A、B 各 240 个：

- 均匀混合：每个 60 秒窗口均为 A、B 各 120 个。
- 时段变化：前 60 秒 A、B 为 216／24 个，后 60 秒反过来。

两者全局平均输入均为 4,608、输出均为 1,152 token。平均交付需求是 18,432 输入 token/s 和 4,608 输出 token/s；扣除 P 每秒产生的 4 个首 token，D 的需求为 4,604 步/s，对应 1.125 个 P、约 2.248 个 D 的工作量。因此按均值先选 2P3D，只能得到一个候选配置。

| 时间窗 | 输入需求（token/s） | D 需求（序列-token 步/s） | 连续容量折算 P／D |
| --- | ---: | ---: | ---: |
| 均匀混合，两窗相同 | 18,432 | 4,604 | 1.125／约 2.248 |
| 时段变化，前 60 秒 | 29,900.8 | 1,736.8 | 1.825／约 0.848 |
| 时段变化，后 60 秒 | 6,963.2 | 7,471.2 | 0.425／约 3.648 |

3D 的假设服务能力为 6,144 个序列-token decode 步/s。把待生成工作视为连续流体、暂时忽略 P 阶段依赖，第二窗每秒多出 1,327.2 步，60 秒积压 79,632 步；即使之后没有新工作，仍需约 12.961 秒才能排空。这是简化输出工作队列的计算，不是每个请求的延迟，也不能据此声称 P99 为 13 秒。真实请求还要经历 prefill、KV 搬移、连续批处理和状态增长。

固定 2P4D 能通过这里的逐窗速率检查，但仍须验证尾延迟和 KV。也可以考察同样五个实例由 2P3D 换成 1P4D：后窗的 P 需求允许这种安排，角色准备、权重与状态交接却需要时间。第 11 章沿实际启动记录比较多留热副本和等待重配；不能将瞬时切换当成免费资源。

此前把全部输出计给 D 的粗估为 79,872 token 积压和 13 秒排空；逐请求计入首 token 后，差异为 240 步、约 0.039 秒，2P3D／2P4D 的选择判断不变。短输出请求则不能忽略这一项。

这一步只用加乘和速率比较就排除了一个过于乐观的均值判断。随后才把逐请求记录接入真实引擎，测量积压与 SLO。算式及输入保存在[阶段计算](../research/2026-infra-survey/arithmetic.json)的 `workload_mix_teaching`。

## 实验接入与源码核对

[ServeGen 固定源码](../references/framework-history/2026-09-08/workload-generation/README.md)为 `d70c8b2d5bc45f4b60a146fbc43dc5523f871c8b`。已完整阅读 README 与 `construct.py`，未导入或执行下载代码。当前生成入口还需要实验侧核对：

- `_sample_iats` 将所采间隔之和归一到窗口长度，随后过滤窗口终点。目标速率不是最终请求数的直接保证；重放前重新统计实际速率、窗口边界和突发。
- `_sample_data_batch` 对标量字段复用同一组随机分位值。由这段源码推断，单个客户窗口内的这些字段会形成同向分位耦合；不能将生成后的输入／输出关联视为独立测得的生产联合分布。检查联合散点，按实验目标采用已保存的成对记录或明确声明的采样方法。
- 该入口输出请求编号、时间戳和数据字段，没有对话身份或工具依赖。README 所列哈希对话是另一份数据；接入多轮和缓存测试需要另行保留会话、前缀与依赖，不能将长度字段直接当作可执行 prompt。

实验 3-2 先比较同一组请求保持／打乱时间关联的结果，再把生成记录转换成固定 tokenizer 下的受控输入。实验 9-2 用同一记录比较共置与 PD，保存原定发送、实际发送、接收、首 token 和完成时刻；同时记录客户端是否因并发上限延后请求，避免把施压器受阻误认为服务吞吐下降。报告实际输出长度、终止条件、成功数与完整排空时间，长请求不能在测量结束时被静默删掉。
