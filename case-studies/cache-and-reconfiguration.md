# 缓存、图执行与资源重配的取舍

2026-09-07 阅读笔记。下面记录 MLSys 2025 的四个问题及大纲落点，正文只吸收推算和必要案例。论文使用的模型、框架版本和测量条件保留在各段；教学数字均为另设输入，没有运行 GPU 性能实验。

## 压缩后完成一次请求需要多久

[Rethinking KV Cache Compression](../references/proceedings/MLSys/2025/papers/mlsys2025-26289c647c6828e862e271ca3c490486.pdf) 的 §4 与附录 B 区分了三件事：实际引擎的执行效率、自然生成的长度、逐样本质量。论文的吞吐实验主要使用 Llama-2、A6000 和当时的 LMDeploy；长度分析另用 Llama-3.1-8B-Instruct 的 1,000 个 ShareGPT 请求，生成上限为 1,024 token。不能把固定长度微基准、自然输出任务和不同模型的数据拼成一项速度结论。

教学推算先用 `T ≈ TTFT + N_out / r_decode`，其中 decode 速率是该长度区间的平均值。假定 TTFT 都为 0.5 秒，原配置生成 200 token、50 token/s，约需 4.5 秒；压缩后达到 60 token/s，却生成 300 token，则约需 5.5 秒。decode 速率提高 20%，整次请求反而多花约 22% 时间。长度比 1.5 大于速率比 1.2，是反转的原因；这不是压缩必然使回答变长的定律。

实验 9-8 因此保留两组测量：固定形状揭示量化、选择、解压与搬移开销；同一任务自然结束时测输出长度、终止原因、逐任务质量和完成时间。固定请求、采样设置与最大生成上限；单独统计被上限截断的请求，并检查任务成功率，避免短而错的答案看起来更快。若重试，把重试费用计入成功任务成本。低精度存储、模型原生压缩和有损 token 淘汰要分开开关。

论文也有需要核对的记载：附录写出的 LMDeploy `v6.0.1` 应追到 artifact 再确认；“四张 A6000 由 NVLink 相连”不足以确定全互联拓扑。其旧引擎比较不能用来判断 2026 年 vLLM 的性能。书中不沿用这两处模糊配置，也不移植历史速度倍数。

## 混合模型应该留下哪些前缀状态

[Marconi](../references/proceedings/MLSys/2025/papers/mlsys2025-7c180af017258d239bac6248d1eb26ac.pdf) §3–5 的问题不是如何再造一棵前缀树。Attention 的 KV 可以按 token 分段保留，而循环状态原地更新后，通常不能直接退回任意早期位置；额外保留检查点才可能复用那个边界。检查点过密会消耗容量，却未必被再次命中。

Marconi 根据共享输入的分支和上一轮输出末尾决定准入，再结合最近访问与省下的 FLOPs／状态字节决定淘汰。其纯输入公共前缀通常要到第二次出现才识别并保存，第三次才受益，这是少存状态的代价。附带检查点还受 prefill chunk 边界约束；未对齐时要重算尾段或分段执行。用“匹配了多少 token”直接代替“实际跳过多少工作”会高估收益。

第 9.2.5 与实验 9-4 采用这个判断：先确定能恢复的共同边界，再算增量状态占用、可能省下的工作、再次访问机会及恢复开销。共享祖先的容量和工作不能重复记账；`FLOPs/byte` 只有在相近算子与算力约束下才适合近似时间收益，最终仍用轨迹校准。

历史比较必须保留条件：论文为 vLLM、SGLang 添加了混合模型支持；`SGLang+` 已额外采用同样的准入策略，主要对照 LRU 淘汰。主命中实验用 Attention/SSM/MLP 为 4/24/28 层的 7B 模型，TTFT 分析使用 Jamba-1.5-Mini、4×A100-40GB、FP16。这些并非当前 SGLang 的状态。2026 年 [Unified Radix Cache](../references/outline-checks/2026-09-07/framework-evolution/sglang-unified-cache.html) 的 V4/K3 各自存储格式要独立计算；K3 的循环 attention 状态也不能直接套用论文的 Mamba 大小。两项工作按共同问题比较，不声称已有未经核对的代码继承关系。

## 动态请求如何兼容 CUDA Graph

[FlashInfer](../references/proceedings/MLSys/2025/papers/mlsys2025-dbf02b21d77409a2db30e56866a8ab3a.pdf) §3.3–4 的关键是分开 `plan` 与 `run`：CPU 根据长度产生工作分配和归约映射，将元数据写入预留缓冲，GPU 按稳定地址与执行配置运行。请求数据可以变化，不代表图里的任意形状、网格和地址都可以变化。规划不被图捕获，但相同规格的多层可以复用规划结果。

第 5.4.4 和实验 5-8 用 Qwen3-8B 的 36 层举例：假定一次规划需 20 μs，每层重做是 720 μs，每步共用一次为 20 μs；这只是主机工作量推算，实际节省的关键路径时间还取决于异步重叠。V4/K3 有不同类型的层，不能因此假定全模型只需一份计划。实验同时记录 plan、元数据复制、run、padding、临时空间和图捕获，判断规划是否成为下一处瓶颈。

论文测试 FlashInfer v0.2、SGLang v0.3.4、CUDA 12.4、PyTorch 2.4.0，并使用 A100/H100；其后端收益不当作当前引擎实测。当前 [FlashInfer API 快照](../references/framework-history/2026-09-07/flashinfer/attention.html)仍对相应 wrapper 明确规定图模式的 batch 与缓冲约束，部分后端不支持同样的 graph 路径；实验必须固定具体后端。论文 §4.1 的 closed-source 表述没有在本轮实现核对中得到支持，不据此描述 Triton 或当前框架的开放状态。

## 调度可以改变作业的执行方案

[Rubick](../references/proceedings/MLSys/2025/papers/mlsys2025-270339c997293ca2988c62f4308e389f.pdf) §4–7 联合选择资源量和 DP/TP/PP、重计算、梯度累积、ZeRO/卸载方案。它先用少量测点拟合前向、反向、通信、优化器和搬移的时间及重叠，再按资源变化后的执行效率分配资源；不是只把固定卡数需求塞进集群。

第 12.2.1 接回前章同一模型的几种可行方案，比较多给 GPU、增加 CPU 做卸载、等待紧密互联的一组卡。性能曲线要基于同一训练目标归一化，不能把不同模型的 token/s 随意相加。每种方案先检查容量和整除约束，修改梯度累积后仍保持预设全局 batch；固定 batch 本身也不能证明任意精度或随机执行变化下的收敛完全相同。

实验 12-2 增加切换阈值：若旧方案每步 1.2 秒，新方案 1.0 秒，保存、恢复和重排合计 80 秒，则要剩余 **超过 400 步**，切换才缩短任务时间。剩余 1,000 步时，旧方案 1,200 秒，新方案 1,080 秒。这组数是教学假设。迁移或分片重排会改变过渡时间，不能认为重新分配瞬时完成。

论文原型通过检查点退出、重启恢复，并非在线无暂停变形；使用 DeepSpeed 0.9.2、Megatron-DeepSpeed v2.4 等历史栈。其 64×A800 实验的模型最大 30B，作业由缩放后的公开 trace 合成，另外才是仿真扩展。平均 78 秒重配开销和约 1% GPU 时占比只属于原实验，不直接移给 V4/K3 或短作业。读者应学会的是选择与校准的方法。
