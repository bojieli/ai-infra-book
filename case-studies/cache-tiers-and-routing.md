# KV 缓存的取回、共享与路由

本笔记为第 5.2→9.2→10.5 的扩写和实验保留依据，核对日期为 2026-09-08。先沿一个 Qwen3-8B 前缀计算，再比较框架怎样改变数据布局、预取和请求去向。[来源及读取范围](../references/framework-history/2026-09-08/cache-routing/README.md)区分历史文章、固定当前实现和教学假设；没有运行模型或 GPU 实验。

## 从显存里的前缀到多级缓存

SGLang 2024 年 v0.4 的路由器已经用近似 radix tree 预测哪个 worker 可能保有前缀；2025 年 HiCache 把可复用状态扩展到主机和存储，当前文档进一步讲清共享范围、PD 续接与预取策略。缓存位置因此成为路由输入：实例自己的 HBM／DRAM 命中，与共享后端命中，取回路径不同。当前 HiCache 的 L2 属于单个实例，增大 L2 不会自动组成跨实例内存池；L3 是否共享取决于后端、挂载与 namespace。

vLLM 2026 年 1 月文章回顾 v0.9.0 的异步 connector、v0.11.0 的 OffloadingConnector 和 v0.12.0 的布局改进。文章测量还包含当时拟进入后续版本的补丁，不能把全部成绩归到 v0.11.0。固定当前指南已有 CPU primary tier 和可选 FS／OBJ 等 secondary tiers；这条路径经 CPU 中转，不能凭后端名称就画成 GPU 直读存储。LMCache 仍作为另一套集成方案，分别核实接口与支持条件。

Ollama 在本书承担本地对照：已有 MLX 分支快照案例说明哪些状态可以续接；FAQ 中 `keep_alive` 控制模型加载后的保留时间。模型仍然驻留，不足以证明某段前缀 KV 仍在，更不能证明它可跨实例或重启恢复。实验分别测加载、前缀复用与取回，避免把所有“热启动”混成同一个收益。

## 同样的字节，怎样搬才合算

沿用[固定 Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)，取 TP=1、36 层、8 个 KV 头、head dimension 128、BF16，每 token 的完整 KV 为：

`36 × 2（K/V）× 8 × 128 × 2 byte = 144 KiB`。

8,192-token 前缀占 **1.125 GiB**。若每个逻辑块有 16 token，按“每层的 K 和 V 分开连续存储”这一教学布局，每片是 32 KiB，一个逻辑块分成 72 片，整个前缀共 36,864 片；若同一块的各层 K/V 连续，则为 512 个 2.25 MiB 块。有效载荷相同，物理连续段大小和数量不同。这里计算的是两种声明布局；真实后端的 stride、合并搬运和提交次数仍需看实现与 trace。

vLLM 的历史文章用大连续块提高 DMA 效率；SGLang HiCache 用 host 的 page-first 类布局改善存储 IO，并提供不同 host↔GPU 搬运路径。把二者接回第五章：小块传输、布局转换、GPU 核心占用和计算重叠一起衡量。独立拷贝较快的 kernel，可能因占用计算资源而降低服务吞吐；异步 DMA 也仍会消耗链路、主存和缓冲，不能视为零代价。

vLLM 文章表中的 Qwen3-8B 数值与本书固定配置下的上述 BF16 计算不一致；原文没有给足条件来解释差异，本书不采用该行数字。历史图中的倍数也不移作当前框架或本书实测。

## 先比较完成时间，再决定是否等缓存

使用相同的 8,192-token 前缀和 256-token 新输入。以下时间、有效带宽全部是**教学假设**：A 的完整前缀已在 HBM，预计队列等待 250 ms；B 预计等待 20 ms，完整重算至首 token 需要 180 ms，命中前缀后的剩余工作需要 10 ms。远端查找与固定开销 10 ms，host→GPU 有效单向带宽 25 GB/s。

第一遍采用整份状态先到 host、再到 GPU 的串行路径，取回可与等待 GPU 重叠。让 `Q` 为 GPU 最早可执行时刻、`R` 为从请求到达算起的状态就绪时刻、`C` 为剩余 GPU 工作，则 `TTFT = max(Q, R) + C`。这个公式依赖这组执行假设；实际逐层／逐块流水要重新画关键路径。

| 选择 | 教学计算的首 token 时间 | 原因 |
| --- | ---: | --- |
| A：使用本地 HBM 前缀 | 260 ms | 250 ms 队列＋10 ms 剩余工作 |
| B：直接重算 | 200 ms | 20 ms 队列＋180 ms 计算 |
| B：远端 5 GB/s，整份取回 | 309.91 ms | 状态到齐晚于 GPU 空闲 |
| B：远端 20 GB/s，整份取回 | 128.72 ms | 取回节省超过额外交接 |

在这组串行传输假设下，远端有效带宽约 **9.17 GB/s** 才达到与 B 重算相同的首 token 时间。接着让读者改变 A 的队列、共享链路上的并发和实际命中长度，重新选方案。若每秒有 16 个请求都需取回这份前缀，仅有效载荷已需 **19.33 GB/s**；单请求的有利结果不保证持续服务或尾延迟合格。

以 HiCache 的 `best_effort`、`wait_complete` 和 `timeout` 检验这个判断。停止等候后，已经取回且各 TP rank 都认可的连续前缀还能复用，其余部分重算；不能把预取发现的 token 数直接当作可用命中数。实验必须记录查找、实际完成、放弃的传输、首 token 和后续生成，而不只比较一个总命中率。

当前 SGLang Model Gateway 的已读 `cache_aware` 路径仍依据请求文本的近似树及负载阈值选择 worker；它不是上述完成时间模型。源码文件开头还保留“低匹配时选最小树”的说明，实际已读分支选择最低负载并随机打破平局，采用后者。路由器预计的匹配、worker 的 token 命中、命中层级和状态就绪分别验证；不能将另一套 experimental router 的 KV-event 路径混入这个实现。

最后回到多轮 Agent：D 生成的 token 会进入下一轮输入。当前 vLLM 指南的 `offload_prompt_only` 默认为 true，SGLang 的 PD 指南另给 decode 异步卸载路径。因此，“打开前缀缓存”尚未回答新生成的状态是否已发布给下一轮 P。只缓存公共提示和保存完整会话各有写入成本；沿第 10.5.3 的 P→D→P 时序计算，避免重复记账。
