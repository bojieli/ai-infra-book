# 专家执行、容量与服务启动的取舍

2026-09-07 的编辑研究记录。MLSys 2026 首批摘要中选择三篇，读设计与实验条件后补回已有小节。这里保存扩写所需的算式、历史条件与疑点；没有运行 GPU 实验，也没有把论文中的旧模型换名为 V4／K3。

## 先数专家工作，再比较并行方案

[Demystifying the Mixture of Experts Serving Tax](../references/proceedings/MLSys/2026/papers/mlsys2026-42a452cbafa9dd64e9ba4aa95cc1ef21.pdf) 提供两种不同的 dense 对照：匹配激活 FLOPs，以及匹配总参数。前者适合看执行开销，后者体现稀疏计算节省；两者都没有证明模型质量相同，不能由速度决定模型优劣。已读物理页 2–9、12，采用独立活跃专家、padding 与阶段瓶颈的分析方法。

先用本书已固定的 [Qwen3-235B-A22B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-235b-config.json) 推算一个 MoE 层。每个专家的三个矩阵共有 `3×4096×1536=18,874,368` 个参数，BF16 为 **36 MiB**。128 个专家常驻需要 4.5 GiB／层；每 token 选 8 个专家，其必要权重载荷为 288 MiB，但一个 batch 的工作不能简单按单 token 倍乘后当作 HBM 读取量。

令 m 为同一层此次处理的输入 token 数，E=128、K=8。仅在各 token 独立、均匀选择 K 个不同专家的教学假设下，批内独立活跃专家的期望为：

```text
E_active = E × [1 − (1 − K/E)^m]
每个活跃专家的平均 token 工作约为 mK/E_active
理想的批内一次权重读取载荷约为 E_active × 36 MiB
```

m=1 时是 8 个专家；m=8 时约 51.62 个；m=32 时约 111.77 个。独立专家数逐渐接近 128，随后增大 batch 可继续增加权重复用。同样 8 个输入 token，如果恰好都选择同 8 个专家，一次读取仅涉及 288 MiB；均匀假设的期望约 1.815 GiB。这是单层、完整专家权重的逻辑载荷，未计 attention、router、激活、缓存命中、重读、padding 与 TP 分片，不能直接报成实测 HBM 字节或延迟。

由此解释两个看似冲突的选择：访存受限的 decode 可能从专家复用受益；计算受限的 prefill 则容易被最忙设备拖住。宽 EP 的 decode 仍可能因每卡权重载荷不均而变慢。实际 V4／K3 的分组路由、共享专家和跨 token 相关性要使用各自配置与路由记录，不能套用均匀模型。

再用 [Duplex 的共享内存设计](../references/proceedings/MICRO/2024/duplex-body-reading/NOTES.md)解释为什么调度粒度还受硬件约束：不同专家可以选择不同计算单元，但同一 bank 分区里的专家未必能独立分配；为同时执行而拆小 batch，也可能重复读权重、降低复用。沿上述逐专家计数比较可行分配，再计入归约和状态迁移。该例是需要新 Logic-PIM 硬件的模拟研究，不是现成 GPU 的可开启功能，也不替代 CPU／GPU 协作案例。

接到第 5 章的 tile：八个本地专家收到 `[32,16,8,4,2,1,1,0]` 个 token，共 64 行。教学后端若每个非空专家按 32 行块补齐，需要 224 行；若所有八个专家都按局部最大值补齐，则是 256 行。两个公式分别是 `Σ ceil(N_e/B)B` 和 `E_local×ceil(max(N_e)/B)B`；实际内核可能跳过空专家、使用别的块大小或无此补齐，实验须读固定后端。先算执行 FLOPs／有效算力和必要字节／有效带宽，再加入不能隐藏的通信与依赖。

论文实验使用 Mixtral／Qwen2 MoE 的 8 A100、DeepSeek-V3 的 8 B200；通信微基准另有 8／16 H200。它不覆盖跨超节点的端到端服务，主要是短上下文、稳态、无质量对齐的研究。不同图表的硬件不能混成一组。

**扩写前保留的原文疑点：**第 6 页通信比较同时出现全局 token 数和每卡局部 token 数，给出的倍数不能脱离其定义直接复制。本书按同一请求集合、rank 数据所有权、实际目的设备合并、dispatch／combine 分别计数，再与 NCCL／DeepEP 字节记录核对。第 6 章不引用一个通用的“EP 是 TP 几倍流量”。

## 专家副本要与 KV 争夺容量

[CRAFT](../references/proceedings/MLSys/2026/papers/mlsys2026-3a7f9e485845dac27423375c934cb4db.pdf) 已读物理页 4–8。采用的问题是：各层路由倾斜不同，额外副本的边际收益也不同；在总 HBM 预算下，把副本放到最能缩短关键阶段的层，而不是给每层同样数量。正文只解释收益与容量，算法实现留在参考资料。

接着用 Qwen3 算容量：若每张卡在每个 MoE 层各增加一个完整 BF16 专家，94 层需额外 **3.3046875 GiB／卡**；每卡仅增 8 个、分给部分层，则为 **0.28125 GiB／卡**。这是离线方案预算，后者是否达到相同服务目标要用路由与时间记录验证，也不代表已有 EPLB 参数能够直接执行任意逐层方案。释放的空间能多承接几个请求，要按该配置的 KV 分片、上下文和工作区再算。

CRAFT 的历史系统基于 SGLang v0.4.8 与 EPLB，在 AWS p4de.24xlarge（每节点 8 A100 80GB、节点内 NVLink、节点间 EFA）运行 BF16 DeepSeek-R1 与 Kimi K2；CUDA 12.8、NCCL 2.26.2。其路由测量、固定 4096 输入／256 输出和独立评估数据要保留，不能外推成自然长度的 V4／K3 收益。文章的 goodput 通过到达率增加后 TTFT 出现持续排队的拐点确定，不等于任意 P99 SLO。文中的副本预算和定期重排策略不是当前所有 SGLang／vLLM 配置的默认行为，未确认该研究已合入当前引擎。

9.4 与实验 9-6 因此比较三步：先改放置，再按需复制，再看通信重叠。每一步都记录最忙卡、额外容量、迁移时间和服务尾延迟；不把几个优化的独立加速比相乘。

## 稳态优化也有启动成本

[Breaking the Ice](../references/proceedings/MLSys/2026/papers/mlsys2026-29416b66c2149872b9d1415a3fd2c5e0.pdf) 已读物理页 2–10。论文逐阶段分析的是 vLLM **v0.10.1.1**，不是 2026 当前版本；其版本演进图与主要控制实验也不是同一组模型。作者的[公开工具](https://github.com/upb-cn/vllm-startup-profiler)固定同一版本并增加计时日志，可作为实验 9-10 的历史记录对照。

9.6.2 以启动 Qwen3-8B 服务为当前教学任务，沿执行依赖分开记录：进程／依赖与 tokenizer、权重读取及传输、编译和编译缓存、KV 内存探测、CUDA Graph 捕获，然后才是首个请求与扩容后排队消退。引擎就绪不等于用户请求已完成。CPU 串行工作多时，提高 GPU 峰值算力不能按比例缩短启动。

特别保留三个实验条件：

- **哪些缓存是热的。**该论文大部分基础实验已有 Linux 页缓存和编译缓存，远端下载、容器拉取与分布式协调被排除；不能把它叫完整平台从零部署的时间。实验用独立缓存目录区分编译缓存状态，权重页缓存状态另记，避免一个“冷启动”标签包办。
- **计时范围是否嵌套。**首次 dummy forward 会触发编译，不能把日志中包含编译的 KV profiling 和编译耗时再加一次。论文为隔离阶段另做关闭编译的对照；本书依据 trace 的嵌套关系与关键路径计量，不把各日志字段直接相加。
- **图覆盖与服务寿命。**捕获规格增加会延长准备、增加缓冲占用，也可能减少稳态提交和 padding。假定多花 10 秒准备，每次真实执行步在关键路径省 0.2 ms，至少需要 50,000 步才抵消时间；这是教学输入，执行步不等于输出 token 总数，batch、请求到达与实例寿命都要另算。

论文建立的线性关系是所测 CPU、模型、缓存与软件环境中的经验拟合，不能作为 V4／K3 的普适启动定律。第 9 页 CPU 对比还同时改变了部分 OS／Python／CUDA 条件，不能仅按 CPU 微架构归因；PCC 的负号说明和部分图文速度比措辞亦有问题。本书采用阶段分析，不引用这些不充分的归因或图 14 的后端排名；引用图中精确值前须再核对原图与原始数据。

这一案例连接 5.4 的图执行、9.6 的部署与恢复和 11.3 的扩缩容。扩写时对新版本重测各阶段，保留引擎提交、模型版本、CPU 核数、缓存、图规格和计时边界，而不另开一个冷启动章节。
