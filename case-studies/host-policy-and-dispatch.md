# 主机调度的放置与任务吞吐

用于 1.5.2 的 SmartNIC 延伸例子，接回 11.1.2 的 Agent 平台预算。2026-09-09 选读 Wave 的设计和评估，对照公开 ghOSt 固定源码；论文评估的是 CPU 系统软件，没有测量 Qwen、DeepSeek 或 Kimi 推理。这里借它解释处理位置的取舍，AI 服务部分采用本书独立教学输入。

## 省下主机核心，需要付出什么

Wave 将线程调度、内存管理等策略移到 SmartNIC 的 Arm 核心，执行决策的内核机制仍在主机。线程就绪消息和调度决定因此要跨 PCIe；省下主机上的策略计算，不等于消除了任务开始前的等待。[原论文 §3–5](../references/proceedings/ASPLOS/2026/paper-168.pdf#page=5)

先给一个 32 核平台：原先 2 核处理基础工作、30 核执行任务；卸载后 32 核都可执行任务，但每核有效吞吐下降比例为 `d`。假定任务可均匀分配、CPU 是唯一瓶颈，吞吐比为 `32(1−d)/30`。只有 `d < 6.25%` 才提高吞吐；损失 2% 时约提高 4.53%，损失 8% 时约下降 1.87%。这还没有扣除网卡核心、内存和功耗成本，不能直接称为整机成本收益。

论文有一个很好的对照办法：先固定主机上的工作线程数，测量跨 PCIe 的损失，再允许任务使用卸载释放的核心。FIFO 实验中，同为 15 个工作核心时 Wave 的饱和吞吐低 1.1%；使用第 16 个核心后，报告比原主机方案高 4.6%。这两个实验共同解释收益，不能只摘后一个百分比。它们是该 RocksDB 负载的测量，不是上面理想线性公式的精确实例。[§7.2.2，物理页 11](../references/proceedings/ASPLOS/2026/paper-168.pdf#page=11)

## 提前准备能否避开往返

Wave 在有足够就绪任务时提前准备下一次调度决定，再把读取与主机已有工作重叠。若教学输入是读取 0.75 μs、可重叠工作 1 μs，读取可完全隐藏；可重叠工作只有 0.2 μs 时，仍暴露至少 0.55 μs。这个计算只隔离已准备决定的读取，没有计入产生决定、提交校验和切换。论文也明确指出，抢占路径需要立即读取，可能没有同样的预取机会。[§5.4 与 §7.2.3](../references/proceedings/ASPLOS/2026/paper-168.pdf#page=9)

更早作出决定，也增加了使用前状态变化的机会。公开 ghOSt 的 `RunRequestOptions` 带有任务和 agent 的 barrier；其中 agent barrier 的检查有本地提交条件。`Open` 发布待处理事务，`committed()` 表示已到终态，只有 `succeeded()` 才表示成功。目标退出、状态过期或 CPU 不可用都可能返回失败。不能把“已准备”“已提交”“已执行”画成同一个时刻。[固定接口](../references/framework-history/2026-09-09/smartnic-policy/ghost-enclave.h)、[完成处理](../references/framework-history/2026-09-09/smartnic-policy/ghost-enclave.cc)

第 5 章 CUDA Graph 的提前准备、第 8 章异步请求调度、第 10 章 RL 权重交接也要区分这些时刻，但各自保留的状态不同。图保留执行和地址约束，调度器检查请求进度及可用状态，权重交接还需确认版本和重新加载；这是一种共同的分析方法，不表示它们采用 ghOSt 的事务实现。已有[图执行](graph-execution-tradeoffs.md)和[权重交接](weight-handoff.md)算例保留各自条件。

## 回到 Agent 平台的完整预算

沿用 11.1.2：每项任务驻留 30 秒、占 2 GiB、执行 3 核秒，每秒进入 10 项任务。先将上面的 32 核平台和 600 GiB 环境预算代入；假设驻留量固定、其他服务能力充足，暂不加入突发余量。原先任务侧 30 核支持 `30/3=10` 项每秒，环境容量同样只支持 `600/(2×30)=10` 项每秒。

卸载后的每核损失若为 2%，CPU 能力上界变成 `32×0.98/3≈10.453` 项每秒，环境上界仍为 10。平台没有因此多完成任务，只增加了 CPU 余量。环境预算升到 720 GiB 后，其上界为 12，CPU 才重新成为瓶颈。真实环境寿命还会随排队变化；平均需求不能代替满足尾延迟的配置，也不能据此认定该平台应该安装 Wave。

**实验 1-6 的延伸**保留主机核数，改变卸载后的每核损失，求吞吐翻转点；在**实验 11-1 的延伸**中加入环境容量和任务时间线，再判断整体是否受益。图 1-5 可加一条决策往返的虚线；图 11-1 继续标出任务执行与环境驻留。图均由本书自绘 SVG，采用教学输入，不复制论文的性能曲线。保持现有章节、实验和图号。

## 论文与可用实现的范围

Wave 的实验配置是 Intel Mount Evans、16 个 3 GHz Neoverse N1 核心、200 Gbps 网络功能，以及 AMD Zen3 主机；主机／网卡内核分别为 Linux 4.15／5.10。小消息调度和大批量页表传输使用不同机制。200 Gbps 是网络功能规格，不能用它推算一次 PCIe MMIO 读取延迟。[§7，物理页 10](../references/proceedings/ASPLOS/2026/paper-168.pdf#page=10)

公开 ghOSt 仓库的固定提交为 `9ca0a1f`（2023-11-08），获取时仓库已归档，README 要求配套 ghOSt 内核。它可核对原有用户态调度接口，不能充当 Wave 的 SmartNIC 工件。所读作者主页为 Wave 提供论文和演讲入口，未给该条目的代码链接；本次没有核到 Wave 的公开实现，也没有证据表明 vLLM、SGLang 或 E2B 已集成它。

原稿中几处数字与名称需保留边界：426 ns 是发出决定与通知的局部测项；同页完整上下文切换另报 3.32–4.04 μs。4 μs 工作加两次 1 μs 等待，在独立串行模型中是耗时增 50%、吞吐降三分之一。论文另有 AMD 双路实验使用 UPI 名称、物理核与逻辑核表述不一致等问题，本书不据这些段落采用互联结论或核心节省数字。逐页范围与取舍见[来源记录](../references/framework-history/2026-09-09/smartnic-policy/README.md)。
