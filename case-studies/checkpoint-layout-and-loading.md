## 同一模型的状态会去往不同地方

第 6 章已经为模型选择 TP、PP、DP、EP；第 10 章开始考虑部署与恢复，第 11 章再问改变布局之后如何取回训练进展。ByteCheckpoint 的动机不仅是故障：中途更改资源、长上下文阶段、后训练和独立评估都会重新划分状态。其表示把张量名字、全局形状、各维偏移／长度和文件字节位置分开，让目标布局寻找所需片段，避免先提交一个离线重分片任务、写出整套新文件，再启动目标任务。[正式论文 §2–3](https://www.usenix.org/system/files/nsdi25-wan-borui.pdf)

只用一块真实矩阵把这件事讲清楚。Qwen3-8B 的逻辑 `gate_proj` 为 `[12288,4096]`，共 50,331,648 个参数；BF16 权重为 96 MiB。沿输出维做 TP=4，每份 24 MiB；改成 TP=8，每份 12 MiB。目标 rank `r` 从原文件 `floor(r/2)` 取前半或后半即可。先画矩阵坐标，再画文件偏移，验证八份目标块无重叠地覆盖同一矩阵。这里使用未融合的逻辑矩阵，真实框架可能把 gate/up 合并或转置，仍需对应的 planner，不能按文件名直接拼接。

如果还要恢复 Adam 的 FP32 主权重、一阶矩和二阶矩，同一矩阵总共需要 672 MiB；独立推理一般只要模型权重。这个 14 字节／参数的教学口径不含梯度、CPU 状态和元数据，也不等于所有训练栈的保存格式。优化器扁平化分片还可能跨过矩阵行边界，论文用多个规则片段表示，避免为保存先聚合完整张量。真正恢复训练还需数据位置、已经组装的 token buffer、随机数和学习率等状态；改变 DP 时，不能把数据缓冲无条件复制给所有新副本。[配置与分片计算](../research/2026-infra-survey/arithmetic.json)

论文保存规划还会在拥有相同状态的 rank 之间分摊写入；加载时可把一次存储读取与 GPU 间分发结合。是否值得，要比较存储、主机复制和组内互联各自的余量。优化器分片的所有权不同，不能像完整权重副本一样消重。名称一致、全局坐标和数值格式正确是重分片基础，不能据此保证任意框架与融合／量化格式自动互通。

## 返回、稳定快照和持久化是不同事件

第 11.4.3 沿保存时间线区别：请求保存、形成不再受训练修改影响的快照、后台序列化／上传、所有必要分片完整可恢复。异步只改变这些操作与训练怎样重叠，还要算后台带宽、主机内存及最慢 rank。

以取整的 8B 教学模型计，BF16 权重为 16 GB，加三份 FP32 Adam 数组为 112 GB，暂不含 CPU 和存储放大。若全局有效上传带宽是 8 GB/s，单次传输下界为 14 秒。每 10 秒生成一份状态，供给为 11.2 GB/s，超过写入能力；若允许排队，待写数据净增 3.2 GB/s，有限缓冲最终耗尽。每 20 秒保存一次则为 5.6 GB/s，才通过这项必要检查。不能因为 API 的暂停只有 0.5 秒，就认为任意频率的保存都能隐藏。

再给两次快照的明确时间点：在 20、40 秒捕获，在 20.5、40.5 秒结束各自的 staging；后台写入分别到 34.5、54.5 秒完成。若 50 秒故障，此时只能用第一份已完整持久化的快照。有效写入带宽翻倍时，完成点为 27.5、47.5 秒，可用第二份。两个方案阻塞训练的时间相同，但恢复起点不同。这个教学例子假定两个阶段串行、没有其他争用，恢复点是快照捕获时间；不把 API 返回或主机内存副本当作远端持久化完成。[教学时间线](../research/2026-infra-survey/arithmetic.json)

PyTorch 的 2024 公告主要说明把 GPU→CPU staging 后的保存移至线程，并使用独立通信组防止与训练集合调用错序。2025 公告进一步指出后台线程仍会竞争 GIL、拖慢主机提交，同时元数据规划有多轮通信；后台进程与计划缓存一起减少了这些影响。其 1856 H200、TorchTitan、Llama3-70B 的结果报告后台处理约 436→67 秒，不能写成训练整体快 6.5 倍，也不是当前 V4／K3 的测量。第一次进程初始化和规划与后续缓存命中分开；完整吞吐影响应看保存期间的下降面积。[2024 公告](https://pytorch.org/blog/reducing-checkpointing-times/)、[2025 公告](https://pytorch.org/blog/6x-faster-async-checkpointing/)

当前 stable 页面重定向到 PyTorch 2.14，已保留重定向原件并跟到版本文档。2.14 源码仍默认 `THREAD`，内部默认 stager 的配置也不是全部异步。只有 staging 返回 Future 的路径才返回含 `staging_completion` 与 `upload_completion` 的 `AsyncSaveResponse`；其他路径返回上传 Future。示例应按固定版本和配置处理。staging 完成表示后续训练不应再修改快照，上传完成的语义还依赖 StorageWriter；本轮未审所有存储后端的落盘／远端复制承诺。[2.14 API](https://docs.pytorch.org/docs/2.14/distributed.checkpoint.html)、[对应源码](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/distributed/checkpoint/state_dict_saver.py)

ByteCheckpoint 的历史对比也需保留口径：DCP 基线为 `c7338f4`、MCP（Megatron Distributed Checkpoint）为 `3fb5c51`，双方都加了同配置 HDFS 适配。vDiT 4B 使用 A100 80GB／FSDP，tGPT 70B 使用 H800 80GB／Megatron；表 4 中 2400→4800 卡的重分片，GPU states 为 62.10 秒，full states 为 401.21 秒。论文解释数据缓冲处理和部分 worker 持有 CPU 状态形成长尾，不能拿前一个数当完整训练恢复时间。

其 ETTR 是在每检查点间隔内发生故障的假设下计算，并平均普通加载与重分片，不能解释成一般生产利用率。表 8 的 405B／8960 卡保存阻塞为 0.59 秒，而完整保存是 51.06 秒；正文概述里的“微秒”“几秒”不能替代表格数值。改变 DP 的正确性实验同时增大了全局 batch，曲线继续下降不证明相同优化轨迹；未改变布局时的复现与改变布局后的数值等价分别讨论。图注文与表格已读，曲线未独立量化。

## 推理预分片换取的是固定部署的加载效率

第 10.6.2 用 vLLM 与上述表示对照。v0.6.0 的 `ShardedStateLoader` 已按 `model-rank-{rank}-part-{part}.safetensors` 读取各 worker 的模型状态；v0.9.2 增加所读文件中的 S3 与可选 Run:ai 路径；2026 固定提交保留 rank 专用文件，在读取迭代器按 `runai_streamer_sharded` 分支选择。这里记录版本中已存在的行为，不把取样时间当首次发布日。

这条路径直接把张量拷入当前 rank 的模型，没有 ByteCheckpoint 式的全局分片坐标查询与重分片计划。LoRA padding 的 narrowed view 也不是自动 TP 转换。由此推断，改变 TP 后应重新准备匹配的预分片文件，或选择支持目标布局的其他加载／转换路径；不能把原 TP=4 文件直接用于 TP=8。这里也没有保存优化器、dataloader、请求 KV 和采样环境，完整故障恢复仍需上层系统。

预分片可以减少重复逻辑读取，但实际磁盘流量还受 mmap、操作系统页缓存、存储并发和源文件布局影响，不能承诺 TP 增大后启动时间恒定。实验 10-10 比较同一固定模型、精度、布局下普通与预分片加载，分别记录冷／热缓存、实际读字节、转换准备成本和就绪时间。与第 11.4 的实验共用逻辑矩阵和状态清单，使用各自框架真正支持的格式，避免把推理权重文件当作可续训的完整检查点。
