# 一名 24×7 数字员工的 serving 成本

第 13.5.1／实验 13-6 的综合估算，连接第 11.4.1 的计费口径。题目来自作者[数字员工文章](../references/author-materials/2026-09-09/digital-worker.md)：只取一条串行 Agent 轨迹持续 decode，工具等待置零，prefill 与周期压缩作为修正；历史长度受限，不无限累积。

估算已完成，输入快照、脚本、完整结果统一放在 [experiments/ch13/13-06/single-agent-serving](../experiments/ch13/13-06/single-agent-serving/README.md)。覆盖 8B、70B、235B MoE，BF16／4-bit 与 8K／32K／128K 容量情景，以及独占、共享、卸载和 API；没有匹配测量的速度保留为未测。

一个月取 720 小时。每人速度为 r token/s、池小时价 h、持续共租人数 B，则月输出为 2.592r 百万 token、月分摊为 720h/B，再相除得到每百万成本。API 另按实际计费的输入和输出求和。共享人数指其他独立员工，不能将池总吞吐当作本员工速度。

[结果表](../experiments/ch13/13-06/single-agent-serving/RESULTS.md)中，现有 Qwen3-8B 的 8K 共享前缀实验按公开起租价归一化后：独占约 38.60 token/s、$1504.80/月；16 人共享每人约 32.80 token/s、$94.05/月；64 人共享降至 17.54 token/s、$23.51/月。要求至少 30 token/s 时，四个已测点中选 16 人。这里是短实验的持续运行外推，且共享前缀和满载条件必须成立。

不同规模的容量月租不能替代速度测量；API 在假定持续 50 token/s 下的账单也不能证明端点能达到该速度。比较时同时报告产出、费用和质量门槛。较少的 prefill 计算不等于较少的输入收费，反复计费历史可能改变排序；具体敏感性计算见实验结果。
