# 加速器架构与执行比较

本书的主要比较对象为 Apple、NVIDIA 和昇腾。Apple 以 M2 Max 为实机，NVIDIA 以 RTX PRO 6000 Blackwell 为实机并联系 A100／H20 等系统案例；昇腾覆盖 910A、910B／910C 到 950。当前没有昇腾芯片可供本书实测，仍按相同算子与形状分析其计算、存储、搬运和同步，公开规格、源码机制、条件式推导及论文测量分别引用；有效性能与编程工作量中无法实证的部分保留为未知。

配对设备的延伸案例见 [M2 Max／RTX PRO 6000](macbook-rtx-pro6000.md)，包含 Apple 统一内存、Metal 与 Ollama 适配；阶段及算子放置的系统案例见 [A100／H20 PD 与 KTransformers AF](pd-af-heterogeneous.md)。前者贯穿第 4、5、8、12 章，后者在第 9.2、9.3 节展开。

核对日期：2026-09-05。用于第 4 章“加速器架构”和第 5 章“算子与运行时”，并由第 8 章“单实例推理”、第 10 章“训练系统”承接。本文是写作依据、比较框架和条件式算例，尚未执行跨设备性能或开发工时实验。

## 从模型与负载进入硬件

第 2 章解释 Transformer 的矩阵乘、归约、非线性和数据依赖；第 3 章分别给出训练、prefill、decode 的执行形状、并发和状态寿命。第 4 章依据这些需求分析硬件，第 5 章研究实现与执行。比较不只问峰值算力，而要逐项回答：什么工作可以并行，谁执行它，数据经过哪里，什么限制了供数，软件需要作出哪些决策。

硬件会适应主流负载，负载也会利用既有硬件。设计同时受工艺、面积、功耗、内存、互联和软件兼容性约束。今天的 Transformer 算例可以解释一项设计的适用性，但不能单独证明早期设计者的动机。

| 负载中的工作 | 硬件问题 | 后续实现问题 |
| --- | --- | --- |
| GEMM、卷积映射后的矩阵乘 | 矩阵单元吞吐、操作数复用、精度、tile 形状 | 分块、布局、矩阵指令选择、尾块与供数 |
| Softmax、RMSNorm、激活 | 向量／通用执行吞吐、归约、特殊函数、局部存储 | 融合边界、中间状态、同步与数值稳定性 |
| 注意力的矩阵—向量—矩阵依赖 | 各类执行资源配比、交换路径和缓冲容量 | FlashAttention／MLA 的流水与缓冲生命周期 |
| 小批量 decode | 小矩阵效率、权重／KV 访问、任务启动 | 算子融合、图重放、批次组织 |
| MoE、变长序列和非连续视图 | 地址生成、分支、负载分配和不规则访存 | 动态 tiling、mask、分桶、特化与回退 |

## Cube、Tensor Core 与 Triton 的比较层次

Cube 和 Tensor Core 都提供专用矩阵计算能力。比较对象应是完整计算路径：控制和指令如何发起矩阵运算，操作数以什么布局放在哪里，矩阵结果怎样交给向量／通用计算，如何实现复用和同步。一个 Cube Core 与一个 Tensor Core 不构成等规模、等功能的比较单元。

Triton 是语言与编译器，其意义是把许多线程映射、存储安排和异步调度工作交给编译器。它应与 CUDA、Ascend C 和相应编译／算子接口比较。不能把 Triton 的引入写成 NVIDIA 增加了一种矩阵硬件。

| 维度 | 昇腾一侧 | NVIDIA GPU 一侧 | 比较时记录什么 |
| --- | --- | --- | --- |
| 控制与计算 | 早期 Scalar／Vector／Cube；分离 AIC／AIV；950 增加 SIMD／SIMT 混合编程 | SM 中的 warp 调度与 SIMT；矩阵指令使用 Tensor Core，细节按代际区分 | 同步域、控制流、驻留限制、非矩阵工作和资源冲突 |
| 自动缓存与局部存储 | L1 Buffer、L0、片上 UB 缓冲具有明确用途；另有 L2 等缓存 | 普通访存可以利用硬件缓存；高性能 tile 也使用显式管理的 shared memory 和寄存器 | 分清缓存命中、软件复用和缓冲生命周期，不把相同的“L1”名字视为相同语义 |
| 搬运与地址生成 | MTE／DataCopy 等描述搬运；950 NDDMA 支持多维地址生成、布局变换与内部缓存 | 常规 load/store；Ampere 异步拷贝；Hopper TMA 通过 tensor map 搬运多维 tile | 支持的方向、维度、stride、对齐、边界、重排与完成条件，逐项匹配功能 |
| 矩阵与向量交换 | 早期同核通路、分离架构交换、950 CV 直接通路各自分析 | 矩阵与通用指令间的寄存器／共享存储及同步方式按代际、指令明确 | 每个中间张量实际跨过的存储接口和依赖 |
| 编程抽象 | Ascend C 的 tiling、局部张量、队列与搬运；高层库和编译器也可承担部分工作 | CUDA 底层实现可以显式管理布局与流水；Triton 自动组织其中许多细节 | 相同算子、相近抽象层次下的手工决策、代码维护、调优工作与性能覆盖 |

NVIDIA 并非没有显式搬运。已归档的 [Hopper Tuning Guide](../references/files/documents/nvidia-hopper-tuning.html)说明 TMA 沿用并扩展 Ampere 的异步拷贝，支持 1–5 维张量在全局内存与 shared memory 间搬运。[CUDA 13.2.1 异步拷贝文档](../references/files/documents/nvidia-async-copies.html)进一步定义描述符、stride、对齐及完成同步。这与 950 NDDMA 都体现了硬件承担更多地址生成工作，但两者的存储端点、转换能力和同步语义不能直接画等号。

[Triton 编程模型](../references/files/documents/triton-introduction.html)解释块级数据流分析如何自动组织布局、共享存储、同步和异步搬运；[矩阵乘教程](../references/files/documents/triton-matmul.html)仍要求程序表达尺寸、stride、分块和边界处理。由此可以讨论软件抽象降低哪些成本；若要断言某平台“难很多”，还须比较开发者经验、库覆盖、目标性能和维护范围。

## 动态 shape 必须拆开比较

“支持动态 shape”至少包含四类不同问题：调用间尺寸变化、非连续 stride／非对齐尾块、数据依赖的输出尺寸、以及变长序列或 MoE 形成的不均匀工作。硬件能寻址和分支、算子能正确处理、编译器能复用产物、执行图能重放，以及变化后仍然高效，是不同层次。

Ascend C 已有 host tiling 和运行时参数机制。CloudMatrix384 的 MLA 方案还针对 MTP 引入动态 tiling，并改变布局以缓解任务不均；这说明必须比较具体实现成本与适用条件，不能写成昇腾不支持动态 shape。GPU 的 SIMT 和通用访存提供灵活的执行基础，但矩阵指令、TMA、编译特化和图重放仍有自己的约束。

第 5 章采用相同输入族测试 GEMM、归约／Softmax、带 stride 的布局变换和变长注意力：先覆盖正确性，再记录首次编译、host tiling、稳态设备时间、额外 padding、产物数量、回退和尾延迟。开发成本另记显式管理事项与调优过程，代码行数仅作辅助记录。不同厂商库的成熟度与底层硬件限制分别归因。

## 贯穿第 4、5、8 章的算例

### 中间结果经过哪一级存储

教学假设：一个 `128 × 128` 的 FP32 中间张量，生产者与消费者之间恰好一次完整写出、一次完整读入。其容量为 `128 × 128 × 4 = 65,536 B = 64 KiB`，该交换在所选接口上产生 `128 KiB` 流量。若直接通路能完整承载它，且不需要另行物化，可减少原交换接口上的这部分工作；直接通路自身仍有带宽、延迟和同步成本。

在第 4 章将这个张量放到两条真实通路上，分别标注 L0、L1 Buffer、片上 UB 缓冲、寄存器、shared memory、L2 与 HBM。Global Memory 是地址空间，实际访问可能命中缓存，因此 `128 KiB` 不能无条件记为 HBM 流量。只有同一接口上的流量才汇总；依赖允许的重叠才可以进入最大值下界。

第 5 章再用分块／融合实现验证上述条件，检查生产者和消费者的数值格式、额外布局转换、缓冲驻留与并发。如果中间张量需要 FP32 而交换路径按较低精度传输，须同时检查数值误差和新的字节数。

### 从静态形状到变长负载

第 2 章给出注意力与 MLA 的数学计算，第 3 章固定训练、prefill、decode 和 MTP 的形状分布，第 4 章推导矩阵、向量和存储资源需求，第 5 章比较布局、融合和动态 tiling。第 8 章加入连续批处理，测量图选择、padding 与 KV 容量对 TPOT、有效吞吐的联合影响。逐阶段保持输入、精度、正确性标准和计量边界可检查。

### 图重放与融合的不同收益

用同一段计算比较普通执行、仅融合、仅图重放及二者组合。分别记录 CPU 派发、设备启动、kernel 运算、同步、编译／捕获时间和显存；不把全部启动时间简单乘 kernel 数后加到设备时间上。

[CUDA Graph 文档](../references/files/documents/cuda-graphs.html)说明定义、实例化与重复执行；[vLLM 设计](../references/files/documents/vllm-cuda-graphs.html)说明按批次选择整图、分段图或普通执行，并权衡捕获时间、内存和兼容性。CloudMatrix384 §4.2.2 明确区分图捕获对 CPU 派发的摊销与设备端每算子启动成本，因此不能把融合和重放的收益合并成一个不加解释的加速比。

## 写作时必须完成的交付

- 第 4 章：一组相同算子的跨架构数据通路与资源表；每项演进分别说明改变的约束、付出的资源和软件代价、适用负载及依据。
- 第 5 章：对应实现的缓冲生命周期、搬运／同步责任和执行轨迹；区分编译、捕获、预热和稳态执行。
- 第 8、10 章：分别在在线推理和训练迭代中加入批次变化、通信重叠与服务要求，复核整步收益。
- 待补证据：910A → 910B → 910C 的逐项指令与通路差异及设计历史，950 的可复现有效性能，以及跨平台开发、调优和维护成本。已有论文结构与尚未闭合的历史因果分别登记。
