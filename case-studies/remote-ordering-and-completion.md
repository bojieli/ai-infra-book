# 远端访问：并发窗口之后还要检查什么

> 对应当前 7.3.2／7.4.2，承接 6.6 的内存池访问，服务于第 9 章 KV 交接。复用实验 7-5、7-7 和图 7-6。2026-09-09 核对；这是扩写用的推算与证据，不是新增正文小节。

## 同一笔带宽预算，三种执行条件

[既有案例](collective-paths-and-diagnosis.md)给定每次返回 256 B、完成等待 2 μs、有效单向带宽 40 GB/s，算出至少约需 313 个在途请求。若窗口只有 128 个，`128×256 B / 2 μs = 16.384 GB/s`。这只给出窗口限制，还没有证明这些请求能够同时推进；这里的 256 B 是小访问的教学输入，不是模型 KV 块的统一大小。

保持这些输入，再假设所有请求都经过一个严格串行的服务点，每处理完一个请求用 0.1 μs，则还要加上 `256 B / 0.1 μs = 2.56 GB/s` 的上界。因而这一安排满足：

`吞吐 ≤ min(链路带宽 B, 在途窗口 Wm/T, 串行服务上界 m/τ)`。

若发起端更保守，每等到一个请求完成才发下一个，即使分配了 128 个槽位，实际窗口也只有 1，所得上界只有 0.128 GB/s。提高线速、扩大队列、缩短串行服务时间解决的是不同约束。反过来，若目标端能够流水处理，τ 应是可持续的启动间隔，而不是单次访问延迟；不能因为一次访存耗时 0.1 μs，就断定吞吐只有 2.56 GB/s。这些数是条件推算，不是任何产品或论文的实测值。

实验 7-5 用这三种条件问读者：128 个槽位里到底有几个请求在推进？先在路径图上指出限制，再选择扩大窗口、批量访问或改变执行组织；不能只把 `BT/m` 算对就结束。

## 保留顺序，改变检查顺序的位置

ASPLOS 2026 的 [Efficient Remote Memory Ordering](../references/proceedings/ASPLOS/2026/paper-116.pdf)提供了一个设计参照：已知地址的若干访问存在顺序要求时，可以让请求带上顺序信息，在更靠近目标内存的地方执行，而不是每次由发起端等完整往返。其 RLSQ 方案进一步利用并行访问、失效检查和重试，尝试缩短必要顺序造成的停顿。

这与删除依赖不同。设数据 D 和可用标志 F 初始都是 0：读取器先投机读到 D=0；生产者随后写 D=1，再发布 F=1；读取器最后读到 F=1。即使返回时先交付 F=1、再交付先前保存的 D=0，仍然违背了“看到可用标志后获得已发布数据”的要求。重排响应不能修正已经读旧的数据。论文为此让 RLSQ 跟踪投机读，在主机写入触发失效时丢弃并重读冲突数据。

把这个反例放进实验 7-7 的手画时序：分别标出实际取值、失效／重读和结果交付。它是说明错误安排的事件模型，不是可执行的 NVSHMEM 或 C++ 无同步程序；后者还涉及各自内存模型的合法性。

还有两类等待不能顺手删掉。其一，下一次读取的地址要从上一次结果中取得，属于真实地址依赖；论文图 2 的 Two Ordered DMA 正是先取 WQE、再按其中的地址取载荷。其二，需要先读取 CPU 内存中的状态、再访问另一设备的数据时，一个目标端未必能看到完整依赖，论文 §6.6 的方案仍退回源端等待。跨设备问题须单独检查，不能把同一 Root Complex 上的收益套过去。

## 论文结果与当前实现之间的距离

这篇论文主要面向 CPU—NIC 路径，需要 PCIe／ISA 扩展和 Root Complex 的新机制。[作者固定提交](https://github.com/icsa-caps/efficient-remote-memory-ordering/tree/e46840e779495d0d81ace5b199b3a14c7b7a5f5d)的 README 区分 gem5 24.1 仿真、CACTI 估计和 CloudLab 实验。论文中的新机制由仿真评估；真实 ConnectX-6 Dx 实验用无写入冲突时的无序吞吐估计潜力，没有在这块网卡上实现新的排序硬件。图 7 的性能不能作为并发写入下已保证正确的证据。

核对图 2 时也要保留分母和执行差异：64 B RDMA WRITE 的四种提交方式改变了客户端 NIC 的 DMA 次数与依赖，并非只切换一个等价的排序开关。因而可用来说明等待的量级，不能直接推导更换当前 GPU／网卡后的收益。仿真中的队列、存储配置，真实实验中的线程／QP，以及 CACTI 使用的工艺又各有范围。[页级阅读记录](../references/proceedings/ASPLOS/2026/remote-ordering-reading.json)保存这些边界；没有运行作者代码。

## 从 API 的承诺找到实际等待

再看现有 GPU 通信接口。[NVSHMEM 的排序文档](https://docs.nvidia.com/nvshmem/api/latest/gen/api/ordering.html)区分 `fence` 的同目标保序和 `quiet` 对相应已发出操作的完成保证；非阻塞 Get 不受 fence 保序。消费者仍需合适的 wait／test 等同步，CPU、GPU 与其他线程发起的操作也不能随意混用保证范围。扩写时用具体的“写数据—通知—消费”路径说明这几个选择即可。

API 规定的是必须提供什么保证，不直接规定代价。[固定 NVSHMEM 提交的公共 IB 路径](https://github.com/NVIDIA/nvshmem/blob/b0d9d3dc08fc3ee0840fdb6f3a2c11932d85a2e2/src/modules/transport/common/transport_ib_common.cpp#L767)中，`nvshmemt_ib_common_fence` 在 `multiple_qps || is_multi` 条件下调用 quiet；quiet 再遍历相应端点等待完成。这里的条件分支值得让读者自己找到：更弱的 API 语义，也可能用更强的等待实现。这个局部路径不代表所有 NVLink、IBGDA 或推理引擎的实际执行，更不能用它声称 vLLM／SGLang 已实现论文的 RLSQ。

实时文档与固定源码的身份分别保存于[交叉核对目录](../references/framework-history/2026-09-09/remote-ordering/README.md)。文档中的 GPU 发起通信还列有网卡、驱动、传输选择等条件；GPU 发起并不等于没有排序成本。此处不把这些配置扩展成框架特性清单。
