# 专家分派、重排与扩缩容

2026-09-08 的扩写准备。接续[专家工作与副本预算](moe-and-startup.md)，只增加三种调整各自何时合算的判断，并接到训练中的梯度通信。来源、版本与实际读取范围见[归档记录](../references/framework-history/2026-09-08/ep-reconfiguration/README.md)。数值为教学输入与配置推算，尚未运行引擎或 GPU 实验。

## 已有副本怎样接收当前 batch

EPLB 改变专家的物理放置；SGLang 2026 的 LPLB 在已有副本之间分配当前 batch 的工作。后者保留逻辑 top-k，按全局专家计数求各副本的分配概率。固定源码中，空 token 的 rank 也须参与计数归约；放置改变后要重建相应求解状态。概率分配不保证每个有限 batch 恰好达到连续优化的最优行数，均衡行数也不保证最短时间。

沿 Qwen3-235B 的单层形状建立一个**离线分派练习**：256 个 token、top-8，共 2,048 次专家执行。某个热点专家接到 256 行，在 rank 0、1 已有相同权重的副本；其余工作固定为 `[512,256,512,512]` 行。仅改变这个热点的分配：

| 分派 | 热点两副本的行数 | 四个 rank 的总行数 | 最忙 rank |
| --- | --- | --- | --- |
| 各分一半 | 128、128 | 640、384、512、512 | 640 |
| 按当前余量分配 | 0、256 | 512、512、512、512 | 512 |

四卡平均 512 行是下界，第二种分配达到它；无需复杂求解器。每行的三个矩阵乘法约需 `2×3×4096×1536=37,748,736 FLOPs`。若这一段计算受限、有效算力固定为 50 TFLOP/s，则最忙 rank 的矩阵计算预算从 **0.4832 ms** 降为 **0.3865 ms**，只腾出约 **96.6 μs**。全局有效计算量未变。若统计、归约、求解、采样及额外通信在关键路径增加 60 μs，净余量只剩约 36.6 μs；增加 120 μs 就得不偿失。实际 tile、权重重读、通信和非均匀设备速度必须回填，不能把 640/512 宣称为服务加速比。

这个练习只改已有副本，驻留容量不变。若先创建一个完整 BF16 副本，则增加 36 MiB／层；实际引擎还要求合法的全局槽位数与逐卡布局。**固定 SGLang 的 LPLB 支持检查不包含 Qwen3 或 DeepSeek V4**，因此 Qwen3 用于手算，不给它虚构 `lp` 启动命令；可运行变体采用已验证支持的 DeepSeek 系模型。V4 的 Waterfill 支持是另一条路径。

Waterfill 把共享专家加入 dispatch／grouped GEMM／combine，使较空闲设备承接共享专家工作；它不改变模型原来选出的 routed experts。接回第 6 章逐目的设备计流量：候选限于 token 已访问的设备时，通信与任意设备选择不同。当前静态／动态路径及小 batch 回退各有条件；动态路径即使回退本地执行，也先参加全局统计。Qwen3 没有这条共享专家路径，不能硬套同一实验。

SGLang 文章的历史 V3 FP8 与 V4-Flash FP8 测试均设置 `max_tokens=1`，报告 total throughput；它们不能证明长 reasoning decode 的输出吞吐或 P99 改善。V4 表的 batch／并发还与 V3 表不同。数学上的相同专家计算，不自动意味着浮点逐位相同；质量与 RL 概率要求接第 11 章。正文采用机制与条件，不抄表中的加速比。

## 重排需要多长时间收回成本

先保留现有分派，只移动八个完整 BF16 Qwen3 专家：目的设备需接收 **288 MiB**。若关键入口可用带宽为 25 GB/s，单纯传输下界约 **12.08 ms**；统计、复制、同步及共享链路干扰另计。假定 trace 显示整个重排暴露 20 ms，此后每个引擎执行步省 0.04 ms，负载分布至少保持 **超过 500 步**才收回时间成本。仅保持 200 步会净损失 12 ms，保持 2,000 步才净省 60 ms。一次执行步可以包含多个请求和 token，不能按请求数换算窗口。

这也解释观察窗口与更新间隔的取舍。当前 vLLM guide 按 engine steps 定义，SGLang manager 按迭代推进；SGLang guide 中“每 1000 requests”的例子不能直接用于计时。异步复制减少停顿时，也要计入它抢占的 HBM、互联和临时缓冲。

进一步考虑 Qwen3-235B 的 **8→16 rank** 教学布局：128 个专家、94 层，全部 BF16 routed 权重合计 **423 GiB**。均分后，每 rank 的这部分从 52.875 GiB 降到 26.4375 GiB；新加入的八个 rank 共需得到 **211.5 GiB**。如果旧设备对外发送的聚合有效带宽只有 100 GB/s，这一部分至少约 **2.27 s**，还未计 attention 等非专家权重、建组、图捕获和服务中断。不能只算“多八张卡就多一倍吞吐”；缩容则要检查剩余设备是否放得下权重、KV 和工作区。

vLLM 2026 Elastic EP 的文章和固定源码提供真实对照：准备新组、交接非专家权重、切换与重新 warmup，再结合 EPLB 处理专家；缩容要先把专家搬离退出设备。现有 DP attention 的 KV 属于各自请求状态，不能从专家权重迁移推断 KV 已迁移。文章中的 TP=1、Ray、单 API server 等范围与当前源码分别记录；所读当前路径仍显式拒绝 DBO，重置图与编译状态。Elastic EP 是重配置机制，扩缩容策略、故障后丢失状态的恢复还需上层系统负责。

## 训练中的梯度要放进哪些空隙

[FSMoE，ASPLOS 2025](../references/proceedings/ASPLOS/2025/public/paper-094.pdf) 的作者 v1 物理页 1–13 已读，图 3／4 已查看。采用一个判断：MoE 的 All-to-All 与梯度归约共享跨机链路时，梯度分桶必须同时满足“已经就绪”和“链路可用”；前向的切块方案不能直接复制给反向。论文的 ESP 是专家内部切分，文中假定 MP／ESP 对齐节点内设备，这与任意并行布局不同。

继续使用同一个 Qwen3 专家：若梯度以 FP32 归约，三个矩阵共有 **72 MiB** 梯度。教学设定持有该专家相同参数的四个 DP 成员进行 ring AllReduce（与前面的 EP 分派组分别定义），每 rank 的发送载荷为 `2×(4−1)/4×72=108 MiB`；假定有效单向带宽 25 GB/s、每次集合调用启动成本 0.02 ms，则需约 **4.550 ms**。这放不进一个 2 ms 的空隙。

若梯度已就绪，而随后有三个各 2 ms、没有 token 通信占用的可重叠空隙，可将梯度切为三个 24 MiB 块，每次约 **1.530 ms**，分别放入。总通信时间反而比整桶多 0.04 ms，但暴露在关键路径的尾部可能更少。若空隙只剩 1 ms、梯度尚未就绪，或同时进行的 All-to-All 占满链路，这个安排就失效。实际 bucket 往往跨多个参数，归约类型与精度由训练栈记录确定；该算例不是完整训练步时预测。

论文用 PyTorch 1.12／CUDA 11.3／NCCL 2.12，在 RTX A6000 与 RTX 2080 Ti 集群上评估修改过层数／专家数的 GPT-2／Mixtral 模型；并非当前完整模型的性能结果。其设计中存在单专家必须跨卡、DGX 网络带宽、Testbed-A 每节点卡数、公式双倍反向参数及图 5 标注等疑点，见阅读记录，未采用对应硬件数字或通用加速比。新实验用固定 Megatron Core 的实际 bucket／trace 验证这个预算，不声称 FSMoE 已成为 vLLM／SGLang 默认功能。
