# RL 长尾、样本选择与流式训练

核对于 2026-09-08，补充第 10.5 与第 11.3 的既有实验。[RollPacker（NSDI 2026）](https://www.usenix.org/conference/nsdi26/presentation/gao-wei)的物理页 2–15 已读，涵盖设计、实现、评估与讨论；[阅读记录](../research/2026-infra-survey/reading-nsdi-2026.md)列出与正式整卷的逐页核对。以下概率、容量和时间均为教学计算，没有运行论文代码、RL 训练或 GPU 性能测试。

## 先问缩短的是哪一种等待

长轨迹使一轮采样迟迟不能结束，即使大部分 GPU 已空下来。可以改变 prompt 分组、额外启动回答，也可以让已完成样本先计算梯度。这几种安排的时间线和训练含义不同。与 [Weave 的跨作业共享](rl-scheduling-and-recovery.md)相比，RollPacker 主要处理单个同步 RL 作业内部的长尾；它用 ROLL 组织 vLLM 0.8.4 rollout、CPU／GPU 奖励和 Megatron-LM 0.12.2 训练，不能把整套调度归为 vLLM 的默认能力。[论文 §4–5](../references/proceedings/NSDI/2026/selected/nsdi26-gao-wei.pdf#page=5)

短轮次把 prompt 数和每个 prompt 的回答数都放大，然后保留先完成的足量回答组，取消其余运行请求。未入选的 prompt 积累到一批后进入长轮次，重新生成完整回答。若目标是 128 个 prompt、每个 8 个回答，两维都取 1.25，初始提交量便是 `160 × 10 = 1600`，相对目标 1024 增加 56.25%。这只是提交数量；多算了多少 token、占了多少 KV、消耗多少设备时间，要按实际取消时刻累计，不能直接放大 56.25%。长轮次必须计入周期平均，不能只报短轮次的速度。

论文中的“推测执行”在这里指额外启动完整 rollout 请求，与第 8 章的草稿模型推测解码不同。固定源码的多域调度器先等待奖励、执行过滤，再把回答放入完成组，因此回放还应区分生成完成和验证完成。沿这条实现路径，验证时长也可能影响样本入选次序。[源码范围与版本](../references/framework-history/2026-09-08/rollout-tail/README.md)

## 参数新鲜与回答分布分别检查

所有 prompt 最终被处理，不表示每个 prompt 的回答仍按原分布进入更新。给一个最小反例：固定策略对同一 prompt 以各 1/2 的概率产生短／长回答，分别需要 1／10 秒；两个独立执行槽同时采样，只保留先完成的一个，忽略取消延迟。只有两个回答都长时，保留下来的才是长回答，所以其概率由 `1/2` 变成 `1/4`。权重全程未变，选择仍改变了条件分布。

四种等概率组合可以直接枚举。单次采样期望耗时 5.5 秒；两次抢先完成的期望墙钟时间是 3.25 秒，但两个槽合计期望占用 6.5 槽·秒，超过原来的 5.5。这里的槽是独立教学执行槽，不能当作连续批处理下的 GPU·秒。这个反例只证明“新鲜权重”不足以推出“采样分布不变”，不预测 RollPacker 的质量损失，也不否定它报告的验证结果。

对 GRPO 还要检查同 prompt 的组成员、奖励方差和 advantage；延后的 prompt 使用哪个策略版本也要记录。基线固定回答身份，先单独测重新安排执行次序；再加入额外采样与取消，分别比较保留／丢弃回答的长度、任务难度、奖励和最终验证质量。不能仅用每秒产出的训练样本数证明同等学习进展。[论文 §4.1、§6.1、§7](../references/proceedings/NSDI/2026/selected/nsdi26-gao-wei.pdf#page=5)

## 同一批样本能否边生成边算梯度

Stream Trainer 将部分完整的 rollout TP 组转为训练副本，把剩余请求迁走；保留生成 token，重新 prefill 得到 KV。已完成的完整回答组先做前向／反向，梯度暂存，所有 rollout 完成后再归约和更新。它没有在本轮尚未生成完时改变 actor 权重。训练状态、梯度卸载、通信组以及迁移后 KV 容量都约束可腾出的 GPU 数。[论文 §4.4–5](../references/proceedings/NSDI/2026/selected/nsdi26-gao-wei.pdf#page=9)

先代入贯穿模型 Qwen3-8B 的[固定配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)：BF16 KV 每 token 为 `2 × 36 × 8 × 128 × 2 = 147456` 字节。32 条轨迹各保有 8192 token，共需 36 GiB；若迁移后四个 TP=1 rollout 副本均匀各承接 8 条，且每卡扣除权重、运行时等后确有 12 GiB 可供 KV，单卡 9 GiB 可以放下。轨迹变成 16384 token，则总计 72 GiB、单卡 18 GiB，已超过预算。这里长度包含 prompt 与已生成部分；还要为继续增长留空间。不能仅凭“完成了一半请求”就释放一半卡。

通过容量检查后再画教学时间线：八卡 rollout 在 40 秒结束，八卡处理整批梯度需 16 秒，最后归约与更新另需 4 秒，串行为 60 秒。设 10 秒时恰好一半完整回答组已完成，可腾出四卡；迁移和状态交接花 3 秒，并使剩余 rollout 完成点延至 43 秒。假设训练工作均匀且 DP 理想缩放，早到的一半在四卡上用 16 秒，于 29 秒算完；另一半随后在八卡上用 8 秒，最终完成时间是 `max(43, 29) + 8 + 4 = 55` 秒。

同样的安排若使 rollout 延后 10 秒，完成时间就是 `max(50, 36) + 8 + 4 = 62` 秒，比串行更慢。该算例并未预测实机时间；真实实验需测半规模训练效率、KV 重建、状态加载和最后同步，把原来能重叠的工作与新引入的等待逐项对齐。

副本处理的样本数不等时，梯度归一化也要随之改变。两个副本分别处理 1／3 个样本，局部平均梯度为 1／3，则整批样本平均为 `(1×1 + 3×3)/4 = 2.5`；直接平均两个局部平均只得 2。若集合操作取平均，局部平均需要乘 `副本数 × 本地样本数／总样本数`；若先保留局部梯度和，则先除总样本数再求和。实际损失若按有效 token 归一化，就按对应 token 分母重做，不能一律套样本权重。数学上的目标一致还不意味着不同归约顺序逐位相同。

## 奖励变快以后，验收标准是否相同

RollPacker 还让奖励与生成重叠；judge 共置涉及 GPU 竞争、CPU 权重卸载与 PCIe 流水。它们的收益要回到阶段瓶颈。代码验证的自适应超时则另有含义：论文按已成功程序的运行时间调整限额，取 `min(max(2秒, 1.5×锚点时间), 30秒)`。较慢但正确的新程序可能被更早终止，因此短超时带来的节省应同时报告误判为零奖励的比例，最好用较宽限额复验抽样失败项。CPU 竞争、RPC 等待和测试程序执行限额要分开记录；调度器里的 RPC 外层超时不是论文所述单测试公式。[§4.3、§6.5](../references/proceedings/NSDI/2026/selected/nsdi26-gao-wei.pdf#page=7)

评估保留历史条件：端到端为 Qwen2.5-7B／14B／32B，最大回答长 8K／16K／32K，分别用 16／32／64 张 H800；128 卡用于扩展性实验，并非每个结果都用满平台。相对 veRL 的 2.03／2.22／2.56 倍是整套方案收益，不能全部归给 streaming。Table 3 的无缩容 124.2 秒到自适应 115.2 秒约为 1.078 倍；Table 2 的 2.02→2.22 是相对加速比约提高 9.9%，对应时间减少约 9.0%，不沿用正文所称 20%。这些数值不是 V4、K3、MoE 或 Agent 环境的已验证性能；论文把后两者列为扩展方向。
