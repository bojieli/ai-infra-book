# 算子拆分、融合与量化边界

供第 5.3 节和既有实验 5-4 扩写。沿一个真实 Qwen3 矩阵，把“kernel 越少越快”的直觉改成可核算的判断：哪些中间结果必须写出，哪些计算适合合在一起，新的实现又占用了什么资源。

## 历史案例：三个 kernel 与四个 kernel

Korch 的[作者版本](../references/proceedings/ASPLOS/2024/selected/korch-arxiv-v1.pdf)先将算子分解为更细的原语，再选择 kernel 组合。图 12 的 Candy 子图原来按 InstanceNorm、ReLU、Pad 执行三个 kernel，论文所报时间分别为 38.7、24.2、28.2 μs；重新拆分和组合后是四个 kernel，分别为 7.6、18.4、7.5、35.7 μs。总时间从 91.1 降到 69.2 μs。这里是论文的 V100／FP32 历史测量，没有在本机复现；它说明算子边界与高效执行边界可以不同。

Korch 以候选的实测时间求和选择串行执行方案，允许重复部分原语。其最优性受图划分、候选生成、后端和成本模型限制，不能推广到多流并发或任意程序。固定公开代码还有手工切图、候选剪枝和生成器支持范围；调优时间主要可能花在候选测量，求解器用时并不等于全部准备成本。[实现核对](../references/framework-history/2026-09-08/kernel-orchestration/README.md)

## Qwen3 的同一条激活与量化链

采用[固定 Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)，FFN intermediate size 为 12288，TP=1。令 T 表示本次执行的 token 行数，gate-up 投影输出为 BF16 `[T,24576]`，SwiGLU 输出为 `[T,12288]`。比较两种都输出同一 FP8 格式的方案：先做 SiLU+Mul 再量化，或在同一内核中完成激活和量化。量化方案固定为每行每 128 元素一组、每组一个 FP32 scale，无额外 padding；不是与未量化模型比较质量或精度。

T=1024 时，gate-up 输入是 48 MiB，中间 BF16 激活是 24 MiB，FP8 输出是 12 MiB。每行有 96 组，scale 共 `1024×96×4 B = 0.375 MiB`。T=1 的小 decode 变体按比例缩小。

| 数据流 | 分开执行 | 融合执行 |
| --- | --- | --- |
| 读取 gate-up | 48 MiB | 48 MiB |
| 写出、再读取中间 BF16 激活 | 24＋24 MiB | 0 |
| 写出 FP8 与 scale | 12＋0.375 MiB | 12＋0.375 MiB |
| 算子边界的逻辑读写合计 | 108.375 MiB | 60.375 MiB |

省下的是中间激活的一写一读，共 48 MiB。若暂用有效 1 TB/s 作教学预算，它对应约 50.33 μs 的搬运时间；T=1 时只有约 0.049 μs。小 decode 是否受益，更要检查暴露的启动间隙、量化归约和执行资源。这里的字节是逻辑账本：L2 命中、重复读取、对齐和编译变换会改变真实 HBM 流量，不能把这个比值直接当作加速比。

容量还要另算。假设单条链、输入最后一次使用后立即释放、输出按需分配：分开执行的活动张量峰值是 `max(48+24, 24+12+0.375) = 72 MiB`；融合执行为 `48+12+0.375 = 60.375 MiB`。消除 24 MiB 中间张量，活动张量峰值却只下降 11.625 MiB，因为最终输出需要更早分配。这只是这条链的存活张量载荷，不是整个模型的显存占用；allocator 保留、其他消费者、graph pool 和 workspace 都要补入真实预算。

## 从手工算子到当前框架的融合

vLLM v0.6.0 的 `SiluAndMul` 已将 SiLU 和乘法封装到一个自定义调用。当前固定提交的编译 pass 则匹配激活后接量化的图，将受支持组合替换为融合实现；每组 128／64 元素的 FP8 路径与 NVFP4 路径有不同条件。这是两个固定时点的能力对照，不据此认定融合特性的首次发布日。

这个对照更重要的一点是可见性：编译器看得见普通张量运算时，Inductor 可能自行融合；已有 opaque custom op 边界则可能需要专门匹配。当前文档因此对自定义激活／量化融合设置条件。实验中把 `fuse_act_quant` 设为 false，并不能证明实际执行就没有融合，必须检查图、生成内核和 trace。[固定文档和源码](../references/framework-history/2026-09-08/kernel-orchestration/README.md)

教学计算选择 FP32 scale、非 UE8M0、无额外对齐的明确变体。实际安装还要核模型量化配置、scale 布局、硬件、后端和模式是否匹配；不能把同名选项或文档支持表当作已经执行。不同融合可能改变中间舍入，仍须对同一参考输出检查误差。

## 权重、激活与低比特实现

2026-09-09 沿第 4.2.5→5.3→8.4 补充。仍用 Qwen3-8B 的一支 `[12288,4096]` FFN 权重，共 50,331,648 个值：BF16 为 96 MiB；MXFP4 每 32 值配一个字节的 scale，为 25.5 MiB。M²XFP 在每组再增加一个字节的元数据，理想载荷为 27 MiB，相比 MXFP4 多约 5.88%。NVFP4 每 16 值配一个字节的 scale，也约为 27 MiB，另外还要计全局 scale。平均位数相近，不表示数值含义、执行指令或质量相同。[格式与版本依据](../references/framework-history/2026-09-09/metadata-quantization/README.md)

M²XFP 将这些额外位数分别用于静态权重的子组尺度，以及动态激活中一个选中值的额外精度。前者的尺度搜索在加载前就可以完成，后者处于每次执行的路径上。按论文的三种组指数、四种子组尺度候选，整块权重有约 6.04 亿次“候选—数值”评估；这些不是等量 FLOPs。若将相同搜索用在每次 `[1024,4096]` 激活上，每次都要评估约 5,033 万对。不能因为离线搜索成本可以接受，就推定它适合实时激活；还要比较更简单的量化规则、专用单元及融合路径。

随后检查程序究竟保存了什么。作者公开工件将值量化后转换回原来的浮点 dtype，再调用普通矩阵乘法；假定原 dtype 为 BF16，上述权重的张量载荷仍是 96 MiB。这样的程序可以研究质量，却没有实现 27 MiB 的打包驻留。若另一实现先保存 27 MiB 压缩权重，再整块解压成 BF16，两份同时存活时仅这两块载荷就达 123 MiB；边解码边计算则需要按 tile 另算缓冲与吞吐。文件大小、实际驻留和矩阵执行精度必须分别验证。

框架演进也按实际对象比较。vLLM v0.12.0 的所读 MXFP4 方法对普通 Linear 回退到未量化路径，对 MoE 分配打包权重并选择后端；当前固定版本则已有普通 Linear 的加载时量化与 kernel 入口。当前指南仍允许不同后端选择 BF16 或低精度激活，所以不能仅凭 `mxfp4` 名称就认定 W4A4。这里也没有把 M²XFP 的研究格式当作 vLLM 原生支持。

将这些判断作为现有实验 4-2 的一条跟算路径：先核格式字节，再核权重和激活的工作发生在什么时候，最后查实际 dtype、分配和 kernel。图 4-3 标出“打包保存、整块解压、分块消费”三种路径，接到实验 5-4 的融合与生存期；第 8 章沿用任务质量比较。论文的速度来自专用架构模拟及满足质量条件后的混合精度基线，不移用为现成 GPU 的加速比。[独立算例](../research/2026-infra-survey/metadata-quantization-arithmetic.json)同时保留舍入和元数据身份的反例，不新增实验或图号。
