# KV 位宽、容量与执行成本

2026-09-08 扩写依据，落在第 8.4.4、实验 8-8 和图 8-7。正文保留一组可跟算的例子，版本、代码范围与论文限制留在这里和[来源记录](../references/framework-history/2026-09-08/kv-quantization/README.md)。这是推算与实验计划，没有运行模型或测得硬件性能。

## 从缓存的值数算起

沿用[固定 Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)：36 层、8 个 KV head、head dimension 128。一个请求有 8,192 个有效缓存位置，K、V 分开存，共 `2 × 36 × 8 × 128 × 8192 = 603,979,776` 个值。这里没有共享前缀、TP 复制或页尾空槽，也未计权重和其他状态。

| 表示方式 | 每组存什么 | 这组请求的格式容量 |
| --- | --- | --- |
| BF16 | 每值 2 B | 1,152 MiB |
| FP8 数值 | 每值 1 B，scale 另算 | 576 MiB＋相应 scale |
| q8_0 | 32 个 INT8 值＋2 B scale | 612 MiB |
| q4_0 | 32 个 4-bit 值＋2 B scale | 324 MiB |
| block-16 FP4 | 16 个 4-bit 值＋1 B scale | 324 MiB＋配方要求的全局 scale |

q8_0 和 q4_0 的组定义见 [Ollama v0.9.6 内含的 GGML 类型](../references/framework-history/2026-09-08/kv-quantization/ollama-096-blocks.txt)。这证明格式开销，不等于某个当前后端最终分配量。FP8 的 scale 不能随意按 token 数相乘：假定每层每个 KV head 分别保存 K、V 的一个静态 FP32 scale，只增加 `2 × 36 × 8 × 4 = 2,304 B`；若改成每 token 一个 scale，就是另一套格式。该教学假定不包含 Q scale 或框架其他张量。

SGLang 固定实现进一步说明为什么相同 4.5 bit/value 仍有不同预算：block-16 FP4 与 NVFP4 的 scale 语义不同，后者另有全局 FP32 scale；其已声明的 prefill 路径还分配跨层复用的 FP8 解量化工作区，decode 则可以交给支持原生 FP4 的后端。若池中恰有本例这些位置，一份 K、V 工作区为 `2 × 8192 × 8 × 128 = 16 MiB`，不能忘记，也不能再乘 36 层。实际池分配还有额外页，且这一读取范围没有审查所有模型的后端选择。见[配方与访问规则](../references/framework-history/2026-09-08/kv-quantization/sglang-fp4-recipe.txt)及[缓存池](../references/framework-history/2026-09-08/kv-quantization/sglang-memory-pool.txt)。

Oaken 提供另一个容易算错的例子：它为每个位置保留 4-bit 密集槽，异常值另用 8-bit 条目保存位置、组别和剩余位。异常值比例为 `p` 时，这两部分平均需要 `4 + 8p` bit/value；`p = 10%` 时为 4.8 bit/value，本例的理想密度容量约 345.6 MiB，仍未计 scale、阈值、变长管理和对齐。8 bit 是附加条目，不是异常值的全部存储。论文的 6-bit 索引不能直接解释为覆盖任意长度 head；本书不补造它未说明的局部索引规则。见 [Oaken §4.3–4.5，物理页 6–8](../references/proceedings/ISCA/2025/paper-033.pdf)。

## 从少存字节到少花时间

容量只是第一道约束。对原本受内存限制且串行执行的那一段，先比较节省的传输时间 `ΔM / BW_effective` 与新增量化、解量化、索引和启动开销；有重叠时则画依赖关系，比较关键路径。格式容量不等于每步实测 HBM 流量：融合、缓存命中、布局、查询头复用和工作区物化都会改变读写。

[vLLM 2026-04-22 官方评估](https://vllm.ai/blog/2026-04-22-fp8-kvcache)给了一个历史验证：在 H100／FA3、单并发的 Llama-3.1-8B 实验中，作者拟合的 BF16／FP8 ITL 分别为 `6.44 + 4.37e-5 L` 和 `6.58 + 2.37e-5 L` 毫秒。用这组已四舍五入的系数算交点，得到约 7,000 个 token；它只解释该组数据，不是 Qwen3 或其他设备的经验阈值。变化包括查询量化融合、分块与累加精度修正，还允许跳过短窗口层；收益需要连同 TTFT 和质量看。

SGLang 的 [2025 MLA FP4 PR](https://github.com/sgl-project/sglang/pull/10078)更适合作反例：同一份 B200／TP4／R1 报告中，FP4 比它的 FP8 路径快，仍明显慢于直接消费 BF16 KV 的基线，量化两组的给定 SLO goodput 都为零。模型权重同样采用该报告的 FP4 设置，不能把这项对照归因于权重量化。当前实现已细分 prefill、decode 的访问规则，不能把旧 PR 的慢路径写成今天全部 SGLang 后端的行为。

Oaken 用专用 DMA 量化／解量化单元、变长稀疏缓冲与内存管理隐藏转换；其模拟器、RTL 验证和综合数据不能作为已有 GPU 内核实测。论文中的硬件研究帮助提出问题，真实框架实验负责检验本机能否实现收益。

## 实验的两个层次

基础计算由相同模型和请求完成：值数→格式字节→额外工作区→容量上限。模型实验只选一个实际相容的引擎／后端，先固定输入输出形状扫描上下文和并发，记录数值格式、scale 粒度、实际分配、转换 kernel、TTFT、ITL 和关键路径；再用相同任务自然生成，记录质量、输出长度、截断、重试和总耗时。不能要求读者为一个判断同时安装三套框架。

SGLang 的历史 MHA PR 中，Qwen3-235B 在 GSM8K 上的近似持平没有延续到 AIME25；不同任务必须分别报告，不能用“大模型对 FP4 不敏感”代替验证。[原始表与条件](https://github.com/sgl-project/sglang/pull/12612)只作为设计实验的依据，不移用成 V4／K3 的结论。现有实验 8-8 的自然生成质量比较继续保留，配图在该实验附近生成。

## 论文的读取边界

Oaken v1 的物理页 2–12 文本已读，另实际查看页 6、7、11、12 的图表或公式；第 1 页之前只读摘要／身份，第 13–15 页不计为本轮正文阅读。[逐页记录](../references/proceedings/ISCA/2025/oaken-reading.json)保留哈希和评估限制。

正文 §4.3 的离线阈值与在线 per-token/per-group scale 分开；不能由少量校准数据推断任意输入的分布不变。论文将注意力称为不可批处理，只能用来提醒不同请求通常不共享 KV，不能否认批处理 kernel、GQA 或共享前缀。v1 的图 12(b) 实际为延迟分解，图 13 为序列长度扫描，两个图注内容互换；不据图注转抄性能数值。0.54% 与 0.87% 的质量损失采用不同基线，面积比例的分母是计算核心，功耗估计与 A100 TDP 也不是同口径实测。上述问题保留在研究记录，不塞入正文扩成论文勘误。
