# 分块执行、阶段分离与请求迁移

2026-09-08 的编辑与推算笔记。沿第 8 章同一实例的执行，走到第 9 章阶段放置与运行中迁移；三篇 OSDI 2024 论文用来解释不同决定的来由。这里只补已有小节和实验变体，没有运行 GPU 或云服务实验。

## 相同 token 预算为什么不等于相同执行时间

沿第 2 章的 [Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)，取 8,192 个输入 token，每次 prefill 512 个。假定完整因果注意力、没有前缀命中，暂不计 batch 中其他请求。对一个已有 h 个历史 token、包含 q 个新 token 的块，有效注意力配对数为：

`A(h,q) = qh + q(q+1)/2`。

第一块为 131,328 对，最后一块为 4,063,488 对，后者约为前者的 30.94 倍。36 层、32 个查询头、head dimension 128 的 QKᵀ 与 PV 合计为 `4 × 36 × 32 × 128 × A(h,q)` FLOPs。GQA 减少 KV 头数，不能把这里的查询头也换成 8。投影、FFN、Softmax、位置计算和输出头另计。

十六块合起来仍是 `8192×8193/2 = 33,558,528` 对，对应上述两次矩阵乘约 19.79 TFLOPs。这里按未被 mask 的有效配对计算数学工作；内核的边界 tile、padding 和重算可能增加执行工作。外层分块没有改变因果注意力总配对数，也不能由“最后一块是 31 倍配对”推出总耗时是 31 倍，因为每块还有投影、FFN、访存、提交与同步。

由此引出 Sarathi-Serve 的 token 预算：它是便于调度的第一步近似。把长 prefill 切小，可以缩短其他请求两次 decode 之间的等待；切得过小又会增加提交频次、降低矩阵利用率，影响 tile 对齐和历史 KV 的读取。应按历史长度、batch 组成和图执行状态校准每步耗时，再选择满足服务目标的候选预算。

尤其不要把外层 chunk 数直接换成 HBM 访问倍数。未做外层分块的 FlashAttention 本身也按 query tile 读取 KV；实际流量还取决于 L2 复用、head 映射、布局和内核。配对数、逻辑状态字节与物理 HBM 流量是三笔不同的账。

实验 8-2 先手排相同到达序列，改变 prefill 块所在的历史位置，预测 attention 工作变化，再在固定 vLLM 上记录实际执行步。图 8-1 在时间线旁标出本步新 token 与历史长度，无需增加图号。

## 从分块策略走到统一请求调度

[固定实现与版本说明](../references/framework-history/2026-09-08/chunk-scheduling/README.md)保存 vLLM v0.4.2、v0.8.0 和当前固定提交的相关路径。2024 年 v0.4.2 已提供实验性分块 prefill；不能把分块本身写成 2025 年 V1 的新发明。旧路径分别组织 prefill 与 decode，V1 用每个请求“已完成多少、还需计算多少 token”统一组织执行，使 prefill、decode 与推测验证可以共用预算。

到当前实现，这个预算还要同时满足 KV 分配、远端 KV 就绪、多模态编码、推测占位和图形状等条件。正在运行的请求也可能还没完成 prefill；概括成“每一步严格把所有 decode 排在所有 prefill 前面”会丢失实际调度条件。源码中的输出列表排列也不等于准入优先级。

历史调优文档的 512，以及当前文档针对不同目标举出的 2,048／8,192 以上，是对应环境的调参示例，不能变成全书通用默认值。实验应保存版本、最终配置、请求分布和实际后端，把第 5 章图执行与本章预算连起来。

## 两张卡怎样分工，要把到达率算进去

DistServe 为 prefill 与 decode 分别选择并行和放置，适合接回第 6、7 章的约束推算。先用它的简化排队模型说明“单请求最快”与“给定负载下平均完成最快”可能选择不同方案，然后再加入 PD 的 KV 交接。

给定同长请求、Poisson 到达、FCFS，假设 prefill 在单卡上的固定执行时间 `D=0.2 s`，两路 TP 的实测输入暂以教学值 `K=1.6` 倍加速代替；两段 PP 则完全均衡，每段 `D/2`，暂不计交接。只比较这两个可行候选，两者都使用两张卡。由 M/D/1 等待公式得到：

- TP：平均完成时间 `D/K + λD² / [2K(K−λD)]`，容量上限 `K/D = 8 requests/s`。
- PP：请求仍经过两段，总执行约 D；第一段排队后平均完成时间 `D + λD² / [4(2−λD)]`，容量上限 `2/D = 10 requests/s`。

| 到达率 | TP 平均完成时间 | PP 平均完成时间 |
| --- | --- | --- |
| 1 request/s | 约 134 ms | 约 206 ms |
| 7 requests/s | 约 563 ms | 约 317 ms |

输入均为教学假设，不是 Qwen3 或 A100 的测量。若模型可以完整放入单卡，还应加入两个副本的候选；不能仅比较 TP／PP 就宣称全局最优。变长请求、批处理、非均衡 stage、网络争用会改变上述模型，平均等待也不能证明 P99 达标。这个小算例只用来淘汰不合理方案、选择下一步要回放的配置；不需要先写复杂仿真器。

第 9.2.1 简述这个转折，实验 9-2 用实际请求分布检验两池选择。阶段服务率都换成同一请求分布的 requests/s，不能把 prefill token/s 与 decode token/s 直接相除当卡数比例。

## 链路能承接吞吐，仍然可能增加可见等待

Qwen3-8B 的 8K BF16 KV 为 `8192×36×2×8×128×2 = 1,207,959,552 byte = 1.125 GiB`。假定每个请求都需完整交接、没有共享前缀，链路可供该业务使用的有效单向载荷带宽为教学值 **11 GB/s**：

- 一份 KV 的独占传输时间下界约 **109.81 ms**，尚未计排队、格式转换、暂存、重分片与启动。
- 每秒 8 个请求需要约 **9.66 GB/s**，吞吐条件允许，但不能因此把每次传输等待视为零。
- 每秒 16 个请求需要约 **19.33 GB/s**，已经超过带宽；即使 P、D 两池都还有算力，队列仍会增长。

最大平均承接率约 9.11 requests/s，只是必要的速率边界；接近饱和时的排队、突发和共享通信决定尾延迟。这个 11 GB/s 不是某张卡的标称 NVLink 带宽，也不是本文网络实测。若按层提前传输或与计算重叠，仍保留总字节数，沿依赖图只计入暴露的等待；首 token 是否需要等待全部 KV 取决于服务协议。发送端在接收完成前还要保留相应状态，有限缓冲不能消除回压。

第 9.2.3 保留原有 1 GiB／25 GB/s 的短算术检查，再用这个真实模型形状补“每次等多久”和“每秒搬多少”的区别，实验 9-2 扫描负载验证。

## 计划迁移与故障恢复需要什么状态

Llumnix 将选择实例延伸到请求运行过程中：旧的、不会再修改的 KV 块先复制，请求继续生成；随后追平新增块，在最后交接时短暂停止。源端与目标端要协商接收空间、失败清理和完成确认，成功后才释放原状态。大部分复制可以与生成重叠，但**完整复制时间、占用带宽和请求暂停时间分别计量**。

这建立在论文所用 LLaMA 的旧 KV 块不可变这一条件上。换成 V4 的压缩／窗口状态或 K3 的循环状态，先判断哪些内容仍在修改，为可变状态、token 位置和采样进度建立一致的交接点，不能把“复制完整前缀”自动等同于恢复完整执行。普通 KV connector 提供传输也不自动代表整个请求可以热迁移。

该论文原实现通过 GPU→CPU 连续缓冲→Gloo→GPU 搬运，批量整理块以减少消息数；不是默认采用今天的 GPUDirect 路径。原文对当时 NCCL 并发限制的判断也不能推广为所有当前版本的性质。背景复制仍可能竞争 CPU、HBM、PCIe 和网络。

计划迁移依赖源端仍能合作。Llumnix 原文明确：实例失效会中止其运行请求，并不是持久化故障恢复协议。第 9.6.1 再接 V4 的 token WAL／KV 保存，分别讨论继续执行、依据已交付 token 重做 prefill、重新采样的差别。实验 9-10 的恢复变体先列可恢复状态与故障点，再用已核实系统记录分析；未确认当前后端支持热迁移前，不提供声称可运行的迁移命令。
