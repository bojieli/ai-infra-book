# 历史草稿、验证产出与 RL 供给

核对日期：2026-09-08。用于第 8.3.1 的草稿与每轮产出，以及第 10.5.3 的 RL 资源配比。本文是扩写依据，保留具体推算与来源边界；主大纲只采用能改变设计判断的部分。

## 历史里有答案，为什么仍要计算

代码编辑和重复采样会再次生成相似片段。与其为这些片段运行草稿模型，可以从已有 token 中提出候选，再由目标模型批量验证。vLLM 的 [2024 年文章](https://vllm.ai/blog/2024-10-17-spec-decode)已介绍 prompt lookup；这个机制适合用来问：省掉草稿前向以后，查询与额外验证是否值得？不能只比较匹配率。

[RhymeRL](https://arxiv.org/abs/2508.18588)把这个问题放进 RL：同一个 prompt 在不同轮次得到多个回答，历史既能提供 token 候选，也能帮助预测回答长度。公开稿 §5.1 用完成后的新旧回答做离线匹配；图 6 的约 93%／75% 是这套匹配过程中的数学／代码观察。§7.2.2 和图 17 则分别报告来自推测执行的产出比例与草稿接受率，后者为 65%–79%。这些量的产生过程与分母不同，不能拿前一个比例直接算在线加速。

先看一个独立反例。假设目标只生成 A、B，历史包含全部 16 种四 token 序列。事后查找任何完整四 token 输出，覆盖率都是 100%；在线只能按当前前缀选择草稿，无法事先知道目标接下来会采样哪一串。这个反例说明覆盖率缺少哪项信息，不声称论文的匹配程序采用了这一极端构造。

## 同一个目标分布，两份草稿的收支

固定已完成 temperature、top-p 等处理后的教学目标：每一步独立地以 1/4 概率输出 A，以 3/4 输出 B。草稿确定性地提出 AAAA 或 BBBB。这里刻意不模拟真实语言模型的条件相关性，目的是把验证、补偿和产出数算清。

若提出 A，当前目标以 1/4 的概率接受它；拒绝后，从扣除草稿概率质量的剩余分布采样，此例只能得到 B。提出 B 时反过来。每轮在第一次拒绝处提交一个补偿 token；四个草稿全部接受后，再从目标分布产生一个额外 token。若只检查“在允许词表里”就全部接受，目标分布会改变。

令每个草稿位置在此前位置都接受的条件下，以概率 a 接受。本例的平均每轮产出为

`E[L] = 1 + a + a² + a³ + a⁴`。

假设普通 decode 为 1 ms/token，一轮验证为 1.4 ms，历史查询为 0.1 ms。这些全部是教学输入，未测量 GPU 或 CPU。

| 草稿 | 条件接受概率 | 平均每轮产出，含补偿／额外 token | 平均每输出 token 时间 |
| --- | --- | --- | --- |
| AAAA | 1/4 | 341/256 ≈ 1.332 | 1.5÷1.332 ≈ 1.126 ms |
| BBBB | 3/4 | 781/256 ≈ 3.051 | 1.5÷3.051 ≈ 0.492 ms |

两种方案都保持目标分布，却只有后一种在给定成本下比普通 decode 快。前一种即使查询免费，验证成本也已超过平均产出能抵消的时间。若为了提高接受率扩大搜索，后一种允许的查询时间也不是无限的：稳态获益要求 `查询时间 < E[L]×普通 decode 时间 − 验证时间`，此例约为 1.651 ms。

收益还需抵消启动。若索引建立和搬运有 2 秒无法被其他工作隐藏，按稳态节省估计，后一方案需要约 3,935 个输出 token 才能抵消。这个值用于判断数量级；真实短请求必须逐轮计入 EOS、输出截断、空草稿、并发和实际批形状，不能直接把稳态比值当作完成时限。

[计算脚本](../research/2026-infra-survey/calculate_history_speculation.py)用有理数穷举 40 组目标概率、草稿选择和块长，检查前六个输出的完整联合分布；以事件枚举独立核对平均产出公式。[结果](../research/2026-infra-survey/history-speculation-arithmetic.json)同时保留时间和容量的假设。它没有执行下载的框架代码，也不能证明某个生产采样器的全部路径正确。

## 从插件到框架入口，哪些成本仍在

2025-05 的 [vLLM RFC #18037](https://github.com/vllm-project/vllm/issues/18037)描述 Arctic Inference 与 vLLM 0.8.4 的插件使用，并提出集成方案。这是历史提议，不是合入证明。已归档的 vLLM v0.19.0 标签文件包含 suffix proposer，release 身份给出的发布日期为 2026-04-03；据此只能说该发布快照已有这条入口，不能断言这是首个支持版本。

固定 vLLM `537af2c…` 的 proposer 导入 Arctic 的缓存实现，每步提交 token ID 草稿，并按上下文与最大长度约束起草。固定 Arctic `aca5d9a…` 的 `cache.py` 维护局部树与全局历史；路径草稿依据频次选择，并用经验分数控制长度和选择来源。它们用于提出候选。vLLM 所读 rejection sampler 的无草稿概率路径则将所提 token 当作确定性提案，使用处理后的目标概率决定接受，并在拒绝时去除该 token 的概率质量。经验分数不应直接冒充目标概率，也不是这里传给采样器的完整草稿分布。[固定原件与行段](../references/proceedings/ASPLOS/2026/rhymerl-reading.json)

当前 SGLang 固定指南也提供 NGRAM，但注明 CUDA、DP attention、重叠调度和混合 chunked prefill 的限制。比较真实引擎时，需将这些配置变化的成本放回同一服务基线；只测一次字符串查找不能代表完整推理收益。没有将 SGLang 文档中的支持声明扩大为完整 worker 或采样路径审计。

局部树在活动请求结束时释放；全局历史可以保留已生成的回答，并在生成过程中更新。因而“仅缓存完成请求”并不足以描述当前代码。全局缓存按请求数执行 FIFO 限制，活动请求的局部树另外存在；`max_cached_requests` 不能直接换算成固定 GB，也不能当作所有主机内存的上限。

容量练习取 1,024 个 prompt、每个 8 条各 4,096 token 的历史。uint32 token ID 本身为 128 MiB。若完整索引表示假定每 token 32 字节，便需 1 GiB；新旧两份同时存在时为 2 GiB，再另计构建暂存、传输缓冲、分配器和其他进程。这里的 32 字节已包含 ID，不能再加一次 128 MiB；也不能将其写成 RhymeRL 或 Arctic 的实测常数。

## 起草加速以后，重新安排 RL

RhymeRL 的 HistoSpec 为每个 prompt 索引上次 rollout 的回答，并以奖励信息选择历史分支；窗口从 2 开始，全接受时加 2、最多 32，发生拒绝则重置为 2。论文称其受 AIMD 启发，并非照搬减半规则。大 batch 是否仍值得起草，由结合接受率的 profile 决定。这提供一种工作分配原则：先测当前机制下的供给，再配资源，不能拿普通 decode 的容量直接当作推测执行容量。[公开稿 §5](../references/proceedings/ASPLOS/2026/paper-101.pdf#page=5)

HistoPipe 再用历史回答组的中位长度分组，使相邻轮次的长短工作互补；第二层调度改变分配给各组的 rollout worker 数量。每个 worker 内部模型并行配置由用户给定，增加 worker 主要改变 DP 副本和每个副本的 batch，不能称作动态改变 TP。其 `τ(长度, worker 数)` 来自包含 HistoSpec 影响的 profiling。接受率、查询成本或长度分布改变时，这张时间表也需要重新校准。[公开稿 §6](../references/proceedings/ASPLOS/2026/paper-101.pdf#page=8)

把它接到实验 10-8：固定任务和质量条件，先用普通 decode 算生成供给，再代入历史起草后的实际产出、索引工作和验证时间，检查奖励、学习或权重交接是否接替成为瓶颈。历史 token 是提案来源，旧 KV 是特定权重下的状态，Router Replay 记录离散专家选择；三个对象分别登记。关于跨轮迁移、样本成员变化和重采样偏差，复用已有[RL 状态](rl-state-and-reproducibility.md)与[RollPacker 算例](rollout-tail-and-sampling.md)，不再增加一套相同推导。

## 证据范围与采用取舍

读取的是 2025-08-26、15 页的 arXiv v1。作者出版条目与官方日程确认 ASPLOS 2026 的 RhymeRL 题名和 DOI，正式版为 17 页；出版商下载返回 403，尚未取得正式全文。当前选读为物理页 2–11 的相关正文和第 12 页参考文献前的部分，实际查看七张图表页；未将整份抽取文本算成全文阅读。

公开稿主要评估 8B–32B 数学／代码任务，使用 verl v0.4.1、AReaL v0.3.0，披露 16 节点、128 GPU，但未给 GPU 型号。吞吐指标是生成并处理的 samples/s，基线的策略滞后设置不同；RhymeRL 采用一步滞后。图 19 的两组奖励曲线是限定条件的评估，不能证明任意迁移、草稿或采样设置均不影响训练。裁剪目标也不等于策略每一步变化都受到硬约束。

主大纲采用两条判断：第 8 章先比较真实产出和完整成本；第 10 章按改变后的 rollout 供给重配资源。窗口常数、索引实现、旧性能倍数和完整算法留在扩写材料。现阶段不补写 RhymeRL 的开源部署实验，也不把 vLLM／Arctic 的代码检查说成 RhymeRL 采样器的实现证明。
