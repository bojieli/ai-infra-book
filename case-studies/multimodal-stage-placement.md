# 多模态输入的字节、状态与阶段放置

核对于 2026-09-08，接第 8 章的 Computer Use、第 9 章的请求调度与第 10 章的阶段分离。[版本原件与读取范围](../references/framework-history/2026-09-08/multimodal-execution/README.md)已归档；本轮只读文档、论文和固定源码，没有运行模型或测量 GPU。教学值与公开实验分开。

## 从接收图片到独立安排编码

vLLM v0.6.0 的视觉指南仍声明实验性支持、每 prompt 一张图片，同时已有直接输入 image embeddings 的例子。它说明接口能接收张量，并不等于已有完整的远程编码服务。2025 年 EC transfer 把存在检查、调度、保存、加载与完成通知分开：PR #25233 于 **2025-11-12** 合入，v0.11.1 于 **11-18** 发布，设计文章发表于 **12-15**。这些日期不混为一个首次发布日期。

当前固定 vLLM 指南的参考 connector 是 ExampleConnector；所读实现先把 EC 转到 CPU、写 safetensors，消费端再加载到设备。这是调试／共享目录路径，不是零复制 RDMA；其方法名里的 start 也不能代替实际异步重叠证据。生产传输后端应另固定版本和支持范围。

SGLang 2026 年 1 月公告把视觉编码从 P／D 中拆开，允许多编码实例分担一请求里的多张图片。当前指南进一步区分 **encoder 传输后端**与 **全局视觉 embedding 缓存**：都可以使用 Mooncake，但启用传输不等于启用缓存，缓存命中也不等于命中语言模型 KV。图像较少时，额外交接和独占编码资源可能抵消收益。

Ollama 2025 年的新引擎则从本地模型边界出发，强调投影、位置与图像跨 batch 的处理遵循模型要求，并缓存仍被使用的图像。接回已经核读的 2026 GGUF／MLX runner：应用入口相同，不表示执行路径相同；文本层驻留 GPU 也不保证 projector 在 GPU。这三个框架按各自实际能力进入实验，不要求它们提供相同的分布式部署。

## 一张截图会产生多少特征与 KV

沿官方固定 [Qwen3-VL-4B 配置](../references/framework-history/2026-09-08/multimodal-execution/qwen3-vl4-config.json)与 [预处理配置](../references/framework-history/2026-09-08/multimodal-execution/qwen3-vl4-preprocessor.json)，增加一个视觉变体，不替换全书的 Qwen3 Dense、V4／K3 主例。题设使用**预处理后 640×640、一个静态图像、BF16、不作视觉 token 剪枝**：patch 为 16，空间合并为 2×2，得到 `40×40=1600` 个 patch，合并为 **400 个视觉 token**。静态图像的时间维按一个 temporal grid 计，不因 temporal patch size=2 再把 token 数翻倍。

“400 个 token”仍不足以算传输。语言模型宽度 2560；最终投影为 `[400,2560]`，占 **2,048,000 byte**。该模型另取第 5、11、17 个视觉 block 的三组 DeepStack 特征；固定 vLLM 实现把它们与最终输出沿特征维拼接，完整 encoder 输出为 `[400,10240]`，占 **8,192,000 byte，约 7.8125 MiB**。后续再拆成主 embedding 与三层注入，并不是把语言序列变成 1600 个位置。实际 connector 若另行分块、压缩、量化或剪枝，应核实它真正发送的张量，不能只按模型 hidden size 估计。

与第 8 章题设的 **0.8 MB 压缩截图**相比，在有效上行 6.4 Mbit/s 时，传图片的载荷时间为 **1 s**，传这份完整 BF16 特征为 **10.24 s**，尚未计本地编码和协议。端侧先编码在这组条件下增加了传输，不能仅凭“云端少运行 ViT”决定放置。若换成数据中心内有效单向 **25 GB/s**，同一特征载荷下界为 **0.32768 ms**；仍需计入调度、D2H／H2D、序列化、接收就绪和拥塞。

KV 再单独算：36 层、8 个 KV 头、head dimension 128、K/V 各一份、BF16，每位置为 `36×8×128×2×2=147456 byte`。只计这 400 个视觉位置，逻辑 KV 为 **56.25 MiB**。四张图的 encoder 输出为 **31.25 MiB**，对应视觉位置的 KV 为 **225 MiB**；若再加 400 个文本位置，输入 KV 共 **281.25 MiB**。这些数不含特殊 token、输出增长、页碎片及工作区，也不是实际 HBM 访问量。

图像 EC 可以在相同编码条件下跨不同问题复用；语言 KV 还依赖之前的文本、图片顺序与位置。当前 SGLang identity helper 将内容、预处理参数、处理器指纹组成 identity，指纹包含版本等信息；调用方如何传入这些值仍需核实。Computer Use 每轮截图改变时不能沿用旧内容身份。RAW 精修又有不同的输入语义，视觉理解的 embedding 不能当作精修所需原件的等价替代。

## 编码缓存改变配比，却不自动减少下游流量

沿上述四图请求给一组明确的教学效率：总共四张同型 GPU；每 E 卡在限定形状下能处理 12 张未缓存图像/s，每 PD 卡能完成 4 个同分布请求/s；E→PD 共享有效单向链路为 300 MB/s。这里只算候选方案的平均服务率上界，不预测尾延迟，也不把这些效率称作 Qwen3 实测。

设图像 EC 命中比例为 h。假定命中发生在 encoder 侧，命中与未命中都需把完整 EC 送到 PD，缓存查询、取回和回写暂未计入，则：

`候选请求率 ≤ min(12×E卡数 / [4×(1−h)], 4×PD卡数, 300000000 / 32768000)`。

| 四卡方案 | h=0 的上界 | h=75% 的上界 |
| --- | ---: | ---: |
| 1E＋3PD | 3 requests/s，编码受限 | 约 9.16 requests/s，交接链路受限 |
| 2E＋2PD | 6 requests/s，编码受限 | 8 requests/s，PD 受限 |

命中较少时多配 E 有意义；命中较多时同样四张卡可能应多留给 PD。h=75% 只把未命中编码工作降为四分之一，本题跨池特征字节没有下降。若缓存改放在 PD 或省掉重复特征传输，必须重画数据路径再算；外部缓存自身的取回能力也可能成为更早的约束。实际请求到达率应留有余量，不能取服务率上界就宣布 SLO 已满足。

## TriInfer：先缩小候选，再重放比较

[TriInfer 的 MLSys 2026 正式稿](../references/proceedings/MLSys/2026/papers/mlsys2026-f068c65585985c25c17f221390774ec7.pdf)物理页 1–12 的正文及页 15 附录已读，参考文献未逐项阅读，图中曲线未独立数字化。会议目录标题与 PDF 标题略有区别；目录摘要的 3.7×、PDF 摘要的 2.4×及正文分模型比较的倍数不强行合并成一个通用速度结论。

采用三项思路。第一，image budget 与 text-token budget 分开，根据含不含 decode 选择本轮时间预算；不能只控制 prefill chunk 就认为图像编码不会打断生成。第二，允许 E、P、D 的不同组合，先用各阶段工作量／有效吞吐估卡数，再重放历史请求比较候选。第三，接收方先取得容量再拉取状态，源端等完成通知再释放；需算交接中的双份状态。

“EP＋D”在这篇论文中表示 encode 与 prefill 共置，**不是专家并行 EP**。正文用中文解释共置关系，避免与第 6、10 章的专家并行混淆。

双 stream 仍要经实际并发 profile 校准。教学假定 D 单独 18 ms、E 单独 23 ms，若题设给出同卡并发 35 ms，则两者单独均低于 30 ms 的步预算，合在一起仍可能超时；`max(18,23)` 只是假定完全重叠且无争用的理想值。减少图像批量或独立编码都可以成为候选，最后检查真正暴露在 decode 间隔上的等待。

论文通过启动时 profiling、历史数据抽样与重放选择配置，重配加权重加载为分钟级，并假设负载不会在很短时间内突然剧变；不能写成任意每步自动切换的全局最优调度器。接回 ServeGen 的短窗案例，在同一四卡预算下检验图片突发、命中率变化与准备期间积压。

实验条件保留原样：vLLM 0.11.0、SGLang 0.5.3 的普通共置基线；FP16；关闭 prefix cache 与 CUDA Graph；输出长度预先记录后用 `max_tokens`／`ignore_eos` 固定；其 EPDServe／DistServe 对照是在 TriInfer 内重做核心分离方式，并非直接运行两套原系统。论文图文采用 LLaVA 系列／Qwen2-VL，不能替换为当前 Qwen3 或 K3 实测。论文自报的 H20 141 GB 测试环境也不替代本书 H20 96 GB 规格来源。

TriInfer 的请求 SLO 先检查 TTFT 与该请求 90% 的 TBT，再要求至少 90% 请求达标；vLLM 公告的 P99 TTFT／TPOT 是另一口径。当前 vLLM／SGLang 已有 EPD，不能沿用旧基线的限制来描述今天的框架。对 Qwen3-VL 变体先固定相同设备数，再分别开放图、缓存与阶段分离，记录实际形状、总字节、均值和尾部。

## vLLM-Omni 的生成卸载：保留研究对照

上一轮只读开头的 [DLO 文章](../references/framework-history/2026-09-08/offload-execution/vllm-omni-dlo-2026.html)本轮已读正文、表格及限制，并核对固定 backend 的分片、复制／AllGather 事件和共享缓冲。它解决 DiT 反复执行时的权重容量，与 E→P 传图像特征是不同对象。除两份完整 block 缓冲，还要计 AllGather 输入分片、激活和其余常驻模块；跨 DP 的权重集合操作也要求请求具有相容控制流。

B300 的 1024² T2I 表中，四输出 43.69 s 对一输出 15.19 s，聚合吞吐约为 1.39 倍，每轮等待却更长。200B 规模只作主存容量外推，没有实际运行该规模模型。Ascend 的 cgroup 与 CUDA 的 PSS 统计范围不同；MiniMax-H3 拓扑实验还包含本地补丁及关闭图执行。暂不为这些结果新增生成模型小节，以免扩大背景和实验规模；保留用于扩写时检验容量、吞吐、延迟及版本口径。
