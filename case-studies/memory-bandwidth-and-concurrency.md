# 访存并发与带宽估算

本笔记支持 1.3.3／实验 1-4／图 1-3，并由 4.3.3 承接。先用字节数除以带宽求服务时间下界，再判断执行能否提供足够多的独立访存。正文保留一个选择发生变化的例子；完整输入留在实验中。

## 从 Qwen3 的 KV 读取开始

沿用 [Qwen3-8B 固定配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)：36 层、8 个 KV heads、head dimension 128、BF16。单请求已有 8,192 token 时，全历史 KV 的逻辑载荷为 `36×2×8×128×2×8192 = 1,207,959,552 bytes = 1.125 GiB`。本例只讨论这部分读取；权重、新 token 写入、片上命中及分块重读分别计数，不能把结果当作完整 decode 时间。

设整个设备最多维持 `N` 个独立未完成事务，每个事务跨所选接口传 `s` bytes，工作点的平均完成延迟为 `L`。稳定执行时，事务速率至多为 `N/L`，因此 `B_effective ≤ min(B_interface, Ns/L)`。这里的 N 不是用户 batch、CUDA 线程数或 SM 数；合并访问、依赖和硬件队列都会改变可用并发。L 必须对应同一接口和负载，不能用空载探针延迟代替任意内核的完成延迟。

以下全部为教学假设：事务 128 bytes、延迟 500 ns、接口上限 1 TB/s。达到该带宽至少需要约 3,907 个并发事务。用同一份 KV 载荷改变条件：

| 独立事务上限 | 接口上限 | 工作点延迟假设 | 吞吐上界 | KV 服务时间下界 |
| --- | --- | --- | --- | --- |
| 128 | 1 TB/s | 500 ns | 32.768 GB/s | 36.864 ms |
| 4,096 | 1 TB/s | 500 ns | 1,000 GB/s | 1.208 ms |
| 4,096 | 2 TB/s | 500 ns | 1,048.576 GB/s | 1.152 ms |
| 4,096 | 1 TB/s | 800 ns | 655.36 GB/s | 1.843 ms |

第一项说明依赖与并发不足可以让高带宽闲置。第二、三项说明只把接口带宽翻倍，给定并发下的上界改善有限。第四项提醒读者：更重的负载也可能提高完成延迟。表中不是四次测量，也没有预测某款 GPU 的队列大小；各工作点假设需要测量校准，不能通过自洽公式证明它们可达。[独立复算](../research/2026-infra-survey/arithmetic.json)保存全部输入。

## 用 Mess 的方法校准

[Mess 作者接受稿](../references/proceedings/MICRO/2024/paper-011.pdf)的物理页 3–6 给出一种实用方法：让一个 CPU core 或 GPU SM 运行 pointer chase，其他执行单元产生可控读写流量，分别记录探针延迟和硬件计数器带宽。改变流量强度与读写组成，就得到一组带宽—延迟曲线。探针是观察争用的手段，它不直接测得每个模型事务的延迟。

实验 1-4 加一个可选变体：先对固定 Qwen3 attention 片段列逻辑载荷，再用同设备、同存储路径的测量曲线解释预测差距。增加独立工作时，观察持续带宽是否仍增长、延迟是否明显升高；据此决定下一步该增加可并行工作、减少访问量，还是减少同接口的争用。没有设备时使用随实验提供的原始记录；当前只规划实验，尚未生成这组硬件数据。

逻辑字节与计数器字节要并列。CPU 写分配可能增加读取，GPU 的事务合并、缓存命中和重读也会改变接口流量，但不能把 CPU 写分配规则直接套到 GPU。Mess 为贴近硬件而处理 TLB／page walk 等开销；分析模型端到端时间时，这些真实发生的工作仍需保留。曲线应来自相同硬件、频率、读写组成及缓存／地址转换条件，不能简单从总带宽中减去一个后台流量数字便预测尾延迟。

图 1-3 沿用现有图号，补一个由实验记录生成的 SVG 面板：横轴实际带宽，纵轴探针延迟，分曲线标读写组成，并标出模型片段的位置。示意、教学计算和测量点明确区分；不描摹论文曲线充当本书实测。
