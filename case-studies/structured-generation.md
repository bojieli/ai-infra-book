# 工具参数生成中的 CPU 工作与状态

核对日期：2026-09-08。用于第 9.1 的请求调度、9.3 的推测验证与第 12.1 的工具执行，沿用实验 9-2，不增加语法或框架专题。[固定来源与读取范围](../references/framework-history/2026-09-08/structured-generation/README.md)保留历史版本、当前接口和实现边界；未运行模型／GPU 测试。

## 从一份工具参数开始

让 Agent 为读取文件生成 `path` 和 `max_bytes`。要求输出符合 JSON schema，意味着每一步都要排除不能继续组成合法结果的 token；BPE token 又可能跨越引号、字段和语法规则的边界。输出格式、字段含义、工具是否适合当前任务分别评价，截断输出也未必形成完整对象。论文中的语法正确率不能代替任务成功率。

[XGrammar（MLSys 2025）](../references/proceedings/MLSys/2025/papers/mlsys2025-5c20ca4b0b20b0bd2f1d839dc605e70f.pdf)的选择很适合本书主线：每一步重新检查整张词表太贵，把只依赖局部语法位置的 token 预先分类，仅对依赖完整栈的少部分 token 做运行时判断。规则内联和上下文扩展继续减少待检查集合；持久化栈共享分支和历史，支持试探与回滚。预处理换来了运行时节省，也占用 CPU 时间与缓存，schema 复用率决定准备成本能否摊薄。

论文物理页 1–11 的动机、方法、评估与结论已读，页 8 图 8 已查看。掩码检查与 GPU 前向依赖同一份已提交 token 历史，可以并行，在采样前汇合。其历史端到端比较使用 vLLM v0.6.3＋Outlines、llama.cpp 与当时的 SGLang／MLC-LLM，不能描述当前引擎差距；Table 4 衡量语法正确，不能称工具任务全部完成。摘要／结论有 context-dependent 与 independent 写反之处，采用 §3 的方法定义。

## 用 Qwen3 算掩码和关键路径

固定 [Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)，TP=1、词表 151,936，先取 64 个都需约束的请求。按每 token 一位、32 位整数打包，一行掩码为 `ceil(151936 / 32) × 4 = 18,992 byte`，一批为 **1.159 MiB**。这是给采样使用的完整掩码，区别于编译阶段保存的自适应稀疏集合；实际词表 padding 和部分请求免约束另记。

假设有效 host→GPU 带宽为 25 GB/s，整批掩码纯载荷传输约 **48.62 μs**。如果 FP32 logits 全量物化，独立掩码 kernel 对 `[64,151936]` 做一次读取和写回，逻辑流量为 **74.188 MiB**；在假设有效 1 TB/s 下约需 **77.79 μs** 的供数时间。缓存、融合与实际采样实现可能改变物理访问，不能把两个数字直接称为测得延迟。

再假设每行 CPU 掩码工作 50 μs，64 行串行合计 **3.2 ms**，同一批 GPU 前向为 **2 ms**。两者串行是 5.2 ms；具备依赖与资源条件时重叠，下界变为 3.2 ms，随后仍要处理掩码交接、应用与采样。传输字节不大，CPU 工作却可能先成为瓶颈。用真实 trace 替换这两项假设，再看预处理、编译缓存、线程数或更高效 matcher 哪一个值得优化。

当前 vLLM 已读路径只在无推测、结构化请求超过 128 时采用分组并行填充；编译线程池和逐步填充线程池是两回事。不能看到有线程池就把 64 行工作自动除以核心数。一次冷 schema 的等待也单独计入首 token，不平均到大量后续请求后宣称首请求无开销。

## 2024 的接口怎样接到当前执行

SGLang v0.4 在 2024 年底集成 XGrammar；vLLM 2025 年 1 月文章中的 V0 路径仍是 logit processor，调度层处理和掩码分发当时还是后续计划。固定当前 vLLM 的 manager 已有异步语法创建、编译错误传递和批量掩码准备；`external_launcher` 因各 TP rank 就绪一致性约束，另走同步编译。后端还提供编译缓存。这里只据已读路径解释准备和执行的分工，未审计完整 scheduler／GPU runner，不能把存在异步接口视为所有开销都已隐藏。

当前 SGLang backend 将 CPU 掩码移向执行设备并应用于 logits，可用时分配 pinned memory；不同设备有不同路径。其 reasoning 文档和 structural tag 示例说明另一项设计选择：自由思考与受约束参数需要明确边界。当前文档的旧模型示例不是全模型支持清单，V4／K3 要按各自 parser、chat template 与后端验证后再加入实验。

Ollama 2024-12 的 `format` JSON schema 入口提供本地实验对照，当前文档仍区分普通 JSON 与 schema，并要求消费端验证；获取日文档明确其 Cloud 尚不支持该特性。跨框架比较应固定本地模型、schema、采样与终止条件，不能只对齐 API 请求外形。

## 推测执行增加了哪一种状态

从第 9.3 的四个草稿 token 接过来：除了模型 KV，grammar matcher 也必须沿假定前缀推进。在声明每请求四个草稿加一个额外采样位置的情况下，64 请求最多准备 320 行掩码，载荷为 **5.796 MiB**；这是所选路径的行数和容量推算，不等于每轮都传输并执行全部位置。

vLLM 已读 manager 为草稿位置逐次填掩码、试探推进，最后回滚临时推进的语法状态；reasoning 在验证窗口内结束时还要从相应位置开始约束。模型验证后实际提交了哪些 token，必须与最终 matcher 状态一致。SGLang 的 matcher 也提供 accept／rollback 接口；这里没有证明所有推测后端都已正确组成这套流程。

实验 9-2 的变体固定同一工具 schema，分别加入未约束请求、冷 schema、长 reasoning 与受支持的推测配置。记录编译等待、mask CPU 时间、传输／应用、采样、有效 JSON、参数含义和任务完成；用实际提交前缀检查回滚。在第 12 章的执行时序里，完整参数可校验、工具实际可启动和首段文字到达是不同时间点。
