# 资源共享中的带宽、容量与等待

2026-09-08 的编辑笔记。OSDI 2025 筛选后，采用 NanoFlow 与 FuseLink 深化已有的计算／通信重叠和路径推算；SGLang、Ollama 的历史与当前实现用于检查设计怎样随硬件和执行引擎改变。未运行 GPU 性能实验，下面的时间和带宽均明确区分教学输入与原文条件。

## 先算切分的代价，再安排重叠

沿 [Qwen3-8B 配置](../references/outline-checks/2026-09-07/scaling-history/qwen3-8b-config.json)，取一层 SwiGLU FFN、256 个 token，隐藏维度 4,096、中间维度 12,288。三次线性变换合计 150,994,944 个参数，BF16 权重为 288 MiB，矩阵工作为约 77.31 GFLOPs。将 batch 拆成两个 128-token 微批，数学工作量不变；若每个微批独立读取全部权重且没有跨微批缓存命中，逻辑权重读取增至 576 MiB。实际 HBM 流量还要核对缓存、tile 和实现。

再给一个有依赖的两阶段教学时序：每份数据先经过访存或通信阶段 N，再经过计算阶段 C。完整 batch 的 N、C 分别假设为 0.4、0.8 ms；切成两份后，每份 N 为 0.2 ms，C 因小矩阵效率下降变成 0.48 ms。这些是假定的计时输入，不是上述 FFN 在某张卡上的测量，也不包含完整模型的其他层。

| 执行方式 | 同一批数据的完成时间 |
| --- | --- |
| 原 batch 顺序执行 N→C | `0.4+0.8 = 1.20 ms` |
| 切两份，仍顺序执行 | `2×(0.2+0.48) = 1.36 ms` |
| 让第一份 C 与第二份 N 重叠，假定互不干扰 | `0.2+max(0.48,0.2)+0.48 = 1.16 ms` |
| 假设并发 profiling 得到重叠区间为 0.60 ms | `0.2+0.60+0.48 = 1.28 ms` |

最后一行的 0.60 ms 是为反例设定的联合执行时间；两段共享 SM、缓存或带宽的细节要由真实 trace 补充。这个例子说明，即使理想时间线有收益，也可能被切分与争用抵消。整个 batch 还要计入流水填充、排空、提交和缓冲，不能拿两个完整算子的独占时间做一次 `max` 就宣布实现了该速度。

NanoFlow 先用独占 kernel 的结果找候选流水，再用成对并发 profiling 修正资源分配。其归一化资源量 R 是以 GEMM 性能损失定义的代理，并不是可以独立分配的“百分之几物理 HBM／网络”。论文还近似用成对干扰推断三类 kernel 同时执行，换硬件、形状或实现后要重新验证。把这一点接到第 5.3.5：Agent 对一个 kernel 的优化成功后，仍需在实际并发片段中复测；优化工具的 GPU 时间也计入搜索预算。

第 9.1.4 用该机制接续 Sarathi 的分块。NanoFlow 的整体 compute-bound 分析假定请求充足、batch 接近容量上限，并主要考虑当时的 dense／GQA 模型；它不支持把 batch=1、长 reasoning、V4／K3 的不同状态和专家访问都归入同一种瓶颈。其吞吐统计包含输入与输出 token；在线评估的平均“请求时间／输出长度”也不等于独立的 TTFT 与 P99 ITL。沿本书工作负载重新计量后才比较。

## 硬件改变后重新选择重叠方式

SGLang 的三次 2025 年公告给出一条具体变化：H100 多机部署采用两微批重叠；GB200 NVL72 初期因互联条件改变，可以停用这一安排；后续又把 combine 与 down GEMM／共享专家作更细粒度交错。由此回到第 6 章：超节点改变了通信与计算的比例，第 10.4 的最佳执行时序也会改变。

这些公告中的实验同时改变硬件、batch、精度或内核，不能把代际总加速归因于某一个开关。5 月的 MTP 对照部分为模拟，6 月沿用历史基线，9 月还区分 BF16／FP8 attention 与 FP8／NVFP4 专家；本书只用它们解释选择，不复用宣传倍数。

[当前固定源码](../references/framework-history/2026-09-08/overlap-placement/README.md)进一步表明：SGLang 对 Qwen3 MoE 的 prefill 与 decode／验证使用不同操作顺序和 yield 位置；SBO 按硬件和后端选择可交错的部分，并给通信与计算传入相应 SM 预算。预算不是保证独占某组 SM 的隔离机制，配置常数也不是所有机器的推荐值。

实验 10-6 保持同一模型、路由轨迹和精度，分别记录独占、仅切分、实际重叠三种时间线。每次只改变一个策略，记录后端、每专家 token 数、图模式、缓冲和暴露等待；不把“开关被接受”当作该路径已执行的证据。V4／K3 的可变状态、压缩边界和图条件按受支持路径检查。

## 多张网卡为什么还受一条链路限制

第 7 章从超节点内部走到数据中心网络，既要看交换机，也要看 GPU 到 NIC 的路径。沿第 10 章会使用的 Qwen3-8B 8K BF16 KV，载荷为 1.125 GiB；这里先假设没有共享前缀、每份完整交接。

给两端各三张 NIC，每张**有效单向载荷带宽**为教学值 40 GB/s。若三张卡都访问同一 GPU 的 PCIe 接口，而该共享接口仅能提供 45 GB/s，总吞吐上界是 `min(3×40,45)=45 GB/s`，不能相加成 120 GB/s。

借用邻近 GPU 中继时，假设本 GPU 的直接 NIC 仍有 40 GB/s，两张间接 NIC 合计可用 80 GB/s，但到中继 GPU 的共享互联只剩 60 GB/s，则本端上界为：

`40 + min(80,60) = 100 GB/s`。

还要与接收端同类路径、交换网络和 HBM 访问约束取最小值。仅在两端同样、交换网络与内存足够，并且中继 NIC 此时空闲的条件下，得到下列载荷下界：

| 路径假设 | 带宽上界 | 1.125 GiB 载荷的时间下界 |
| --- | --- | --- |
| 只用直接 NIC | 40 GB/s | 约 30.20 ms |
| 三张 NIC 仍共用本 GPU 的 PCIe | 45 GB/s | 约 26.84 ms |
| 间接 NIC 经 GPU 互联中继 | 100 GB/s | 约 12.08 ms |
| 上述中继路径的交换网络只剩 70 GB/s | 70 GB/s | 约 17.26 ms |

FuseLink 将这类思路实现为 NCCL 网络插件：感知两端 NIC 的负载，通过重映射网络缓冲利用机内 GPU 互联。它将缓冲填写与中继结合，减少额外复制／同步，但没有消除必要字节；接收端缓冲位置、GPU 间访问和控制路径仍要计量。

借用资源还要允许原使用者恢复工作。原论文给直接使用者较高优先级、限制未完成操作和中继内存，并明确采用延迟监测与有界争用的取舍。重映射、排空和频繁切换都有成本，不能将“NIC 一度空闲”视为整个请求期间都可用，也不能把内存上限写成绝无 OOM 的保证。均衡的 ring all-reduce 若已占满各 NIC，就没有同样的空闲资源可借；本书优先用倾斜专家交换和不均匀 KV 交接说明用途。

实验 7-3 增加同一消息的直接路径、共享 PCIe 和中继候选；图 7-3 在既有拓扑中标出路径共享处，不增加网络协议章节。若当前部署的 NCCL／后端没有已核实的 FuseLink 集成，就使用论文或配套通信记录对照，不能把研究插件写成 vLLM／SGLang 默认功能。

## Ollama 的容量规划与实际分配

Ollama 的版本对照提醒读者，框架名字本身不能确定加载路径。2024 年所读调度器用容量预测选择单 GPU 或同类多 GPU；2025 年新引擎按 fit、allocate、commit 逐步取得实际内存需求并调整层放置，旧兼容路径同时存在。分配仍可能遇到可用内存变化，源码保留退让和失败处理。

2026 年 9 月获取的固定主线中，普通 GGML／GGUF 模型转交 upstream llama-server；调度器仍会在启动前预测容量并选择放置，MLX 另走独立客户端。这里是提交快照，不能推断所有已发布版本或用户安装都已如此，也不能由此宣称 2025 的内部加载协议被所有后端继续使用。

让实验 9-7 增加小模型容量对照：Qwen3-8B 若为独立请求各预算 8K 的 BF16 KV，1 个并发槽为 1.125 GiB，4 个槽为 4.5 GiB。权重没有变，逻辑 KV 预算已经多了 3.375 GiB，随后还需加图缓冲、工作区和系统预留。实际后端可能按页分配、共享前缀、量化 KV 或采用不同上下文参数语义，所以要保存解析后的配置和实际分配，不能拿文件大小或某个 RSS 数字替代完整容量。

本书据此保留“先估算、再由实际执行校准”的方法，不把官方公告的内存精确性描述扩成永不 OOM 的承诺。也不为了讲 API 沿革增加产品使用教程。
