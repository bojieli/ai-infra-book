# 快照恢复、首次访问与环境容量

> 2026-09-09，供当前 11.2.4／11.2.5、实验 11-2 与图 11-3 扩写。沿代码 Agent 的环境复用，比较恢复等待、实际驻留和共享读取；以下数字均为独立教学输入，不是 E2B 或 CXLfork 的实测。未运行云环境、作者程序或 GPU 实验。

## 从模板恢复以后，数据还在哪里

代码 Agent 需要的 Python 环境已经装好，并不表示第一次导入库、读取测试数据和执行测试都没有等待。先区分三个时刻：环境创建请求开始、环境接口可调用、首个工具完成。预制模板减少重复初始化，按需恢复则把部分工作留到实际访问时；这两项收益不能重复计算。

E2B 在固定提交 `a586d1e859ecfcaf68df393e9e81a890a5c9d4a1` 的架构说明中，以恢复 Firecracker 快照创建普通模板沙箱，内存按需获取、根文件系统采用写时复制。创建响应等待环境内的 `/init` 完成，因而不是仅仅把创建请求放进队列；但后续工具首次触及的页仍可能需要获取。模板优化阶段收集恢复时的访问页，生成预取提示。[固定说明与选读范围](../references/framework-history/2026-09-09/snapshot-residency/README.md)

继续读调用链：`Uffd.handle` 把模板 memfile 交给缺页处理器；有来源数据的 `faultPage` 分支调用 `ReadAt`，再经 `Fd.copy` 发出 `UFFDIO_COPY`，将数据安装到虚拟机内存。模板在本机缓存中命中，可以省远端读取，仍不能据此把所有沙箱的已安装内存计成一份。这里核的是这条缺页路径；预取、内核页缓存、空页和内存回收另有条件，不把每个逻辑访问都算作一次远端读取。

[CXLfork 的作者论文](../references/proceedings/ASPLOS/2025/public/paper-022.pdf)选择了另一种放置：先把进程数据和可分离的 OS 状态检查点复制到共享 CXL 内存，再让新进程直接映射只读页，写入时复制到本地。于是读取可以经 CPU 缓存访问共享页，免去这部分读缺页复制；缓存未命中后的 CXL 访问仍有延迟和带宽成本。论文还比较将热点只读页复制到本地的分层策略，说明少一份副本和更快的重复执行可能对应不同方案。

两者有相似的复用问题，却不是同一种运行环境。CXLfork 修改 Linux 6.6，以进程／Docker 和 OpenWhisk 工作负载评估；要求相同 OS 镜像及一致的文件系统路径，并不支持任意共享匿名映射。其一台双路主机上的两个 VM 和 FPGA CXL 装置用于原型评估，不是大规模跨主机 microVM 部署。不能据此说 E2B 已采用 CXLfork，也不能把 CPU 检查点推广成 CUDA 状态恢复。[正文范围与限制](../references/proceedings/ASPLOS/2025/cxlfork-reading.json)

## 同一个模板，三种内存预算

假设模板检查点为 2 GiB，100 个环境从它派生。每环境实际触及 512 MiB，其中 128 MiB 会写入，其余 384 MiB 只读；为每环境另预留 4 MiB 私有管理开销。这只是比较放置的简化输入，不代表真实 microVM 的管理成本。忽略其他进程、页表扩张、预取多读和回收；检查点来源在三种方案中都另占 2 GiB。

| 放置假设 | 每环境本地数据与管理开销 | 100 个环境本地占用 | 另计共享检查点 |
| --- | ---: | ---: | ---: |
| 完整复制 2 GiB 模板 | 2,052 MiB | 200.390625 GiB | 2 GiB |
| 只复制实际触及的 512 MiB | 516 MiB | 50.390625 GiB | 2 GiB |
| 直接映射只读页，只复制写入的 128 MiB | 132 MiB | 12.890625 GiB | 2 GiB |

第二行用于理解按需安装的容量，第三行用于理解共享只读页的容量；它们不是两个产品的等价配置或内存实测。若第三行再将 256 MiB 热点只读数据搬到本地，每环境变为 388 MiB，100 个环境为 37.890625 GiB。假设可用于这些环境的本地预算为 64 GiB，四种放置的容量上界分别为 31、127、496、168 个环境。CPU 配额、隔离开销和 P99 要求会进一步收紧上界。

这也补充了 11.1 的 `环境数 × 每环境内存`：其中的每环境内存应取所比较方案的实际私有驻留，共享池和模板缓存另计。不能直接用配置内存、文件大小或各进程 RSS 的简单相加替代物理占用。

## 共享容量之后，还要算共享读取

假定只读共享方案中，每项工具任务在 CPU 缓存之后仍有 64 MiB 流量到 CXL 池。每秒 200 项任务就是 12.5 GiB/s；共享路径有效单向能力若为 32 GiB/s，单从字节预算看，上界为 512 项每秒。它不是达到 P99 的保证：请求并发、访问延迟和突发仍需测量。如果每项任务另消耗 0.05 核秒、平台可用 32 核，则 CPU 上界为 640 项每秒；有空闲核也不表示共享读取还有余量。

热点本地化可能减少远端访问，却增加每环境驻留；必须用同一任务的物理读取和复用次数重算。CXLfork 的作者也把多节点共享带宽列为尚待研究的问题，现有分层策略主要考虑访问延迟。因此，上述带宽计算是本书用于检查规模变化的补充，不是论文已经验证的扩展结果。

## 首次访问的粒度也会改变结果

再给实验 11-2 一个可独立计算的变体：工具只需 64 个互不相同的 4 KiB 小页，且它们分布在 64 个不同的 2 MiB 区块内。按小页恰好取数是 256 KiB；若机制必须取完整大页，就是 128 MiB。以 1 GiB/s 的有效取数能力估算，仅数据服务时间下界就从约 0.244 ms 变成 125 ms。相反，对连续的 64 MiB 内容，字节相同，大页却可减少逐页处理次数。

这是访问粒度的条件推算，不能直接当成 E2B 当前每次网络请求大小：缺页页长、缓存块、对象存储请求和预取窗口不是同一个量。实际实验应记录首次工具前后触及／安装的页、来源层级、传输字节和完成时间，再判断该预取哪些页。不要只凭创建 API 很快就宣布冷启动问题已经解决。

实验仍使用 E2B 的真实创建／恢复接口或配套记录。先保持模板、工具输入和节点缓存条件一致，再改变并发、读写比例与访问分布；CXLfork 作为设计对照，基础练习不要求搭建 CXL 原型。图 11-3 在现有生命周期旁加三条资源线：共享模板、本地私有页、按需读取；SVG 自绘，论文图仅作核读材料。

暂停和分支还要回到状态语义：文件、内存、连接与外部操作分开核对，保存环境不能撤销已提交的外部任务。E2B 文档中异步上传、原节点缓存和受开关控制的恢复方式也不等于任意节点已经获得同一可恢复状态；本轮未审计完整快照持久化路径。
