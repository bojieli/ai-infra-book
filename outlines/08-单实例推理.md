# 第 8 章 单实例推理

> 写作大纲 · 数据搬移主线与章节依赖修订 · 草案 22 · 2026-09-08

已有设备与并行方案之后，本章在一套引擎内安排请求。用权重复用推导批处理，用状态寿命推导 KV 管理，再计算草稿验证是否值得增加工作；同一组 Chat／Agent 请求始终保留质量与延迟目标。

**本章判断：** 复用改变每个有效输出承担的搬移，但会占用容量、等待或额外计算；策略优劣要随到达率、历史长度和真实产出重算。

**前置与交付：** 依赖第 3、5、6、7 章；交付单实例的服务基线，第 9 章再改变阶段放置。视觉输入使用第 3 章定义，不依赖后面的端边云章节。

**阅读安排：** 核心练习为实验 8-2、实验 8-4、实验 8-9；其余练习为延伸。每节的完整参数、实现版本与实验变体见对应[扩写资料](extensions/08-%E5%8D%95%E5%AE%9E%E4%BE%8B%E6%8E%A8%E7%90%86.md)。章末更新[跨章设计决定](decision-record.md)。

## 8.1 批处理：用状态与等待换复用

章首即固定质量与 SLO。先从权重复用推导，再加入连续批处理、长 prefill 干扰和真实执行预算。

### 8.1.1 请求执行时间与状态占用

固定 Qwen3-8B 的层数与矩阵，先给 2,048 输入／256 输出 token 的交互请求，再给 8,192 输入、6,144 可复用前缀的 Agent 请求。分别计算权重、KV、prefill 与每个 decode 步的工作，沿加载到释放画出一次服务；这些是教学输入，随后用第 3 章的长度分布替换。

### 8.1.2 batch 与权重复用

从权重复用和矩阵形状解释 batching，计算它节省的读取；随后加入等待凑批、请求长度差异和显存容量，看到吞吐与延迟的取舍。

沿用第 3 章的 `I_weight ≈ 2q/b_w`，与设备的 `F/B_mem` 比较，先求权重主导近似下的批量转折点；然后算 KV 能否装下，以及用户是否愿意等待这么久。这样得到的 q 是候选范围，不是服务引擎的固定推荐参数。

沿同一 Qwen3-8B 的 BF16 账，2K／8K 历史下，旧 KV 读取达到批内共享权重读取的 batch 分别为 51／13。这个转折说明历史越长，继续合批越难只靠摊薄权重读取获益；它不是计算主导的交叉点。再用 4090／H100 的容量排除装不下的候选，[完整扫描](../calculations/results/batch-reuse-h100-2k.md)保留访问假设与工作区限制。

> **实验 8-1 ★〔延伸〕：batch 与权重复用**
>
> 为什么一批请求比逐个执行更划算？ 对 Qwen3-8B 扫描活跃 batch＝1、4、16、64，先按实际精度预测权重／KV 读取、矩阵工作和逐卡容量，再比较 4090／H100 的可行范围。只对能装下的候选测吞吐与延迟；换成长 Agent 前缀后重算。
>
> 条件：基础·单设备／配套记录。

实测：RTX PRO 6000／Qwen3-8B中，2K输入的batch从1增至64，吞吐约37→1,165 token/s，首输出等待约96→3,286 ms。8K输入已命中6K前缀时，batch64约842 token/s。各条件三轮、固定256输出token；实际满批解码已核实，吞吐提升伴随单请求等待增加。[数据、图与条件](../experiments/ch08/08-01/README.md)。

### 8.1.3 从固定批次到连续批处理

让短请求退出、长请求继续，并把新请求放入腾出的槽位，推导迭代级连续批处理。用固定 vLLM 或 SGLang 的一次调度记录对齐请求进度、KV 分配与 GPU 执行；模型管理和实际执行后端分开。

本节只解决“下一步让谁执行”。语法掩码、数值可重复性、视觉输入及图形状作为需要满足的额外条件，在相应实验变体和延伸材料中检查。CPU 准备可与 GPU 计算重叠的前提是依赖已就绪；准备本身和多做的 token 仍需计量。

先用[四请求教学时序](../calculations/results/iteration-batching-continuous.md)比较固定批次、连续补位与 decode 优先分块：保持计算位置与输出相同，连续补位让长 prefill 更早进入，却可能拉长已有请求的 token 间隔。再用实验 8-2 的六请求实测检验这一取舍；教学时间不用于预测真实 GPU 吞吐。

### 8.1.4 Prefill 干扰与分块执行

用长 prefill 插入 decode 的时间线引出 Sarathi-Serve 的分块安排。把 Qwen3-8B 的 8K 输入切成 512-token 块，首块与末块分别有 131,328 和 4,063,488 个有效注意力配对：新 token 数相同，历史工作不同。沿[推算笔记](../case-studies/chunking-and-state-transfer.md)比较等待、矩阵效率、提交频次与历史读取；配对数不直接等于耗时或 HBM 访问倍数，固定 token 预算需要按实际执行时间校准。

用 NanoFlow（OSDI 2025）的算子级 nano-batch 流水说明如何重叠不同请求的计算、访存与通信。Qwen3-8B 一层 BF16 FFN 权重为 288 MiB，256-token batch 切成两个 128-token 微批后，若没有跨微批缓存命中，逻辑权重读取增至 576 MiB，数学工作不变。沿[时序算例](../case-studies/resource-sharing-and-placement.md)比较仅切分、理想重叠与实际争用；论文的高吞吐分析不能直接外推到 batch=1 或长 reasoning。第 9 章再改变阶段放置，同一请求未就绪的 KV 依赖始终保留。

将上述首末块的工作量与实验 8-2 的[固定块长记录](../calculations/results/chunk-history-book.md)对照：相同的 512 个新 token，历史位置不同，执行时间也不同。正文保留这一判断和代表时间线，完整逐块矩阵计数与统计口径放入扩写资料；不能把有效注意力配对数之比当作时间之比。

### 8.1.5 动态批次与图重放

沿第 5.4 节的图重放与 padding 预算，回到实验 8-2 的同一批请求：减少提交以后，等待究竟来自 CPU 准备、长 prefill，还是 KV 容量不足？先在固定 vLLM 路径中比较图开启前后的时间线，再根据请求形状检查图命中、回退和缓冲占用。

本节新增的选择是捕获哪些形状、为图保留多少容量。图池挤占 KV 后，可能减少可接纳请求；过大的桶也可能增加实际执行。用[已有算例](../case-studies/graph-execution-tradeoffs.md)解释这两个方向，SGLang／TensorRT-LLM 的不同路径留作延伸对照。第 5 章已完成的捕获原理和单层算术不在这里重新推导。

> **实验 8-2 ★〔核心〕：请求调度与等待分布**
>
> 用同一 Qwen3-8B 的六个 Chat／Agent 请求，手排固定批次、连续批处理与分块 prefill，再在固定 vLLM 版本回放同一到达时间。先比较相同块长、不同历史位置的工作与执行时间，再分别改变 token 预算、分块和 CUDA Graph，记录等待、ITL、KV 峰值、主机提交与图缓冲；以 SGLang 作同模型可选对照，每次只改变一项执行策略。NanoFlow 的仅切分与重叠按配套时序复算，SGLang 的 MoE TBO 实测另放在实验 9-6。
>
> 条件：基础·时序推算＋vLLM／配套运行记录。

实测：RTX PRO 6000／vLLM 0.23.0 回放六个合成请求，预算从512增至8192后，一个后到请求的排队从约149 ms降至接近零，但最长token间隔从约32 ms增至183 ms。单独开启decode图未消除小预算的等待。四组各三轮，输出token一致；共享GPU下的局部观察不代表通用最优配置。[原始记录、图与待测项](../experiments/ch08/08-02/README.md)。 [同块长补测](../experiments/ch08/08-02/chunk-history/README.md)中，11次8K请求的首／末512-token块执行区间中位数为25.30／35.07 ms；相同新token预算不等于相同执行时间。

## 8.2 KV：保存、共享与重算

围绕状态生命周期组织分页、分支和前缀复用；每项选择都同时占用容量并影响后续搬移。

### 8.2.1 预留空间、碎片与分页

从请求长度不可预知引入预留与碎片，再讲 PagedAttention 怎样把逻辑序列映射到物理块。用释放出的容量重新计算可接纳请求数，接回上一节的权重复用；页管理与调度也有开销，省显存要落实到服务结果。依据：[成本下降调研](../research/token-cost-2023-2026/report.md#runtime)。

### 8.2.2 共享、分支与状态回收

沿分支生成、前缀共享和用户取消讲引用计数与写时复制的用途。说明一次省下的分配如何增加可接纳请求。

用 Punica／S-LoRA（MLSys 2024）引出另一种共享：同一基座的多个 LoRA adapter 共用 `XW`，低秩修正按 adapter 分组。再看当前 vLLM／SGLang 怎样处理加载、异构批次与热 adapter 槽位；共享基座不代表不同 adapter 可以直接共享 KV。

固定 Qwen3-8B，仅在 Q、V 投影使用 rank 16、BF16 LoRA，每套 adapter 为 14.625 MiB，100 套约 1.428 GiB；100 个各含 8K 独立历史的请求却需要 112.5 GiB BF16 KV。由此区分可提供的 adapter 数与可并发的请求数，再算加载等待、小矩阵执行和租户公平性。推导与历史基线条件见[多 LoRA 服务笔记](../case-studies/multi-lora-serving.md)。

### 8.2.3 换出、保留与重计算

比较 CPU／SSD 分层、淘汰、预取和重计算。用下一次使用时间与传输成本决定选择，而不预设“缓存越多越好”。

> **实验 8-3 ★〔延伸〕：KV 分页与状态分配**
>
> 分页能多接纳多少请求？ 用 Qwen3-8B 每 token 的 144 KiB BF16 KV 作输入，实现小型状态分配器，比较长度、分支和取消下的预留、分页与共享；换 Qwen3-235B 的 188 KiB 后重算可接纳请求数。
>
> 条件：基础·Python＋vLLM 状态记录。

实测：Qwen3-8B的四条并发请求在1 GiB KV空间下发生一次抢占，比2 GiB多调度1,805个token位置，最终输出一致。主动取消一条请求实际归还104个块，其余请求无抢占完成；取消调用返回早于调度器释放。三组最终都归还全部请求块。[原始块记录、图与范围](../experiments/ch08/08-03/README.md)。

### 8.2.4 Chat 与 Agent 的前缀复用

本节应用侧取材以作者 AI Agent 书第 2 章“上下文工程”为主，沿稳定提示与工具定义、前部时间戳、工具排序、状态替换和持久追加，定位首个变化 token 及其后需要重建的状态。比较替换旧状态的后缀重算与持续追加的 KV 驻留、陈旧信息和后续读取；对应实验 2-3 的来源与阅读边界见[作者材料](../case-studies/author-context-and-design.md)。

用 vLLM APC 与 SGLang RadixCache 的同一组共享前缀请求比较重算量。接着用 2026 年 Unified Radix Cache 回到 V4／K3：全注意力、滑窗和 KDA 循环状态有不同的有效复用边界，同样匹配了 N 个 token 不代表所有状态都能在 N 处直接复用。对齐窗口与检查点以后，才核算命中节省的工作。

复用第 2、3 章的请求分布：Chat 的多轮历史、Agent 的系统提示和工具定义、工具返回后增长的上下文，各有不同的公共前缀与复用间隔。前缀匹配依赖 token 序列、模型与缓存格式；工具等待会延长 KV 驻留，reasoning 与分支会增加状态占用。

### 8.2.5 命中收益与缓存淘汰

继续借 AI Agent 书的上下文压缩策略与原书第 2 章第 10 项实验，区分稳定前缀、被替换历史和需要重建的后缀；同时计摘要调用、重建 prefill、未来 decode 读取与质量变化。Programmable KV 论文作为扩写短例，分开事实更新、追加更正与缓存组合，明确上下文依赖和质量验证，不能把普通 KV 当作任意可拼接状态。[取材与论文入口](../case-studies/author-context-and-design.md)。

同时计算按请求与按 token 加权的命中率、节省的 prefill 工作、缓存驻留量与命中后的取回时间。区分本地 HBM、主存和远程池：高命中率仍可能伴随慢取回或 decode 拥塞。用复用间隔分布决定保留多久，再把共享缓存与跨实例路由交给第 9 章。

用 Marconi（MLSys 2025）的混合模型案例解释检查点准入：循环状态不能从任意后续位置直接退回，逐块保存又可能挤掉更值得复用的前缀。先判断可恢复边界，再比较每单位状态省下的工作与再次访问机会；统一前缀身份、保留什么状态、淘汰什么状态是不同决定。其历史改造版 vLLM／SGLang 与当前 Unified Radix Cache 分开说明。

> **实验 8-4 ★〔核心〕：前缀缓存的复用价值**
>
> 哪些前缀值得保留？ 使用同一代码 Agent 的多轮记录，计算前缀省下的 prefill、占用的 KV 和恢复时间；改变复用间隔与本地可用容量，解释缓存命中如何改变排队。
>
> 条件：基础·轨迹分析。

实测：固定12轮真实Agent输入，在vLLM 0.23.0中每轮只生成一个token。相同干扰请求下，6 GiB缓存累计命中16,304个输入token，1 GiB降为0；单纯增加0.2秒间隔未改变命中。五组输出一致。此为共享GPU上的串行单次回放，尚未测混合排队或实际块驻留寿命。[原始记录、对照图与范围](../experiments/ch08/08-04/README.md)。 [缓存身份补测](../experiments/ch08/08-04/cache-salt/README.md)的50请求中，不同非空salt首次命中为零，同salt复用命中3120/3136个token；空字符串与未设置salt共享缓存。

## 8.3 推测执行：增加工作换更多产出

按每轮净产出比较串行、并行和动态草稿。算法名称用于定位实现，正文依次改变成本项。

### 8.3.1 草稿、验证与单轮产出

先用 Qwen3-8B 画一次草稿—目标验证—提交／回退，只保留理解原理所需的早期算法。将每轮耗时除以实际产出 token 数，与普通 decode 比较；区分接受概率、接受长度及补偿 token。严格验证保持所选目标的采样分布，量化目标与原精度模型的差异另行评估。

用 vLLM 的实际计数说明：日志中的平均接受长度可包含额外产出的一个 token，草稿接受率则只数草稿。先用逐轮数据对齐分子分母，再比较平均产出／平均时间；EOS 与输出上限处按真正交付的 token 计量。2024 年的低 QPS 收益与高 QPS 退化作为引子，后面解释框架怎样按负载调整预算。

以代码编辑的重复片段引出历史草稿：vLLM 的 prompt lookup／Suffix 与 SGLang NGRAM 省去草稿模型，却增加查询、索引和验证。给同一目标分布两种历史草稿，算出一快一慢，分别记录历史匹配、在线接受与每轮产出；[推算与版本](../case-studies/history-drafts-and-rollout.md)再把准备时间和主机容量计入收益。

### 8.3.2 复用目标特征与草稿成本

比较独立草稿与复用目标特征的草稿，分别计算起草前向、特征读取和传输、草稿状态及目标验证。EAGLE 系列作为具体路线，Qwen3 采用与目标匹配的固定检查点。草稿更准确可能增加起草成本，接受率和每轮产出分别记录。

先固定目标、采样与并发，比较减少起草工作和增加接受长度两种改动。公开 EAGLE 3.1 部署与其他模型的结果只作各自条件下的证据；版本演进与训练入口留在延伸材料。

### 8.3.3 并行起草与验证块长

用 DFlash 对照逐步起草与并行整块起草：减少串行前向以后，输入行、验证工作、KV、专家集合和图档位仍会变化。先以每轮总时间除以真实产出比较，再扫描块长和上下文，找到收益转折。

把主机准备与 GPU 路径画回同一时序，区分算法并行性、接受长度与运行时重叠的贡献。DFlash 2、P-EAGLE 和各引擎的具体支持范围作为延伸对照，不将不同部署的加速比合并。

> **实验 8-5 ★〔延伸〕：推测解码的每轮收支**
>
> 以 Qwen3-8B 与固定 DFlash 检查点建立可复算基线，记录草稿、验证、回退与产出长度。扫描块长、输入长度和并发；将 EAGLE 3.1／DFlash 2 的公开记录按各自模型和机器单独复算，解释哪个因素改变了收益。
>
> 历史草稿变体先用可穷举目标检查分布和平均产出，再按固定引擎的支持条件比较查询、验证与索引准备；改变并发后复核完整服务收益。
>
> 条件：基础·时序计算／单设备或公开记录。

## 8.4 压缩与卸载的执行代价

从真实文件和状态格式算容量，沿反量化、读取与交接求时间，再检查质量和自然生成长度。

### 8.4.1 权重位宽与真实驻留容量

用 Qwen3-235B-A22B 的固定 GGUF 分片与 M2 Max 96 GB，先逐项算权重、量化元数据、KV、工作区与系统预留，再改变上下文和并发。文件名的 2 bit 不等于全模型平均位宽，统一内存也不能把 CPU 与 GPU 容量相加。

沿第 5.5.1 确认的实际 runner，对照容量预测、实际分配与 CPU／GPU 放置，分开计量 mmap 映射、实际驻留和重打包副本。内存报告中的 100% GPU 不等于利用率；版本演进与支持条件见[本节扩写](extensions/08-单实例推理.md#detail-8.4.1)，供实验复核。

### 8.4.2 完整模型与任务质量

以 Unsloth 的 DeepSeek-R1 动态低比特量化说明不同矩阵采用不同精度的理由。保留全部专家、保持原始权重精度与达到相近质量分别检查；比较代码测试、长推理和长上下文结果。蒸馏、裁剪和量化按实际改动解释，不由“满血”一词代替。

### 8.4.3 主存、磁盘与每步读取

当权重不能全部驻留，沿实际引擎路径计算 CPU 执行、GPU 卸载、mmap／SSD 未命中、反量化和同步。把冷加载、首 token 与持续 decode 分开；MoE 根据批内被访问专家计字节。第 9 章继续展开大型主存与少量 GPU 的协同服务。

以 vLLM 的 2024 按需搬入、2025 V1 主存映射与 2026 显式预取说明差别：GPU 读取主存权重时仍受互联约束，预取则要增加缓冲并保持图中的读写依赖。沿[Qwen3-8B 算例](../case-studies/weight-offload-execution.md)，九层 BF16 FFN 卸载 2.53125 GiB，扣一组缓冲后净省 2.25 GiB，恰好相当于两条独立 8K KV。继续按每步搬移量和有效单向带宽判断是否值得，再比较 prefill 与 decode 的摊销。

以 LLM.265 的视频引擎压缩张量为反例，检查容量收益是否被解压吞吐抵消：Qwen3 单支 FFN 的 96 MiB 权重，若预压成四分之一、解压输出假定为 1 GB/s，在 25 GB/s 链路上，整块搬完再解压约需 102 ms，直接搬入约 4 ms。改变链路速度和分块方式后重算；历史论文的质量与专用硬件估计保留各自条件。

### 8.4.4 KV 压缩与模型状态

用 Qwen3-8B／235B 的 GQA 与 V4-Flash 的混合状态重算长上下文成本，比较 KV 精度、稀疏访问和淘汰。权重压缩后 KV 可能先成为限制；状态结构变化还会影响分页、前缀缓存和图执行。

最后回到同一业务任务：固定 token 数比较执行成本，自然生成比较质量、返回长度、终止与重试。若 TTFT 已含首输出，总时间按 TTFT 加余下 G−1 次 decode 计算；每秒生成更多 token，也可能因回答变长或失败重做而更晚完成。由此区分容量收益、内核收益与任务收益。

从 Qwen3-8B 单请求、8,192 个缓存位置算起：BF16 KV 为 1,152 MiB；若采用每 32 个值带一个 FP16 scale 的 q8_0／q4_0 格式，分别是 612／324 MiB，不能只按位宽除二、除四。以 Oaken 的异常值编码作进一步推算，再把工作区、分页与对齐加回容量预算。沿 vLLM 的 FP8、SGLang 的分阶段量化路径和 Ollama 的本地缓存，区分存储格式与 Attention 执行精度；用上下文长度扫描，判断融合转换和原生低精度计算何时能抵消固定开销。

## 8.5 从单实例到有效服务

用同一到达分布校准排队、取消和有效吞吐；结果成为下一章共置服务的比较基线。

### 8.5.1 延迟约束下的有效吞吐

对同一到达轨迹只统计满足质量和 SLO 的输出，将迟到、取消与失败的资源一并计入。最大吞吐提供执行能力，完整服务选择以有效产出为准。 依据：[成本下降调研](../research/token-cost-2023-2026/report.md#measurement)。

扫描到达率，看排队和取消怎样出现；介绍满足服务目标的吞吐与准入。优化目标要与用户实际收到的结果相连。

### 8.5.2 不同请求下的设备取舍

回到 Qwen3-8B 的 Chat／Agent 请求，比较 M2 Max、4090、H100 与 H20 的容量、权重复用、有效带宽和阶段时间。H20 是否适合由对应形状的能力决定；A100／A800 同形态的主要互联差异用于检验单卡和多卡实例为何受影响不同。所有阶段换成同一请求分布，再计算满足期限的有效吞吐。

> **实验 8-9 ★★〔核心〕：服务条件与设备选择**
>
> 哪块设备更适合这项服务？ 用上述相同模型和请求扫描到达率，比较低延迟 batch＝1、连续批处理和离线批量生成的有效吞吐、整机费用与能耗。先判断哪个资源饱和，再解释本地与数据中心设备各在什么条件下合算；不能仅凭 GPU 利用率或单用户 token/s 排名。
>
> 条件：进阶·单设备／公开记录。

[同模型服务实测](../experiments/ch08/08-09/README.md)的336次生成逐题输出一致，294次答对，但仅155次同时满足3秒期限。连续批处理提高高到达率下的合格吞吐，离线突发不保证按期交付；GPU与CPU package能量已测，整机功耗、费用及跨设备优劣仍未知。

## 本章的设计决定

在固定模型、并行与到达轨迹下，选择 batch、缓存和草稿预算，输出质量／SLO 内的服务率、状态峰值与取消浪费。改变历史长度或并发，使至少一项选择翻转；这些结果成为第 9 章共置部署的基线。 将预测、证据和修改分别填入[跨章设计决定](decision-record.md)。
