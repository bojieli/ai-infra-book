# 第 8 章 单实例推理

> 写作大纲 · 执行基线、状态生命周期与服务验证六节重组 · 2026-09-10

固定设备与并行配置，从一次请求建立执行和容量基线，再依次组织批处理、管理 KV、调整压缩与卸载、引入草稿验证。最后回到同一组 Chat／Agent 到达轨迹，检查这些选择怎样影响质量、等待和有效产出。

**本章判断：** 批处理、状态复用、压缩与推测解码会改变每个有效输出的读取和计算，也会引入容量占用、等待或额外工作；选择必须回到相同质量与 SLO 下验证。

**前置与交付：** 依赖第 3、5、6、7 章。单实例可以由多张设备共同执行；本章固定实例的并行与放置配置，研究内部请求和状态的组织，交付第 9 章所需的共置服务基线。

**阅读安排：** 8.1 建立基线，8.2–8.5 逐项改变执行策略，8.6 综合验证。核心练习为实验 8-2、8-4、8-9，其余为延伸。实验与配图按新阅读顺序编号，原始实验目录保持稳定，旧新对应见[重组记录](../research/ch08-reorganization-2026-09-10/README.md)。章末更新[跨章设计决定](decision-record.md)。

## 8.1 单实例的执行与服务基线

接住前文的模型、负载与设备配置，用一张请求时间线和一份容量预算明确本章比较的起点。

### 8.1.1 实例边界与请求生命周期

固定 Qwen3-8B，沿到达、排队、prefill、逐步 decode、完成或取消、状态释放画出一次服务。单实例的 worker 可以分布在多张卡上，实例内的并行配置沿用第 6、7 章；第 9 章再讨论阶段分离与跨实例协作。沿固定 vLLM 路径辨认调度器、状态管理和模型执行各自的责任。

### 8.1.2 权重、KV 与运行时缓冲的容量预算

沿用 2,048 输入／256 输出的 Chat 请求，以及 8,192 输入、6,144 可复用前缀的 Agent 请求。引用第 2、3 章的模型核算，列出权重、活跃 KV、缓存前缀、工作区与图缓冲，标注产生和释放时刻。预算按实际设备分别检查；逻辑可共享状态在后文满足共享条件后才扣除。

### 8.1.3 从单请求时间到服务目标

引用第 3 章的质量、TTFT、ITL 和完成期限定义，先固定模型、精度、采样及输出长度建立执行基线，再用到达分布观察等待。若 TTFT 已含首输出，总时间为 TTFT 加余下 G−1 次 decode 间隔。自然生成另计返回长度、终止和重试，章末统一计算满足质量与 SLO 的有效产出。

## 8.2 批处理与请求调度

先解释多个请求怎样共享权重读取，再处理进出批次、长 prefill 干扰以及执行预算偏差。

### 8.2.1 权重复用与批量收益

沿用 `I_weight ≈ 2q/b_w`，比较权重复用与矩阵形状，再加入凑批等待、长度差异和 KV 容量。Qwen3-8B BF16 在 2K／8K 历史下，旧 KV 读取达到批内共享权重读取的 batch 分别为 51／13；这说明长历史削弱继续合批的收益，不是计算主导的交叉点。候选 batch 还须通过逐卡容量与延迟检查，完整条件见[扫描](../calculations/results/batch-reuse-h100-2k.md)。

> **实验 8-1 ★〔延伸〕：batch 与权重复用**
>
> 为什么一批请求比逐个执行更划算？ 对 Qwen3-8B 扫描活跃 batch＝1、4、16、64，先按实际精度预测权重／KV 读取、矩阵工作和逐卡容量，再比较 4090／H100 的可行范围。只对能装下的候选测吞吐与延迟；换成长 Agent 前缀后重算。
>
> 条件：基础·单设备／配套记录。

**实测结果（8-1）：** RTX PRO 6000 上固定 vLLM，短 2K 与长 8K（命中 6K 共享前缀）两组输入各扫 batch=1／4／16／64、三轮共 510 请求。短输入 batch 1→64 吞吐约从 37 升到 1,165 token/s，客户端 TPOT 从 26.5 增至 40.5 ms；长前缀组 batch=64 的 TPOT 升到 57.0 ms。实际活跃数与满批 decode 逐批核对，零抢占，同输入输出一致。4090／H100 的可行范围属预测部分，未在本设备上验证。[逐批实测与限制](../experiments/ch08/08-01/README.md)。

代表结果：在固定 RTX PRO 6000／Qwen3-8B 测量中，2K 输入的 batch 从 1 增至 64，吞吐约 37→1,165 token/s，首输出等待约 96→3,286 ms。用这一组结果说明吞吐与单请求等待的取舍；条件与重复测量见[实验记录](../experiments/ch08/08-01/README.md)。

### 8.2.2 从固定批次到连续批处理

让短请求退出、长请求继续，新请求在迭代边界补位。用[四请求教学时间线](../calculations/results/iteration-batching-continuous.md)对比固定批次与连续批处理，再以固定 vLLM 的调度记录对齐 token 进度、KV 分配和 GPU 执行。教学成本用于解释顺序，实际吞吐由测量校准。语法掩码、数值可重复性和视觉输入作为同一实验的扩展条件。

### 8.2.3 长 Prefill 干扰与分块执行

在正在 decode 的请求间插入一个长 prefill，先观察 token 间隔，再推导分块。相同新 token 数仍可能对应不同历史工作：Qwen3-8B 的 8K 输入按 512-token 分块，首块与末块有效注意力配对数不同，不能直接据其比例预测时间。用[分块笔记](../case-studies/chunking-and-state-transfer.md)比较首输出、decode 等待、矩阵效率与提交频次。

进阶框以 NanoFlow 说明切分与重叠：切成微批可能增加权重重复读取，只有实际重叠收益覆盖新增工作才值得采用。完整 nano-batch 算例和单活跃请求的块长补测放入扩写资料。

### 8.2.4 Token 预算、动态图形状与实际执行时间

将第 5.4 节的图重放接回同一到达轨迹，检查 CPU 准备、图命中、padding 和图池容量。捕获更多形状可能减少提交，也可能挤占 KV；相同 token 预算不保证相同时间。先固定其他条件改变一项策略，再判断等待来自主机、长 prefill 还是容量，见[图执行取舍](../case-studies/graph-execution-tradeoffs.md)。

> **实验 8-2 ★〔核心〕：请求调度与等待分布**
>
> 用同一 Qwen3-8B 的六个 Chat／Agent 请求，手排固定批次、连续批处理与分块 prefill，再在固定 vLLM 版本回放同一到达时间。先比较相同块长、不同历史位置的工作与执行时间，再分别改变 token 预算、分块和 CUDA Graph，记录等待、ITL、KV 峰值、主机提交与图缓冲；以 SGLang 作同模型可选对照，每次只改变一项执行策略。NanoFlow 的仅切分与重叠按配套时序复算，SGLang 的 MoE TBO 实测另放在实验 9-6。
>
> 条件：基础·时序推算＋vLLM／配套运行记录。

**实测结果（8-2）：** 同为 512-token 的块，历史位置不同则执行时间不同：11 个请求 176 个块中，首块与末块的 CUDA event 中位数为 25.301 与 35.070 ms，配对比中位数 1.388，11 个输出完全相同。分块 prefill 的“每块工作量相同”只对矩阵项成立，注意力随已有历史增长——排班时不能把块当作等时长单位。主机提交与图缓冲的变体仍待。[逐块记录与限制](../experiments/ch08/08-02/README.md)。

代表结果：六请求回放中，token 预算从 512 增至 8192，使一个后到请求的排队从约 149 ms 降至接近零，但最长 token 间隔从约 32 ms 增至 183 ms；单独开启 decode 图未消除小预算等待。[同块长补测](../experiments/ch08/08-02/chunk-history/README.md)也显示历史位置改变执行时间。这是共享 GPU 的局部观察，完整条件见[实验记录](../experiments/ch08/08-02/README.md)。

## 8.3 KV 的分配、复用与回收

按状态生命周期推进：为活跃请求分配空间，在满足条件时共享，完成后评估前缀保留，容量紧张时选择淘汰或恢复。

### 8.3.1 预留、碎片与分页分配

从输出长度不可预知引出预留与碎片，再用 PagedAttention 解释逻辑序列到物理块的映射。把省下的容量换算为可接纳请求数，接回批处理收益；页表和调度仍有开销。区分第 5 章的 Attention IO 优化、这里的空间分配和后面的计算复用。

### 8.3.2 分支共享、写时复制与取消回收

沿分支生成解释引用计数和写时复制，再沿用户取消区分取消返回、GPU 消费结束与块回收。共享减少分配的前提是状态身份和内容相容。

多 LoRA 作为旁栏：共享基座、adapter 驻留与请求 KV 具有不同的共享条件。共享权重不代表不同 adapter 可以直接共享 KV；完整容量计算及槽位对照见[多 LoRA 笔记](../case-studies/multi-lora-serving.md)和扩写资料。

> **实验 8-3 ★〔延伸〕：KV 分页与状态分配**
>
> 分页能多接纳多少请求？ 用 Qwen3-8B 每 token 的 144 KiB BF16 KV 作输入，实现小型状态分配器，比较长度、分支和取消下的预留、分页与共享；换 Qwen3-235B 的 188 KiB 后重算可接纳请求数。
>
> 条件：基础·Python＋vLLM 状态记录。

**实测结果（8-3）：** 三组真实 vLLM 块状态记录共 3,627 个快照，守恒与全部归还均验证通过：1 GiB KV 预算下发生 1 次抢占、1,805 个调度位置，2 GiB 与主动取消场景无抢占。前缀共享的原生实测中，六条 128-token 序列产生 783 个快照、四分支 253 个快照，95 个共享块加各 9 个私有尾块，416 次引用对应 131 个唯一块，全部 refcount 等于实际拥有者，最终 454 个空闲＋1 个保留＝455。六个输出实际相同，不冒称语义分叉或写时复制。[分配器记录与守恒检查](../experiments/ch08/08-03/README.md)。

代表结果：[状态分配实验](../experiments/ch08/08-03/README.md)中，1 GiB KV 发生一次抢占，2 GiB 没有；取消返回早于实际释放。分支共享与 adapter 隔离补测分别检验共享块数量和身份边界，不能仅用已返回的请求数判断空闲容量。

### 8.3.3 Chat 与 Agent 的前缀复用

以作者 AI Agent 书第 2 章的稳定提示、工具定义、状态替换和持久追加为主例，定位首个变化 token 及需重建的后缀。沿同一请求比较 vLLM APC 与 SGLang RadixCache，先检查 token、模型、adapter 和缓存格式身份，再计算少做的 prefill，来源见[上下文材料](../case-studies/author-context-and-design.md)。

以混合模型作边界反例：全注意力、滑窗和循环状态的可恢复位置不同，相同前缀匹配长度不保证所有状态可在该处复用。正文保留窗口和检查点的判断，Unified Radix Cache 与 Marconi 的实现演进放入扩写资料。

### 8.3.4 缓存准入、淘汰、换出与重计算

请求结束后，比较前缀再次使用的机会、驻留容量、节省的 prefill 与恢复时间，再决定准入和淘汰。对活跃请求抢占与已完成前缀淘汰分别计量；主存／SSD 换出须与重新计算比较，跨实例池与路由交给第 9 章。

同时报告按请求和 token 加权的命中率、实际省下的工作与取回时间。上下文摘要还要计摘要调用、后缀重建、后续 decode 读取和质量变化；不能把普通 KV 当作任意可拼接状态。

> **实验 8-4 ★〔核心〕：前缀缓存的复用价值**
>
> 哪些前缀值得保留？ 使用同一代码 Agent 的多轮记录，计算前缀省下的 prefill、占用的 KV 和恢复时间；改变复用间隔与本地可用容量，解释缓存命中如何改变排队。
>
> 条件：基础·轨迹分析。

**实测结果（8-4）：** 五组真实 Agent 输入的单 token 回放覆盖容量、等待、压力与关闭 APC 的负对照。`cache_salt` 的 50 请求实测给出边界：非空且不同的 salt 冷命中为 0，同一 salt 热命中 3,120/3,136，空 salt 等同缺省，首 token 扰动使冷命中归零，恢复原输入后热命中回来——前缀复用的粒度是**精确 token 前缀**，不是语义相似。相同输入的输出一致。这不是认证、物理驻留或多层缓存的证明。[回放记录与边界](../experiments/ch08/08-04/README.md)。

代表结果：固定 12 轮 Agent 输入、每轮仅生成一个 token 的回放中，相同干扰下 6 GiB 缓存累计命中 16,304 个输入 token，1 GiB 降为零；单纯增加 0.2 秒间隔未改变命中。该串行记录尚未证明混合排队或驻留寿命收益，见[实验及身份补测](../experiments/ch08/08-04/README.md)。

## 8.4 压缩与卸载：容量收益和执行代价

在批处理与 KV 基线之上，先改变权重和状态表示，再处理不能全部驻留时的搬移，最后检查质量约束下的收益。

### 8.4.1 权重量化与真实驻留容量

先沿 Qwen3-8B 区分文件大小、量化元数据、运行格式、重打包副本和实际驻留；再以 Qwen3-235B-A22B 的固定 GGUF 分片与 M2 Max 96 GB 作规模案例。逐项加回 KV、工作区和系统预留，统一内存不能将 CPU 与 GPU 容量相加。沿第 5.5.1 确认实际 runner，“100% GPU”内存放置不等于利用率。

### 8.4.2 KV 压缩与读取成本

从 Qwen3-8B 的 8K 缓存位置算起：BF16 KV 为 1,152 MiB，带分组 scale 的 q8_0／q4_0 分别为 612／324 MiB。位宽比例之外还要计算元数据、分页对齐、转换与工作区。沿[量化执行笔记](../case-studies/kv-quantization-and-execution.md)区分存储格式与 Attention 执行精度，扫描上下文长度，判断容量与访存收益何时覆盖转换成本。V4 的混合状态按自身格式计算。

### 8.4.3 权重卸载、预取与每步搬移

权重不能全部驻留时，沿实际执行路径区分 CPU 计算、GPU 按需搬入、预取和 mmap／SSD 未命中；冷加载、首 token 与持续 decode 分别计时。Qwen3-8B 九层 BF16 FFN 卸载 2.53125 GiB，扣一组缓冲后净省 2.25 GiB，恰相当于两条独立 8K KV；继续按每步搬移与有效带宽判断代价，见[卸载算例](../case-studies/weight-offload-execution.md)。MoE 按批内访问专家计量，第 9 章再展开 CPU／GPU 分工。

LLM.265 作为反例框：压缩传输的收益可能被解压吞吐抵消。正文只保留搬入、解压、消费与缓冲的依赖，完整交点与历史硬件假设见[张量压缩笔记](../case-studies/tensor-codec-and-transfer.md)。

> **实验 8-5 ★〔延伸〕：MacBook 大模型的容量与速度**
>
> 对 Qwen3-235B 的实际量化文件逐片求和，再用 M2 Max 96 GB 的可用内存、8K／32K 上下文与并发计算驻留。对照 R1 极低比特文件，判断何时需要主存／磁盘换入；按实测或注明假设的带宽预测速度，配任务质量记录。普通电脑可先完成元数据与容量分析。
>
> 选做变体沿[张量压缩与传输算例](../case-studies/tensor-codec-and-transfer.md)计算一块权重的解压交点，比较离线编码、在线编码和分块流水；独立登记压缩驻留与解压缓冲。
>
> 条件：基础·文件元数据／计算；设备测量为扩展。

**计算＋实测结果（8-5）：** 对官方发布仓库逐片求和，Qwen3-235B 的 19 个完整变体中，M2 Max 96 GB（预留 8 GiB、可用 81.41 GiB）下**只有 Q2_K 装得下**（79.81 GiB），剩 1.60 GiB 刚够一个 8K 请求的 1.47 GiB KV；32K 需要 5.88 GiB，一路都跑不了。仅比它大 2.16 GiB 的 UD-Q2_K_XL 就已溢出——可行与不可行的间隔小于一个变体档位。Mac 上 Qwen3-8B MLX 4-bit 的实跑另给出 8K 与 32K 的实际槽位与 KV 占用（1.125／4.5 GiB）。[逐片清单、四组容量与实跑](../experiments/ch08/08-07/README.md)。

> **图 8-4：量化文件、可用内存与执行路径（配图计划）**
>
> 自绘 SVG 标出不同位宽矩阵和状态；实验 8-5 生成容量、加载、首 token 与生成时间，注明质量条件。

代表结果：大模型部署先完成文件与容量分析；已有[M2 Max 小模型实测](../experiments/ch08/08-07/README.md)验证 Qwen3-8B 一／四条 8K 历史占用 1.125／4.5 GiB KV，不能替代 235B 的速度结论。[32K 补测](../experiments/ch08/08-07/context32k/README.md)中检索题全对而算术题全错，增加可驻留上下文没有证明答案更可靠。

### 8.4.4 质量约束下的容量与速度选择

固定输出长度隔离执行差异，自然生成另记返回长度、终止、失败和重试。保留全部专家、保持原精度与达到相近任务质量分别验证；R1 动态低比特作为不同矩阵采用不同精度的案例。把原 8K 基线、权重／KV 压缩与卸载候选放在相同质量门槛下比较，输出可行配置供后续服务验证。

> **实验 8-6 ★★〔延伸〕：KV 压缩与任务质量**
>
> 固定前文模型、量化权重与长文档任务，改变 KV 精度或保留策略，计算容量和每步读取，再比较质量、时间和可接纳并发。V4 的不同状态按各自格式计算，不套 GQA 公式。 固定输出长度用于隔离执行差异；自然生成另记录返回长度、终止原因与成功任务耗时，失败重试计入任务成本。
>
> 条件：进阶·模型实验／配套数据分析。

**实测结果（8-6）：** 固定 Qwen3-8B 与 Triton attention，比较 BF16 KV 与 FP8 E4M3 KV。128 行文档（1,863 token）两种精度都是 8/8；512 行（7,239 token）并发 1 时均为 6/8，并发 4 时 BF16 保持 6/8 而 FP8 降到 4/8。在线 FP8 权重变体下两种 KV 都是 28/32，但**答错的任务不同**——质量差异不是简单的单调下降。8 GiB 并发扫描 538 次调用中，两种精度的已测无抢占边界分别是 7 与 15，下一档 8／16 出现抢占。[质量、容量与限制](../experiments/ch08/08-08/README.md)。

代表结果：[精度对照](../experiments/ch08/08-08/README.md)中，在线 FP8 权重的默认路径为 28/32，保留 BF16 Q 后为 32/32，仅代表本组八题；[并发补测](../experiments/ch08/08-08/concurrency/README.md)的容量收益没有同时保持质量。[重试记录](../experiments/ch08/08-08/retry-cost/README.md)将额外时间与生成 token 计入任务成本。

## 8.5 推测解码：草稿、验证与实际产出

固定前文选出的目标模型与执行配置，先建立每轮收支，再比较草稿来源和预算。额外草稿、验证与状态会竞争同一批处理容量。

### 8.5.1 草稿、验证、回退与正确性

画出草稿提出、目标验证、接受或拒绝、状态回退与最终提交的过程。严格验证保持所选目标的采样分布；目标量化造成的质量变化仍由上一节验证。模型 KV、有效上下文长度和语法状态须一致回滚，长度修正不等于物理内存清零。

### 8.5.2 每轮成本与实际产出

以每轮总耗时除以真正交付的 token 数，与普通 decode 比较；分别记录起草、准备、验证和回退，允许重叠的部分按实际时间线计量。对齐草稿接受率、接受长度和含额外 token 的产出计数，EOS 与输出上限处使用实际交付量。平均产出与平均耗时的比值须采用一致的统计区间。

### 8.5.3 草稿来源与串行、并行起草

用统一成本表比较历史查找、独立草稿模型、目标特征复用与并行整块起草。历史草稿省去草稿模型，也有查询与索引成本；EAGLE 改变特征利用与起草工作；DFlash 改变串行前向与块验证。固定目标和采样后比较成本项，不拼接不同部署的加速比。完整历史草稿算例见[推算笔记](../case-studies/history-drafts-and-rollout.md)。

### 8.5.4 块长、动态预算与并发竞争

扫描块长、上下文与并发，检查草稿状态和验证缓冲挤占 KV 后的服务收益。同一 batch 可采用不同请求预算，但减少逻辑验证行只有转化为更少实际执行或更好调度时才会缩短时间；同时检查图档位、回滚和跨 rank 对齐。MTP、EAGLE、DFlash 作为模型与执行系统协同的不同实例，版本演进留在扩写资料。

> **实验 8-7 ★〔延伸〕：推测解码的每轮收支**
>
> 以 Qwen3-8B 与固定 DFlash 检查点建立可复算基线，记录草稿、验证、回退与产出长度。扫描块长、输入长度和并发；将 EAGLE 3.1／DFlash 2 的公开记录按各自模型和机器单独复算，解释哪个因素改变了收益。
>
> 历史草稿变体先用可穷举目标检查分布和平均产出，再按固定引擎的支持条件比较查询、验证与索引准备；改变并发后复核完整服务收益。
>
> 条件：基础·时序计算／单设备或公开记录。

**实测结果（8-7）：** 固定 Qwen3-8B 与 DFlash 检查点，AR-V1／K7／K15 各 8 次预热＋16 次正式，共 48 次正式请求。32 对 DFlash/AR 正式输出**逐 token 完全一致**，全部自然停止。K7 起草 504 个 token 接受 368 个（73.0%），K15 起草 840 个接受 376 个（44.8%）——**块长翻倍使接受率降到六成**，起草成本却翻倍。严格质量三组均为 8/16，失败的格式与算术错误完整保留。共享 RTX 的采样峰值 17.3／20.4／20.3 GiB。[逐轮收支与限制](../experiments/ch08/08-05/README.md)。

代表结果：[Qwen3-8B／DFlash 实跑](../experiments/ch08/08-05/README.md)中，K7／K15 与常规解码的正式配对输出 token 一致，但任务通过率均为 8/16；长提取并发 2 时完整耗时下降而首 token 更晚。用此区分分布保持、任务质量和不同延迟收益；真实拒绝与回退见[阶段观测](../experiments/ch08/08-05/kernel-trace/README.md)。

## 8.6 服务验证与配置选择

把各项策略放回同一到达轨迹，先在同一设备验证组合收益，再考虑设备与完整任务成本。

### 8.6.1 到达率、排队、准入与取消

沿用第 3 章的到达分布，扫描到达率并记录队列、活跃请求、状态峰值和取消浪费。固定设备与模型，先分别调整调度、缓存、压缩或草稿，再验证有依据的组合；资源节省是否变成准入空间和更少等待，以实际执行记录为准。

### 8.6.2 质量与 SLO 约束下的有效吞吐

仅将同时满足质量和期限的交付计入有效产出，迟到、失败、取消与重试耗费仍计入成本。比较低延迟单请求、连续批处理与离线突发，解释最大 token/s 为什么不能单独代表服务能力。检索参数与多模态阶段作为迁移练习，在扩写中检查输入增长、状态驻留和完整任务时间。

### 8.6.3 配置、设备与完整任务成本

先检查单实例配置组合，再将相同模型、请求分布与质量门槛用于 M2 Max、4090、H100、H20 等设备候选。容量、对应形状的处理能力、有效带宽和互联分别计量；缺失的整机费用、能耗或设备实测保留未知。公开高速生成结果用来检查计时边界，不能直接换算 Agent 任务收益。

> **实验 8-8 ★★〔延伸〕：高速生成与完整任务时间**
>
> 选择 MiMo 或 V4 的一项公开加速结果，列清模型、量化、硬件规模、并发和计时边界；用同一 Agent 轨迹分别只加速 decode、prefill 或工具。计算任务收益，并补上草稿挤占 batch 和 CPU 专家验证流量的情景。缺失的部署条件保留未知。
>
> 条件：进阶·公开证据与计算。

**记录结果（8-8）：** 采用 2026-09-07 保存的公开快照核验条件：模型 MiMo-V2.5-Pro-UltraSpeed、8 卡、MXFP4 专家、DFlash，作者报告输出速度超过 1,000 token/s，但**具体 GPU 型号、并发与计时窗口未公开**。同时核对的四条真实 Agent 轨迹为非流式 HTTP，没有可拆分的 prefill/decode 边界，因此按 8-8 要求“分别只加速 decode、prefill 或工具”的任务收益保持为 null。结论是明确的边界：公开的 token/s 不能直接换算成完整任务加速。[条件核验与未知项](../experiments/ch08/08-06/README.md)。

记录边界：MiMo 公告缺少本轮可核对的完整计时条件，已有 Agent 非流式记录也不能拆分 prefill／decode。因此本题先核对条件并完成注明假设的阶段预算，见[公开条件与任务原件](../experiments/ch08/08-06/README.md)。

>
> 哪些配置能在期限内完成更多合格请求？ 先在同一设备上验证调度、缓存及有证据支持的压缩或草稿组合，再比较设备候选。 用上述相同模型和请求扫描到达率，比较低延迟 batch＝1、连续批处理和离线批量生成的有效吞吐、整机费用与能耗。先判断哪个资源饱和，再解释本地与数据中心设备各在什么条件下合算；不能仅凭 GPU 利用率或单用户 token/s 排名。

**实测结果（8-9）：** 同一 Qwen3-8B、同一八道检索题完成 336 次正式生成，每题跨全部条件输出逐 token 相同（294/336 正确，42 个错误全来自同一题）。按事前固定的“计划到达起 3 秒内正确交付”判定，最终只有 155/336 合格。到达率 1/s 时逐个接纳的合格吞吐 0.896 req/s、p95 完成 1.039 s、每合格结果 622.1 J；到达率升到 4/s 后合格吞吐掉到 0.311 req/s、p95 升到 9.359 s、每合格结果 1,982.3 J——**提高到达率使完成吞吐略升而合格吞吐下降三分之二，能耗涨三倍**。整机电表、费用与其他设备仍未知，不以组件能量替代。[三档到达率、能量计数与限制](../experiments/ch08/08-09/README.md)。
