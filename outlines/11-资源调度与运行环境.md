# 第 11 章 资源调度与运行环境

> 写作大纲 · 任务生命周期与资源选择重组 · 2026-09-10

沿一项代码 Agent 修复任务，从执行与等待推导资源需求，比较环境驻留、暂停与预热，再安排共享资源和模型服务，最后核算失败恢复与成功任务成本。RL 案例用于增加阶段配比、环境重置和批次长尾约束。

**本章判断：** 计算空闲时状态仍可能驻留；释放、复用和迁移状态都要支付准备或恢复代价。资源与模型服务的选择，以满足质量和期限的完整任务及其全部成本评价。

**前置与交付：** 依赖第 3 章 Agent 轨迹、第 9 章模型服务与第 10 章 RL 阶段需求。交付任务执行图、状态与恢复条件表、资源和模型服务方案；第 12 章沿用这些条件，再改变执行位置。

**阅读安排：** 核心练习为实验 11-1、实验 11-2、实验 11-10，分别建立需求、比较环境路径和作出扩容决定；其余为延伸。完整参数、版本、实验追踪与计量案例见[扩写资料](extensions/11-资源调度与运行环境.md)。实验显示编号按当前阅读顺序调整，原始证据目录保持稳定，见[编号映射](../research/ch11-reorganization-2026-09-10/README.md)。章末更新[跨章设计决定](decision-record.md)。

## 11.1 从任务轨迹到资源需求

沿同一项代码修复建立执行图、资源预算和状态表；RL 只在新增阶段或批次约束时作为对照。

### 11.1.1 一项代码任务的执行与等待

跟随代码任务经历排队、环境准备、模型调用、代码执行和结果保存。承接第 3 章的 Agent 与 Computer Use 负载，把一轮内部依赖与多轮累计等待画出来，找出改善模型速度之后仍在关键路径上的部分。

用 Ollama 2025 年流式工具调用说明首段文本、完整工具参数与可开始执行的时刻并不相同。流式返回可以减少部分等待，但参数未完整或操作未确定时不能提前执行有副作用的工具；预热环境则可按第 11.2.4 节另算。

### 11.1.2 CPU 工作量、环境驻留与并发容量

对稳定任务流先用 `平均环境数 = 到达率 × 平均驻留时间`，再乘每环境内存；CPU 核时按实际执行另算，预热池和突发余量另加。代码执行、浏览器和 RL 验证的资源组合由具体任务决定。

例如每秒进入 10 项任务、每项驻留 30 秒、每环境占 2 GiB，则平均需要约 300 个环境和 600 GiB 内存；若每项只执行 3 核秒，平均 CPU 工作量约为 30 核。用这个差距引出等待模型时暂停环境的收益与恢复代价。数值为教学输入，平均值不能直接当作满足 P99 的配置。

> **实验 11-1 ★〔核心〕：Agent 的 CPU 与环境需求**
>
> 根据逐轮时间线，分别计算 CPU 工作、内存驻留和任务完成时间。改变模型等待、工具耗时和到达突发，判断先补哪种资源，以及平均容量之外需要补测什么。
>
> 条件：基础·计算／记录分析。

**实测结果（11-1）：** 12 轮真实修复轨迹中采集 186 个控制器 RSS/CPU 样本与工具子进程 CPU：模型墙钟 8.995 s，控制器自身 CPU 只有 0.157 s，RSS 约 1,298 MiB——**Agent 的 CPU 瓶颈不在控制器，而在工具子进程与环境**。另有 36 组真实 Linux 工具子进程的等待、CPU 与突发对照。最终 2/6 测试未通过，失败消耗完整保留。控制器不等待环境全进程树，因此平均容量之外还需补测进程树的驻留与回收。[逐轮时间线与资源样本](../experiments/ch11/11-01/README.md)。

> **部分实测：** 模型等待期间，控制器 CPU 工作很少而内存持续驻留；控制器并非完整沙箱，容量仍需按环境边界测量。[采样与边界](../experiments/ch11/11-01/README.md)。

### 11.1.3 任务完成条件与必须保留的状态

先固定代码修复的验收测试、完成期限和输入不变条件，再列出模型历史、工作目录、进程、工具结果与外部操作。每类状态记录所属任务、版本、持久化位置，以及丢失后是取回、重建还是重新执行；后面的暂停、抢占与换模型沿用这张表。

## 11.2 运行环境的生命周期与取舍

从一项任务的执行环境出发，先讲边界和生命周期，再比较释放资源与提前准备的收益。

### 11.2.1 工具执行路径与隔离边界

以 E2B 的 Serverless 沙箱为例，跟随代码 Agent 创建环境、写入文件、执行测试、读取输出并继续下一轮。模型通过工具接口使用环境，计算发生在环境中的 CPU 或另行配置的设备上；SDK 仅展示帮助理解调用关系的步骤。

沿本章模型与工具的分工展开抽象边界：模型接口承接上层任务表达，工具执行仍承载用户的通用代码。分别定义模型请求共享、GPU 作业隔离与工具环境隔离，再讨论多租户和状态生命周期。 依据：[系统抽象边界调研](../research/system-abstraction-boundary/report.md#environments)。

从工具代码所需的隔离边界，引入进程、容器、完整虚拟机和 microVM。沙箱可由多种机制实现；E2B 公开实现使用 Firecracker microVM，容器镜像可以作为模板构建输入。

### 11.2.2 资源交付与环境创建

将第 11.1 节预算落实到 CPU 配额、内存限额、文件与网络需求。CUDA 验证和普通 CPU 工具环境分别配置，不把普通 E2B 沙箱视为默认带 GPU。设备直通用 UB OS 的 QEMU／VFIO 作补充，说明设备怎样交给任务。

### 11.2.3 暂停、恢复、快照派生与干净重建

用 E2B 暂停／恢复说明继续同一任务，再用快照派生说明从同一状态开多个分支。区分保存文件与内存、恢复环境、重新建立连接和回到干净起点；快照不会撤销环境之外的操作。

接回 DeepSeek-V4 的 DSec 与 RL 验证：Agent 保留工作目录继续做，大量 rollout 则按要求复现或重置初始条件。计算保存字节、恢复等待与驻留内存，选择继续占用、暂停还是重建。

> **实验 11-2 ★〔核心〕：E2B 环境的创建与恢复**
>
> 先算容量和启动预算，再使用可用 E2B 环境或配套记录，比较模板创建、暂停后恢复、快照派生与干净重建。检查文件、进程、连接恢复和首个工具完成时间，判断 Agent 与 RL 验证各适合哪种。
>
> 条件：基础·估算／记录分析；有账号时可选实测，不要求付费部署。

**记录结果（11-2）：** 当前环境无 E2B 凭据，因此五条路径（模板创建、暂停恢复、快照派生、干净重建、冷启动）的实测字段全部保持 null，不填造。官方两份文档已按 SHA 封存并核对六项契约：envd ≥ 0.5.0、**快照会断开连接**、文件系统仅保存会重启，以及区域灰度与之分开。这些契约本身已足以判断适用性：Agent 的多轮任务需要连接保持，因此更适合暂停恢复；RL 验证每次都是干净输入，快照派生的断连代价可以接受。[契约核对与未测字段](../experiments/ch11/11-02/README.md)。

> **记录核对（未实测）：** 文件与内存保留不代表活动连接恢复；四条路径的原始计时仍待补齐。[契约及待测项](../experiments/ch11/11-02/README.md)。

### 11.2.4 始终驻留、按需创建与提前准备

在已知创建、暂停和恢复代价后，对同一条代码 Agent 轨迹比较始终驻留、按需创建、暂停恢复与提前准备。先计算等待模型期间能够释放的 GiB·秒，再核算恢复等待、额外读写和准备工作；预热池按准备时间与到达过程配置，平均值之外另查突发和尾延迟。

从等待工具调用后才创建环境，推到利用模型生成期间的空隙提前准备。以 SpecBox（2026 年 8 月 v2 预印本）解释按流式意图与历史工具顺序预热。先算可重叠时间，再扣除猜错环境带来的内存驻留与创建工作。

预测只触发可撤销的准备，实际工具操作仍由明确调用触发。语义结果复用要检查文件版本和状态，不能把类似请求都视为相同任务。其 Docker 原型与第 11.2 节 E2B 的 microVM 路径分别说明，不移植启动数值。

> **实验 11-3 ★★〔延伸〕：环境预热的收益与浪费**
>
> 对同一组多轮任务比较始终驻留、按需创建与提前准备。按预测准确率、提前量、环境内存和工具切换频率计算任务时间与 GiB·秒，找出预热过多开始得不偿失的位置。
>
> 条件：进阶·计算／轨迹分析。

**实测结果（11-3）：** 用 3-4 的真实工具序列在 Mac 上重放，4 种生命周期策略 × 3 轮共 144 次调用、126 个 worker 退出，结果与文件逐项一致。常驻、按需创建、提前 50 ms 准备、整段提前四条路径的实际 RSS 与就绪／调用／销毁时刻完整记录。模型间隔来自重放而非实时推理，且不是 Docker／E2B／SpecBox 环境，因此完整的预测准确率、环境大小与工具切换频率扫描仍待。[四策略重放与限制](../experiments/ch11/11-06/README.md)。

> **局部实测：** 扩大提前准备窗口没有降低本次调用延迟中位，却增加了进程驻留；该结果来自本地工具进程与模型间隔重放，不代表云沙箱。[144 次工具调用](../experiments/ch11/11-06/README.md)。

## 11.3 共享资源池的分配与调度

从单任务环境扩大到多任务共享：先判断能否放下，再安排运行顺序和资源回收，最后加入 RL 阶段与批次依赖。

### 11.3.1 异构资源、成组分配与放置约束

接回第 6、7 章算出的并行方案：一个作业需要的不是任意若干张卡，还包括卡型、主机内存、CPU 和网络位置。用 ASI 的生产集群研究（OSDI 2026）解释空闲设备为何仍分配不出去，再比较打包放置、迁移整理和跨交换机放置，权衡等待完整一组设备与立即开跑之后的通信代价。

> **实验 11-4 ★〔延伸〕：异构集群中的成组作业**
>
> 使用前文具体模型的设备需求，在含两类 GPU、不同 CPU 余量和两级网络的资源图上安排在线推理、训练和离线任务。比较等待、迁移与跨机器启动的预计完成时间，指出哪种约束使空闲卡无法使用。
>
> 条件：基础·手工放置／短脚本；运行时间与通信输入沿用前章估算。

**计算结果（11-4）：** 在两机架异构资源图上放置四类作业后，仍有 **32 张 L40S 完全空闲**，而只要 2 张卡的验证服务却放不进去——缺的是 CPU（要 48 核，剩余主机只有 24 或 4 核）。使空闲卡不可用的约束依次是：逐卡容量把异构集群切成互不相通的两块；CPU 余量让 GPU 空闲不等于主机可用；成组语义使零散空闲卡拼不成 16 卡训练；同主机约束让跨主机的空闲卡对 TP 推理没有意义。跨机架启动比同机架贵 2.3 倍（420 对 180 s），这也是调度器宁可让卡闲着也不迁移在线服务的原因。[资源图、放置过程与约束](../experiments/ch11/11-03/README.md)。

### 11.3.2 队列、优先级与抢占代价

在同一资源图上加入在线服务预留、队列和低优先级任务。先判断整组资源是否可用，再用等待上限、完成进度和抢占损失安排准入与优先级；说明提高某类任务优先级会推迟哪些工作。DRF、Gavel、Pollux 只作为公平分配与异构调度的背景。

资源分配比例、实际忙碌时间和有效任务进展分别计量，异构设备不能按卡数等价替换。抢占前核对第 11.1 节的状态表，将保存、迁移、加载与重做计入代价。自建模型副本还需预留权重加载和初始化时间；多 adapter 仅在共用基座时节省对应权重。接下来用 RL 的阶段变化与批次反馈检验这些规则。

**计算结果（11.3.2）：** 这类判断的输入几乎全是声明值，因此值得先问哪一个输入的不确定性真能改变结论。对本书两项已解决的决定（专用化是否回本、执行图选哪种改写）逐个输入在其声明区间内单独移动、其余保持标称，结果是两项决定的任何单一区间都不足以翻转结论；因此"最小补测"要老实写成买到信心而非买到另一种选择。翻转以二分区间给出而不是精确根：机器数的区间落在 [253, 254]，独立重新发现了案例的 254 台答案；单位节省要超过约 1.268 美元/百万 token、经济寿命要超过 30 个月才翻转；利用率与电价在 64 倍搜索范围内单独都翻不动。逐输入标注证据类型，且对同一模型的复算不充当该模型的独立测量，所以"观察"一栏明确为空、修改后的决定与初次预测一致。[区间扫描、翻转区间与留出配置的可证伪预测](../calculations/results/design-record-uncertainty.md)。

### 11.3.3 RL 生成与训练的动态资源配比

用 RLBoost（NSDI 2026）的 Qwen3 8B–32B 案例连接第 10 章：训练组保留紧密互联的设备，额外资源承接 rollout。先根据采样量、训练耗时和权重分发求出增加 rollout 设备的收益上限，再解释为什么需要动态调整。

计算实例出现后加载权重的时间、抢占时已生成 token 的保存，以及换实例重新 prefill 的代价。论文的部分响应续接适用于其生成路径；带工具调用的 Agent 还要保存环境与外部操作状态，不能认定所有 rollout 都无状态。训练检查点继续沿用第 10 章。

沿 Qwen3 案例给一次 30 GB 权重、六个接收实例的教学输入：发送端共用 200 Gbps 出口，各接收端为 50 Gbps，全部传完的下界是 7.2 秒。接收端 TP=2 不自动让这条路径的字节减半。再扣除加载、重建前缀和恢复时舍弃的进度，计算额外实例是否降低完成同一批训练的成本。

> **实验 11-5 ★〔延伸〕：可抢占 rollout 的有效产出**
>
> 给定 Qwen3 权重大小、网络吞吐、生成记录与抢占时刻，比较固定资源、额外 rollout、保留部分响应后三种安排。区分已经生成、管理器收到、实际恢复与完成训练的 token，计算同一批有效样本的时间与费用；改变资源存活时间，求出增加资源不再划算的条件。
>
> 条件：基础·计算／短脚本；论文实例配置和教学价格分别标注。

**实测结果（11-5）：** Mac Metal 上的真实 Qwen3-8B 生成覆盖 12 条逻辑路径、8 次“提交后 ACK 前”抢占；完整 token 恢复与质量全部通过，但**保留前缀仍然要重建 KV，没有稳定加速**——这正是“已经生成、管理器收到、实际恢复、完成训练”四种 token 必须分开数的原因。额外资源扩张、费用与训练联动未实测。[抢占路径与恢复记录](../experiments/ch11/11-04/README.md)。

> **部分实测：** 保留前缀消除了重复采样，但一组完成时间从 11.619 秒增至 12.800 秒；恢复仍需重建 KV，扩容与训练联动尚未实测。[生成抢占恢复](../experiments/ch11/11-04/README.md)。

### 11.3.4 验证批次、长尾与资源释放

用 DistRS（NSDI 2026）的 CUDA 代码验证引入 CPU 编译与 GPU 执行两类资源。样本陆续生成，训练却要等整批反馈；先画少量样本的到达和完成时间，算最早批次完成点，再决定编译与执行 worker 数。早到的验证不必全部立即运行，关键是不能拖住批次末尾。

加入一个长尾反例：九条验证各用 1 秒，一条用 100 秒；已经执行 10 秒还未完成的任务，不能用平均耗时减去 10 秒估计剩余时间。由此推到最迟启动点，再核算减少验证资源是否会让训练组付出更多等待。对照 verl 的逐条评分入口，分清提前提交、批次优先级与实际资源释放各需要什么支持。

与第 5 章优化 Agent 相连：这里的编译、正确性检查和 profiling 都是实际工具工作。并行生成候选可以扩充 CPU 环境，但性能计时需要控制 GPU 竞争，不能让多个候选互相干扰后再拿噪声作为优化奖励。

> **实验 11-6 ★★〔延伸〕：验证资源与训练等待**
>
> 给定两批代码的生成时刻、编译与执行时间，手算最早完成点，再比较固定配额、先到先服务与按批次目标分配。加入长尾与超时样本，分别记录排队、执行、反馈返回和资源释放，核算资源节省是否抵得上训练组的额外等待。
>
> 条件：进阶·时间线计算／记录回放。

**实测结果（11-6）：** 受控 CPU 超时、线程完成、子进程终止回收与宽限额复验三轮已完成；另有 54 个真实子进程、两批固定工作、三种策略各三轮的对照。结果是一个清晰的权衡：**A 优先策略让 A 的反馈提前，却延后了 B 以及全部资源回收**——资源节省与训练组的额外等待落在不同的账上。逐任务的编译、执行、反馈与回收时刻及策略核验完整封存。仍非 DistRS／verl 的真实模型候选。[三策略时间线与回收](../experiments/ch11/11-05/README.md)。

> **部分实测：** 超时反馈后线程仍继续工作，终止子进程才观察到资源释放；优先完成一批也会推迟另一批，应连同全部释放时间评价。[超时与释放](../experiments/ch11/11-05/README.md)、[双批次记录](../experiments/ch11/11-05/batch-scheduling/README.md)。

## 11.4 模型服务的选择与调用成本

先确定合格模型与实际用量，再加入服务等待和路由，最后比较满足同一需求的容量采购方式。

### 11.4.1 任务质量与思考预算

用“一个模型思考 100 个 token，另一个需要 1,000 个”引出选择。固定任务和质量门槛，比较实际 reasoning token、可见输出、工具调用次数与成功率；区分配置预算、实际用量和预算截断。少思考却经常失败的模型未必经济，隐藏思考不能用可见摘要长度估算。

先做等单价教学算例：输入 10,000 token、可见输出 200 token，输入／生成价格分别为每百万 2／10 美元。实际思考从 1,000 减为 100 token，单次费用由 0.032 降为 0.023 美元；思考部分缩为十分之一，总费用并没有缩为十分之一。换模型时重新代入各自 tokenizer、计费项与速率；reasoning 若已含在 output usage 中，不再加一次。

**计算结果（11.4.1）：** 自建容量还要把站点账单摊进每 token 才能和按量价格比。按教学金额，100 台各 10 kW、散热系数 1.3、电价 0.08 美元/kWh，加上每年 25 万网络与 15 万备份，一年站点合计 1,311,040 美元；按利用率 50%、每台 10,000 tok/s 交付的 1.5768×10¹³ token 摊薄，是每百万 token 0.0831 美元。散热系数只乘计量电费，不乘网络与备份这两条年度线。有效速率掉到 6,000 tok/s 时同一设施摊到更少 token，站点成本升到每百万 0.1386 美元——闲置的预留在这里第一次显形，这也是把"固定投入、闲置预留与实际用量分开"做成数字的地方。[站点分项与四种情形](../calculations/results/specialization-payback-baseline.md)。全部金额为教学输入，不冒称任何厂商报价。

### 11.4.2 服务路径、前缀缓存与实际用量

沿任务→入口→后端→返回画清鉴权、路由、排队、限流、缓存与计量。换后端之前先检查模型版本、质量、reasoning 设置及状态复用条件，再判断价格与吞吐。

把第 8、9 章的 KV 复用接到 API 选择：重复系统提示、工具定义、仓库内容和多轮历史能命中多少前缀，多久再次访问，换后端会丢掉多少复用。分别计算未缓存输入、缓存创建、命中读取和按时长计费的存储；比较请求命中率与 token 加权命中率。

安排 10 轮代码 Agent 算例，固定公共前缀，再改变新增上下文、命中比例、轮间间隔和 TTL，算缓存费用的交点。结合最低缓存长度、前缀变化与工作区边界解释命中条件。API 缓存 token 是计费和复用证据，不能直接反推出 KV 在哪级存储或读取多少字节；资源模型回到第 2、9 章。

> **图 11-6：模型调用的请求路径与计费位置（配图计划）**
>
> 自绘 SVG，连接客户端、中转层与不同上游，标明排队、缓存、计量及付费位置；订阅入口按实际产品边界单独标出。

### 11.4.3 排队、限流与模型路由

在同一任务质量下绘制模型选择的成本与完成时间范围，再加入缓存与思考预算。API 售价决定使用者账单，生产成本用于供应侧分析，两者分别取证。 依据：[成本下降调研](../research/token-cost-2023-2026/report.md#economics)。

将候选写成“模型版本＋服务商／副本＋思考预算＋缓存条件”，先排除不满足质量、上下文和功能的选项，再比较完成时间和成功任务成本。限流区分请求数、输入／生成 token 及并发槽位；长 reasoning 会占用更久的槽位，也可能降低有效请求吞吐。

用两套假想服务跟算：B 的各项 token 单价都是 A 的两倍，但思考量更少、任务通过率更高；缓存全部命中时 B 更省，命中比例下降后选择翻转。由[配套输入](../case-studies/routing-cost-and-completion.md)算出约 84.93% 的费用交点，再加入完成时限，说明便宜与可用分别受哪些条件约束。

> **实验 11-7 ★★〔延伸〕：思考预算、缓存与模型选择**
>
> 使用含实际用量字段的配套任务记录，改变 reasoning 预算、缓存命中和后端排队，比较固定路由、最低 token 单价与质量约束下的完成成本。提交成功任务费用、首段可用结果时间、总完成时间和失败率；加入“100 对 1,000 个思考 token”与“缓存命中但有队列”两组手算，解释选择何时变化。
>
> 条件：进阶·先估算再离线回放；扩写时提供记录和版本，不用虚构结果代替测量。

**实测结果（11-7）：** 同一已知修复任务的三条件两轮真实请求：thinking 总 cap 100 与 1,000 **都被截断**；no-thinking 用 84 token 自然结束却只通过 3/6 测试；把总 cap 提到 4,000 后两次自然结束、用 2,524 token，通过 4/6。六次失败与原始用量、事件、质量全部保留，费用为 null。**总 cap 不等于纯思考配额**——它同时包含思考与最终输出，这一点直接改变“100 对 1,000 个思考 token”这组手算的前提。[三条件记录与手算对照](../experiments/ch11/11-08/README.md)。

> **部分实测：** 放宽生成预算后请求自然结束，修复仍未通过输入不变检查；现有候选不能用于比较合格任务成本。[原始用量](../experiments/ch11/11-08/README.md)、[宽预算检查](../experiments/ch11/11-08/wide-budget/README.md)。

### 11.4.4 自建容量、按量 API 与订阅的成本比较

沿前面确定的质量、速度、缓存和用量条件，比较自建推理容量、按量 API 与产品允许入口下的订阅。自建服务需分配设备，外部服务受配额、并发与限流约束；先筛除无法满足任务量和完成期限的方案，再比较费用。

以[单 Agent、24×7 serving 成本题](../case-studies/single-agent-serving-cost.md)为已解算例：先按上下文容量和至少 30 token/s 的单员工速度筛选 GPU 组，再按相同月输出量比较租金与 API 账单。独占速度、共享池吞吐、闲置预留及缓存用量分别计算；完整 GPU／API 情景矩阵、官方时段费率和版本快照留在[配套估算](../experiments/ch13/13-06/single-agent-serving/COMPARISON-RESULTS.md)，结果属于分析估算。

正文保留一张教学计费表，推导使用量变化时的费用交点。订阅消息、应用积分与 API token 按实际边界核对，无法换算的额度保留未知；未完成需求保持可见。中转服务的经营算例与具体产品账单留在扩写资料。

> **实验 11-8 ★〔延伸〕：订阅、API 与中转费用**
>

>
> 条件：基础·计费表与任务记录分析；不要求购买服务。

**记录结果（11-8）：** 21 个正常结束的 turn、17 个 thread、17 个 worker 的原始用量与最终文字已核验，字节摘录可追溯。但这些**不代表独立合格任务或完整月度账单**：恢复区间、模型方案、额度与三条渠道（订阅／API／中转）的配对仍未知，因此费用交点保持为空，不补造 token 配额。这正是本题要求的“没有可换算的产品用量时保留未知量”。[用量记录与未知项](../experiments/ch11/11-07/README.md)。

> **记录核验：** 现有代理日志缺少月度覆盖、产品额度与账单，日志结束也不等于质量验收，不能据 token 数推导订阅完成成本。[用量记录](../experiments/ch11/11-07/README.md)。

## 11.5 完整任务的恢复、核算与扩容

把环境、调度与模型选择放回章首任务，检查失败后如何续接、完整成本怎样累积以及扩容是否改变结果。

### 11.5.1 工具失败、局部续接与模型升级

沿跨模型与工具的任务讨论取消、幂等、已有输出及外部副作用，比较整项重做和局部恢复。模型回退与环境恢复是不同操作，换模型仍需接上正确文件和工具状态。

以代码 Agent 测试已完成、确认却丢失为例，区分逻辑操作、重传消息与重新执行的尝试。核对结果持久化位置、文件版本和尝试身份，再决定查询或重试；消息队列去重和 E2B 快照恢复都不能独自保证外部操作只发生一次。任务结果用于续接与核算，诊断 trace 可以采样，RL 反馈还需满足轨迹与验证条件。三种记录共享身份，不能相互替代。

### 11.5.2 成功任务的完整成本

沿同一条代码 Agent 轨迹，汇总模型调用、CPU 工作、环境驻留、存储、网络、空闲预留以及全部失败尝试，再计算 `成功任务平均成本 = 全部支出／满足质量条件的完成任务数`。固定统计范围和时间窗口，未完成需求单列；没有合格完成任务时，报告已发生支出和成功数为零，不给出有限的成功任务平均成本。

自建资源成本与外部服务账单按实际支付边界汇合，订阅、预留和按量项避免重复计费。同时列出完成时间与超时比例，用同一验收门槛比较整项重做、局部续接和模型升级。

任务恢复记录、诊断 trace 与成本账本共享任务及尝试身份，但各自承担不同职责。诊断可以采样，恢复和完整核算所需记录必须满足相应持久化条件；事件产生率、队列积压与故障排空预算放在扩写资料的计量案例。

> **实验 11-9 ★★〔延伸〕：重试、成功率与任务费用**
>
> 在实验 11-7 的模型记录上加入工具失败与环境恢复，比较整项重做、局部续接和模型升级的总成本与时间，解释单次调用省钱为何不一定使任务省钱。
>
> 条件：进阶·数据分析；保留同一质量门槛及全部失败尝试。

**实测结果（11-9）：** Collector 0.133.0 的两轮三故障对照，每条件 6 个工作：内存 SIGKILL 下旧的 5 个事件**未能恢复**，file_storage 路径全部恢复；提交后 503 触发重传，SQLite 唯一键完成去重。持续到达排空补测的四条件 480 个事件逐字核验，注入等待 10／80 ms。全部原始 DB、队列文件与日志封存。结论方向明确：**单次调用省钱不等于任务省钱**——失败后的整项重做把省下的部分一次抹平，而局部续接的前提是状态可恢复。[故障注入与恢复记录](../experiments/ch11/11-09/README.md)。

> **部分实测：** 文件队列可在所测进程崩溃后恢复事件，重传去重仍不能消除真实重执行成本；修复对照尚不足以建立完整任务成本优势。[故障记录](../experiments/ch11/11-09/collector-faults/README.md)、[修复与验收边界](../experiments/ch11/11-09/exit-status/README.md)。

### 11.5.3 CPU、GPU、内存与服务额度的扩容选择

回到章首业务，用排队、阶段等待和成功记录判断应该增加 GPU、CPU、内存、模型服务额度还是预热环境。先用简单预算找出能缩短关键路径的候选，再提出需要补测的一个量。

> **实验 11-10 ★★〔核心〕：资源池的扩容选择**
>
> 给定任务轨迹、资源价格与服务目标，比较扩充 CPU、GPU、内存、API 容量与预热池；提交一页估算、选择及验证计划，说明增加哪种资源不会改善当前瓶颈。
>
> 条件：进阶·方案研究。

**实测结果（11-10）：** 基于已封存的原始记录完成离线分析与一页选择／验证计划：77 组分组记录、8 份文件 manifest 与 228 个来源 SHA 的主复核、7,053 项检查；主 Agent 12 轮的时间、CPU 与 token 独立核对。模型请求占整段 96.128% 而最终只有 2/6 通过——**占比高不等于该资源饱和**，不能据此推断 GPU 饱和并去扩容 GPU。本地路径之外的外部 API 容量与预热池仍需按计划验证。[一页计划与核对记录](../experiments/ch11/11-10/README.md)。
