# 第 9 章 分布式推理

> 写作大纲 · 数据搬移主线与章节依赖修订 · 草案 22 · 2026-09-08

第 8 章给出共置服务基线，本章沿同一请求逐次加入阶段分工、专家就地计算和共享状态。PD、AF 与 KV 池分别改变交接的数据、频次和寿命；用同一张图比较新增搬移是否换来足够的匹配与复用收益。

**本章判断：** 分离和池化可以增加数据移动；成立条件是资源收益足以覆盖交接、双端缓冲、排队、失效和恢复。

**前置与交付：** 依赖第 7、8 章；交付完整部署的阶段能力、状态交接与恢复预算，第 10 章将这些能力组成 RL，第 11 章扩展到资源池和任务。

**阅读安排：** 核心练习为实验 9-4、实验 9-7、实验 9-10；其余练习为延伸。每节的完整参数、实现版本与实验变体见对应[扩写资料](extensions/09-%E5%88%86%E5%B8%83%E5%BC%8F%E6%8E%A8%E7%90%86.md)。章末更新[跨章设计决定](decision-record.md)。

### 9.1.2 请求阶段与状态寿命

将同一请求画成 E（有视觉输入时）→P→D→工具→下一轮 P，记录每个阶段的执行位置及状态身份。权重跨请求复用，激活通常跨相邻算子交接，KV 随会话增长；EC 由图像和编码配置决定，语言 KV 还依赖文本位置与前缀。模型、格式和版本不兼容时重新准备。

## 9.2 PD：阶段分离与 KV 交接

先比较调度改善，再比较独立资源池。A100＋H20 是可核算实例，配比由同一请求单位的需求决定。

### 9.2.1 Prefill 与 Decode 的资源冲突

从第 8 章混合执行的冲突进入 DistServe／Splitwise，比较更好调度与独立资源池两条改进路线。接回第 6 章的切分：同样两张卡，单请求较快的 TP，在负载增加后未必比均衡 PP 的平均完成时间短。用[简化排队算例](../case-studies/chunking-and-state-transfer.md)选候选，再按 prefill／decode 的实际请求分布决定并行与池规模；均值推算不能替代尾延迟验证。

实验入口采用 SGLang 的 PD 服务与实际 KV 传输后端，或固定 vLLM 的分离式 prefill connector。推理引擎安排请求，Mooncake／NIXL 等承担相应数据通路，不能把传输库当成完整服务。先检查两端模型、KV 格式和设备支持，再选择能运行的组合；A100＋H20 的硬件推算与特定版本是否支持这一部署分别记录。

### 9.2.2 阶段能力与异构设备配比

案例采用 A100 80 GB SXM 做 prefill、H20 SXM5 96 GB 做 decode。先分别看两卡在相同模型、精度和请求形状下的两个阶段，再决定是否这样分工；两池都执行 attention 和 FFN，也都需要相应模型权重。比较共置、同构 PD、A100→H20 异构 PD 与角色互换。先用 Qwen3-8B 的实际 KV 与两个阶段工作量计算，再换 Qwen3-235B／V4-Flash 的状态和专家路径；增加前缀命中、reasoning 输出或 batch 后重新选择角色与池规模。H20 未取得的精确规格保留未知，阶段效率用相应 GEMM 与请求测量校准。

### 9.2.3 KV 交接与收益边界

把分离前后的资源配比收益，与 KV 交接、专家通信、两端暂存和排队逐项比较。增加搬移仍可能改善任务，但必须用同一工作量和时限证明。 依据：[成本下降调研](../research/token-cost-2023-2026/report.md#serving)。

把实际模型的 KV 大小、传输路径、格式转换、双份暂存与两侧排队纳入完整请求。Qwen3-8B 在 8K 长度的 BF16 KV 为 1.125 GiB；原有 1 GiB 教学算例用于检查算术，随后全部代入模型值。按请求吞吐求池配比，画出分离开始值得的位置。

先沿案例算一笔 KV：同构 GQA 的 32 层、8,192 token、8 个 KV 头、128 维、每元素 2 byte，得到 1 GiB。人为给定有效单向带宽 25 GB/s，仅载荷传输约 42.95 ms；再加格式转换、接收缓冲与排队。这是条件式计算，不能标成 A100／H20 的实测。沿真实 PCIe／NIC／RDMA 或 host staging 路径计算，不能假定跨代设备直接通过 NVLink 互联。

## 9.3 AF：移动权重还是就地计算

沿 CPU／GPU 和跨机两条路径比较搬权重、搬激活与独立资源能力；频次和同步必须进入判断。

### 9.3.1 专家驻留与算子放置

从 MoE 总参数与激活差异进入 KTransformers：对照“把专家权重搬到 GPU”和“让 CPU 使用本地 DRAM 就地计算专家”。画清 attention、路由、共享／路由专家、其余 dense 层与 KV 的放置；热点专家可能驻留 GPU，prefill 与 decode 也可能采用不同配置。由此解释 AF 的切分位置，不能把一个项目概括为所有 attention 永远在 GPU、所有 FFN 永远在 CPU。

结合 SGLang 2025 年的 KT 集成预览与当前 wrapper，把框架分工落实为提交 CPU 专家、并行执行 GPU 专家、同步合并结果。它与第 8 章的 GPU 权重预取分别计算；CPU 专家使用的格式、线程和物理专家映射也进入记录。[执行路径与算例](../case-studies/weight-offload-execution.md)连接容量和实际服务能力。

### 9.3.2 CPU 就地计算与 NUMA

以固定版本公开文档的 RTX 4090 24 GB＋双路 Xeon Gold 6454S 为主案例，解释 AMX／AVX-512、专家打包、内存通道、线程绑核与 NUMA。先按每专家 token 数比较矩阵—向量和矩阵—矩阵的复用，再判断省下的 PCIe 权重流量是否值得付出 CPU 计算和 DRAM 读取。SOSP 论文的双 8452Y＋A100／4080 实验作为另一组证据，不能移作这台主案例机器的性能。

### 9.3.3 逐层交接与阶段交接

用 MegaScale-Infer（2025）的 ping-pong pipeline 作跨机 AF 的具体案例：将请求批次分成微批，在 attention 与专家节点之间交错执行。先按两侧计算时间和往返激活流量判断能否形成稳定流水，再算微批数量、填充排空与小矩阵损失；不把 KTransformers 的同机路径和这套分布式实现合并成一个系统。

对照 AF 与 PD 的时序，比较反复交接激活和一次请求 KV 交接；把同机协作延伸到跨机 attention／FFN 池化时重新核算启动、带宽和同步。

用简化的 32 层、单 token、宽度 4,096、每元素 2 byte 算例：每层完整激活送出一次、合并结果返回一次，每步总载荷 0.5 MiB，却有 64 次有方向的交接。先算 `64 × 启动与同步时间 + 载荷 / 带宽`，再代入 Qwen3／V4-Flash 的真实层数、专家路径与切分位置修正。将同机 PCIe 换成跨机网络，判断新增启动是否已经超过期限，再考虑压缩、流水和聚合；不把少字节直接理解成低开销。

### 9.3.4 大主存与少量 GPU 的服务条件

另以 vLLM AFD Plugin（2026 年 7 月实验性发布）展示跨服务 AF 的实际接口，接回上一小节的流水分析。其已披露模型和 GPU／NPU connector 各有阶段、图执行与微批限制；公开强制均衡及缩层测试不能充当自然路由下完整 V4／K3 的质量或线上性能结论。

沿固定 KTransformers 文档还原 V4-Flash 的单 RTX 5090＋至少 200 GB 主存，以及 Kimi K2 Q4_K_M 的约 600 GB 主存＋14 GB 显存案例。先从完整权重放在哪里解释容量，再计算 CPU 实际专家工作、GPU attention、NUMA 与交接。Kimi K2 的证据不替代 K3；单卡与八卡 MTP 成绩分开引用。

### 9.3.5 并发增长与专家复用

保持模型和请求不变，将并发从 1 增加，统计批内专家集合、每专家 token 数和最忙 NUMA 节点。热点专家缓存与较长 prefill 的 GPU 分层执行会改变瓶颈；比较 CPU 就地计算、按需搬权重、混合驻留和全 GPU 服务，计算达到同一质量与延迟要求的负载范围。

沿 Qwen3-235B 的 128 个专家、top-8 和单专家 36 MiB BF16 矩阵，教学固定 32 个专家驻留 GPU：分别计算其余专家的不同权重数与 token—专家任务数。由单 token 到 2048-token prefill，CPU 可能从 DRAM 受限转为计算受限；用路由记录替换均匀假设后，再决定热点放置和两侧资源配比。

## 9.4 专家放置与共享资源

在固定逻辑路由下比较副本、迁移和执行重叠，扣除多占的权重、KV 与缓冲。

### 9.4.1 路由倾斜与设备负载

分别使用 Qwen3-235B 和 V4-Flash 的路由记录，把 top-k、专家宽度、共享专家及批内复用代入每卡和每链路工作。相同请求数下找最忙的设备，解释平均激活参数为何不足以预测完成时间。

接回 6.3 的独立活跃专家数：访存受限的 decode 可能因路由集中而少读权重，计算受限的 prefill 则可能因集中而等待最忙卡。先判断阶段瓶颈，再选择均衡目标；宽 EP 下 decode 的逐卡载荷仍需检查。

### 9.4.2 专家复制与 token 迁移

比较专家复制、放置、迁移和调度，计入额外权重与更新成本。将负载变化放进同一实验，看静态最佳安排何时失效。

以 vLLM／SGLang 的 EPLB 连接路由统计、逻辑专家到物理副本的映射，以及热点专家复制。保持模型的逻辑 top-k 语义；复制相同权重的专家与修改模型路由规则不是一回事。负载观察窗口过短可能频繁迁移，过长又跟不上变化。

用 CRAFT（MLSys 2026）引出逐层副本预算：不同层的倾斜程度和复制收益不同，新增专家又会挤占 KV。Qwen3-235B 若每卡每层多放一个 BF16 专家，94 层合计约 3.305 GiB／卡；把预算集中给少数层后，是否能达到相同服务目标，要用路由和时间记录判断。论文基于 SGLang v0.4.8 的 R1／Kimi K2 实验作历史对照，当前引擎支持的放置能力单独核对。

### 9.4.3 Grouped GEMM 与计算通信重叠

沿一次 MoE 层展开路由、排列、dispatch、grouped GEMM 和 combine，按每专家 token 数算矩阵形状。举八个本地专家分别收到 32、16、8、4、2、1、1、0 个 token 的教学输入：实际 64 个专家 token，全部补齐到 32 则执行 256 行。由此比较 padding、变长分组和 persistent 调度；合成一个 kernel 能减少提交，但不能自动消除长尾专家或 tile 的浪费。

同一输入若只对非空专家按 32 行块补齐，则为 224 行。把后端的实际补齐规则放回第 5 章的算力和访存估算，比较有效工作与执行工作，不把 grouped GEMM 当作已经消除 padding 的保证。

## 9.5 KV 的层次、身份与复用

先确定存在哪里和何时有效，再处理持久化、路由与多种分工组合；命中信息必须对应实际状态。

### 9.5.1 缓存层次与访问方式

以 SGLang HiCache 与 LMCache 的真实后端作为 HBM、主机和外部存储的实验入口：分别记录写入、预取、命中和淘汰，而不是仅画一个内存池方框。2026 年 Unified Radix Cache 把混合模型状态接到这些层次；沿 V4 的压缩／窗口与 K3 的循环状态重新核算有效边界。

沿 HiCache 从 2025 公告到当前实现，明确单实例私有的 host 层与按后端配置共享的存储层。再用 vLLM 从异步 connector、CPU offload 到当前多级后端作对照；其原生路径先经过 CPU，不能由“远端存储”推断 GPU 直读。缓存容量、共享范围和数据通路分别落到实际部署。

沿用 1 GiB 前缀和 25 GB/s 条件式算例：取回一次的纯传输下界为 42.95 ms；假定每个 decode 步都要从远端读取这份不变前缀，生成 100 token 至少累计约 4.295 s 的链路服务时间，另计增长中的 KV。与一次本地 prefill 重算和搬回本地继续生成比较，解释远端容量能否成为活跃 KV 的供数来源；有重叠或分片时按每条链路和依赖重算。

> **实验 9-7 ★〔核心〕：共享 KV 池的命中收益**
>
> 复用远端 KV 何时比本地重算更合适？ 两个实例交替服务同一 Agent，比较本地重算、一次取回并驻留、每步远程访问三条路径。按前缀大小、命中间隔、带宽、重算时间与 HBM 占用求收益边界；增加池写入和回收后，检查 PD 交接是否仍有收益。
>
> 条件：基础·手算／请求重放。

### 9.5.2 持久化与多级命中

以 DeepSeek-V4 的 on-disk KV 为例，说明缓存怎样跨请求、模型实例重启或任务暂停保存。CSA／HCA 的压缩条目、SWA 的窗口状态和不完整压缩块分别处理；全量保存、周期检查点与部分重算具有不同的写入、读取和恢复成本。缓存身份包含模型版本、adapter、位置与格式，过期或不兼容状态不能直接复用。

给定复用间隔和请求长度分布，分别计算 HBM／DRAM／SSD／远端的命中收益、写入字节与取回时间。高命中率不保证低延迟，SSD 小块访问与写放大也不同于持续带宽；把后台存储、预取与用户关键路径分开，比较留存、迁移和重算。

> **实验 9-8 ★★〔延伸〕：持久化与多级 KV 的取舍**
>
> 使用同一组 Agent 轨迹，扫描 HBM、DRAM、SSD 与远端容量；比较全量保存、周期检查点和重算。依据 V4 的压缩与窗口状态计算每次写入／取回及必要重算，加入重启恢复和缓存失效，报告命中率、p95 取回时间、写入量与任务完成时间。
>
> 条件：进阶·请求重放／存储记录。

### 9.5.3 缓存亲和性与负载路由

从两次同前缀请求引出缓存亲和与负载均衡的冲突，比较原实例排队、新实例重算和跨池取回的完成时间。Preble、SGLang 与 Mooncake 作设计对照；命中率、复用间隔和正在占用的显存决定选择。

用同一 Qwen3 的 8K 前缀给出具体选择：在声明的队列与串行取回假设下，原实例 HBM 命中约 260 ms，空闲实例重算约 200 ms；远端有效带宽从 5 改为 20 GB/s，取回方案从约 310 降到 129 ms。先画状态就绪与 GPU 等待的依赖，再增加共享链路负载，说明单请求的选择何时失效。数字是教学输入，[算例](../case-studies/cache-tiers-and-routing.md)不冒充框架成绩。

再沿 vLLM 的 KV events、SGLang HiCache 与 Dynamo 的实际集成，解释缓存怎样成为路由依据：拷贝完成才报告新位置，GPU 淘汰后 CPU 副本可能仍在，事件缺失则需恢复索引。用同一前缀把 A 的队列改为 80 ms，计算有效命中时的 90 ms 与全部失效后的 260 ms；即使平均值优于 B 的 200 ms，尾延迟也可能不合格。由此区分缓存层级的评分权重、命中概率和实际取回时间。Agent 并发分支还会先于缓存发布到达，短期预测可帮助聚集请求，但不能保证前缀已经可用；[扩写依据](../case-studies/cache-events-and-routing.md)保留版本与计算条件。

> **实验 9-9 ★★〔延伸〕：缓存亲和性与完成时间**
>
> 该去有缓存的机器，还是空闲机器？ 从 Chat 和 Agent 的多轮记录提取缓存 token 数、复用间隔、队列和远程取回耗时；比较队列优先、缓存优先和预测完成时间路由。命中率同时按请求与 token 加权统计，报告命中层级和 p95 取回时间。
>
> 条件：进阶·计算／真实系统记录，可选多实例部署。

### 9.5.4 PD、AF 与内存池的组合

将 PD、AF 与共享 KV 放回同一状态图：P 产生历史，D 读取并增长；专家权重与逐层激活各有不同的寿命和交接频次。比较直接交接和经池暂存，额外写入、读取和双份驻留逐项计量。

沿 Agent 的 P→D→下一轮 P 检查哪些生成状态真正已保存，复用收益不能重复计入。前面已定义持久化身份和缓存路由，此处才选择组合。给一次条件变化，使原本值得分离的部署重新共置，或使保留状态变成重算更合适。

### 9.6.1 流式输出与部分故障

### 9.6.2 异构推理的部署取舍

接回第 6 章的四卡切分，用 ArcticInference＋vLLM 比较固定 TP、固定 SP×TP 和运行中切换。额外权重会挤占 KV，额外图准备需要足够执行次数抵消；阈值按本轮调度 token 数校准，并记录补齐、实际并行模式与 Graph 路径。相同 KV 布局是切换条件，完整服务收益仍由排队、状态容量和请求分布决定。[版本与推算](../case-studies/parallel-switching-and-state.md)
