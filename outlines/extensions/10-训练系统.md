## 10.1 有效训练进展与状态预算

<a id="detail-10.1.1"></a>

### 10.1.1 参数、梯度与优化器状态

用 Qwen3-8B 与混合精度 Adam 逐项算权重、梯度、优化器和激活；约 8B 参数按 16 byte／参数粗估持久状态约 128 GB，再按实际参数和实现修正。与第 8 章推理逐项对照：单卡能推理，为什么全参数训练仍需分片或卸载。V4 的 Muon 与低精度状态另算。

把 16 byte 拆开：BF16 权重 2、BF16 梯度 2、FP32 主权重 4、Adam 两项状态各 4。若梯度以 FP32 常驻，同一口径变为 18 byte；混合精度本身不能确定是哪一种。沿下一节的 gate 矩阵，前一种总计 768 MiB，其中不含梯度的权重与优化器部分为 672 MiB。转换时若 BF16 梯度尚未释放、又生成 FP32 副本，临时峰值还需另外计算；不把检查点字节或卸载后的 GPU 驻留当成完整训练状态。

<a id="detail-10.1.2"></a>

### 10.1.2 重计算、卸载与分片

以 PyTorch FSDP／DeepSpeed ZeRO 的具体配置承接容量预算，再用 Megatron Core（2026）的细粒度重计算和卸载说明不同模块不必采取同一种策略。分别算省下的激活、增加的 FLOPs 与主机传输；重计算、通信重叠和 CUDA Graph 有实现上的组合限制，不能把每项独立收益相乘。

卸载继续第 5.2.3 的缓冲时序：节省的 HBM 要扣除取回暂存，主机还需为锁页池留容量。取回能否提前，由其他微批的可用计算窗口和缓冲复用点决定；异步提交后立即改写源张量会影响正确性。

SuperOffload 的转换放置作为同一问题的进一步推算：Qwen3-8B 一层 gate 梯度有 50,331,648 个元素，BF16／FP32 分别为 96／192 MiB。以 CPU／GPU 有效转换吞吐 100／1500 GB/s 为教学输入，单向链路从 32 提高到 300 GB/s，较快路径由 CPU 转换变为 GPU 转换；后者还需要额外 192 MiB GPU 暂存。两条路径都使用锁页主机缓冲，论文旧路径的未锁页临时分配另作实测因素。[完整公式、版本与排除项](../../case-studies/training-offload-and-casting.md)保存在配套笔记。

真实系统选 DeepSpeed ZeRO-3 与固定 Qwen3-14B 官方示例作为设备实验入口；纸笔算例继续使用本书 Qwen3-8B。先记录卸载比例、亲和性、序列长度和实际 batch，再看转换、传输、CPU Adam 与最后几个梯度桶的暴露尾部。v0.18.0 的配置和当前示例不是同一时期的性能证据，所选脚本两种模式还改变了 ratio，必须先对齐比较条件。

先比较保存更少激活、重计算、卸载和状态分片：每省一个字节会增加什么计算或传输。LoRA／QLoRA 作为训练目标改变后的另一类任务，不能直接代替全参数训练比较。用 KTransformers 的具体微调方案核对哪些参数冻结、哪些需要梯度和优化器；其 BF16 全量更新与低比特冻结专家的 LoRA 分别核算。

### 10.3.2 通信重叠与资源竞争

检查梯度就绪、分桶和下一步依赖，比较理想重叠与共享资源下的实际情况。GPU、NPU 的具体执行记录用于说明相同想法怎样落地。沿第 6.4 的通信调优算例，重新标出训练中的并发汇合与暴露尾部：局部带宽收益必须回到整步时间，搜索成本按实际剩余训练长度摊薄。

## 10.4 持续供给与可恢复状态

<a id="detail-10.4.1"></a>

### 10.4.1 数据读取与预处理

从一次设备空闲记录引出读取、预处理、长度打包与预取。计算每秒所需样本和字节，先定位最窄环节，再选择缓存或增加处理能力。

沿第 5.2.3 区分 CPU 准备、锁页暂存与 H2D：文本 token 输入和卸载激活的字节可能相差很大，先由真实张量决定是否值得预取；`pin_memory` 与异步提交的作用用实际流水记录解释。

>

### 10.4.2 故障规模与检查点周期

用设备数与单设备故障率估计一次中断的量级，解释保存频率、持久化和恢复的取舍。不要等到万卡实验才发现恢复成本不可接受。

### 10.4.3 保存、恢复与存储带宽

## 10.5 RL：生成、验证与更新的闭环

<a id="detail-10.5.1"></a>

### 10.5.1 Rollout、奖励与训练闭环

承接第 3 章的 RL 负载，组织 rollout、奖励／验证、样本缓冲与梯度更新，再把新权重交回采样端。DeepSeek-R1 交代推理训练路线，DeepSeek-V4 的 §5.2 作为系统主例；逐项计算生成、验证、训练、权重分发与数据组织的资源需求，代码与 Agent 任务连接第 11 章的 CPU 沙箱。

以 verl 的实际数据流对应这些角色：rollout 可调用 vLLM／SGLang，梯度更新由 FSDP／Megatron 等后端执行，verl 组织样本、奖励与权重交接。用小模型配套实验贯通真实流程，再将 V4 教学预算代入，不能用开源实验反推 V4 未公开部署。AReaL 用于异步供给的对照。

<a id="detail-10.5.2"></a>

### 10.5.2 长轨迹、抢占与采样恢复

依据 V4 的 token 级 WAL、抢占时 KV 保存及故障后重做 prefill，比较从断点继续与从头重采样。用长短轨迹的不同存活概率解释后者可能引入长度偏差，恢复同时影响系统成本与训练样本分布。同步／异步供给作为部署选择分析，只把报告明确披露的机制归于 V4。

再以 AReaL 的部分 rollout 区分“恢复同一策略”与“换权重后继续”：token、环境与行为 logprob 可以保留，新权重所需 KV 要重新验证或重建。给同一轨迹的不同段标出实际权重版本，比较版本滞后、暂停交接和有效样本供给；Qwen3-8B 的 8K KV 虽为 1.125 GiB，重建成本仍要回到 prefill 计算。沿[状态与版本算例](../../case-studies/rl-state-and-reproducibility.md)解释扩大 rollout 池何时只会积压待验证或过期样本。

用 RobustRL（OSDI 2026）的 verl＋vLLM 路径补一次 trainer 故障：先判断已生成轨迹、环境、训练检查点分别在哪里，再决定重做多少。沿[恢复算例](../../case-studies/rl-scheduling-and-recovery.md)，300 秒 rollout 后更新失败，保留轨迹可把教学完成时间从 790 秒减至 490 秒。讲清按角色恢复的边界、检查点版本及尚未持久化的状态；正常等待工具不能判为 GPU 故障。

以 RollPacker（NSDI 2026）的长短轮次补充主动取消：多启动回答、保留先完成的组，可以缩短等待，也可能改变入选分布。沿[两次采样的算例](../../case-studies/rollout-tail-and-sampling.md)，固定权重下长回答入选概率仍可由 1/2 降至 1/4。分开核算 prompt 覆盖、回答选择、额外生成与验证质量；公开实现的完成组还受奖励与过滤时间影响。

<a id="detail-10.5.3"></a>

### 10.5.3 采样、教师与学习的资源配比

沿 SGLang 2025 的内存优化过程与 vLLM Sleep Mode，先算同一 Qwen3-8B 的阶段容量：训练和推理各自能放下，交接时却可能因训练状态、推理权重和 KV 同时驻留而超限。给定 64 GiB 可用预算，推算先恢复全部状态的 83.26 GiB，与先同步权重、释放训练状态后再恢复 KV 的 59.26 GiB 峰值。保留地址可以省去部分初始化，不能恢复已丢弃的数据；[计算条件与版本依据](../../case-studies/weight-handoff.md)留在扩写材料。

再比较保留旧权重与直接装入新权重：完整 actor 更新、LoRA adapter 更新和 MTP 起草器的保留要求不同。用固定 verl 的 vLLM／SGLang 集成说明，暂停请求、释放显存、同步权重、完成后处理与恢复采样是不同操作；跨 DP／EP 的切换要等所有相关 rank 到达可交接状态。

阶段交接选做加入一次部分更新失败：按固定 SGLang 的[成功边界补读](../../research/2026-infra-survey/root-weight-update-boundary.md)，区分传输完成、安装成功、缓存处理与版本发布。target 成功而 draft 失败、某 rank 安装中断时，先判断哪些状态仍可信，再计恢复工作；局部返回或 barrier 到达不能单独作为全体恢复采样的依据。再沿[控制层的结果汇总](../../research/2026-infra-survey/root-weight-controller/NOTES.md)看磁盘更新如何等待预期 worker 并判断全部成功：返回失败不代表已回滚，恢复采样还要由调用方在确认状态一致后触发。

分置时把第 6 章的模型切分继续算到权重分发。以 Qwen3-235B 的专家矩阵比较整份广播与按 EP 所需分片取回：423 GiB 专家权重在 EP16 下每 rank 只需 26.44 GiB，但瓶颈还可能在生产端网卡、训练侧重组和最大接收缓冲。用 vLLM 2026 的原生权重同步与 Sharded RDT 作案例，分别计入非专家权重、复制与量化；传输量缩小不能直接当作端到端加速倍数。

统一生成、验证和学习的有效样本单位，再决定 GPU、CPU 与环境池配比。以 V4 的多教师 OPD 为例，比较保存全词表 logits 与保存末层 hidden state、使用时重算输出头的容量和计算代价；加入教师权重按需读取、分组调度与异步传输。把第 9 章的分离与缓存方案代入这一循环，比较分置、共置和阶段切换的收益边界。

再用 Weave（OSDI 2026）的 H20／H800 双池案例引向第 11 章：保持每个作业采样后更新，用其他作业填等待。收益取决于阶段互补、主机状态驻留和切换时间；省下设备与单作业变快分别核算。RobustRL 借 rollout 机器恢复 trainer 还要求同型资源，不能直接套到异构双池。

回到单作业，用 RollPacker 的 ROLL＋vLLM＋Megatron 路径解释已完成样本先算梯度、整批结束后再更新。先算迁移后剩余副本的 KV 容量，再扣除重新 prefill、状态切换和最后归约。样本分配不均时按实际损失分母累积，不能直接平均各副本的局部平均；该调度由 RL 系统组织。

### 10.5.4 MoE 的 Routing Replay

先固定相同权重和 token，比较推理与训练引擎重算的专家选择及 logprob：不同精度、kernel 和 batch 形状产生的微小数值差异，可能翻转接近边界的 top-k，逐层积累成与策略更新无关的差异。由这个问题引出 Rollout Routing Replay／R3（2025），再用 NeMo RL 的 vLLM rollout＋Megatron 训练路径说明落地。

记录生成时每层、每 token 的专家 ID，在训练前向重放离散选择，同时以当前权重重新计算路由分数和专家输出，保留梯度。它不是重放旧输出，也不是省掉整个 router 计算；不能因此认为策略滞后、数值误差或 RL 收敛问题全部解决。与第 9 章 EPLB 区分：逻辑专家 ID 不随物理副本位置改变。

先对齐 rollout logprob 的定义：vLLM V1 的 raw 与经过温度等处理的概率有区别，请求 prompt logprob 也可能改变前缀缓存路径。没有对齐这些条件时，不能把所有差异归因于 MoE router；后端返回的缺失路由与回退必须进入实验记录。

分别标明行为策略、更新前训练策略与当前策略，区分当前／行为比、PPO 更新比与各自的裁剪位置；保留行为记录与训练端另行重算可以同时需要。教学例中当前／行为比值为 1，若把 `−3` 的行为 logprob 错换成 `−3.25`，比值就变为约 1.284，越过题设的 1.2 上界。先验证引擎内部的 batch invariance，再检查跨引擎与路由差异；可重复的 rollout 不自动等于 on-policy，训练端重算也不能不加说明地覆盖行为概率。

按 `有效 token 数 × MoE 层数 × top-k × ID 字节数` 先算路由记录，再加入多轮前缀、打包、上下文切分、传输与保存。例用 8,192 token、48 层、top-8、uint16 得 6 MiB；这是编码假设，真实后端若用 int32 则翻倍。缓存 KV 时要能找到同前缀的路由记录；采样、logprob、训练和激活重计算都要对齐 token 身份与权重版本。

> 沿固定 NeMo RL 的 Qwen3-30B-A3B R3 配方或其配套 trace，关闭／开启 replay 比较专家集合不一致率、同权重 logprob 差异、记录容量与阶段时间，再比较相同任务下的训练曲线。加入多轮缓存命中、样本 packing 和缺失路由检查，验证 token 对齐；小批检查只证明被覆盖路径，不冒充完整收敛结论。

## 10.6 期限与资源投入的复核

<a id="detail-10.6.1"></a>

### 10.6.1 有效训练进展与设备利用

先说明 MFU 的算法 FLOPs、精度峰值、卡数与计时边界，使用 30%／40%／50% 三档估计敏感性；50% 是较乐观情景，需要由对应模型与拓扑的训练步验证。稳态 MFU 若已包含重计算、通信与气泡，就不再把这些时间重复相加；日历完成时间另计区间之外的保存、故障、恢复和数据停顿。RL 按有效样本及质量进度核算，不把 rollout 与梯度计算硬合成一个 MFU。

再用 Google TPU 的 MPG 研究解释分配率为何不等于训练产出：沿具体训练记录，依次区分所有卡同时就绪、进展已保存的执行，以及同一数学工作的理想计算时间。100 张同型卡的一小时教学例中，单卡分配率可达 97.22%，最终计算基准对应的有效产出却只占容量的 33.33%；先算各段 GPU 时间，再给比例。聚合时统一分子分母，计算指标不能替代第 4 章的带宽瓶颈判断。[定义与复算](../../case-studies/kernel-and-fleet-efficiency.md)。

### 10.6.2 模型规模、硬件代际与完成时间

用 A100、H100 与 B200 的明确形态和 dense 精度比较。先固定卡数、数据量与期限，反推可行规模；再分别固定预算或让数据量随参数增长，解释问题改变后答案为何不同。1T、5T、10T 作为明确标注的 Dense 扩展情景，真实 MoE 则按 V4-Pro／Kimi K3 的总状态与执行路径分别计算。

在 16,384 卡、20T token、BF16 dense、50% MFU 的教学条件下，1T Dense 的粗估为 A100 约 543 天、H100 约 171 天、B200 约 75 天；随后检查容量与通信能否支撑这一效率。读者应据此推算 5T／10T、90／180 天与不同集群规模，理解不存在脱离卡数、任务和期限的“A 卡／H 卡／B 卡参数上限”。

> **实验 10-10 ★★：模型规模与训练完成期限**
>
> 综合前题，分别为具体 Qwen／V4 任务及 1T／5T／10T Dense 教学情景计算 A100、H100、B200 的完成时间。扫描卡数、数据量、MFU 与 90／180 天期限，检查逐卡状态、并行规模、供数和恢复，再比较满足质量目标的总成本；用公开训练记录校准计算口径。
>
> 加一份成组分配、启动、保存和故障记录，计算高分配率下的实际训练进展；固定工作量后，比较优先改善内核、恢复还是资源就绪的完成时间收益，不能直接相乘各作业平均百分比。
>
> 条件：进阶·方案推算／公开训练记录。
