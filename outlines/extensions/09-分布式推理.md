## 9.2 PD：阶段分离与 KV 交接

从同一套服务里 prefill 与 decode 互相干扰的现象进入，提出 A100 承担 prefill、H20 承担 decode 的具体方案。沿阶段性能、KV 交接与资源配比判断它在什么请求下值得采用。

<a id="detail-9.2.1"></a>

### 9.2.1 Prefill 与 Decode 的资源冲突

从第 8 章混合执行的冲突进入 DistServe／Splitwise，比较更好调度与独立资源池两条改进路线。接回第 6 章的切分：同样两张卡，单请求较快的 TP，在负载增加后未必比均衡 PP 的平均完成时间短。用[简化排队算例](../../case-studies/chunking-and-state-transfer.md)选候选，再按 prefill／decode 的实际请求分布决定并行与池规模；均值推算不能替代尾延迟验证。

实验入口采用 SGLang 的 PD 服务与实际 KV 传输后端，或固定 vLLM 的分离式 prefill connector。推理引擎安排请求，Mooncake／NIXL 等承担相应数据通路，不能把传输库当成完整服务。先检查两端模型、KV 格式和设备支持，再选择能运行的组合；A100＋H20 的硬件推算与特定版本是否支持这一部署分别记录。

承接第 3 章的 ServeGen 案例，用论文中的 vLLM 实例规划和 SGLang PD 评估说明为什么配比依赖请求组成及其时间变化。保留其 Qwen2.5／A100／H20 历史设置，只借用检验方法；本章的 Qwen3 与 V4 候选配置按自身负载重新计算。

再把第 3 章的视觉输入接到 PD 之前：用 vLLM 2025 EPD 与 SGLang 2026 EPD 比较编码共置、独立 E→PD、E→P→D。沿第 3 章定义的同一 Qwen3-VL-4B 截图算 EC 交接及其后产生的 KV；编码阶段可独立选择并行方式，单图与多图、缓存命中和视觉突发分别判断。公开 4／5／6 卡成绩保留资源差异，不能把额外卡数的收益全部归给分离。

<a id="detail-9.2.2"></a>

### 9.2.2 阶段能力与异构设备配比

案例采用 A100 80 GB SXM 做 prefill、H20 SXM5 96 GB 做 decode。先分别看两卡在相同模型、精度和请求形状下的两个阶段，再决定是否这样分工；两池都执行 attention 和 FFN，也都需要相应模型权重。比较共置、同构 PD、A100→H20 异构 PD 与角色互换。先用 Qwen3-8B 的实际 KV 与两个阶段工作量计算，再换 Qwen3-235B／V4-Flash 的状态和专家路径；增加前缀命中、reasoning 输出或 batch 后重新选择角色与池规模。H20 未取得的精确规格保留未知，阶段效率用相应 GEMM 与请求测量校准。

<a id="detail-9.2.3"></a>

### 9.2.3 KV 交接与收益边界

**占位 TC-14：** 补 PD 分离、专家通信与异构资源对成本的影响及交接代价。 详见[成本下降调研](../../research/token-cost-2023-2026/report.md#serving)。

把实际模型的 KV 大小、传输路径、格式转换、双份暂存与两侧排队纳入完整请求。Qwen3-8B 在 8K 长度的 BF16 KV 为 1.125 GiB；原有 1 GiB 教学算例用于检查算术，随后全部代入模型值。按请求吞吐求池配比，画出分离开始值得的位置。

先沿案例算一笔 KV：同构 GQA 的 32 层、8,192 token、8 个 KV 头、128 维、每元素 2 byte，得到 1 GiB。人为给定有效单向带宽 25 GB/s，仅载荷传输约 42.95 ms；再加格式转换、接收缓冲与排队。这是条件式计算，不能标成 A100／H20 的实测。沿真实 PCIe／NIC／RDMA 或 host staging 路径计算，不能假定跨代设备直接通过 NVLink 互联。

两侧能力都换成相同请求分布下的 requests/s，检查 `到达率 < min(P 池服务率, D 池服务率, 共享链路带宽 / 每请求平均 KV 字节)`，再扫描池配比与延迟。不能拿两种 token/s 直接相除当设备配比。首 token 的产生位置、后续间隔和完整请求时间分别比较，部分 KV 与计算重叠时只累加暴露的等待。

将 Qwen3 的 1.125 GiB KV 代入假设有效单向带宽 11 GB/s：独占传输下界约 110 ms，8 requests/s 需约 9.66 GB/s，16 requests/s 则需约 19.33 GB/s。前者满足平均速率条件也不表示没有可见等待，后者即使两池有空闲算力仍会积压；接收完成前的双端状态也要占用容量。

> **实验 9-2 ★：A100＋H20 的 PD 分离**

## 9.3 AF：移动权重还是就地计算

AF 指 attention／FFN 的分工。本节从 KTransformers 的同机 CPU／GPU MoE 执行讲起，再推到跨机 AF 池化；每一步都先确定哪些算子与状态在哪里，再算需要来回交接多少次。

<a id="detail-9.3.1"></a>

### 9.3.1 专家驻留与算子放置

从 MoE 总参数与激活差异进入 KTransformers：对照“把专家权重搬到 GPU”和“让 CPU 使用本地 DRAM 就地计算专家”。画清 attention、路由、共享／路由专家、其余 dense 层与 KV 的放置；热点专家可能驻留 GPU，prefill 与 decode 也可能采用不同配置。由此解释 AF 的切分位置，不能把一个项目概括为所有 attention 永远在 GPU、所有 FFN 永远在 CPU。

结合 SGLang 2025 年的 KT 集成预览与当前 wrapper，把框架分工落实为提交 CPU 专家、并行执行 GPU 专家、同步合并结果。它与第 8 章的 GPU 权重预取分别计算；CPU 专家使用的格式、线程和物理专家映射也进入记录。[执行路径与算例](../../case-studies/weight-offload-execution.md)连接容量和实际服务能力。

<a id="detail-9.3.2"></a>

### 9.3.2 CPU 就地计算与 NUMA

以固定版本公开文档的 RTX 4090 24 GB＋双路 Xeon Gold 6454S 为主案例，解释 AMX／AVX-512、专家打包、内存通道、线程绑核与 NUMA。先按每专家 token 数比较矩阵—向量和矩阵—矩阵的复用，再判断省下的 PCIe 权重流量是否值得付出 CPU 计算和 DRAM 读取。SOSP 论文的双 8452Y＋A100／4080 实验作为另一组证据，不能移作这台主案例机器的性能。

### 9.3.3 逐层交接与阶段交接

用 MegaScale-Infer（2025）的 ping-pong pipeline 作跨机 AF 的具体案例：将请求批次分成微批，在 attention 与专家节点之间交错执行。先按两侧计算时间和往返激活流量判断能否形成稳定流水，再算微批数量、填充排空与小矩阵损失；不把 KTransformers 的同机路径和这套分布式实现合并成一个系统。

对照 AF 与 PD 的时序，比较反复交接激活和一次请求 KV 交接；把同机协作延伸到跨机 attention／FFN 池化时重新核算启动、带宽和同步。

用简化的 32 层、单 token、宽度 4,096、每元素 2 byte 算例：每层完整激活送出一次、合并结果返回一次，每步总载荷 0.5 MiB，却有 64 次有方向的交接。先算 `64 × 启动与同步时间 + 载荷 / 带宽`，再代入 Qwen3／V4-Flash 的真实层数、专家路径与切分位置修正。将同机 PCIe 换成跨机网络，判断新增启动是否已经超过期限，再考虑压缩、流水和聚合；不把少字节直接理解成低开销。

### 9.3.5 并发增长与专家复用

## 9.4 专家放置与共享资源

<a id="detail-9.4.1"></a>

### 9.4.1 路由倾斜与设备负载

分别使用 Qwen3-235B 和 V4-Flash 的路由记录，把 top-k、专家宽度、共享专家及批内复用代入每卡和每链路工作。相同请求数下找最忙的设备，解释平均激活参数为何不足以预测完成时间。

接回 6.3 的独立活跃专家数：访存受限的 decode 可能因路由集中而少读权重，计算受限的 prefill 则可能因集中而等待最忙卡。先判断阶段瓶颈，再选择均衡目标；宽 EP 下 decode 的逐卡载荷仍需检查。

<a id="detail-9.4.2"></a>

### 9.4.2 专家复制与 token 迁移

比较专家复制、放置、迁移和调度，计入额外权重与更新成本。将负载变化放进同一实验，看静态最佳安排何时失效。

以 vLLM／SGLang 的 EPLB 连接路由统计、逻辑专家到物理副本的映射，以及热点专家复制。保持模型的逻辑 top-k 语义；复制相同权重的专家与修改模型路由规则不是一回事。负载观察窗口过短可能频繁迁移，过长又跟不上变化。

用 CRAFT（MLSys 2026）引出逐层副本预算：不同层的倾斜程度和复制收益不同，新增专家又会挤占 KV。Qwen3-235B 若每卡每层多放一个 BF16 专家，94 层合计约 3.305 GiB／卡；把预算集中给少数层后，是否能达到相同服务目标，要用路由和时间记录判断。论文基于 SGLang v0.4.8 的 R1／Kimi K2 实验作历史对照，当前引擎支持的放置能力单独核对。

再区分已有副本间的分派与权重重排。用 SGLang 2026 的 LPLB／Waterfill 说明当前 batch 的均衡自由度：同一个 Qwen3 单层练习，最忙设备从 640 行降到 512 行，究竟腾出多少时间给统计、求解和额外通信？共享专家另按 V4 路径计量。随后用 288 MiB 的迁移预算判断热点持续多久才值得重排；[完整推算与版本边界](../../case-studies/expert-dispatch-and-resizing.md)保留在实验材料。

<a id="detail-9.4.3"></a>

### 9.4.3 Grouped GEMM 与计算通信重叠

沿一次 MoE 层展开路由、排列、dispatch、grouped GEMM 和 combine，按每专家 token 数算矩阵形状。举八个本地专家分别收到 32、16、8、4、2、1、1、0 个 token 的教学输入：实际 64 个专家 token，全部补齐到 32 则执行 256 行。由此比较 padding、变长分组和 persistent 调度；合成一个 kernel 能减少提交，但不能自动消除长尾专家或 tile 的浪费。

同一输入若只对非空专家按 32 行块补齐，则为 224 行。把后端的实际补齐规则放回第 5 章的算力和访存估算，比较有效工作与执行工作，不把 grouped GEMM 当作已经消除 padding 的保证。

用 vLLM DBO、SGLang TBO／SBO 和 DeepEP 的真实执行图，比较两微批交错、共享专家与通信重叠。沿 SGLang 从 H100 多机到 GB200 NVL72 的[历史选择](../../case-studies/resource-sharing-and-placement.md)，解释通信缩短后为何需要重新权衡切分损失与更细粒度的重叠。当前 Qwen3 MoE 的 prefill 与 decode／验证也有不同操作顺序和资源预算；图模式、后端及缓冲一起核实，不能只按独占时间的 max 承诺收益。

> **实验 9-6 ★：热门专家的放置与复制**
>
> 在固定 vLLM 或 SGLang 的受支持 MoE 配置中收集每专家 token 数及 dispatch／GEMM／combine 时间；先用 Qwen3 MoE 的实际形状算热点与 padding，再分别改变 EPLB、grouped GEMM 后端和 DBO／TBO。比较最忙设备、暴露通信、额外权重、缓冲及请求尾延迟；V4／K3 用已核实后端记录复算，不能将不支持的选项组合列作可运行命令。
>
> 副本变体在同一显存预算下比较各层平均分配与按收益分配，计算剩余 KV 能承接的请求，再扣除重排和迁移。原生引擎无法表达的逐层方案只做离线路由复算，不能写成已实现的配置开关。
>
> 分派选做比较已有副本的均分与负载分配，再扣除全局统计和求解。Qwen3 用于离线矩阵计算；固定 SGLang 的 LPLB 实测采用其明确支持的模型，V4 Waterfill 单独验证。保持逻辑路由，记录实际副本行数、目的设备数和长输出时延，不能把单输出 token 的 total throughput 当作 decode 吞吐。
>
> 重叠变体保持路由与精度，比较独占、仅切分、实际交错三种记录；从 trace 检查通信就绪、GPU 提交顺序和资源争用，解释某个内核变慢后整层是否仍然更快。
>
> 条件：基础·轨迹分析。

## 9.5 KV 的层次、身份与复用

接着作者 UB 文章中“先设想内存池，后来遇到 KV cache 应用”的经历，把第 6 章的容量借用、第 7 章的远程访问落实到推理服务。Mooncake／LMCache 提供软件 KV 池的实例，UB 提供另一类访问和资源管理机制，分别分析各自路径。

<a id="detail-9.5.1"></a>

### 9.5.1 缓存层次与访问方式

以 SGLang HiCache 与 LMCache 的真实后端作为 HBM、主机和外部存储的实验入口：分别记录写入、预取、命中和淘汰，而不是仅画一个内存池方框。2026 年 Unified Radix Cache 把混合模型状态接到这些层次；沿 V4 的压缩／窗口与 K3 的循环状态重新核算有效边界。

沿 HiCache 从 2025 公告到当前实现，明确单实例私有的 host 层与按后端配置共享的存储层。再用 vLLM 从异步 connector、CPU offload 到当前多级后端作对照；其原生路径先经过 CPU，不能由“远端存储”推断 GPU 直读。缓存容量、共享范围和数据通路分别落到实际部署。

用 HiSparse（2026）的 DSA 案例补充另一种问题：本步选中的 KV 很少，完整历史容量却仍然很大。比较按需从主机取回与 HBM 热缓冲，计算低并发时的额外 IO 和高并发时释放容量的收益；这是其已披露 DSA 路径，不能直接假定适用于 V4 的全部压缩层或 K3 的状态。

沿 Qwen3-8B／235B 的两个实例反复处理同一 Agent 前缀，比较本地 HBM、主机 DRAM、本地 SSD 和远端缓存池。逐层计算容量、访问带宽、启动延迟、块大小与排队；热的活跃 KV 与等待复用的冷前缀采取不同放置。Mooncake／LMCache 提供软件层次与共享实例，UB 的硬件访问语义另行对应。

沿用 1 GiB 前缀和 25 GB/s 条件式算例：取回一次的纯传输下界为 42.95 ms；假定每个 decode 步都要从远端读取这份不变前缀，生成 100 token 至少累计约 4.295 s 的链路服务时间，另计增长中的 KV。与一次本地 prefill 重算和搬回本地继续生成比较，解释远端容量能否成为活跃 KV 的供数来源；有重叠或分片时按每条链路和依赖重算。

接回第 5 章的布局：Qwen3-8B 的 16-token BF16 块，按声明布局可拆成 72 个 32 KiB 连续段，也可组织成一个 2.25 MiB 连续块。有效载荷相同，再比较 DMA、搬运 kernel、布局转换与并发计算争用；[完整推算](../../case-studies/cache-tiers-and-routing.md)与实验使用同一配置。

> **实验 9-7 ★：共享 KV 池的命中收益**
>
> 复用远端 KV 何时比本地重算更合适？ 两个实例交替服务同一 Agent，比较本地重算、一次取回并驻留、每步远程访问三条路径。按前缀大小、命中间隔、带宽、重算时间与 HBM 占用求收益边界；增加池写入和回收后，检查 PD 交接是否仍有收益。
>
> 采用 SGLang HiCache＋Mooncake 或 vLLM＋LMCache 的受支持部署收集实际字节和命中时间；每步远程读取作为明确的对照模型，不假定引擎默认如此执行。
>
> 预取变体用 HiCache 的 best_effort／wait_complete／timeout，对比实际完成的连续前缀、放弃的传输和重算；另以固定 vLLM 原生 KV offload 对照 CPU 中转。布局和 IO 后端仅比较受支持组合，独立拷贝与并发服务分别计时。
>
> 条件：基础·手算／请求重放。

视觉变体用 SGLang 的全局 embedding cache 说明另一类状态：命中 EC 可以省 ViT，仍可能要取回并发送完整特征，再执行语言 prefill。当前指南将 encoder 传输后端和全局 EC 缓存分开配置；沿内容、预处理、模型版本与前缀位置检查 EC／KV 的不同身份，不能把两种命中收益重复相加。

<a id="detail-9.5.2"></a>

### 9.5.2 持久化与多级命中

以 DeepSeek-V4 的 on-disk KV 为例，说明缓存怎样跨请求、模型实例重启或任务暂停保存。CSA／HCA 的压缩条目、SWA 的窗口状态和不完整压缩块分别处理；全量保存、周期检查点与部分重算具有不同的写入、读取和恢复成本。缓存身份包含模型版本、adapter、位置与格式，过期或不兼容状态不能直接复用。

给定复用间隔和请求长度分布，分别计算 HBM／DRAM／SSD／远端的命中收益、写入字节与取回时间。高命中率不保证低延迟，SSD 小块访问与写放大也不同于持续带宽；把后台存储、预取与用户关键路径分开，比较留存、迁移和重算。

> **实验 9-8 ★★：持久化与多级 KV 的取舍**
>
> 使用同一组 Agent 轨迹，扫描 HBM、DRAM、SSD 与远端容量；比较全量保存、周期检查点和重算。依据 V4 的压缩与窗口状态计算每次写入／取回及必要重算，加入重启恢复和缓存失效，报告命中率、p95 取回时间、写入量与任务完成时间。
>
> 使用 SGLang HiCache 或 LMCache 的固定存储后端记录卸载、预取、恢复和淘汰，持久化能力按后端版本验证。
>
> 条件：进阶·请求重放／存储记录。

### 9.5.3 缓存亲和性与负载路由

从两次同前缀请求引出缓存亲和与负载均衡的冲突，比较原实例排队、新实例重算和跨池取回的完成时间。Preble、SGLang 与 Mooncake 作设计对照；命中率、复用间隔和正在占用的显存决定选择。

用同一 Qwen3 的 8K 前缀给出具体选择：在声明的队列与串行取回假设下，原实例 HBM 命中约 260 ms，空闲实例重算约 200 ms；远端有效带宽从 5 改为 20 GB/s，取回方案从约 310 降到 129 ms。先画状态就绪与 GPU 等待的依赖，再增加共享链路负载，说明单请求的选择何时失效。数字是教学输入，[算例](../../case-studies/cache-tiers-and-routing.md)不冒充框架成绩。

对照 SGLang 2024 的近似缓存树与固定当前 Model Gateway：已读策略依据文本匹配和负载阈值，并未直接预测上述完成时间。区分 router 预计命中、worker 的实际 token 命中和 KV 所在层级，实验检查过期信息怎样改变选择。

再沿 vLLM 的 KV events、SGLang HiCache 与 Dynamo 的实际集成，解释缓存怎样成为路由依据：拷贝完成才报告新位置，GPU 淘汰后 CPU 副本可能仍在，事件缺失则需恢复索引。用同一前缀把 A 的队列改为 80 ms，计算有效命中时的 90 ms 与全部失效后的 260 ms；即使平均值优于 B 的 200 ms，尾延迟也可能不合格。由此区分缓存层级的评分权重、命中概率和实际取回时间。Agent 并发分支还会先于缓存发布到达，短期预测可帮助聚集请求，但不能保证前缀已经可用；[扩写依据](../../case-studies/cache-events-and-routing.md)保留版本与计算条件。

> **实验 9-9 ★★：缓存亲和性与完成时间**
>
> 该去有缓存的机器，还是空闲机器？ 从 Chat 和 Agent 的多轮记录提取缓存 token 数、复用间隔、队列和远程取回耗时；比较队列优先、缓存优先和预测完成时间路由。命中率同时按请求与 token 加权统计，报告命中层级和 p95 取回时间。
>
> 以 SGLang 的缓存感知 router 连接两个真实 worker，逐项改变前缀亲和与负载策略。
>
> 先复算 260／200／310／129 ms 的条件式选择，再重放真实记录；加入 worker 淘汰或重启，核对路由预测与实际命中的偏差。预测完成时间方案先做离线比较，不将其写成原生 router 已有的开关。
>
> 选做：在一种经版本核对的 Dynamo＋vLLM 或 SGLang 集成中记录缓存事件，区分 GPU 淘汰、CPU 仍有副本与全部失效。离线重放时延迟或丢弃一段事件，比较恢复前后的判断；复算 90／260 ms 的两点分布，说明平均收益为何不足以保证 p99。检查 Agent 同前缀分支在首次发布前的重复 prefill，不要求同时部署两套后端。
>
> 条件：进阶·计算／真实系统记录，可选多实例部署。

## 9.6 服务寿命、重配置与恢复

<a id="detail-9.6.1"></a>

### 9.6.1 流式输出与部分故障

区分普通交互、Agent 续接与 RL rollout 的恢复目标。依据 DeepSeek-V4 的 token 级 WAL 与 KV 保存机制，比较继续 decode、用已生成 token 重做 prefill，以及重新采样的差别；最后一种会改变输出和采样分布。计算不同故障下的重做工作、缓存访问和已经交付结果的处理，第 10 章再分析训练影响。

**占位 D14-04：** 沿实际 DP／TP／EP 分组追踪单 rank 故障影响的请求、同步操作与状态，以原始记录或受控注入比较检测、重建、首个有效 token 和积压消退；将故障范围与恢复策略放回实验 9-10。详见[EP 服务故障验证](../../research/draft14-15-outline-audit/report.md#failure)。

用 Llumnix 的计划迁移解释另一条路径：先复制不再改变的历史 KV，生成继续，最后暂停并追平新增状态；分别计算完整复制与暂停时间。源端仍可配合迁移，与实例突然失效的恢复条件不同。换成 V4／K3 时要检查可变压缩状态、窗口和循环状态的一致交接点，不能仅凭 KV connector 就认定请求可以热迁移。

<a id="detail-9.6.2"></a>

### 9.6.2 异构推理的部署取舍

回到同一模型和请求集，把 A100＋H20 的 PD、KTransformers／跨机 AF 和有无共享 KV 池放进完整部署，再与副本、TP／PP、EP 的候选组合比较容量、质量、延迟、费用及恢复。让原来的“选哪张卡”变成可检验的系统选择。

以 vLLM 的启动记录补齐服务寿命：分开看 CPU 初始化、权重读取、编译缓存、KV 探测与 CUDA Graph 捕获，计时按依赖关系避免重复相加。先算增加准备时间换来的稳态节省需要多少执行步才能抵消，再计入扩容期间的队列与热副本费用。MLSys 2026《Breaking the Ice》的 v0.10.1.1 实验作为历史参照；新版本用 Qwen3-8B 重测，权重页缓存与编译缓存的冷热分别记录。

沿 vLLM 2024／2025／2026 的 ShardedStateLoader 比较普通权重加载与部署专用的预分片：每 rank 读取自己的文件可以减少重复读取，但改变 TP 后仍需匹配的新布局。它保存模型状态，不包含优化器、请求 KV 与环境；第 10.4 节再讲可重分片的完整训练检查点。把文件转换成本、冷热页缓存、存储吞吐和新副本就绪时间一起计算，具体证据见[检查点布局与加载](../../case-studies/checkpoint-layout-and-loading.md)。

用 vLLM 2026 Elastic EP 把启动接到运行中的扩缩容：Qwen3-235B 的 BF16 routed 权重从 8 rank 均分到 16 rank，新设备需接收多少数据？再计入建组、非专家权重、图重新准备和队列。缩容先检查剩余权重与 KV 容量；专家迁移不代表请求 KV 已交接，暂停、排空与上层策略分别从记录确认。

以 TriInfer 的阶段 profiling 与历史重放补一个视觉配比判断：在同样四张卡下比较 1E＋3PD 和 2E＋2PD，按未缓存图像数、语言工作与完整 EC 流量找最早的瓶颈。命中率改变后再选配比，并计入分钟级重配和启动；论文的旧共置基线不代表当前框架缺少 EPD。[算例与版本](../../case-studies/multimodal-stage-placement.md)与实验 12-3 使用相同图像形状。

> **实验 9-10 ★★：异构推理的完整部署**
>
> 你会怎样部署这个模型服务？ 综合 A100＋H20 的 PD 分离、KTransformers 的 AF 分离与共享 KV 池三项案例，按 Chat、Agentic、Real-time 请求选择硬件、切分和路由。加入 reasoning 长输出、计划迁移与实例失效，先列可恢复状态和交接条件，再算服务目标与成本；说明哪些组合值得进一步实测。
>
> 方案至少给出一个已核实的引擎＋传输／缓存后端组合及对应运行记录，部署命令与算术输入随实验提供。
>
> 启动变体用同一 Qwen3-8B 配置比较缓存未命中、命中和不同图捕获规格；保留引擎就绪、首请求完成与积压消退三个时间点。若额外准备 10 秒、每执行步省 0.2 ms，先算 50,000 步的抵消门槛，再由真实 batch 和实例寿命判断；教学值不当作框架实测。
>
> 权重加载变体固定 Qwen3、精度和 TP，比较普通文件与预分片文件的实际读取、转换准备与首次就绪时间；修改 TP 时先检查格式与分片兼容性。和训练恢复实验共用张量坐标，不将推理权重文件当成完整训练检查点。
>
> 视觉配比变体用固定 vLLM 或 SGLang EPD，先比较相同卡数，再单独增加 E；扫描每请求图像数和 EC 命中，记录 EC／KV 实际交接、图模式及阶段尾延迟。用短时图片突发检验历史配比与重配期间积压；TriInfer 原论文与当前框架分别作证据。
>
> EP 扩缩容选做沿受支持的小型 MoE 或配套记录，标记新组准备、权重移动、图准备与请求恢复；先用 Qwen3 预算判断瓶颈，再用实际配置校准，不能把前述 DBO／图模式开关无条件组合。
>
> 条件：进阶·综合设计；可选多设备。
