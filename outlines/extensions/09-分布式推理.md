## 9.1 从单实例到分布式服务

第 8 章已经给出调优后的单实例服务。请求继续增加时，先比较增加完整副本，再判断阶段分离与共享状态是否值得；每个实例内部沿用第 6、7 章的并行与通信条件。

### 9.1.1 共置服务基线与扩展需求

沿用第 6、7 章已经推算的 TP／PP／DP／EP 组合、具体硬件与请求，不再重新介绍并行方式。采用第 8 章相同的长度分布、前缀命中、质量和到达率，先求共置服务率与首 token／逐 token 时间。再把模型换成 Qwen3-235B 和 V4-Flash，按实际 attention／专家形状复算；基础参数见[业务推算笔记](../../case-studies/inference-training-scenarios.md)。

<a id="detail-9.1.2"></a>

### 9.1.2 完整副本、阶段分离与状态共享

增加完整副本可以承接更多独立请求；PD 与 AF 改变计算分工，共享 KV 改变历史状态的保存与复用范围。先把三种动作放到同一组资源与服务目标下比较，避免在尚未确定瓶颈时就选定分离方案。

用阶段性能、交接字节、访问频次、缓存命中与服务目标建立基线收支，再分别考察 PD、AF 和缓存层次。容量够用、请求足够长或命中率高都只是部分条件；后文每项优化都要与同一基线比较。

## 9.2 PD：阶段分离与 KV 交接

先理解分离的动机和 KV 交接，再配置两池的服务能力。同构 PD 也可能改善调度；A100＋H20 是否合适由两阶段实测能力及请求组成决定。

<a id="detail-9.2.1"></a>

### 9.2.1 Prefill 与 Decode 的干扰及分离动机

从第 8 章混合执行的冲突进入 DistServe／Splitwise，比较更好调度与独立资源池两条改进路线。接回第 6 章的切分：同样两张卡，单请求较快的 TP，在负载增加后未必比均衡 PP 的平均完成时间短。用[简化排队算例](../../case-studies/chunking-and-state-transfer.md)选候选，再按 prefill／decode 的实际请求分布决定并行与池规模；均值推算不能替代尾延迟验证。

实验入口采用 SGLang 的 PD 服务与实际 KV 传输后端，或固定 vLLM 的分离式 prefill connector。推理引擎安排请求，Mooncake／NIXL 等承担相应数据通路，不能把传输库当成完整服务。先检查两端模型、KV 格式和设备支持，再选择能运行的组合；A100＋H20 的硬件推算与特定版本是否支持这一部署分别记录。

承接第 3 章的 ServeGen 案例，用论文中的 vLLM 实例规划和 SGLang PD 评估说明为什么配比依赖请求组成及其时间变化。保留其 Qwen2.5／A100／H20 历史设置，只借用检验方法；本章的 Qwen3 与 V4 候选配置按自身负载重新计算。

再把第 3 章的视觉输入接到 PD 之前：沿 vLLM v0.11.1 的 EC transfer 到当前固定 connector，对照 SGLang 2026 EPD，比较编码共置、独立 E→PD、E→P→D；传输接口的出现与完整阶段服务的支持分别核对。沿第 3 章定义的同一 Qwen3-VL-4B 截图算 EC 交接及其后产生的 KV；编码阶段可独立选择并行方式，单图与多图、缓存命中和视觉突发分别判断。公开 4／5／6 卡成绩保留资源差异，不能把额外卡数的收益全部归给分离。

<a id="detail-9.2.2"></a>

### 9.2.2 KV 交接路径与双端驻留

沿用 Qwen3-8B 的同一请求，把 KV 大小、传输路径、格式转换、双端驻留与两侧排队纳入完整预算。按请求吞吐求池配比，画出分离开始值得的位置。

先沿第 2 章的模型账复算 KV：36 层、8,192 token、8 个 KV 头、128 维、BF16，得到 1.125 GiB。人为给定有效单向带宽 25 GB/s，仅载荷传输约 48.32 ms；再检查启动、格式转换、接收缓冲与排队。这是条件式计算，不能标成 A100／H20 实测。实际 PCIe／NIC／RDMA 或 host staging 路径另核，不能假定跨代设备直接通过 NVLink 互联。

<a id="detail-9.2.3"></a>

### 9.2.3 阶段能力、设备选择与池配比

案例采用 A100 80 GB SXM 做 prefill、H20 SXM5 96 GB 做 decode。先分别看两卡在相同模型、精度和请求形状下的两个阶段，再决定是否这样分工；两池都执行 attention 和 FFN，也都需要相应模型权重。比较共置、同构 PD、A100→H20 异构 PD 与角色互换。先用 Qwen3-8B 的实际 KV 与两个阶段工作量计算，再换 Qwen3-235B／V4-Flash 的状态和专家路径；增加前缀命中、reasoning 输出或 batch 后重新选择角色与池规模。H20 未取得的精确规格保留未知，阶段效率用相应 GEMM 与请求测量校准。

<a id="detail-9.2.4"></a>

### 9.2.4 不同请求与负载下的收益边界

两侧能力统一换算为同一请求分布下的 requests/s，再检查计算、链路与缓冲约束。扫描输入／输出长度、前缀命中、到达率和池规模，用 TTFT、ITL 与 SLO 内有效吞吐判定收益。

**占位 TC-14：** 补 PD 分离、专家通信与异构资源对成本的影响及交接代价。 详见[成本下降调研](../../research/token-cost-2023-2026/report.md#serving)。

两侧能力都换成相同请求分布下的 requests/s，检查 `到达率 < min(P 池服务率, D 池服务率, 共享链路带宽 / 每请求平均 KV 字节)`，再扫描池配比与延迟。不能拿两种 token/s 直接相除当设备配比。首 token 的产生位置、后续间隔和完整请求时间分别比较，部分 KV 与计算重叠时只累加暴露的等待。

将 Qwen3 的 1.125 GiB KV 代入假设有效单向带宽 11 GB/s：独占传输下界约 110 ms，8 requests/s 需约 9.66 GB/s，16 requests/s 则需约 19.33 GB/s。前者满足平均速率条件也不表示没有可见等待，后者即使两池有空闲算力仍会积压；接收完成前的双端状态也要占用容量。

**已复算（C47-pd-pool）：** [整数池配比](../../calculations/results/pd-pool-book.md)以官方Qwen8、8192输入／129输出统一请求口径：P处理8192新token，首输出来自prefill，D仅调用128次。两类教学副本各4个，P/D有效token每秒分别16384/64和4096/256，枚举25配比，4个前者给P、4个后者给D时上界8请求/s；共置逐副本加资源秒后为3.2请求/s。[同构对照](../../calculations/results/pd-pool-homogeneous.md)分池与共置均4请求/s；[网络限制](../../calculations/results/pd-pool-network.md)按每请求1207959552bytes将上界限至1请求/s，到达率等于上界不标为严格低于。[命中6144前缀](../../calculations/results/pd-pool-prefix.md)只减少P新工作，D冷缓存仍收完整KV，最佳P配比降至2个、上界9请求/s；[1025输出](../../calculations/results/pd-pool-long-output.md)最佳P仅1个、D为7个，上界19/16请求/s。[仅首输出](../../calculations/results/pd-pool-first-output.md)无需D或KV交接。运行 `python3 calculations/calc.py pd-pool --format md`，`--inputs`可输入实际阶段能力。上述为有效服务能力教学假设，不代表A100/H20测量；副本放置可行性、混跑干扰、排队和SLO须另核，枚举最优只对本候选成立。

## 9.3 AF：算子分工与逐层交接

先画算子分工，再完整分析同机 CPU／GPU 协作，最后推进到跨机 AF。逐层激活交接与 PD 的阶段交接具有不同的频次和依赖。

<a id="detail-9.3.1"></a>

### 9.3.1 Attention、FFN 与专家的执行边界

AF 指 Attention／FFN 的分工。先画 attention、路由、共享与路由专家、其他 dense 算子及 KV 的执行位置：权重驻留在何处，激活跨哪条边往返，谁必须等待返回结果。KTransformers 用于说明同机异构放置，跨机 AF 的网络与同步条件在 9.3.4 单独核算。

<a id="detail-9.3.2"></a>

### 9.3.2 CPU／GPU 协作：搬权重还是搬激活

从 MoE 总参数与激活差异进入 KTransformers：对照“把专家权重搬到 GPU”和“让 CPU 使用本地 DRAM 就地计算专家”。画清 attention、路由、共享／路由专家、其余 dense 层与 KV 的放置；热点专家可能驻留 GPU，prefill 与 decode 也可能采用不同配置。由此解释 AF 的切分位置，不能把一个项目概括为所有 attention 永远在 GPU、所有 FFN 永远在 CPU。

结合 SGLang 2025 年的 KT 集成预览与当前 wrapper，把框架分工落实为提交 CPU 专家、并行执行 GPU 专家、同步合并结果。它与第 8 章的 GPU 权重预取分别计算；CPU 专家使用的格式、线程和物理专家映射也进入记录。[执行路径与算例](../../case-studies/weight-offload-execution.md)连接容量和实际服务能力。

以固定版本公开文档的 RTX 4090 24 GB＋双路 Xeon Gold 6454S 为主案例，解释 AMX／AVX-512、专家打包、内存通道、线程绑核与 NUMA。先按每专家 token 数比较矩阵—向量和矩阵—矩阵的复用，再判断省下的 PCIe 权重流量是否值得付出 CPU 计算和 DRAM 读取。SOSP 论文的双 8452Y＋A100／4080 实验作为另一组证据，不能移作这台主案例机器的性能。

**已复算（C48-expert-reuse-threshold）：** [78行边界](../../calculations/results/expert-locality-boundary78.md)与[79行边界](../../calculations/results/expert-locality-boundary79.md)使用相同官方专家与教学能力，精确分段解CPU激活交接＋max(计算,权重读取)和GPU搬权重＋max(计算,权重读取)。CPU／GPU等时knee分别每专家10／100token；单个非驻留专家1–78token时CPU服务较小，79及以上搬权重GPU较小。全部正整数区间均已求解，末段无上界；等号单独保留，不靠有限扫描猜测长期趋势。[CPU有效能力200TF/s敏感性](../../calculations/results/expert-locality-fast-cpu.md)边界变为3225／3226，仍可能受激活交接限制，不是CPU产品性能声明。运行 `python3 calculations/calc.py expert-locality --format md` 查区间。这里只比较相同专家批及固定服务能力，非均匀专家负载、实际量化／NUMA／小矩阵效率仍需单独核对。

### 9.3.3 容量、并发与专家复用的服务边界

沿固定 KTransformers 文档还原 V4-Flash 的单 RTX 5090＋至少 200 GB 主存，以及 Kimi K2 Q4_K_M 的约 600 GB 主存＋14 GB 显存案例。先从完整权重放在哪里解释容量，再计算 CPU 实际专家工作、GPU attention、NUMA 与交接。Kimi K2 的证据不替代 K3；单卡与八卡 MTP 成绩分开引用。

保持模型和请求不变，将并发从 1 增加，统计批内专家集合、每专家 token 数和最忙 NUMA 节点。热点专家缓存与较长 prefill 的 GPU 分层执行会改变瓶颈；比较 CPU 就地计算、按需搬权重、混合驻留和全 GPU 服务，计算达到同一质量与延迟要求的负载范围。

沿 Qwen3-235B 的 128 个专家、top-8 和单专家 36 MiB BF16 矩阵，教学固定 32 个专家驻留 GPU：分别计算其余专家的不同权重数与 token—专家任务数。由单 token 到 2048-token prefill，CPU 可能从 DRAM 受限转为计算受限；用路由记录替换均匀假设后，再决定热点放置和两侧资源配比。

**已复算（C49-expert-locality）：** [专家就地与搬权重子账](../../calculations/results/expert-locality-book.md)按官方Qwen235的H4096、F1536、128专家／top8，gate/up/down每专家BF16共36MiB。每层固定ID0–31驻留占1.125GiB，94层合计105.75GiB，仅专家权重已不能放进单24GB卡；此驻留数是教学输入，需另做实际放置。128-token均衡路由的非驻留部分为96个不同专家、768个token—专家任务，权重3.375GiB、矩阵28991029248 FLOPs，逐assignment BF16激活往返12MiB。教学CPU2TF/s、DRAM200GB/s、GPU100TF/s、HBM1TB/s、链路25GB/s、启动5us，CPU子账19.582710ms、搬权重GPU149.059025ms；两者是声明路径的资源估计，非KTransformers实测。[2048-token prefill](../../calculations/results/expert-locality-prefill.md)、[单token无驻留](../../calculations/results/expert-locality-single.md)、[热点全命中](../../calculations/results/expert-locality-hot.md)、[8192token](../../calculations/results/expert-locality-long.md)检查复用与瓶颈变化。运行 `python3 calculations/calc.py expert-locality --format md` 查逐专家M/K/N；`--inputs`可输入128项counts。直方图缺token身份，因此明确按assignment交接，不推断跨专家去重。只计单层非驻留专家，量化／NUMA／激活访存／合并／不均衡与实际重叠仍待补。

### 9.3.4 跨机 AF、微批流水及与 PD 的比较

原 32 层教学控制保留在下列记录中；当前主线统一使用 Qwen3-8B 的 36 层，不混用两套输入。

**已复算（C48-pd-af-handoff）：** [PD／AF交接账](../../calculations/results/pd-af-handoff-book.md)复算32层教学模型：8K BF16 KV为1GiB，AF单步双向激活0.5MiB、64次消息。有效25GB/s、每hop启动5us，串行通信PD42.954673ms、AF0.340972ms；相同1GiB分成64次的对照只因启动多315us。启动增到1ms时AF64.020972ms大于PD43.949673ms，不能仅按载荷判断开销。[双端host staging](../../calculations/results/pd-af-handoff-staged.md)逐消息串行D2H→网络→H2D，各接口各算一次，双端GPU与host完整消息槽分列。[官方Qwen8](../../calculations/results/pd-af-handoff-qwen8.md)按36层得到1.125GiB KV、单步576KiB激活／72次；[Qwen235](../../calculations/results/pd-af-handoff-qwen235.md)另计B=4、128步。运行 `python3 calculations/calc.py pd-af-handoff --format md`，用 `--inputs` JSON修改长度、batch、步数、带宽与启动。PD一次请求快照与AF指定decode调用是不同交接范围，不能据此断言部署优劣；未含计算、排队、格式转换、MoE跨专家dispatch和流水重叠。

用 MegaScale-Infer（2025）的 ping-pong pipeline 作跨机 AF 的具体案例：将请求批次分成微批，在 attention 与专家节点之间交错执行。先按两侧计算时间和往返激活流量判断能否形成稳定流水，再算微批数量、填充排空与小矩阵损失；不把 KTransformers 的同机路径和这套分布式实现合并成一个系统。

## 9.4 MoE 服务：专家放置与负载均衡

AF 决定算子之间怎样分工，专家放置决定专家工作怎样分布到设备；两者可以组合。保持逻辑路由语义，检查最忙设备及副本占用。

<a id="detail-9.4.1"></a>

### 9.4.1 路由倾斜与最忙设备

分别使用 Qwen3-235B 和 V4-Flash 的路由记录，把 top-k、专家宽度、共享专家及批内复用代入每卡和每链路工作。相同请求数下找最忙的设备，解释平均激活参数为何不足以预测完成时间。

接回 6.3 的独立活跃专家数：访存受限的 decode 可能因路由集中而少读权重，计算受限的 prefill 则可能因集中而等待最忙卡。先判断阶段瓶颈，再选择均衡目标；宽 EP 下 decode 的逐卡载荷仍需检查。

### 9.4.3 Dispatch、计算与 Combine 的重叠

读取第六章的路由与逐卡工作，按第五章的方法核对后端实际执行量。八个本地专家收到 32、16、8、4、2、1、1、0 个 token，共 64 个有效专家 token；全部补齐到 32 是 256 行，仅非空专家补齐则为 224 行。保留这一反例，避免把 grouped GEMM 当作已经消除 padding 的保证。

**已复算（C49-grouped-experts）：** [逐专家tile账](../../calculations/results/grouped-experts-book.md)按官方Qwen235单层128token／top8，均衡时128专家各8行。独立64×32×128 tile完全补齐，有效38654705664F、补齐309237645312F（8倍）；8rank工作均衡仍不能消除小M浪费。[集中路由](../../calculations/results/grouped-experts-concentrated.md)只激活8专家、各128行，无M padding，但连续放置让全部工作落在rank0；[相同路由交错放置](../../calculations/results/grouped-experts-striped.md)保持总工作与接口字节不变，最忙rank工作降至八分之一。[2048token](../../calculations/results/grouped-experts-prefill.md)与[8行tile](../../calculations/results/grouped-experts-small-tile.md)另列复用变化。运行 `python3 calculations/calc.py grouped-experts --format md`，JSON保留逐专家gate/up/down的M/K/N与分块载荷；权重按M块重读、输入按N块重读，边界只读有效元素，不能用FLOPs padding倍数放大bytes。此为指定output-stationary工作缓冲接口，非HBM实测；后端跳过无效指令、通信、融合、设备能力与真实重叠尚未计。

## 9.5 共享 KV：状态复用与请求路由

<a id="detail-9.5.1"></a>

### 9.5.1 缓存身份、共享范围与可用状态

从两个实例接续同一 Agent 请求开始，先定义可复用状态的身份：模型与 adapter 版本、token 前缀与位置、状态格式及必要的编码配置必须兼容。目录里存在文件、预测会命中和请求实际读到有效状态分别检查；发布位置须晚于拷贝完成，淘汰、失效与回收必须更新可用范围。

<a id="detail-9.5.2"></a>

### 9.5.2 多级存储：取回、驻留还是重算

增长中的远端 KV 延伸计算（原实验 6-9 资料，当前在本节展开）：

**已复算（C36-growing-kv）：** [增长KV全部远端](../../calculations/results/growing-kv-qwen8-all-r1.md)按已产生P=8192位置、G=128次单token追加，旧历史读取为G×P+G(G−1)/2，当前位置操作数另列；初始化复制、每步读一个副本和向全部副本写入分开。[两副本](../../calculations/results/growing-kv-qwen8-all-r2.md)增加初始化与追加发送、不增加旧历史读取；声明同一发送接口串行、全副本提交后下一步才使用新epoch。[固定远端前缀/本地增长tail](../../calculations/results/growing-kv-qwen8-prefix-r1.md)免去tail的远端重读和副本写入，却新增本地tail容量。[Qwen3.6](../../calculations/results/growing-kv-qwen36-all-r1.md)只把10层完整attention的20KiB/位置算作历史，30层递推/卷积固定状态留本地，不能与Qwen8的144KiB/位置混用。[tail预算反例](../../calculations/results/growing-kv-tail-budget-fail.md)明确容量失败；未因此把反事实通信时间称可实现方案。运行 `python3 calculations/calc.py growing-remote-kv --inputs calculations/scenarios/growing-remote-kv-example.json --format md`，可改模型、P/G、batch、副本和声明接口。时间轴仅为startup+bytes/B的通信骨架，KV生成计算、真实传输协议/控制流、故障恢复和完整内存峰值未知；不是实测decode或系统一致性实现。

以 SGLang HiCache 与 LMCache 的真实后端作为 HBM、主机和外部存储的实验入口：分别记录写入、预取、命中和淘汰，而不是仅画一个内存池方框。2026 年 Unified Radix Cache 把混合模型状态接到这些层次；沿 V4 的压缩／窗口与 K3 的循环状态重新核算有效边界。

沿 HiCache 从 2025 公告到当前实现，明确单实例私有的 host 层与按后端配置共享的存储层。再用 vLLM 从异步 connector、CPU offload 到当前多级后端作对照；其原生路径先经过 CPU，不能由“远端存储”推断 GPU 直读。缓存容量、共享范围和数据通路分别落到实际部署。

用 HiSparse（2026）的 DSA 案例补充另一种问题：本步选中的 KV 很少，完整历史容量却仍然很大。比较按需从主机取回与 HBM 热缓冲，计算低并发时的额外 IO 和高并发时释放容量的收益；这是其已披露 DSA 路径，不能直接假定适用于 V4 的全部压缩层或 K3 的状态。

沿 Qwen3-8B／235B 的两个实例反复处理同一 Agent 前缀，比较本地 HBM、主机 DRAM、本地 SSD 和远端缓存池。逐层计算容量、访问带宽、启动延迟、块大小与排队；热的活跃 KV 与等待复用的冷前缀采取不同放置。Mooncake／LMCache 提供软件层次与共享实例，UB 的硬件访问语义另行对应。

沿用 Qwen3-8B 的 8K 前缀、1.125 GiB BF16 KV 和 25 GB/s 条件式带宽：取回一次的纯传输下界约 48.32 ms；假定每次 decode 都远程读取这份不变前缀，100 次 decode 调用累计约 4.832 s 的链路服务时间，增长中的 KV 另计。这里计调用次数，首输出已由 prefill 产生时不能把它混作总返回 token 数。与一次本地 prefill 重算和搬回本地继续生成比较，解释远端容量能否成为活跃 KV 的供数来源；有重叠或分片时按每条链路和依赖重算。

接回第 5 章的布局：Qwen3-8B 的 16-token BF16 块，按声明布局可拆成 72 个 32 KiB 连续段，也可组织成一个 2.25 MiB 连续块。有效载荷相同，再比较 DMA、搬运 kernel、布局转换与并发计算争用；[完整推算](../../case-studies/cache-tiers-and-routing.md)与实验使用同一配置。

以 [Aqua 的邻卡显存卸载](../../references/proceedings/ASPLOS/2025/parallel-next/READINGS.md)补一个拷贝粒度对照：按论文 A100 微基准的十进制带宽，16 次 4 MB 拷贝与一次 64 MB 拷贝分别需约 1.28 ms、0.32 ms，差额还要支付聚集、分散与调度成本。实验 9-7 同时观察提供显存一方的干扰；这是基于 vLLM v0.5.3 的论文改造，不代表当前框架默认支持，也不把纯传输预算当作端到端收益。

> **实验 9-7 ★：共享 KV 池的命中收益**
>
> 复用远端 KV 何时比本地重算更合适？ 两个实例交替服务同一 Agent，比较本地重算、一次取回并驻留、每步远程访问三条路径。按前缀大小、命中间隔、带宽、重算时间与 HBM 占用求收益边界；增加池写入和回收后，检查 PD 交接是否仍有收益。
>
> 采用 SGLang HiCache＋Mooncake 或 vLLM＋LMCache 的受支持部署收集实际字节和命中时间；每步远程读取作为明确的对照模型，不假定引擎默认如此执行。
>
> 预取变体用 HiCache 的 best_effort／wait_complete／timeout，对比实际完成的连续前缀、放弃的传输和重算；另以固定 vLLM 原生 KV offload 对照 CPU 中转。布局和 IO 后端仅比较受支持组合，独立拷贝与并发服务分别计时。

### 9.5.4 缓存亲和性与完成时间路由

从两次同前缀请求引出缓存亲和与负载均衡的冲突，比较原实例排队、新实例重算和跨池取回的完成时间。Preble、SGLang 与 Mooncake 作设计对照；命中率、复用间隔和正在占用的显存决定选择。

用同一 Qwen3 的 8K 前缀给出具体选择：在声明的队列与串行取回假设下，原实例 HBM 命中约 260 ms，空闲实例重算约 200 ms；远端有效带宽从 5 改为 20 GB/s，取回方案从约 310 降到 129 ms。先画状态就绪与 GPU 等待的依赖，再增加共享链路负载，说明单请求的选择何时失效。数字是教学输入，[算例](../../case-studies/cache-tiers-and-routing.md)不冒充框架成绩。

对照 SGLang 2024 的近似缓存树与固定当前 Model Gateway：已读策略依据文本匹配和负载阈值，并未直接预测上述完成时间。区分 router 预计命中、worker 的实际 token 命中和 KV 所在层级，实验检查过期信息怎样改变选择。

再沿 vLLM 的 KV events、SGLang HiCache 与 Dynamo 的实际集成，解释缓存怎样成为路由依据：拷贝完成才报告新位置，GPU 淘汰后 CPU 副本可能仍在，事件缺失则需恢复索引。用同一前缀把 A 的队列改为 80 ms，计算有效命中时的 90 ms 与全部失效后的 260 ms；即使平均值优于 B 的 200 ms，尾延迟也可能不合格。由此区分缓存层级的评分权重、命中概率和实际取回时间。Agent 并发分支还会先于缓存发布到达，短期预测可帮助聚集请求，但不能保证前缀已经可用；[扩写依据](../../case-studies/cache-events-and-routing.md)保留版本与计算条件。

## 9.6 服务生命周期：启动、重配置与恢复

将稳态收益扩展到服务启动、运行中变化与实例失效。这里只处理推理引擎、模型和请求状态；第 11 章接着讨论任务环境与资源池调度。

<a id="detail-9.6.1"></a>

### 9.6.1 启动、预热与准备成本的摊销

以 vLLM 的启动记录补齐服务寿命：分开看 CPU 初始化、权重读取、编译缓存、KV 探测与 CUDA Graph 捕获，计时按依赖关系避免重复相加。先算增加准备时间换来的稳态节省需要多少执行步才能抵消，再计入扩容期间的队列与热副本费用。MLSys 2026《Breaking the Ice》的 v0.10.1.1 实验作为历史参照；新版本用 Qwen3-8B 重测，权重页缓存与编译缓存的冷热分别记录。

沿 vLLM 2024／2025／2026 的 ShardedStateLoader 比较普通权重加载与部署专用的预分片：每 rank 读取自己的文件可以减少重复读取，但改变 TP 后仍需匹配的新布局。它保存模型状态，不包含优化器、请求 KV 与环境；第 10.4 节再讲可重分片的完整训练检查点。把文件转换成本、冷热页缓存、存储吞吐和新副本就绪时间一起计算，具体证据见[检查点布局与加载](../../case-studies/checkpoint-layout-and-loading.md)。

<a id="detail-9.6.2"></a>

### 9.6.2 运行中重配置与状态交接

运行中重配置先列出目标布局、需要移动的权重和请求状态，再确定排空、复制、最终暂停与恢复接流的顺序。计划迁移依赖源端仍可合作；动态并行切换还须满足 KV 布局、图准备与容量条件。

用 vLLM 2026 Elastic EP 把启动接到运行中的扩缩容：Qwen3-235B 的 BF16 routed 权重从 8 rank 均分到 16 rank，新设备需接收多少数据？再计入建组、非专家权重、图重新准备和队列。缩容先检查剩余权重与 KV 容量；专家迁移不代表请求 KV 已交接，暂停、排空与上层策略分别从记录确认。

用 Llumnix 的计划迁移解释另一条路径：先复制不再改变的历史 KV，生成继续，最后暂停并追平新增状态；分别计算完整复制与暂停时间。源端仍可配合迁移，与实例突然失效的恢复条件不同。换成 V4／K3 时要检查可变压缩状态、窗口和循环状态的一致交接点，不能仅凭 KV connector 就认定请求可以热迁移。

**已复算（C52-migration）：** [TP4→TP8迁移子账](../../calculations/results/reconfiguration-dense-tp4-to-tp8.md)按官方Qwen3 BF16逐权重分片与完整KV头所有权复算：默认B=2、8192历史token，网络16449646080 bytes，本地物化读写4704125952 bytes；声明有效带宽下传输资源下界46.99194368秒，切换时间仍未知。[TP×EP互换](../../calculations/results/reconfiguration-qwen30-tp2-ep4-to-tp4-ep2.md)另核专家归属及非专家／同请求KV复制。[同卡物化](../../calculations/results/reconfiguration-same-card-materialization.md)免网络但仍列本地读写；逐卡峰值按旧缓冲保留至新缓冲完整物化计算。[声明串行路径](../../calculations/results/reconfiguration-declared-serial.md)把网络资源下界与另给的网络时间分列；10秒额外投入、每步省0.0002秒时50000步仅持平，50001步才严格获益，且须另核容量与SLO。[重放路径](../../calculations/results/reconfiguration-dense-disjoint-replay.md)不搬旧KV仍保留目标KV容量，未知物化／网络时间保持空值。运行 `python3 calculations/calc.py reconfiguration --format md`，以 `--inputs` 修改声明快照。此处只闭合静止快照迁移与条件摊销子账；真实排空、分流、缓存身份验证、恢复重试、服务质量及完整生命周期费用仍待实测或补齐执行图，原C52尚未完整完成。

接回第 6 章的四卡切分，用 ArcticInference＋vLLM 比较固定 TP、固定 SP×TP 和运行中切换。额外权重会挤占 KV，额外图准备需要足够执行次数抵消；阈值按本轮调度 token 数校准，并记录补齐、实际并行模式与 Graph 路径。相同 KV 布局是切换条件，完整服务收益仍由排队、状态容量和请求分布决定。[版本与推算](../../case-studies/parallel-switching-and-state.md)

<a id="detail-9.6.3"></a>

### 9.6.3 部分故障与流式生成恢复

区分普通交互、Agent 续接与 RL rollout 的恢复目标。依据 DeepSeek-V4 的 token 级 WAL 与 KV 保存机制，比较继续 decode、用已生成 token 重做 prefill，以及重新采样的差别；最后一种会改变输出和采样分布。计算不同故障下的重做工作、缓存访问和已经交付结果的处理，第 10 章再分析训练影响。

**占位 D14-04：** 沿实际 DP／TP／EP 分组追踪单 rank 故障影响的请求、同步操作与状态，以原始记录或受控注入比较检测、重建、首个有效 token 和积压消退；将故障范围与恢复策略放回实验 9-10。详见[EP 服务故障验证](../../research/draft14-15-outline-audit/report.md#failure)。

## 9.7 完整部署的选择与验证

将前六节得到的阶段能力、交接条件、状态寿命和恢复预算组成完整候选，在相同质量与资源约束下选择，并给出使选择翻转的条件。

<a id="detail-9.7.1"></a>

### 9.7.1 组合副本、PD、AF 与共享 KV

**占位 TC-15：** 补缓存、状态复用与资源共享的降本机制，避免重复计算收益。 详见[成本下降调研](../../research/token-cost-2023-2026/report.md#serving)。

将三个案例画到同一系统里：P 池产生 KV，D 池消费并继续更新；AF 的专家权重和逐层激活具有不同的寿命与访问频率。比较 KV 直接交接、经共享池暂存与跨实例前缀复用，计入新增写入、读取、容量和回收责任。权重扩容、KV 缓存和细粒度远程访问分别判断，不能只用“都是内存池”概括性能。

再沿 Agent 的 P→D→下一轮 P 检查新增状态：vLLM 当前 prompt-only 卸载与 SGLang 的 decode 异步卸载配置，决定生成 token 是否已经进入可复用层。用真实多轮轨迹比较只存公共提示和保存会话，计算写入成本及下一轮节省的工作。

>
> 比较同一份1.125 GiB状态经一条边直传与经两条边中转，再标后续实例的复用；AF逐层激活单独在正文计数。

<a id="detail-9.7.2"></a>

### 9.7.2 同质量、同资源约束下的方案比较

回到同一模型和请求集，把 A100＋H20 的 PD、KTransformers／跨机 AF 和有无共享 KV 池放进完整部署，再与副本、TP／PP、EP 的候选组合比较容量、质量、延迟、费用及恢复。让原来的“选哪张卡”变成可检验的系统选择。

以 TriInfer 的阶段 profiling 与历史重放补一个视觉配比判断：在同样四张卡下比较 1E＋3PD 和 2E＋2PD，按未缓存图像数、语言工作与完整 EC 流量找最早的瓶颈。命中率改变后再选配比，并计入分钟级重配和启动；论文的旧共置基线不代表当前框架缺少 EPD。[算例与版本](../../case-studies/multimodal-stage-placement.md)与实验 12-3 使用相同图像形状。

先比较两套固定配置，再给双方相同质量、资源上限和调优机会，开放量化、TP／PP、EP 与完整副本组合，分别求最低延迟、SLO 内最大吞吐和单位有效产出成本。价格、功耗与有效效率保留能改变排序的区间；兼容性与资源可行性检查先于方案排名。

### 9.7.3 负载变化后的选择翻转与设计交付

先用 Chat、Agent 和实时请求形成部署决定，再分别改变输出长度、复用间隔、到达率或实例寿命，找出应扩大副本、调整池配比、重新共置或改为重算的条件。给第 10 章交付阶段能力与可恢复生成状态，给第 11 章交付新副本就绪时间与积压消退预算。

> **实验 9-10 ★★：异构推理的完整部署**
>
> 你会怎样部署这个模型服务？ 综合 A100＋H20 的 PD 分离、KTransformers 的 AF 分离与共享 KV 池三项案例，按 Chat、Agentic、Real-time 请求选择硬件、切分和路由。加入 reasoning 长输出、计划迁移与实例失效，先列可恢复状态和交接条件，再算服务目标与成本；说明哪些组合值得进一步实测。
>
> 方案至少给出一个已核实的引擎＋传输／缓存后端组合及对应运行记录，部署命令与算术输入随实验提供。
>
> 启动变体用同一 Qwen3-8B 配置比较缓存未命中、命中和不同图捕获规格；保留引擎就绪、首请求完成与积压消退三个时间点。若额外准备 10 秒、每执行步省 0.2 ms，先算 50,000 步的抵消门槛，再由真实 batch 和实例寿命判断；教学值不当作框架实测。
>
> 权重加载变体固定 Qwen3、精度和 TP，比较普通文件与预分片文件的实际读取、转换准备与首次就绪时间；修改 TP 时先检查格式与分片兼容性。和训练恢复实验共用张量坐标，不将推理权重文件当成完整训练检查点。
>
> 视觉配比变体用固定 vLLM 或 SGLang EPD，先比较相同卡数，再单独增加 E；扫描每请求图像数和 EC 命中，记录 EC／KV 实际交接、图模式及阶段尾延迟。用短时图片突发检验历史配比与重配期间积压；TriInfer 原论文与当前框架分别作证据。
>
> EP 扩缩容选做沿受支持的小型 MoE 或配套记录，标记新组准备、权重移动、图准备与请求恢复；先用 Qwen3 预算判断瓶颈，再用实际配置校准，不能把前述 DBO／图模式开关无条件组合。
>
> 动态并行变体沿用第 6 章四卡输入，固定插件与引擎版本，先验证模型路径和参考输出，再扫描切换阈值；记录每步 token 数、补齐、模式和显存峰值，用 TTFT、ITL 与 SLO 内产出检查推算。

**本书实验记录与适用范围（由主大纲移入）：**

**局部实测：** [实际启动与8请求积压](../../experiments/ch09/09-10/startup/README.md)中，空／完整文件目录的排空中位约18.44／18.70秒。完整目录虽发生成功读取，首个完成请求仍报告缓存命中为0；文件读出不等于有效复用，尚不能据此评价缓存加速。

**机制补测：** [三个入口的12组对照](../../experiments/ch09/09-10/cache-mechanism/README.md)及[独立native读取观测](../../experiments/ch09/09-10/native-storage-observation/README.md)均显示单请求命中1008个存储token，同前缀8请求波的首个完成请求却未命中。[两轮直接分支观测](../../experiments/ch09/09-10/branch-observation/README.md)确认：首完成的native-4因预取占用4096超过限额3289而未登记预取，随后经“无ongoing”分支进入零命中prefill。文件成功读取不能替代该请求的有效复用；跟踪会扰动时间，本批不用于性能排名。
