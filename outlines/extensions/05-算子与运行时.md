## 5.1 复用如何改变实际访问

### 5.1.1 矩阵形状与访存开销

用朴素矩阵乘展示反复读取、循环顺序和数据复用，先把实际访问与第 4 章的预测对上。区别数学工作量与实现产生的流量。

再用 Qwen3 归一化中的 `[M,4096]` 行归约，对照单 token decode 与多 token prefill：M 决定能同时安排多少行，归约宽度决定每行工作与通信。把归约维继续加大作为教学变体，比较一行一个工作组与拆分归约；新增并行度要付出 partial buffer、同步和第二次归约的代价。切分也会改变浮点累加顺序：先比较固定形状的重复结果，再改变 batch，给第 8 章的服务可复现性和第 10 章的训练／推理差异铺垫。

<a id="detail-5.1.2"></a>

### 5.1.2 循环变换与分块复用

由片上容量推出 tiling，再比较三种硬件怎样分配工作。用块太小、太大和边界不齐的例子说明为什么没有通用的最佳块形状。

先给一个可手算的片上预算：三个矩阵块至少占 `b(mk + kn + mn)` 字节，再加入累加格式和双缓冲。枚举少数可行块，比较复用与并发；自动调优在这一步之后出现。

沿 Qwen3-8B 的 `[1024,4096] × [4096,12288]` 单支投影继续算：128 MiB 是输入输出各走一次的最低流量；在给定循环下，64×64 与 128×128 输出块分别需要 24／80 KiB 活动空间，产生 3,096／1,560 MiB 的下一层访问。用 Orojenesis 引出容量约束下的复用，再区分某个方案的计数、搜索所得最好结果和流量下界；L2 能服务的重读不应全部记成 HBM 流量。[计算条件](../../case-studies/buffer-capacity-and-data-movement.md)留作扩写依据。

容量和总字节算完，再检查访问落在哪些 bank。把同一投影中的 32×32 FP32 暂存块作为简化例子：行跨度从 32 改为 33 个字，可用额外 128 字节分散按列访问，代价是片上占用增加。用 FEATHER 说明分块与布局需要共同选择，再由实际内核或 trace 核对；标量计数不能直接当作 Tensor Core／TMA 的访问规则或整段加速比。

## 5.2 融合边界与缓冲寿命

<a id="detail-5.2.1"></a>

### 5.2.1 算子融合的收益与代价

从矩阵乘后接逐元素运算进入融合，计算写回与读取；随后加入寄存器、缓冲占用和并发，解释融合收益为什么会有转折。

先算最容易看见的收益：若中间张量有 X 字节，取消一次写回和读取，理想上少走约 `2X` 字节；再问这些数据能否留在片上、会不会挤掉并行工作。用这个问题自然进入 FlashAttention，先算注意力分数矩阵随长度平方增长的字节，再决定怎样分块。

接回前节的容量预算：融合若迫使 tile 缩小，新增的权重重读可能抵消中间张量的节省。以 Orojenesis 的分段融合结果作历史对照，再让 Qwen3 的同一条链比较独立执行、全链融合和保留一个边界；先找转折条件，再讨论实际编译器选择。

布局也沿整条链计价：分别选出两个最快的独立内核后，还要加上中间转换；比较接受同一布局、另做重排和由生产者直接写出消费方布局。沿前节投影的 24 MiB BF16 输出，另行物化一份完整重排结果要增加一次读和一次写，再判断能否在现有交接中完成。

> **实验 5-2 ★：融合的流量与资源占用**
>
> 融合省下的流量够不够抵消资源占用？ 对同一算子链比较融合前后，记录字节、缓冲和时间；无加速器时做容量模型。
>
> 改变片上预算，分别列出省掉的中间读写和新增的输入／权重重读，找出应保留融合边界的条件。不同方案使用相同精度与计算语义；设备测量再检查布局、并发和实际融合范围。
>

### 5.2.3 异步搬运与计算重叠

## 5.3 从手工优化到编译选择

<a id="detail-5.3.1"></a>

### 5.3.1 AKG：独立算子优化之后的问题

从前一节已经调好的独立算子出发，加入归一化、激活、残差和量化转换，观察原有接口与中间写回怎样阻碍进一步融合。单算子做成高效内核以后，跨算子分块、布局、生命周期和融合边界仍需共同选择；这是引出作者 AKG 工作与算子编译器的主要问题。

用含 k 个算子的线性链说明，仅相邻融合边界就有 `2^(k−1)` 种形式划分，尚未加入 tile、布局和动态形状。合法性与硬件约束会排除许多组合，但手工枚举和维护仍迅速变得昂贵。编译器负责表达依赖、选择可行组合并生成代码，不能许诺自动得到全局最优。

用 Korch 的历史子图说明另一层选择：InstanceNorm 拆开后再与 ReLU、Pad 组合，kernel 从三个变四个，整条链仍可能更快。由此区分算子的数学边界、并行与访存特点，以及真正的 kernel 边界；候选的串行实测时间、切图与后端限制一起决定结论。[案例与适用条件](../../case-studies/kernel-orchestration-and-quantization.md)

### 5.3.2 两条代表链与融合机会

安排一张“模型—算子—形状—融合机会”表：小尺寸序列模型、Qwen3-8B Dense、Qwen3 MoE、DeepSeek-V3／V4-Flash、Kimi K3。每行沿真实计算路径列投影、归一化、位置编码、注意力、FFN／专家、路由、状态更新和残差；给典型输入尺寸、逻辑算子数、可融合边界与主要中间张量字节。新模型带来的压缩器、索引器、线性状态和 mHC 等算子由这张表自然引出。

### 5.3.3 图变换、分块与自动调优

沿 Qwen3 的 QKV 投影—QK Norm—RoPE—注意力，以及 V4 的压缩／索引或 MoE 链，讲依赖、融合合法性、布局和分块怎样共同决定代码。用一个具体变换引入多面体与 isl，再比较 AKG、TVM／TensorIR、TileLang 等表达与搜索方式；计算编译调优成本在多少次执行后才能摊薄。

区分三个问题：多面体／isl 表达迭代域、访问和依赖，用来判断变换是否保持语义；硬件与成本模型估计候选运行得怎样；实际 profiling 校准缓存、寄存器溢出、并发和流水损失。性能预测失准不等于依赖分析失效，MFU 不到 100% 也不能直接证明是哪一个模型错了。

以 TVM 的规则 schedule 作起点，再比较固定模板参数搜索、Ansor／MetaSchedule 的结构与参数搜索，以及让 LLM 修改 schedule 或算法实现。MetaSchedule 本身已经通过真实硬件测量更新成本模型；不能把“传统编译器没有反馈”作为 Agent 的优势。固定空间较容易控制合法性和搜索成本，但可能漏掉新融合与算法；开放生成空间更大，验证与调优成本也更高。

接回当前 vLLM 的 SiLU+Mul→量化路径：从 v0.6.0 的手工激活算子，走到编译 pass 对跨算子模式的匹配。以 Qwen3 的 `[1024,24576]` gate-up 输出计算省掉的 48 MiB 中间读写，再单独推算活动张量峰值。编译器可见的表达也可能被 Inductor 自行融合，因此比较实际图和 trace；禁用某个自定义融合 pass 不等于恢复了两个独立 kernel。

### 5.3.5 性能反馈与候选验证

从 Qwen3-8B 的归一化或 SwiGLU 链选一个真实热点，先算流量与性能上界，再让 Agent 完成“profile → 瓶颈判断 → 修改候选 → 正确性校验 → 计时 → 保留或撤回”。用 KernelAgent（2026）的硬件反馈流程解释每轮需要提供什么：实际形状、精度、布局、芯片资源、生成代码与测量记录。Nsight Systems 先找整条路径的等待，Nsight Compute 再检查热点内核，不能只给 Agent 一个总耗时。

对照只改 TVM schedule 参数、允许改变合法融合，以及生成 Triton／CUDA 实现三种范围；观察优化一轮后瓶颈怎样转移，而不预设 Agent 总会胜过成熟库。FlashInfer-Bench（2026）用于连接真实服务输入、数值校验与内核替换；CUDA Agent（2026）说明也可以把执行反馈用来训练优化能力，本节习题先使用现成模型驱动工具。

用 NanoFlow 的两步搜索补充反馈条件：先测独占内核选择候选，再测并发干扰修正流水。Agent 若只追求某个 GEMM 的独占速度，可能挤占 attention 或通信所需资源；沿[切分与争用算例](../../case-studies/resource-sharing-and-placement.md)解释为何局部计时与实际并发片段都要保留。

用 Anthropic 2026 年公开的历史性能考核作简短对照：先固定机器、输入与参考验证，再谈加速。沿基线数指令和发射槽位，区分保持工作不变的调度下界与改变算法后的新预算；模拟周期不换算为 GPU 时间。回到 Qwen3 实验，设备数、精度和语义改变都另列条件，不能让 Agent 修改验证器后继续比较原成绩。[算例与核对](../../case-studies/evaluation-and-agent-records.md)

### 5.4.3 主机提交与设备执行

### 5.4.4 图捕获与重放

比较普通提交、融合、图重放和组合方案，各自减少什么工作。动态形状、地址稳定和图缓冲解释哪些任务值得捕获、何时需要回退。

沿 vLLM v0.6.0 的 decode 捕获、v0.9.2 的分段图，再到按 batch 选择整图／分段／回退的实现，说明 capture、instantiate 与 replay 如何适应负载。记录地址与元数据约束、形状分桶、padding、首次捕获时间和常驻缓冲；图重放减少重复提交，并不自动融合算子或消除数据依赖。[版本与选择算例](../../case-studies/graph-execution-tradeoffs.md)区分历史文档、当前实现与实际安装配置。

以 FlashInfer 的 `plan/run` 说明动态请求如何进入稳定执行路径：CPU 先按长度规划工作，再把元数据写入固定缓冲供图执行。同规格的多层可以复用计划，但规划本身不被捕获；从 Qwen3-8B 的 36 层推算重复规划的代价，再检查 V4/K3 不同层型的复用边界。计划、复制和 padding 的开销仍要放回时间线。

补入 SGLang 2026 年的 Breakable CUDA Graph：把不适合捕获的动态操作留作 eager，其余区域分段捕获；对照编译器切图与运行时显式断点。再用 prefill 全图的请求 padding 解释动态负载怎样变成可重放形状，比较启动成本、额外工作和多形状图的内存复用。

用 GraCE（OSDI 2026）追问每个图段是否值得捕获：Qwen3 的 2／16 MiB hidden tensor 若要复制到固定边界，分别增加多少 HBM 流量？再比较直接写入固定缓冲、数据复制与间接寻址，计入指针传输和参数更新，先排除不划算路径再 profiling。当前 vLLM 的可用图分派与研究原型的逐段性能选择分别说明；稳定地址也不等于每步复制整份 KV。

以 SGLang 的内存暂停和 vLLM Sleep Mode 留一个后续问题：释放物理显存而保留虚拟地址，可以省去哪些重新捕获工作？地址不变也不代表内容有效；第 10 章沿[权重交接案例](../../case-studies/weight-handoff.md)计算恢复次序、额外缓冲与重新 prefill。

<a id="detail-5.4.5"></a>

### 5.4.5 Persistent Kernel 与细粒度流水

用 Mirage Persistent Kernel／MPK（2025 初稿、2026 修订）把一个算子拆成 SM 级任务，解释为什么“每个算子一个 kernel”的边界会阻碍 tile 就绪后立即开始通信。设备内任务与事件可以表达跨算子流水，但也增加调度、同步和资源驻留开销。

比较 CUDA Graph、融合、persistent kernel 与 pipelining 各自省掉什么。增大 batch 可以摊薄单 token 启动成本；切微批有助于重叠，却也可能增加启动次数和小矩阵损失。下一章继续讨论跨卡数据，8.1 和 9.4 再用真实服务判断这些方法的适用条件。

> **实验 5-8 ★★：图重放与算子融合**
>
> 对 Qwen3 的代表算子链比较普通提交、融合、CUDA Graph 与组合执行，使用 Nsight Systems 记录主机与设备间隙，计入捕获、padding 和缓冲容量。以 MPK 的匹配模型／硬件案例补充 persistent 路径，不能把独立论文的加速比相乘；说明增加微批何时会使启动开销更大。
>
> FlashInfer 变体在实际支持的后端上分开测 plan、元数据复制与 run，比较逐层重复规划和同规格层共用计划。先手算主机工作量，再从轨迹判断省下多少关键路径时间。
>
> 图段选择变体改变外部输入大小和边界接口，比较额外拷贝、暴露的提交等待和完整链路时间；沿 GraCE 的记录说明为什么同一模型有的段应保留 eager。未集成的研究路径只作记录对照，同时计算准备成本需要多少次重放才能摊平。
>
> 条件：进阶·单设备／轨迹分析。

>
