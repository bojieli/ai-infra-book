**已复算（C42-batch-reuse）：** [H100／2K batch账](../../calculations/results/batch-reuse-h100-2k.md)按官方Qwen8 BF16完整权重16381470720bytes、理想每批共享读取15136811008bytes（embedding逐请求查行）、KV每token147456bytes。扫描1/4/16/64，2K旧KV读达到共享权重需batch51，8K需13；这不同于计算／带宽交叉点。[H100／8K](../../calculations/results/batch-reuse-h100-8k.md)、[4090／2K](../../calculations/results/batch-reuse-4090-2k.md)、[4090／8K](../../calculations/results/batch-reuse-4090-8k.md)严格选BF16输入／FP32累加／dense Tensor峰值，四场景均无有限计算主导交叉点。标称80／24GB、workspace=0时2K容量上限210／25，8K为52／6；不可行行不给可运行吞吐。[无历史对照](../../calculations/results/batch-reuse-no-history.md)另算交叉点；运行 `python3 calculations/calc.py batch-reuse --format md` 查逐batch矩阵、KV和节省权重读取。理想权重读一次／旧KV读一次，未计中间激活及tile重读，容量不代表实际引擎可用，资源下界不代表TTFT或SLO。

从权重复用和矩阵形状解释 batching，计算它节省的读取；随后加入等待凑批、请求长度差异和显存容量，看到吞吐与延迟的取舍。

### 8.2.2 从固定批次到连续批处理

**已复算（C42-iteration-batching）：** [固定批次](../../calculations/results/iteration-batching-fixed.md)、[连续补位](../../calculations/results/iteration-batching-continuous.md)、[decode优先分块](../../calculations/results/iteration-batching-chunked.md)复放相同4请求，官方Qwen8工作2636833882112矩阵FLOPs、188已计算输入位置和16输出保持一致。固定／连续／分块分别12／8／12迭代，教学完成317004／277004／317004ns，最大ITL12146／147274／28945ns；连续补位让长prefill更早进入，同时扩大短decode间隔。教学步成本为10000ns＋新token数×1000ns＋有效因果配对数×1ns，不是GPU校准。分块预算32、单prefill块最多16、活跃最多2；只在迭代边界接纳，固定批次整组结束再补位。[20MiB KV准入](../../calculations/results/iteration-batching-capacity.md)按prompt+output-1预留、FIFO不绕过队首；实际KV每步分配新行、结束请求释放，最新输出仍pending。运行 `python3 calculations/calc.py iteration-batching --format md` 查逐步计划及请求TTFT／ITL；不把教学时间或输出数量一致当作真实吞吐／质量证据。

让短请求先结束、长请求继续，观察空槽位，再介绍 Orca 等系统的迭代级安排。比较旧批次和新请求如何交接。

实际入口使用 vLLM 或 SGLang：它们负责模型执行、请求批处理、KV 管理与服务接口，分别沿调度日志看新请求怎样进入下一步。Ollama 的本地模型管理与 runner 在 8.4 出现；TensorRT-LLM 是面向 NVIDIA 的 LLM 推理栈，在图执行和内核选择处对照。TensorRT 则是更通用的网络优化与执行工具，图像编码器可以使用它，不将二者当作同一产品的两个简称。

用 vLLM v0.4.2（2024）的实验性分块执行，到 V1（2025 起）的统一 token 进度，解释 prefill、decode 与推测验证如何共用预算；当前路径还要等待 KV 就绪并满足图形状等约束。沿[固定版本](../../references/framework-history/2026-09-08/chunk-scheduling/README.md)比较调度如何变化，不把分块本身写成 V1 首创。SGLang v0.4（2024 年底）的 CPU／GPU 重叠则解释为何准备下一批不必等当前 GPU 工作结束；“零开销”仍需核算排队、准备工作和可能多做的 token。

从 Agent 生成一份文件读取参数引入 XGrammar：把可预先判断的 token 缓存下来，仅对依赖完整语法栈的部分做运行时检查，再与 GPU 前向重叠。沿 SGLang 2024 集成、vLLM 2025 的 logit processor 与当前语法管理路径，比较冷 schema、编译等待和每步掩码；Ollama 的本地 JSON schema 入口作对照。有效格式与参数含义、任务成功分别评价。

用 Qwen3-8B 的 151,936 词表和 64 请求算一批约 1.159 MiB 的位掩码，再给 CPU 每行工作与 GPU 前向时间，找采样前的汇合点。字节不多不代表 CPU 开销可忽略；当前填充路径也不总按线程数并行。实验 8-2 用实际 trace 校准，[计算与版本条件](../../case-studies/structured-generation.md)供扩写查用。

连续批处理还会改变同一请求遇到的矩阵形状和归约切分。接回第 5 章的数值对照，用 SGLang 的确定性路径和 vLLM batch invariance 说明为何温度设零仍未必复现；固定归约、请求种子与兼容后端各解决什么问题，又牺牲哪些执行选择。比较[历史与当前版本](../../case-studies/rl-state-and-reproducibility.md)，本节保留同一请求随 batch／归约路径变化的局部数值对照；跨引擎 logprob 与 MoE 路由重放接第 10.5.4 节及实验 10-8，按各自模型与执行条件验证。

**配套观测与写作补充：**

让短请求退出、长请求继续，并把新请求放入腾出的槽位，推导迭代级连续批处理。用固定 vLLM 或 SGLang 的一次调度记录对齐请求进度、KV 分配与 GPU 执行；模型管理和实际执行后端分开。

本节只解决“下一步让谁执行”。语法掩码、数值可重复性、视觉输入及图形状作为需要满足的额外条件，在相应实验变体和延伸材料中检查。CPU 准备可与 GPU 计算重叠的前提是依赖已就绪；准备本身和多做的 token 仍需计量。

先用[四请求教学时序](../../calculations/results/iteration-batching-continuous.md)比较固定批次、连续补位与 decode 优先分块：保持计算位置与输出相同，连续补位让长 prefill 更早进入，却可能拉长已有请求的 token 间隔。再用实验 8-2 的六请求实测检验这一取舍；教学时间不用于预测真实 GPU 吞吐。

### 8.2.3 长 Prefill 干扰与分块执行

**已复算（C42-chunk-history）：** [固定块长的实测与工作复算](../../calculations/results/chunk-history-book.md)核对实验8-2补测15个封存文件，11次8K请求共176个512-token块、另排除11次空execute。首／末块有效因果配对131328／4063488（5291/171倍），官方backbone矩阵7189926248448／9509208588288 FLOPs（62977/47617倍），实测区间中位25.300640／35.070015ms。配对末／首比例中位1.388425，与两个中位数之比1.386132分列；16块矩阵和133593078693888等于整段8K工作。运行 `python3 calculations/calc.py chunk-history --format md` 查逐历史位置，JSON保留176个样本。CUDA event覆盖execute_model而非纯attention；外部logits／采样不计，采用head=none矩阵账。共享GPU单引擎重复，历史／内容／末块处理并未独立控制，不把配对比例当作访存或时间比例。

### 8.2.4 Token 预算、动态图形状与实际执行时间

承接第 5 章，把图分桶、padding、分段和回退放进同一调度过程。图缓冲会与 KV 竞争容量，最终用服务结果比较。

继续同一条请求时间线：多步窗口会延后新请求准入；提前准备下一批仍要在设备消费前接到真实 token。沿[固定版本的主机调度演进](../../research/2026-infra-survey/parallel-host-timeline/NOTES.md)，比较 SGLang 2024 overlap 与当前 Spec V2、vLLM V1 与当前 AsyncScheduler。实验 8-2 增加一个时序变体，记录结果复制、长度发布、语法等待与缓冲复用；推测验证每轮推进多少位置另算，不能按普通 decode 固定加一，也不能把算法与引擎优化的加速比相乘。

以 vLLM 的 CUDA Graph 模式和 TensorRT-LLM 的匹配执行路径做真实对照，记录动态图形条件、首次捕获与稳定重放。先用 Nsight Systems 判断 CPU 提交是否暴露，再开启异步调度或图重放；不要把没有启动瓶颈的工作负载也预计成相同加速。

代入 Qwen3-8B 的矩阵：1536 token 补到 2048，一层 FFN 额外增加约 154.62 GFLOPs。分别计算 token padding 和空 request 槽位，不能按一个比例估算全部算子。沿 SGLang 的捕获上限案例比较图常驻量与最大 prefill 的瞬时峰值；图池复用可能替代部分峰值，捕获不足则可能两份成本并存。实际图命中和回退连接[图执行算例](../../case-studies/graph-execution-tradeoffs.md)。

将第 5 章注意力内核放回请求：SGLang 可以分别选择 prefill、decode 与目标验证的后端；vLLM 则要区分框架后端和其内部 FA 版本。用 Qwen3 固定形状说明页大小、KV 精度、确定性要求和图支持怎样影响选择及回退。实验 8-2 加一个可选后端对照，逐阶段确认真实路径再解释时间变化，[固定实现](../../references/framework-history/2026-09-08/attention/README.md)不直接等于任何安装环境的默认行为。

**配套观测与写作补充：**

沿第 5.4 节的图重放与 padding 预算，回到实验 8-2 的同一批请求：减少提交以后，等待究竟来自 CPU 准备、长 prefill，还是 KV 容量不足？先在固定 vLLM 路径中比较图开启前后的时间线，再根据请求形状检查图命中、回退和缓冲占用。

本节新增的选择是捕获哪些形状、为图保留多少容量。图池挤占 KV 后，可能减少可接纳请求；过大的桶也可能增加实际执行。用[已有算例](../../case-studies/graph-execution-tradeoffs.md)解释这两个方向，SGLang／TensorRT-LLM 的不同路径留作延伸对照。第 5 章已完成的捕获原理和单层算术不在这里重新推导。



实测：RTX PRO 6000／vLLM 0.23.0 回放六个合成请求，预算从512增至8192后，一个后到请求的排队从约149 ms降至接近零，但最长token间隔从约32 ms增至183 ms。单独开启decode图未消除小预算的等待。四组各三轮，输出token一致；共享GPU下的局部观察不代表通用最优配置。[原始记录、图与待测项](../../experiments/ch08/08-02/README.md)。 [同块长补测](../../experiments/ch08/08-02/chunk-history/README.md)中，11次8K请求的首／末512-token块执行区间中位数为25.30／35.07 ms；相同新token预算不等于相同执行时间。

> **实验 8-2 ★：请求调度与等待分布**
>
> 用同一 Qwen3-8B 的六个 Chat／Agent 请求，手排固定批次、连续批处理与分块 prefill，再在固定 vLLM 版本回放同一到达时间。先比较相同块长、不同历史位置的工作与执行时间，再分别改变 token 预算、分块和 CUDA Graph，记录等待、ITL、KV 峰值、主机提交与图缓冲；以 SGLang 作同模型可选对照，每次只改变一项执行策略。NanoFlow 的仅切分与重叠按配套时序复算，SGLang 的 MoE TBO 实测另放在实验 9-6。
>

### 8.3.4 缓存准入、淘汰、换出与重计算

比较 CPU／SSD 分层、淘汰、预取和重计算。用下一次使用时间与传输成本决定选择，而不预设“缓存越多越好”。

**已复算（C43-kv-pages）：** [KV分页与引用计数](../../calculations/results/kv-pages-branches.md)按官方Qwen3-8B每token 144KiB、16-token页2.25MiB计算。17-token前缀共享给三请求，a追加1、b追加16，再取消c：最终a/b长18/33，预留64-token/请求需18MiB，独占分页11.25MiB，共享分页9MiB；唯一有效35-token为5160960 bytes，空位29-token为4276224 bytes。两次共享未满尾页写前分别复制1-token，共288KiB有效内容；[16-token对齐前缀](../../calculations/results/kv-pages-aligned.md)追加时新建页，无需复制已满页。[Qwen235变体](../../calculations/results/kv-pages-qwen235.md)用188KiB/token重算；[全部取消](../../calculations/results/kv-pages-release.md)归还所有页。运行 `python3 calculations/calc.py kv-pages --format md` 查事件和字节，JSON保留页表及引用。逻辑请求总和、物理唯一有效和完整页分配分别计算，碎片不能用分配减逻辑请求总和。cancel发生于无在途访问的安全点，不代表真实异步取消API返回就可回收；真实引擎COW也可能复制整页。

**已复算（C43-kv-page-capacity）：** [有限页池准入](../../calculations/results/kv-pages-capacity-two.md)给Qwen8B两个16-token页共4.5MiB：17-token前缀可以共享给三请求，但后续a+1需额外1页、b+16需额外2页，均完整拒绝，原页表／长度／引用不变。[三个页预算](../../calculations/results/kv-pages-capacity-three.md)允许第一项追加，第二项仍拒绝。[取消后重试](../../calculations/results/kv-pages-capacity-retry.md)先拒绝共享尾页写入，取消另一引用后虽然未释放物理页，尾页变成独占，重试可原地追加且复制为零。[同4.5MiB预算换Qwen235](../../calculations/results/kv-pages-capacity-qwen235.md)只能容纳一个2.9375MiB页，17-token创建被拒绝。JSON输入加capacity_bytes复算，不能把共享当下省页等同未来增长保证；本例不自动抢占、重算或排队重试。

### 8.4.2 KV 压缩与读取成本

用 Qwen3-8B／235B 的 GQA 与 V4-Flash 的混合状态重算长上下文成本，比较 KV 精度、稀疏访问和淘汰。权重压缩后 KV 可能先成为限制；状态结构变化还会影响分页、前缀缓存和图执行。

最后回到同一业务任务：固定 token 数比较执行成本，自然生成比较质量、返回长度、终止与重试。若 TTFT 已含首输出，总时间按 TTFT 加余下 G−1 次 decode 计算；每秒生成更多 token，也可能因回答变长或失败重做而更晚完成。由此区分容量收益、内核收益与任务收益。

从 Qwen3-8B 单请求、8,192 个缓存位置算起：BF16 KV 为 1,152 MiB；若采用每 32 个值带一个 FP16 scale 的 q8_0／q4_0 格式，分别是 612／324 MiB，不能只按位宽除二、除四。以 Oaken 的异常值编码作进一步推算，再把工作区、分页与对齐加回容量预算。沿 vLLM 的 FP8、SGLang 的分阶段量化路径和 Ollama 的本地缓存，区分存储格式与 Attention 执行精度；用上下文长度扫描，判断融合转换和原生低精度计算何时能抵消固定开销。

结合 MLSys 2025 对 KV 压缩的实证研究，解释少存字节之后还要付出选择、解压或误差补偿的工作。再算整次请求：如果 decode 速率提高 20%，输出却增长 50%，仅看 token/s 就会误判。固定形状测执行成本，自然生成测长度、逐任务质量和完成时间；两类实验共同决定是否值得压缩，不把旧模型结论直接移给 V4/K3。

以 [COMET 的历史结果](../../references/proceedings/ASPLOS/2025/serving-113-117/COMET-READING.md)补充比较方法：区分同 batch 的执行收益与容量释放后扩大 batch 的吞吐收益，质量同时对照原精度模型和其他量化方案；混合位宽要加回转换、元数据与调度成本。旧模型和 A100 上的结果只用于说明如何比较，不代替当前模型的测量。

### 8.4.3 权重卸载、预取与每步搬移
