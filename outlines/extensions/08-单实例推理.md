## 8.1 批处理：用状态与等待换复用

<a id="detail-8.1.1"></a>

### 8.1.1 请求执行时间与状态占用

固定 Qwen3-8B 的层数与矩阵，先给 2,048 输入／256 输出 token 的交互请求，再给 8,192 输入、6,144 可复用前缀的 Agent 请求。分别计算权重、KV、prefill 与每个 decode 步的工作，沿加载到释放画出一次服务；这些是教学输入，随后用第 3 章的长度分布替换。

<a id="detail-8.1.2"></a>

### 8.1.2 batch 与权重复用

从权重复用和矩阵形状解释 batching，计算它节省的读取；随后加入等待凑批、请求长度差异和显存容量，看到吞吐与延迟的取舍。

沿用第 3 章的 `I_weight ≈ 2q/b_w`，与设备的 `F/B_mem` 比较，先求权重主导近似下的批量转折点；然后算 KV 能否装下，以及用户是否愿意等待这么久。这样得到的 q 是候选范围，不是服务引擎的固定推荐参数。

> **实验 8-1 ★：batch 与权重复用**
>
> 为什么一批请求比逐个执行更划算？ 对 Qwen3-8B 扫描活跃 batch＝1、4、16、64，先按实际精度预测权重／KV 读取、矩阵工作和逐卡容量，再比较 4090／H100 的可行范围。只对能装下的候选测吞吐与延迟；换成长 Agent 前缀后重算。
>
> 实测使用固定 vLLM 的 Qwen3-8B，GPU 效率由该引擎记录校准。
>
> 条件：基础·单设备／配套记录。

### 8.1.3 从固定批次到连续批处理

让短请求先结束、长请求继续，观察空槽位，再介绍 Orca 等系统的迭代级安排。比较旧批次和新请求如何交接。

实际入口使用 vLLM 或 SGLang：它们负责模型执行、请求批处理、KV 管理与服务接口，分别沿调度日志看新请求怎样进入下一步。Ollama 的本地模型管理与 runner 在 8.4 出现；TensorRT-LLM 是面向 NVIDIA 的 LLM 推理栈，在图执行和内核选择处对照。TensorRT 则是更通用的网络优化与执行工具，图像编码器可以使用它，不将二者当作同一产品的两个简称。

用 vLLM v0.4.2（2024）的实验性分块执行，到 V1（2025 起）的统一 token 进度，解释 prefill、decode 与推测验证如何共用预算；当前路径还要等待 KV 就绪并满足图形状等约束。沿[固定版本](../../references/framework-history/2026-09-08/chunk-scheduling/README.md)比较调度如何变化，不把分块本身写成 V1 首创。SGLang v0.4（2024 年底）的 CPU／GPU 重叠则解释为何准备下一批不必等当前 GPU 工作结束；“零开销”仍需核算排队、准备工作和可能多做的 token。

从 Agent 生成一份文件读取参数引入 XGrammar：把可预先判断的 token 缓存下来，仅对依赖完整语法栈的部分做运行时检查，再与 GPU 前向重叠。沿 SGLang 2024 集成、vLLM 2025 的 logit processor 与当前语法管理路径，比较冷 schema、编译等待和每步掩码；Ollama 的本地 JSON schema 入口作对照。有效格式与参数含义、任务成功分别评价。

用 Qwen3-8B 的 151,936 词表和 64 请求算一批约 1.159 MiB 的位掩码，再给 CPU 每行工作与 GPU 前向时间，找采样前的汇合点。字节不多不代表 CPU 开销可忽略；当前填充路径也不总按线程数并行。实验 8-2 用实际 trace 校准，[计算与版本条件](../../case-studies/structured-generation.md)供扩写查用。

连续批处理还会改变同一请求遇到的矩阵形状和归约切分。接回第 5 章的数值对照，用 SGLang 的确定性路径和 vLLM batch invariance 说明为何温度设零仍未必复现；固定归约、请求种子与兼容后端各解决什么问题，又牺牲哪些执行选择。比较[历史与当前版本](../../case-studies/rl-state-and-reproducibility.md)，完整实验放在 11-9，与跨引擎 logprob 和 Routing Replay 连起来。

<a id="detail-8.1.4"></a>

### 8.1.4 Prefill 干扰与分块执行

用长 prefill 插入 decode 的时间线引出 Sarathi-Serve 的分块安排。把 Qwen3-8B 的 8K 输入切成 512-token 块，首块与末块分别有 131,328 和 4,063,488 个有效注意力配对：新 token 数相同，历史工作不同。沿[推算笔记](../../case-studies/chunking-and-state-transfer.md)比较等待、矩阵效率、提交频次与历史读取；配对数不直接等于耗时或 HBM 访问倍数，固定 token 预算需要按实际执行时间校准。

用 NanoFlow（OSDI 2025）的算子级 nano-batch 流水说明如何重叠不同请求的计算、访存与通信。Qwen3-8B 一层 BF16 FFN 权重为 288 MiB，256-token batch 切成两个 128-token 微批后，若没有跨微批缓存命中，逻辑权重读取增至 576 MiB，数学工作不变。沿[时序算例](../../case-studies/resource-sharing-and-placement.md)比较仅切分、理想重叠与实际争用；论文的高吞吐分析不能直接外推到 batch=1 或长 reasoning。第 9 章再改变阶段放置，同一请求未就绪的 KV 依赖始终保留。

接第 3 章的视觉请求：视觉编码时间不能只用语言 token 预算约束。用 TriInfer 的 image／token 两种预算，对照 vLLM／SGLang 的实际调度，先测独占 E、独占 D，再看同卡并发是否超过 decode 步间隔；多个 stream 仍可能争用同一芯片。第 9 章才比较独立编码资源，原请求的 E→P 依赖保持。

### 8.1.5 动态批次与图重放

承接第 5 章，把图分桶、padding、分段和回退放进同一调度过程。图缓冲会与 KV 竞争容量，最终用服务结果比较。

以 vLLM 的 CUDA Graph 模式和 TensorRT-LLM 的匹配执行路径做真实对照，记录动态图形条件、首次捕获与稳定重放。先用 Nsight Systems 判断 CPU 提交是否暴露，再开启异步调度或图重放；不要把没有启动瓶颈的工作负载也预计成相同加速。

代入 Qwen3-8B 的矩阵：1536 token 补到 2048，一层 FFN 额外增加约 154.62 GFLOPs。分别计算 token padding 和空 request 槽位，不能按一个比例估算全部算子。沿 SGLang 的捕获上限案例比较图常驻量与最大 prefill 的瞬时峰值；图池复用可能替代部分峰值，捕获不足则可能两份成本并存。实际图命中和回退连接[图执行算例](../../case-studies/graph-execution-tradeoffs.md)。

将第 5 章注意力内核放回请求：SGLang 可以分别选择 prefill、decode 与目标验证的后端；vLLM 则要区分框架后端和其内部 FA 版本。用 Qwen3 固定形状说明页大小、KV 精度、确定性要求和图支持怎样影响选择及回退。实验 8-2 加一个可选后端对照，逐阶段确认真实路径再解释时间变化，[固定实现](../../references/framework-history/2026-09-08/attention/README.md)不直接等于任何安装环境的默认行为。

### 8.2.2 共享、分支与状态回收

沿分支生成、前缀共享和用户取消讲引用计数与写时复制的用途。说明一次省下的分配如何增加可接纳请求。

用 Punica／S-LoRA（MLSys 2024）引出另一种共享：同一基座的多个 LoRA adapter 共用 `XW`，低秩修正按 adapter 分组。再看当前 vLLM／SGLang 怎样处理加载、异构批次与热 adapter 槽位；共享基座不代表不同 adapter 可以直接共享 KV。

固定 Qwen3-8B，仅在 Q、V 投影使用 rank 16、BF16 LoRA，每套 adapter 为 14.625 MiB，100 套约 1.428 GiB；100 个各含 8K 独立历史的请求却需要 112.5 GiB BF16 KV。由此区分可提供的 adapter 数与可并发的请求数，再算加载等待、小矩阵执行和租户公平性。推导与历史基线条件见[多 LoRA 服务笔记](../../case-studies/multi-lora-serving.md)。

### 8.2.4 Chat 与 Agent 的前缀复用

用 vLLM APC 与 SGLang RadixCache 的同一组共享前缀请求比较重算量。接着用 2026 年 Unified Radix Cache 回到 V4／K3：全注意力、滑窗和 KDA 循环状态有不同的有效复用边界，同样匹配了 N 个 token 不代表所有状态都能在 N 处直接复用。对齐窗口与检查点以后，才核算命中节省的工作。

复用第 2、3 章的请求分布：Chat 的多轮历史、Agent 的系统提示和工具定义、工具返回后增长的上下文，各有不同的公共前缀与复用间隔。前缀匹配依赖 token 序列、模型与缓存格式；工具等待会延长 KV 驻留，reasoning 与分支会增加状态占用。

本地例子采用 Ollama 2026 年 MLX 的选择性快照：在响应前和常见分支处保存状态，以便删除旧 reasoning 或改走另一分支后继续。对照全注意力 KV 与滑窗／循环状态，算保存边界怎样影响尾段重算，再接到 8.3 的拒绝回滚；按其支持模型说明，不把两种恢复位置混为一谈。

同时区分 Ollama 的模型保留时间与前缀状态寿命：`keep_alive` 保留模型，并不保证某段 KV 仍可复用。分别记录加载、前缀命中和恢复时间，第 9 章再扩展到跨实例共享。

**占位 D11-07：** 补跨租户前缀复用的边界：内容匹配之外，还须确定信任组、命名空间和授权；以 vLLM `cache_salt` 为具体机制，计算限制共享后命中率、TTFT 与驻留的变化，衔接第 9 章共享池与第 11 章多租户。详见[缓存复用边界](../../research/draft11-outline-audit/report.md#cache)。

### 8.2.5 命中收益与缓存淘汰

同时计算按请求与按 token 加权的命中率、节省的 prefill 工作、缓存驻留量与命中后的取回时间。区分本地 HBM、主存和远程池：高命中率仍可能伴随慢取回或 decode 拥塞。用复用间隔分布决定保留多久，再把共享缓存与跨实例路由交给第 9 章。

用 Marconi（MLSys 2025）的混合模型案例解释检查点准入：循环状态不能从任意后续位置直接退回，逐块保存又可能挤掉更值得复用的前缀。先判断可恢复边界，再比较每单位状态省下的工作与再次访问机会；统一前缀身份、保留什么状态、淘汰什么状态是不同决定。其历史改造版 vLLM／SGLang 与当前 Unified Radix Cache 分开说明。

## 8.3 推测执行：增加工作换更多产出

<a id="detail-8.3.1"></a>

### 8.3.1 草稿、验证与单轮产出

先用 Qwen3-8B 画一次草稿—目标验证—提交／回退，只保留理解原理所需的早期算法。将每轮耗时除以实际产出 token 数，与普通 decode 比较；区分接受概率、接受长度及补偿 token。严格验证保持所选目标的采样分布，量化目标与原精度模型的差异另行评估。

用 vLLM 的实际计数说明：日志中的平均接受长度可包含额外产出的一个 token，草稿接受率则只数草稿。先用逐轮数据对齐分子分母，再比较平均产出／平均时间；EOS 与输出上限处按真正交付的 token 计量。2024 年的低 QPS 收益与高 QPS 退化作为引子，后面解释框架怎样按负载调整预算。

接回工具参数生成：四个草稿位置加一个额外采样位置，会增加掩码行和语法试探工作；模型 KV 与 grammar matcher 都要跟随实际提交前缀。用固定 vLLM 的临时推进／回滚及 SGLang 的状态接口说明约束，特别检查 reasoning 在验证窗口中结束的情况，不将接口存在当作所有推测组合都已支持。

<a id="detail-8.3.2"></a>

### 8.3.2 复用目标特征与草稿成本

从已有目标特征能省去什么工作引入 EAGLE，重点用 EAGLE 3.1 的归一化与反馈状态解释长上下文和提示变化下的接受长度。公开 Kimi K2.6 部署作为具体证据，保留目标／草稿版本、精度、TP 和并发；与 Qwen3-8B 小实验分别引用，不拼接速度。

## 8.4 压缩与卸载的执行代价

<a id="detail-8.4.1"></a>

### 8.4.1 权重位宽与真实驻留容量

沿 Ollama 的容量规划变化校准模型：2024 年所读实现先预测是否装得下，2025 年新引擎按 fit／allocate／commit 的反馈调整层放置；2026 年固定主线的普通模型又转交 llama-server，启动前预测与 MLX 路径分别处理。用[固定版本](../../references/framework-history/2026-09-08/overlap-placement/README.md)说明为什么要记录实际 runner、上下文、并发、图缓冲和分配结果，不能将某次公告推广成所有版本都不再 OOM。

结合 v0.30 的 GGUF 路径看实际放置：当前 runner 可自动选择 GPU 层，多模态 projector 还可能单独留在 CPU。内存报告中的 100% GPU 不等于利用率，也不说明图像阶段的耗时；将 mmap 映射、实际驻留与重打包副本分开计量。[版本与读取范围](../../references/framework-history/2026-09-08/offload-execution/README.md)供实验复核。

从“MacBook 能运行数百 B 模型”的具体说法进入。用 Qwen3-235B-A22B 的固定 GGUF 分片总量与作者 M2 Max 96 GB，逐项算权重、量化元数据、KV、工作区与系统预留。文件名的 2 bit 不等于全模型平均位宽，统一内存也不能把 CPU 与 GPU 容量相加。

<a id="detail-8.4.2"></a>

### 8.4.2 完整模型与任务质量

以 Unsloth 的 DeepSeek-R1 动态低比特量化说明不同矩阵采用不同精度的理由。保留全部专家、保持原始权重精度与达到相近质量分别检查；比较代码测试、长推理和长上下文结果。蒸馏、裁剪和量化按实际改动解释，不由“满血”一词代替。

<a id="detail-8.4.3"></a>

### 8.4.3 主存、磁盘与每步读取

当权重不能全部驻留，沿实际引擎路径计算 CPU 执行、GPU 卸载、mmap／SSD 未命中、反量化和同步。把冷加载、首 token 与持续 decode 分开；MoE 根据批内被访问专家计字节。第 9 章继续展开大型主存与少量 GPU 的协同服务。

以 vLLM 的 2024 按需搬入、2025 V1 主存映射与 2026 显式预取说明差别：GPU 读取主存权重时仍受互联约束，预取则要增加缓冲并保持图中的读写依赖。沿[Qwen3-8B 算例](../../case-studies/weight-offload-execution.md)，九层 BF16 FFN 卸载 2.53125 GiB，扣一组缓冲后净省 2.25 GiB，恰好相当于两条独立 8K KV。继续按每步搬移量和有效单向带宽判断是否值得，再比较 prefill 与 decode 的摊销。

> **实验 8-7 ★：MacBook 大模型的容量与速度**
>
> 对 Qwen3-235B 的实际量化文件逐片求和，再用 M2 Max 96 GB 的可用内存、8K／32K 上下文与并发计算驻留。对照 R1 极低比特文件，判断何时需要主存／磁盘换入；按实测或注明假设的带宽预测速度，配任务质量记录。普通电脑可先完成元数据与容量分析。
>
> Ollama 的相应本地 runner 提供加载与请求记录；极低比特格式若仅由 llama.cpp 支持则明确换用该入口，不假定两者覆盖完全一致。MLX 扩展对照只选该版本支持的模型与格式；若同时改变位宽，分别记录容量、质量与后端变化。
>
> 小模型容量变体保持 Qwen3-8B 权重不变，将独立 8K 上下文的并发槽从 1 增至 4：BF16 逻辑 KV 预算从 1.125 增至 4.5 GiB。与实际 runner 分配比较，解释分页、共享和预留的差异，不能只看模型文件大小。
>
> 卸载变体在受支持的 vLLM 版本比较按需访问与预取；按相同 FFN 参数集合核算实际卸载量，扣除一／两组静态缓冲，再检查可容纳的 KV。用明确假设的 24 GiB/s 先求每步约 105 ms 的复制服务时间，随后从 trace 看能隐藏多少；同时报告总吞吐与单请求间隔，不能把 prefill 的单输出测试当作 decode 成绩。
>
> 条件：基础·文件元数据／计算；设备测量为扩展。

### 8.4.4 KV 压缩与模型状态

用 Qwen3-8B／235B 的 GQA 与 V4-Flash 的混合状态重算长上下文成本，比较 KV 精度、稀疏访问和淘汰。权重压缩后 KV 可能先成为限制；状态结构变化还会影响分页、前缀缓存和图执行。

从 Qwen3-8B 单请求、8,192 个缓存位置算起：BF16 KV 为 1,152 MiB；若采用每 32 个值带一个 FP16 scale 的 q8_0／q4_0 格式，分别是 612／324 MiB，不能只按位宽除二、除四。以 Oaken 的异常值编码作进一步推算，再把工作区、分页与对齐加回容量预算。沿 vLLM 的 FP8、SGLang 的分阶段量化路径和 Ollama 的本地缓存，区分存储格式与 Attention 执行精度；用上下文长度扫描，判断融合转换和原生低精度计算何时能抵消固定开销。

结合 MLSys 2025 对 KV 压缩的实证研究，解释少存字节之后还要付出选择、解压或误差补偿的工作。再算整次请求：如果 decode 速率提高 20%，输出却增长 50%，仅看 token/s 就会误判。固定形状测执行成本，自然生成测长度、逐任务质量和完成时间；两类实验共同决定是否值得压缩，不把旧模型结论直接移给 V4/K3。

> **实验 8-8 ★★：KV 压缩与任务质量**
>
> 固定前文模型、量化权重与长文档任务，改变 KV 精度或保留策略，计算容量和每步读取，再比较质量、时间和可接纳并发。V4 的不同状态按各自格式计算，不套 GQA 公式。
>
> 以固定引擎实际支持的 KV 格式作实验；模型原生压缩与运行时 KV 量化分别开关和校验。先用算例拆出数值、scale 与工作区字节，再选一个相容后端扫描上下文长度与并发，记录实际分配、转换 kernel、TTFT 和 ITL；判断少存的字节是否真的减少了关键路径上的访存。
>
> 增加同一任务自然结束的对照，固定采样设置与最大生成上限，记录输出长度、终止原因、质量和整次耗时；单独报告被上限截断及需要重试的请求。检查固定输出长度的速度排名是否仍成立。
>
> 条件：进阶·模型实验／配套数据分析。
