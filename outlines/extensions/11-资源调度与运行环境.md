<a id="detail-11.1.2"></a>

### 11.1.2 共享平台与并发需求

对稳定任务流先用 `平均环境数 = 到达率 × 平均驻留时间`，再乘每环境内存；CPU 核时按实际执行另算，预热池和突发余量另加。代码执行、浏览器和 RL 验证的资源组合由具体任务决定。

例如每秒进入 10 项任务、每项驻留 30 秒、每环境占 2 GiB，则平均需要约 300 个环境和 600 GiB 内存；若每项只执行 3 核秒，平均 CPU 工作量约为 30 核。用这个差距引出等待模型时暂停环境的收益与恢复代价。数值为教学输入，平均值不能直接当作满足 P99 的配置。

## 11.3 资源池与生命周期调度

<a id="detail-11.3.1"></a>

### 11.3.1 异构设备、成组分配与资源碎片

接回第 6、7 章算出的并行方案：一个作业需要的不是任意若干张卡，还包括卡型、主机内存、CPU 和网络位置。用 ASI 的生产集群研究（OSDI 2026）解释空闲设备为何仍分配不出去，再比较打包放置、迁移整理和跨交换机放置，权衡等待完整一组设备与立即开跑之后的通信代价。

在同一资源图上加入在线服务预留与低优先级任务，用完成进度、等待上限和抢占损失讨论公平性。DRF、Gavel、Pollux 作为历史背景简述。ASI 的 GPU 分配比例不能当作 MFU，异构设备不能按卡数等价替换。自建模型服务还需计算权重加载、初始化和热副本预留；多 adapter 只在共用基座时节省相应权重。

直接使用 9.6 的引擎启动记录估算新副本何时真正能分担请求；即使 GPU 已分配，CPU 准备、编译与图捕获尚未完成，队列仍在增长。扩缩容比较保温费用、准备时间和积压消退，不能只用稳态 token/s 推导资源供给。

承接 Elastic EP 的组规模变化，区分引擎提供的重配置机制与平台何时触发它的策略。先比较热点预计持续时间和搬移回本时间，再看切换期间的队列与缩容后的 KV；保持 GPU 数不变的专家分派和新增 GPU 不能用同一个收益口径。

接回实验 3-2／9-2 的请求组成变化：QPS 没有增加，decode 池仍可能积压。沿[同一算例](../../case-studies/workload-and-provisioning.md)比较预留 D 热副本、将 P 改成 D 和等待突发结束；只有新角色在需要它的时段内准备好，重配才能缓解这次等待。

用 Rubick（MLSys 2025）补充另一种选择：沿前章推算，为同一训练作业保留几种并行、重计算和卸载方案，再根据 GPU、CPU 与互联余量选择。比较多给一张卡与多给 CPU 的实际收益；少量测点校准各阶段及重叠，预测有偏差时更新。保证相同训练目标并计入检查点和重启成本，避免把缩放卡数视为无代价操作。

沿第 7.5.1 的通信记录，用 CASSINI 补充网络位置的时间因素：上层已经决定卡数和 batch，调度器仍可在等价放置中选择共享链路需求更合适的组合。让三个作业经过两条或三条共享链路，检查每个作业能否只有一个一致的启动偏移；论文采用无环作业—链路图保证这一点，并修正运行中的漂移。它假定各作业独占 GPU、训练网络相对独立，与下一节 RL 资源池的阶段共享分别讨论。[案例与局限](../../case-studies/network-planning-and-collectives.md)

### 11.3.2 RL 阶段切换与可抢占资源

用 RLBoost（NSDI 2026）的 Qwen3 8B–32B 案例连接第 10 章：训练组保留紧密互联的设备，额外资源承接 rollout。先根据采样量、训练耗时和权重分发求出增加 rollout 设备的收益上限，再解释为什么需要动态调整。

计算实例出现后加载权重的时间、抢占时已生成 token 的保存，以及换实例重新 prefill 的代价。论文的部分响应续接适用于其生成路径；带工具调用的 Agent 还要保存环境与外部操作状态，不能认定所有 rollout 都无状态。训练检查点继续沿用第 10 章。

用 Weave 的跨作业共享补充“不增加资源”的选择。给两项 Qwen3 教学任务的 rollout／训练分别设为 360／120 秒和 120／360 秒，先画出共享双池仍保持 480 秒周期的稳态时间线；再换成两个 rollout 都为 360 秒的任务，仅资源下界就达到 720 秒。按作业允许的减速、逐主机状态容量和交接成本决定是否共享，不能只看空闲卡数。[算例与论文条件](../../case-studies/rl-scheduling-and-recovery.md)连接第 10.5 节。

资源还承担恢复职责：沿 RobustRL 比较额外空闲温备与借用同型 rollout 机器，计算 trainer 少等多久、采样少产多少及新实例补齐时间。异构部署需要明确预留可替换的卡型、拓扑和环境，不能把任意空闲 GPU 都当作备用机器。

> **实验 11-4 ★：可抢占 rollout 的有效产出**
>
> 给定 Qwen3 权重大小、网络吞吐、生成记录与抢占时刻，比较固定资源、额外 rollout、保留部分响应后三种安排。计算完成同一批有效样本的时间与费用，改变资源存活时间，求出增加资源不再划算的条件。
>
> 多作业变体先用两组阶段时间排除不满足 SLO 的共享方案，再加入热／冷切换和主机容量；分别报告每作业周期与两池配置成本。时间线取自受支持的实际 RL 后端或明确标注的教学记录，不将 ROLL 上的 Weave 当作 vLLM 默认调度器。
>
> 条件：基础·计算／短脚本；论文实例配置和教学价格分别标注。

### 11.3.3 RL 验证的批次约束

用 DistRS（NSDI 2026）的 CUDA 代码验证引入 CPU 编译与 GPU 执行两类资源。样本陆续生成，训练却要等整批反馈；先画少量样本的到达和完成时间，算最早批次完成点，再决定编译与执行 worker 数。早到的验证不必全部立即运行，关键是不能拖住批次末尾。

与第 5 章优化 Agent 相连：这里的编译、正确性检查和 profiling 都是实际工具工作。并行生成候选可以扩充 CPU 环境，但性能计时需要控制 GPU 竞争，不能让多个候选互相干扰后再拿噪声作为优化奖励。

在此基础上解释历史批次预测、批次优先级与超时后的资源调整。论文使用历史记录驱动的搜索；本书先用纸笔下界排除不合适的配置，仅在尾部到达和竞争会改变结论时回放记录。分别统计 CPU 核时、GPU 时和训练等待。

用[条件剩余时间与框架对照](../../case-studies/reward-deadlines-and-feedback.md)展开：九条 1 秒、一条 100 秒的历史，平均 10.9 秒；执行了 10 秒仍未完成时，条件剩余时间为 90 秒。再给 120 秒批次目标和 100 秒执行上限，推出最迟 20 秒启动。若节省 60 GPU·秒却让仍占有 64 张卡的训练组多等 2 秒，在相同单位成本下反而多占用 68 GPU·秒；能够转借资源时另算实际代价。

固定 verl v0.4.1 与 2026-09-07 提交，比较整批生成后异步评分与 Agent Loop 逐条评分的具体入口。逐条提交提供重叠机会，DistRS 的跨作业批次优先级和阶段资源规划仍需另行实现。所读限流路径的执行超时不含前置排队，等待超时也不证明同步线程或外部 GPU 工作已停止；实验分别标记反馈与释放。PolyRL 的文档示例与论文配置差别放在案例中，不将定制 SGLang 接口写成标准框架默认能力。

用第 10 章 RollPacker 的[自适应验证超时](../../case-studies/rollout-tail-and-sampling.md)补一个取舍：较短限额减少等待，也可能把较慢的正确程序记为零奖励。将测试执行、CPU 竞争和 RPC 等待分开，抽样用较宽限额复验，判断省时是否改变了训练反馈。

> **实验 11-5 ★★：验证资源与训练等待**
>
> 给定两批代码的生成时刻、编译与执行时间，手算最早完成点，再比较固定配额、先到先服务与按批次目标分配。加入长尾与超时样本，分别记录排队、执行、反馈返回和资源释放，核算资源节省是否抵得上训练组的额外等待。
>

>

### 11.4.1 容量采购与按量调用

从同一位开发者的月度代码任务出发，比较订阅内使用与自建 Agent 调用 API 的费用和限制。扩写时安排一张小表，以 Claude 与 Gemini 的官方方案为例，列订阅费、使用入口与额度、超额计费、API 输入／输出价格、缓存费用及速率限制，保留日期、地区和档位。

解释订阅费怎样摊到实际完成的任务，API 费用又怎样随上下文、思考长度和重复调用增长。消息或计算额度、特定应用积分与 API token 不是同一单位；有无开发者额度逐项核对。比较同类任务的实际账单，不能由月费推出订阅相当于 API 的固定几折，也不能把使用上限当作无限供给。

<a id="detail-11.4.2"></a>

### 11.4.2 服务入口、后端与缓存身份

沿“Agent → 中转入口 → 上游服务 → 流式返回”说明鉴权、接口适配、后端选择、限流、回退与计量，这是模型中转服务的基本请求路径。比较上游按量 API、购买或自建的推理容量，以及通过产品允许的入口使用订阅额度：来源不同，价格、并发和可持续供给也不同。不能把所有中转服务都解释成订阅与 API 的价差。

从上游与下游两张账单计算服务收入、容量及运维成本，再加额外网络跳转和排队。模型名称相同仍要核对实际版本、量化、上下文、reasoning 设置和缓存支持；中转层若改变这些条件，输出 token 单价就不足以说明服务是否等价。

> **实验 11-7 ★：订阅、API 与中转费用**
>
> 用相同月度任务集与公开方案快照，分别算订阅的实际完成成本、API 账单和中转服务成本。列出受额度或并发影响而未完成的任务，求不同使用量下的费用交点；没有可换算的产品用量时保留未知量，不补造 token 配额。
>
> 条件：基础·计费表与任务记录分析；不要求购买服务。

> **图 11-6：模型调用的请求路径与计费位置（配图计划）**
>
> 自绘 SVG，连接客户端、中转层与不同上游，标明排队、缓存、计量及付费位置；订阅入口按实际产品边界单独标出。

<a id="detail-11.4.3"></a>

### 11.4.3 任务质量与思考预算

用“一个模型思考 100 个 token，另一个需要 1,000 个”引出选择。固定任务和质量门槛，比较实际 reasoning token、可见输出、工具调用次数与成功率；区分配置预算、实际用量和预算截断。少思考却经常失败的模型未必经济，隐藏思考不能用可见摘要长度估算。

先做等单价教学算例：输入 10,000 token、可见输出 200 token，输入／生成价格分别为每百万 2／10 美元。实际思考从 1,000 减为 100 token，单次费用由 0.032 降为 0.023 美元；思考部分缩为十分之一，总费用并没有缩为十分之一。换模型时重新代入各自 tokenizer、计费项与速率；reasoning 若已含在 output usage 中，不再加一次。

再比较首段可用结果与任务结束时间。思考与可见输出速率、排队、prefill 和工具等待共同决定延迟；每秒输出更多 token 的模型，可能因为生成更长而更晚完成。先用分阶段预算解释，再用任务记录检查延迟和质量分布。

<a id="detail-11.4.4"></a>

### 11.4.4 前缀缓存的成本与延迟

把第 8、9 章的 KV 复用接到 API 选择：重复系统提示、工具定义、仓库内容和多轮历史能命中多少前缀，多久再次访问，换后端会丢掉多少复用。分别计算未缓存输入、缓存创建、命中读取和按时长计费的存储；比较请求命中率与 token 加权命中率。

安排 10 轮代码 Agent 算例，固定公共前缀，再改变新增上下文、命中比例、轮间间隔和 TTL，算缓存费用的交点。结合最低缓存长度、前缀变化与工作区边界解释命中条件。API 缓存 token 是计费和复用证据，不能直接反推出 KV 在哪级存储或读取多少字节；资源模型回到第 2、9 章。

命中主要改变前缀处理，不意味着 decode 或 reasoning 自动免费、加速。比较“命中但排队”与“空闲但要重算”，把缓存亲和性、传输和容量压力放进预计完成时间；更换模型或供应商通常不能延续原缓存。

<a id="detail-11.4.5"></a>

### 11.4.5 质量、成本与完成时间的联合选择

**占位 TC-16：** 补价格竞争、模型路由与能力价格前沿，区分 API 售价和生产成本。 详见[成本下降调研](../../research/token-cost-2023-2026/report.md#economics)。

将候选写成“模型版本＋服务商／副本＋思考预算＋缓存条件”，先排除不满足质量、上下文和功能的选项，再比较完成时间和成功任务成本。限流区分请求数、输入／生成 token 及并发槽位；长 reasoning 会占用更久的槽位，也可能降低有效请求吞吐。

用同一任务集比较固定模型、按任务选择、失败后升级，以及保持缓存亲和性的路由。计入路由判断、排队、超时、失败尝试与回退后的缓存重建；自建后端还要计入冷启动、热副本及共享容量。第 9 章负责同模型 KV 放置，本节解释跨模型、跨服务选择如何反过来影响它。

补[两套假想服务的完整手算](../../case-studies/routing-cost-and-completion.md)：各提交 1,000 个任务，分别用实际思考量、互斥输入计费项和通过任务数计算费用。B 的单价更高，全部命中时成功任务成本却更低；改变请求命中比例，求出约 84.93% 的费用交点。再用给定的完整请求耗时检查 6 秒时限与 90% 联合通过条件，得到约 91.84% 的最低命中比例。先区分这两个判断，再用真实记录检验质量、命中和耗时的相关性。

> **实验 11-8 ★★：思考预算、缓存与模型选择**
>
> 使用含实际用量字段的配套任务记录，改变 reasoning 预算、缓存命中和后端排队，比较固定路由、最低 token 单价与质量约束下的完成成本。提交成功任务费用、首段可用结果时间、总完成时间和失败率；加入“100 对 1,000 个思考 token”与“缓存命中但有队列”两组手算，解释选择何时变化。
>
> 手算变体采用上述 A／B 数据，先求费用交点，再加入任务完成时限。所有失败尝试都计费；分母为同一任务集内的通过数，不假设重复尝试一定成功。请求命中率、全部输入的 token 命中率与跨模型缓存身份分别说明。
>
> 条件：进阶·先估算再离线回放；扩写时提供记录和版本，不用虚构结果代替测量。

## 11.5 任务续接与完整成本

<a id="detail-11.5.1"></a>

### 11.5.1 工具失败与任务续接

沿跨模型与工具的任务讨论取消、幂等、已有输出及外部副作用，比较整项重做和局部恢复。模型回退与环境恢复是不同操作，换模型仍需接上正确文件和工具状态。

以代码 Agent 测试已完成、确认却丢失为例，区分逻辑操作、重传消息与重新执行的尝试。核对结果持久化位置、文件版本和尝试身份，再决定查询或重试；消息队列去重和 E2B 快照恢复都不能独自保证外部操作只发生一次。任务结果用于续接与核算，诊断 trace 可以采样，RL 反馈还需满足轨迹与验证条件。三种记录共享身份，不能相互替代。

<a id="detail-11.5.2"></a>

### 11.5.2 任务成功率与总成本

**占位 TC-17：** 补包含思考、重试、工具和环境的成功任务成本算例。 详见[成本下降调研](../../research/token-cost-2023-2026/report.md#economics)。

将模型账单与 CPU、环境驻留、存储、网络、空闲预留汇合，计算 `总支出／满足质量条件的完成任务数`。失败和超时的花费留在分子中；订阅、资源采购与按量调用按实际范围入账，不能重复计费。

再算记录本身的供给：沿 10 tasks/s，每任务 20 条、每条 2 KiB 的必需事件，产生 400 KiB/s；后端中断 120 秒积压 46.875 MiB。恢复后即使能排出 1 MiB/s，新事件仍在到达，净排空约需 76.92 秒。用 OpenTelemetry 的队列、重试与持久化条件检查这个预算；诊断采样可以省流量，却不能代替完整账本。数值为[教学输入](../../case-studies/evaluation-and-agent-records.md)，实际元数据、保留期及故障范围另计。

> **实验 11-9 ★★：重试、成功率与任务费用**
>
> 在实验 11-8 的模型记录上加入工具失败与环境恢复，比较整项重做、局部续接和模型升级的总成本与时间，解释单次调用省钱为何不一定使任务省钱。
>
> 记录变体注入结果已提交但确认丢失、采集后端中断和恢复，先算 32／64 MiB 载荷缓冲及排空时间，再核对消息重传去重与真实重执行的费用。用固定 OpenTelemetry Collector 的配套记录检查队列、重试和落盘；诊断 trace 的采样不改变必需任务记录的完整性要求。
>
> 条件：进阶·数据分析；保留同一质量门槛及全部失败尝试。
