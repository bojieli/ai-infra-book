# 第 6 章 超节点

> 写作大纲 · 多卡切分、通信实现与超节点规模选择 · 2026-09-10

第 5 章在芯片内组织数据复用，本章把计算和状态切到多张卡。由逐卡需求推出 TP、PP、DP、EP 及组合，再决定需要多大的紧密协作范围；拓扑与产品在具体限制出现时引入。

**本章判断：** 并行换来容量或处理能力，也增加交接与同步。总容量足够时仍要检查最忙设备；同一组卡应扩大协作还是增加推理实例数量，取决于负载和时限。

**前置与交付：** 依赖第 3、5 章；交付逐卡状态与跨边界流量，第 7 章沿实际路径继续计算。

**阅读安排：** 核心练习为实验 6-2、实验 6-3、实验 6-10；其余练习为延伸。每节的完整参数、实现版本与实验变体见对应[扩写资料](extensions/06-%E8%B6%85%E8%8A%82%E7%82%B9.md)。6.2、6.3 先形成并行候选，6.4、6.5 校正通信实现与物理路径代价，6.7 用实验 6-10 完成规模选择。章末更新[跨章设计决定](decision-record.md)。

## 6.1 从单卡到多卡

先比较独立推理实例和共同执行，再判断一次任务为何需要跨卡。总需求和局部需求分别记录。

### 6.1.1 独立部署还是多卡协作

手上有八张卡，是运行八个独立推理实例，还是让多张卡共同执行一个请求？先固定质量、请求和完成目标，分别提出容量不足、吞吐不足和单请求延迟过长三种情形；本节建立预算，6.2 再用具体切分比较。

这里的“推理实例”指能够独立完成模型推理、承接请求的一组执行资源。每个实例持有完整模型，模型可以放在一张卡上，也可以通过 TP／PP 等方式分布在多张卡上。同样八张卡，可以部署八个单卡实例、两个各用四卡的实例，或一个使用八卡的实例；分别核算实例内协作与实例间请求分工。

复用第一章的资源地图和第四章的互联图，在图 6-1 的物理概览中标出单卡、服务器、超节点与跨超节点边界。超节点按紧密协作范围理解，服务器和机柜数量由具体实现决定；端口与拓扑细节在 6.5 展开。

从单卡、八卡服务器到更大超节点，固定 GPU 可用显存、有效矩阵性能、HBM 带宽、卡间单向带宽与小消息延迟；模型、精度、请求长度和并发共同构成实验输入。先用一组条件完成推算，再换硬件检验原选择是否仍然成立。

### 6.1.2 从单卡需求到逐卡容量与时间预算

**贯穿配置查阅：** 复用第 2、3 章配置：Qwen3-8B Dense；235B／22B 激活的 Qwen3 MoE 与 284B／13B 激活的 V4-Flash；约 1.6T／49B 激活的 V4-Pro 与 2.8T／104B 激活的 Kimi K3。DeepSeek-V3 的 671B 总参数作为历史过渡。它们代表不同规模与结构，不能写成参数量完全相同的模型。

配置表用于查阅，按推导阶段引入模型：先以 Qwen3-8B 讲清 Dense 切分，再用 Qwen3-235B 与 V4-Flash 比较专家放置，最后用 V4-Pro 与 Kimi K3 检查规模和结构改变后的选择。第 2 章已有的模型需求在这里作为输入，本章新增逐卡放置与跨卡交换。

逐卡检查 `权重＋KV／递推状态＋激活＋工作区 ≤ 可用内存`。分别数每步实际激活专家的权重读取、所有活跃序列的 KV 读取、算子 FLOPs，以及每条必要链路的字节和启动次数；总参数、激活参数、实际读取字节不能相互替代。

给出第一遍时间下界：本地计算 `F/P`、本地读取 `(W_read+KV_read)/B_mem`、路径传输 `V/B_link` 与必要同步；共享链路合并流量，串行依赖沿实际时序累加。以最忙的设备或链路定位瓶颈，再决定该减少哪项工作。

### 6.1.3 Prefill、Decode 与训练为什么提出不同要求

同一模型分别代入一段 prefill、一次 decode 和一轮训练。低并发 decode 的小消息与逐层依赖，不能按大矩阵 prefill 的带宽效率估计；训练另有梯度、优化器和反向通信。增加推理实例数量主要改变吞吐，把一次计算分到多卡可能改变容量与单请求延迟，两者从计算结果比较。

> **实验 6-1 ★〔延伸〕：模型与硬件的资源收支**
>
> 先对 Qwen3-8B 完成逐卡容量和每 token 的计算、权重／KV 读取，再换为 Qwen3-235B 与 V4-Flash；固定一组 prefill／decode 输入，指出每个候选方案首先受容量、内存带宽、算力、互联带宽还是延迟限制。
>
> 条件：基础·手算／短脚本。

**计算结果（6-1）：** 同一组八卡上，六个场景的首要限制并不相同：Qwen3-8B prefill 始终受算力限制，decode batch=64 在单卡上先受容量限制、切开后转为内存带宽限制；Qwen3-235B 与 V4-Flash 在 TP≤4 时全部卡在容量上，只有 TP=8 才进入时间比较。互联在 Qwen3-8B prefill 的 TP=8 处成为首要限制（21.81 ms 超过算力的 16.88 ms）——切得越细，交接越贵。[逐候选收支表](../experiments/ch06/06-01/README.md)。

## 6.2 Dense 的多卡执行：数据并行、TP 与 PP

沿同一矩阵逐步增加 TP 或 PP，比较减少的本地工作和新增交接；用注明假设的通信代价输出初步候选，6.4、6.5 再校正实现与物理路径。

### 6.2.1 Qwen3-8B 的多实例推理与训练数据并行

从单卡可以驻留的请求开始，比较八个推理实例、少量 TP 的多个推理实例、以及把八张卡交给一个请求。训练 DP 为不同卡分配样本并同步梯度，推理实例不需要这项同步；把两者分别放回自己的工作流。容量充足并不自动说明需要模型并行。

### 6.2.2 张量并行与层内数据交换

沿 Qwen3-8B 的实际 QKV、输出投影和 SwiGLU，画列切分、行切分，以及必须归约或收集的张量。逐卡写矩阵尺寸，比较减少的权重／计算与新增通信；KV 头分片和复制按实际实现处理。用 TP=1、2、4、8 的 prefill 和 decode 推算解释适用条件，不能把 TP≤8 当成通用规则。

按“原矩阵与结果—每卡分片—局部结果—下一步缺少的数据—必要通信”的顺序推导。行切分得到部分和且各卡后续都需要完整结果时，用 all-reduce 求和并分发；各卡持有不同片段而后续需要完整张量时，用 all-gather 收集；归约后只需各卡保留对应分片时，用 reduce-scatter。操作由输入与输出布局决定，先画数据归属再命名，环／树实现与实际耗时到 6.4 校正。

先完成这一组基本切分，再在扩写资料中比较保留双模式状态与二维切分流水。Arctic 和 MeshSlice 分别提供这两种设计的具体对照，正文不在基础 TP 推导中同时展开多套调度与状态组织。

### 6.2.3 流水线并行与组合方案

按层划分 PP，计算每个阶段的权重、状态、计算与边界激活。PP 通常减少层内的频繁协作，但一个 token 仍须经过相应阶段；微批与并发才可能填充流水线。比较 TP×PP 与多个推理实例，保留首 token、逐 token 延迟、吞吐和训练气泡的不同目标。

以 BF16 的 4096 维激活为例，一个逻辑张量每 token 为 8 KiB，8192-token prefill 对应 64 MiB；实际 PP 载荷还要按实现加上 residual 等交接状态；TP 的集合通信还要按算法、分片与轮次计算实际链路字节。改变消息规模后，同一网络延迟对两者的影响不同。

> **实验 6-2 ★〔核心〕：Qwen3-8B 的并行组合**
>
> 在同一组八卡资源上比较独立推理实例、TP=1／2／4／8 与若干 TP×PP 组合。逐卡算权重、KV、计算及每层通信，用实际或注明假设的 α、带宽修正；扫描 batch 和长度，给出各服务目标下的候选区间，再提出一项最值得补测的量。
>
> 延伸入口：四卡 SP×TP／完整 TP 的双模式切换放到第 9.6.2 节，届时沿用本题固定切分，再检查 KV 头身份、额外权重与切换准备。
>
> 条件：基础·手算／短脚本。

**计算结果（6-2）：** 八卡上八种组合的容量全部通过，取舍在两端：纯副本给出 64 路并发但 32K 历史时最忙卡驻留 53.3 GiB，TP=8 把逐卡驻留压到 5.03 GiB、逐卡矩阵工作压到 1/8，全局并发却只剩 8。TP 增大不改变每层激活载荷（8 KB），只把词表 logit 分片按 TP 均分；流水线组合把每步非空通信操作从 75 增加到 77–79。最值得补测的是 TP=8 每层 all-reduce 的实际启动开销 α。[逐卡收支、通信与候选区间](../experiments/ch06/06-02/README.md)。

**部分实测：** [JAX实际TP/SP路径](../experiments/ch06/06-02/jax-tp-sp/README.md)执行了Qwen3-8B形状的完整FFN子层，8个配置均通过FP64参考检查，配对TP/SP输出逐位相同。SP减少了每rank保留的输出，但需要聚集和分散归约；此处是单机CPU实现核验，不能代替八卡性能测量。

## 6.3 MoE 的多卡执行：专家放置、复用与负载

先放置专家与注意力状态，再跟踪 token 的跨卡执行；将独立专家集合和每专家 token 数分别计量，检查最忙卡及路由差异怎样改变选择。

### 6.3.1 专家权重与注意力状态怎样放到多张卡

固定 Qwen3-235B-A22B 的 94 层、4096 隐藏维度、128 选 8 路由专家、1536 专家中间维度，以及 V4-Flash 的 43 层、4096 隐藏维度、256 选 6 加共享专家、2048 专家维度。Qwen 的 GQA 与 V4 的混合压缩注意力分别核算 KV，不能由接近的总参数量推断相近的状态与通信。

用统一 BF16 权重作第一轮教学估算，两者约需 470 GB 与 568 GB；相对于八张名义 80 GB 卡，总容量看似都够，留给 KV、工作区和不均匀放置的空间却不同。随后按实际混合精度、量化附加数据和逐卡放置重算，统一 BF16 不是 V4 发布权重的实际格式。

先在八卡图上分配专家集合，并标出注意力权重、KV 与共享专家是分片还是复制；逐卡计算容量余量，再进入 token 交换。第二章交付的逻辑模型需求在这里转成设备所有权，容量通过只是后续候选的必要条件。

### 6.3.2 Token 怎样到达专家：EP 与 dispatch／combine

沿一个 token 画 dispatch 到目标专家、专家计算、combine 返回并按路由权重汇合的过程。all-to-all 表示各参与者向不同对端交换各自的数据；MoE 的消息大小可不相等，具体实现也可采用变长交换或点对点组织。先确认发送者、接收者与输出归属，6.4 再比较实现代价。

把专家分配到不同卡，计算每个专家收到的 token 数、局部矩阵、共享专家工作以及 dispatch／combine。按 token 实际选择的远端设备计流量：同一设备承接多个被选专家时可以复用或合并传输，不能直接把 top-k 当成 k 个不同目的地。接着比较 EP、专家内部 TP、attention TP 和推理实例的组合，明确各通信组的成员与数据所有权。

### 6.3.3 批内复用与负载不均：为什么要看最忙卡

以 Qwen3-235B 的单专家 BF16 权重 36 MiB 为起点，区分总驻留、每 token 选中的专家和批内独立活跃专家。8 个输入 token 若都选同 8 个专家，理想一次读取涉及 288 MiB；均匀独立路由的期望则约为 1.815 GiB。再用真实路由重算逐卡读取与每专家矩阵：decode 的复用收益与 prefill 的计算长尾可能指向不同放置，不能仅按激活参数或平均 FLOPs 决定 EP。

实测（部分）：[完整 V4 的真实路由](../experiments/ch06/06-03/README.md)在4个冻结输入上记录了43层、约131万次专家选择，答案与此前运行一致。不同专家的选中频率明显不同；decode每题仅4个输入，包含调度器额外执行的EOS前向，不能当作稳定分布。图中展示实际路由，跨卡放置与通信性能尚未实测。

### 6.3.4 从数千亿到万亿参数：并行组合怎样变化

V4-Pro 与 Kimi K3 分别沿自己的层数、注意力状态和专家结构推算。K3 的 896 选 16 路由专家在 3584 维潜空间工作，另有 2 个全宽共享专家，首个 dense 层和 MTP 单独计数；路由激活应按实际跨卡表示计量，不能直接套 7168 维全宽传输。总权重、实际激活矩阵、专家粒度、状态和同步次数一起决定放置。

先得到给定质量与服务目标下的可行组合，再在明确的候选范围内求预计时间最短或成本最低的切分，并检查其瓶颈；资料缺失或两方案差距小于估计误差时，输出候选范围与补测条件。以真实模型的不同规模比较为主，若统一总参数预算做反事实实验，明确它是教学控制变量，不改写产品规格。

> **实验 6-3 ★★〔核心〕：MoE 结构与并行选择**
>
> 对 Qwen3-235B／V4-Flash 和 V4-Pro／Kimi K3 两组案例，扫描 EP、TP、PP 与推理实例数量。逐项统计权重驻留、每 token 的专家／KV 读取、计算、dispatch／combine 与最忙设备；分别改变 prefill 长度、decode batch、互联带宽与延迟。说明每次选择改变的瓶颈，未知字段保留区间。
>
> 条件：进阶·配置复算／路由记录。

**计算结果（6-3）：** 纯 EP 的八卡物理权重比纯 TP 多 110 GB（582.1 对 471.7 GB），BF16 可并发请求只有 3 对 47——EP 省的是专家权重的重复，注意力与嵌入仍每 rank 一份。dispatch 的总发送字节与路由分布无关，最忙 rank 的接收量却完全取决于它：1,024 token/rank 时均匀路由每 rank 收 56 MiB，热点路由下有一个 rank 收 448 MiB，时间差 7 倍；换互联只改变斜率，治不了倾斜。真实采集的 1,313,220 个专家 assignment 覆盖全部 43 层，前 3 层用 HashTopK。[切分扫描、dispatch 与真实路由](../experiments/ch06/06-03/README.md)。

## 6.4 集合通信的实现与执行代价

承接前两节已经推出的集合操作，依次核算算法轮次与字节、通信库的资源占用及专用卸载。逻辑消息到实际拓扑的映射在 6.5 继续校正。

### 6.4.1 从并行切分汇总通信需求

用一张通信需求表汇总 TP 的部分和／分片、训练 DP 的梯度以及 EP 的 token／专家结果，列出输入归属、输出归属、参与者、逻辑载荷、调用频次和必要先后关系。与 6.2、6.3 的候选逐项对应，再将同一逻辑操作交给不同算法与实现。

回到刚算过的 TP 与训练 DP，汇总 all-reduce、all-gather、reduce-scatter 分别补齐哪项数据。下一小节用四个参与者跟踪每轮字节，再代入前面真实模型的消息大小。

汇总前节从路由到专家的 all-to-all，列出通信对象、数据量与不均匀性。和梯度归约对照，让读者理解相同总字节并不意味着相同完成时间。

### 6.4.2 环、树与通信轮次

沿一次集合通信画出轮次和链路占用，由消息大小、带宽和启动延迟比较算法。再加入分块、流水与多通道，说明选择为什么随规模变化。

以 p 个参与者、每个输入 M 字节的简化 ring all-reduce 为例，写出 `T ≈ 2(p−1)α + 2(p−1)M/(pB)`，说明轮次项与传输项从哪里来。先用小例子比较消息大小改变后的选择，再由实际拓扑和归约成本修正；公式不替代所有集合算法。

> **实验 6-4 ★〔延伸〕：环与树的选择条件**
>
> 这条消息用环还是树更合适？ 手画四个参与者的环与树，算轮次和字节；用短脚本扫描消息大小，提交选择条件。
>
> 条件：基础·Python。

### 6.5.1 直连、交换与分层拓扑

从端口和路径预算比较小规模直连、交换结构和更大型超节点。让同一组训练／推理通信经过不同拓扑，观察端点注入与共享链路如何限制性能。

用 Swing 的物理路径案例补上公式里隐含的条件：沿 Qwen3-8B 的 BF16 `[1024,4096]` 激活取 8 MiB 归约输入，在 16 节点双向环上比较 reduce-scatter 的前三轮，两种算法每节点都发送 4、2、1 MiB，但最拥塞有向链路分别承担 4／4／4 和 4／2／2 MiB。让读者先数路径，再理解为什么相同算法字节与轮次不等于相同时间；多端口和拓扑形状也会改变结果。论文收益来自 torus 网络仿真，大消息下仍有其他算法胜出，不能直接当作 TPU 或 NCCL 实测。推算与采用范围见[集合通信与作业错峰](../case-studies/network-planning-and-collectives.md)。

[OpenTallas 的通信跨度修正](../case-studies/opentallas.md)提供一个先预测再揭示遗漏路径的变体：60 层、每层两次不可重叠通信，100 µs token 目标只留 30% 给通信，单次预算为 0.25 µs；15 hop、每 hop 100 ns 的传播下界却为 1.5 µs，全 token 为 180 µs。按一次局部 hop 计价会误判可行性，需重选拓扑、切分或时限。上述为教学输入；项目历史版本与当前修正分别保留。实验 6-6 在同一图上对照局部 hop 与完整跨度，不另设练习。

**计算结果（6.5.1）：** 把同一算法换成 Qwen3-8B 的真实 36 层重算，可以把"多少跳才不成立"解出来而不只是举一个失败例子：72 次集合通信、100 µs 预算的 30% 分给通信，单次可用 0.4167 µs，因此单次预算只容许 4 跳直径，整个 token 预算只容许 13 跳；14 跳起仅传播就超过整个 token 预算，案例的 15 跳网格落在失败侧（超出 1.080 倍）。权重按 64 MiB 片上容量摊到每层 6 个 tile 时直径只有 4 跳，说明失败与否取决于切分粒度而非"晶圆一定输"。列切分与行切分把同样的字节换个方向搬：前者每层扇出 49,152 B、扇入 8,192 B 且无需归约，后者正好相反并多出归约轮。[逐项跳数、扇出扇入与直径阈值](../calculations/results/weight-resident-qwen8-8k.md)，宽网格变体见[15 跳的同一预算](../calculations/results/weight-resident-qwen8-wide-mesh.md)。

再用四卡 PCIe 机器承接 Qwen3-8B 的 8 MiB AllReduce：逻辑发送量都是 48 MiB，把中转缓冲全放在一个 NUMA 节点或靠近发送 GPU，CPU 间互联的流量却不同。先逐段算字节，再以 TCCL 的作者材料和当前 NCCL 路径作对照，解释为什么拓扑、ring 次序与缓冲放置要一起考虑；具体假设与下界见[中转算例](../case-studies/pcie-staging-and-numa.md)。

## 6.6 内存池：共享容量与远端访问

从局部不足、全局空闲的实际问题进入内存池，再分别检查冷状态和活跃数据的搬移频次。

### 6.6.1 局部容量不足与全局空闲

以作者早期 UB 内存池的设想进入：一台机器的计算已经很忙，内存却有剩余；另一台机器先被容量卡住。先判断借用容量能解决什么，再跟到后来的 KV cache 应用。

用四个节点各有 64 GiB 可用内存、同时需求为 80／48／32／32 GiB 的教学例子：总需求 192 GiB 小于总容量 256 GiB，仍有一个节点短缺 16 GiB。比较增加本地内存、迁移任务与从池中借用，区分容量节省、复制减少与实际访问成本；不把这个假设配置当成某款 GPU 的远程寻址能力。

### 6.6.2 内存借用与访问边界

按 UB OS 参考设计的内存导入、导出、借用与共享机制，画本地内存、远端内存和地址映射的关系。统一地址、可远程访问和缓存一致性分别解释；哪一方保留访问权、何时归还以及故障时怎样处理，回到具体机制。将容量与带宽分别算，不能把各节点标称内存带宽相加当成借用者可用带宽。

### 6.6.3 共享容量与 KV cache

承接作者“有了内存池以后，什么应用最值得用”的问题，比较冷前缀、等待恢复的会话与正在逐 token 使用的 KV。先按每次读取的字节和频率判断远端链路能否承受，第 9.5 节再展开共享 KV 池、PD 交接和前缀复用。

> **实验 6-9 ★〔延伸〕：内存池的容量收益与访问代价**
>
> 四台机器的总内存够用，为什么仍有任务放不下？ 四个 64 GiB 节点分别承接 80、48、32、32 GiB 的工作集；比较迁移任务、增加本地容量、借用 16 GiB。对这份固定工作集只改变访问频次，求借用路径必须提供的能力；第 9.5 节再将它具体化为增长、失效和取回中的 KV，计算完整服务收益。
>
> 条件：基础·手算／短脚本。

**计算结果（6-9）：** 四个 64 GiB 节点总容量 256 GiB、总需求 192 GiB，富余 64 GiB，80 GiB 的任务却放不下——整任务迁移超过每一个节点，富余被锁在各自节点里，这正是池化要解决的 80 GiB 不可用余量。借用 16 GiB 后容量成立，代价转移到访问：同一条 10 GB/s／2 μs 链路，每分钟读一次负载 0.029 可行，每秒读一次变成 1.718 立刻积压。在途事务比延迟更关键——40 GB/s 下把在途从 128 提到 4096，服务时间从 10.486 s 降到 0.430 s，且此时 2 μs 与 20 μs 延迟结果相同。[容量三路径与 24 组访问条件](../experiments/ch06/06-09/README.md)。

>
> 更大的超节点比更多的小型超节点划算吗？ 改变模型、并发、延迟目标和故障恢复成本，给出选择改变的条件。

**计算结果（6-10）：** 同一组八卡的三种组织中，tp2×4（多个小超节点）在基线、放宽延迟、更长输出和故障注入四种情形下每有效请求费用都最低（基线 0.320 对 tp8×1 的 0.496）；故障时 tp8×1 的单副本一挂就是 0 有效，tp2×4 只损失 1 个请求。选择在两处翻转：延迟目标收紧到 120 ms 时 tp2×4 的单请求 160 ms 全部超时，tp4×2 反而救回 2 个；换成 Qwen3-32B 时 tp2×4 容量放不下，只能退回 tp4×2。超节点该做多大由单请求延迟目标与模型放得下共同框定。[三种组织与翻转条件](../experiments/ch06/06-10/README.md)。

>
> 本教学比较明确把每个 TP 组放在一个独立超节点：8 卡×1 个、4 卡×2 个、2 卡×4 个，总计均为 8 卡；每个超节点运行一个完整推理实例，组间没有请求执行依赖。物理卡 0 故障使所在超节点的推理实例不可用，其余超节点继续服务。这个放置和故障域是假设，不能仅由 TP 数值推断真实部署具有相同隔离性。
>
> 条件：进阶·综合计算。
