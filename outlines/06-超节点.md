# 第 6 章 超节点

> 写作大纲 · 数据搬移主线与章节依赖修订 · 草案 22 · 2026-09-08

第 5 章在芯片内组织数据复用，本章把计算和状态切到多张卡。由逐卡需求推出 TP、PP、DP、EP 及组合，再决定需要多大的紧密协作范围；拓扑与产品在具体限制出现时引入。

**本章判断：** 并行换来容量或处理能力，也增加交接与同步。总容量足够时仍要检查最忙设备；同一组卡应扩大协作还是增加副本，取决于负载和时限。

**前置与交付：** 依赖第 3、5 章；交付逐卡状态与跨边界流量，第 7 章沿实际路径继续计算。

**阅读安排：** 核心练习为实验 6-2、实验 6-3、实验 6-10；其余练习为延伸。每节的完整参数、实现版本与实验变体见对应[扩写资料](extensions/06-%E8%B6%85%E8%8A%82%E7%82%B9.md)。章末更新[跨章设计决定](decision-record.md)。

## 6.1 协作之前的逐卡预算

先比较副本和共同执行，再判断一次任务为何需要跨卡。总需求和局部需求分别记录。

### 6.1.1 贯穿本章的模型与硬件

复用第 2、3 章配置：Qwen3-8B Dense；235B／22B 激活的 Qwen3 MoE 与 284B／13B 激活的 V4-Flash；约 1.6T／49B 激活的 V4-Pro 与 2.8T／104B 激活的 Kimi K3。DeepSeek-V3 的 671B 总参数作为历史过渡。它们代表不同规模与结构，不能写成参数量完全相同的模型。

从单卡、八卡服务器到更大超节点，固定 GPU 可用显存、有效矩阵性能、HBM 带宽、卡间单向带宽与小消息延迟；模型、精度、请求长度和并发共同构成实验输入。先用一组条件完成推算，再换硬件检验原选择是否仍然成立。

### 6.1.2 容量、带宽与执行时间

逐卡检查 `权重＋KV／递推状态＋激活＋工作区 ≤ 可用内存`。分别数每步实际激活专家的权重读取、所有活跃序列的 KV 读取、算子 FLOPs，以及每条必要链路的字节和启动次数；总参数、激活参数、实际读取字节不能相互替代。

给出第一遍时间下界：本地计算 `F/P`、本地读取 `(W_read+KV_read)/B_mem`、路径传输 `V/B_link` 与必要同步；共享链路合并流量，串行依赖沿实际时序累加。以最忙的设备或链路定位瓶颈，再决定该减少哪项工作。

### 6.1.3 Prefill、Decode 与训练的不同切分

同一模型分别代入一段 prefill、一次 decode 和一轮训练。低并发 decode 的小消息与逐层依赖，不能按大矩阵 prefill 的带宽效率估计；训练另有梯度、优化器和反向通信。增加副本主要改变吞吐，把一次计算分到多卡可能改变容量与单请求延迟，两者从计算结果比较。

## 6.2 Dense 的切分与交换

沿同一矩阵逐步增加 TP 或 PP，比较减少的本地工作和新增交接；输出选择范围。

### 6.2.1 Qwen3-8B 的副本与数据并行

从单卡可以驻留的请求开始，比较八个服务副本、少量 TP 的多个副本、以及把八张卡交给一个请求。训练 DP 为不同卡分配样本并同步梯度，推理副本不需要这项同步；把两者分别放回自己的工作流。容量充足并不自动说明需要模型并行。

### 6.2.2 张量并行与层内数据交换

沿 Qwen3-8B 的实际 QKV、输出投影和 SwiGLU，画列切分、行切分，以及必须归约或收集的张量。逐卡写矩阵尺寸，比较减少的权重／计算与新增通信；KV 头分片和复制按实际实现处理。用 TP=1、2、4、8 的 prefill 和 decode 推算解释适用条件，不能把 TP≤8 当成通用规则。

再在四卡组比较完整 TP 与 Arctic 的 SP×TP：基础模式 SP=2、TP=2，切换模式 TP=4。用同一组 KV 头解释为何通信组顺序也必须匹配；一层代表矩阵的每卡权重由 184 MiB 增至双模式的 276 MiB，换来切换时继续使用原有 KV。沿两次归约和 attention 前后的交换数实际发送量，让小批次的权重读取与大批次的通信节省决定候选区间。[头映射、容量与通信推算](../case-studies/parallel-switching-and-state.md)

再把 Qwen3 的一次 `[8192,4096] × [4096,12288]` 投影扩到 16 卡，比较 2×8、4×4、8×2 的二维切分。固定输出驻留，先数两个方向的集合载荷，再由 MeshSlice 引出部分集合与计算流水：在给定教学条件下，分块数 1／16／64 的预计时间约为 0.901／0.547／0.898 ms。解释首尾等待为何减少、同步为何增加，以及小矩阵性能会怎样改变选择；论文当时不能实现完整 AG／RdS 重叠的实测也用来检查执行条件。[矩阵、假设与采用范围](../case-studies/mesh-shape-and-slicing.md)

### 6.2.3 流水线并行与组合方案

按层划分 PP，计算每个阶段的权重、状态、计算与边界激活。PP 通常减少层内的频繁协作，但一个 token 仍须经过相应阶段；微批与并发才可能填充流水线。比较 TP×PP 与多个副本，保留首 token、逐 token 延迟、吞吐和训练气泡的不同目标。

以 BF16 的 4096 维激活为例，单 token 边界张量为 8 KiB，8192-token prefill 的对应张量为 64 MiB；TP 的集合通信还要按算法、分片与轮次计算实际链路字节。改变消息规模后，同一网络延迟对两者的影响不同。

## 6.3 MoE 的专家复用与放置

将独立专家集合和每专家 token 数分别计量，检查最忙卡及路由差异怎样改变选择。

### 6.3.1 两个 200 多 B 模型的逐项比较

固定 Qwen3-235B-A22B 的 94 层、4096 隐藏维度、128 选 8 路由专家、1536 专家中间维度，以及 V4-Flash 的 43 层、4096 隐藏维度、256 选 6 加共享专家、2048 专家维度。Qwen 的 GQA 与 V4 的混合压缩注意力分别核算 KV，不能由接近的总参数量推断相近的状态与通信。

用统一 BF16 权重作第一轮教学估算，两者约需 470 GB 与 568 GB；相对于八张名义 80 GB 卡，总容量看似都够，留给 KV、工作区和不均匀放置的空间却不同。随后按实际混合精度、量化附加数据和逐卡放置重算，统一 BF16 不是 V4 发布权重的实际格式。

### 6.3.2 专家并行与路由流量

把专家分配到不同卡，计算每个专家收到的 token 数、局部矩阵、共享专家工作以及 dispatch／combine。按 token 实际选择的远端设备计流量：同一设备承接多个被选专家时可以复用或合并传输，不能直接把 top-k 当成 k 个不同目的地。接着比较 EP、专家内部 TP、attention TP 和服务副本的组合，明确各通信组的成员与数据所有权。

以 Qwen3-235B 的单专家 BF16 权重 36 MiB 为起点，区分总驻留、每 token 选中的专家和批内独立活跃专家。8 个输入 token 若都选同 8 个专家，理想一次读取涉及 288 MiB；均匀独立路由的期望则约为 1.815 GiB。再用真实路由重算逐卡读取与每专家矩阵：decode 的复用收益与 prefill 的计算长尾可能指向不同放置，不能仅按激活参数或平均 FLOPs 决定 EP。

### 6.3.3 万亿参数模型的结构差异

V4-Pro 与 Kimi K3 分别沿自己的层数、注意力状态和专家结构推算。K3 的 896 选 16 路由专家在 3584 维潜空间工作，另有 2 个全宽共享专家，首个 dense 层和 MTP 单独计数；路由激活应按实际跨卡表示计量，不能直接套 7168 维全宽传输。总权重、实际激活矩阵、专家粒度、状态和同步次数一起决定放置。

先得到给定质量与服务目标下的可行组合，再在明确的候选范围内求预计时间最短或成本最低的切分，并检查其瓶颈；资料缺失或两方案差距小于估计误差时，输出候选范围与补测条件。以真实模型的不同规模比较为主，若统一总参数预算做反事实实验，明确它是教学控制变量，不改写产品规格。

## 6.4 逻辑通信与实际资源

从数据依赖推出集合操作，再算算法字节、物理路径和通信占用的设备资源。

### 6.4.1 梯度归约与集合通信

回到刚算过的 TP 与训练 DP，说明 all-reduce、all-gather、reduce-scatter 分别补齐哪项数据。用四个参与者跟踪每轮字节，再代入前面真实模型的消息大小。

### 6.4.2 MoE 路由与 All-to-All

从路由到专家引入 all-to-all，解释通信对象、数据量与不均匀性。和梯度归约对照，让读者理解相同总字节并不意味着相同完成时间。

### 6.4.3 环与树的通信代价

沿一次集合通信画出轮次和链路占用，由消息大小、带宽和启动延迟比较算法。再加入分块、流水与多通道，说明选择为什么随规模变化。

以 p 个参与者、每个输入 M 字节的简化 ring all-reduce 为例，写出 `T ≈ 2(p−1)α + 2(p−1)M/(pB)`，说明轮次项与传输项从哪里来。先用小例子比较消息大小改变后的选择，再由实际拓扑和归约成本修正；公式不替代所有集合算法。

用 Swing 的物理路径案例补上公式里隐含的条件：沿 Qwen3-8B 的 BF16 `[1024,4096]` 激活取 8 MiB 归约输入，在 16 节点双向环上比较 reduce-scatter 的前三轮，两种算法每节点都发送 4、2、1 MiB，但最拥塞有向链路分别承担 4／4／4 和 4／2／2 MiB。让读者先数路径，再理解为什么相同算法字节与轮次不等于相同时间；多端口和拓扑形状也会改变结果。论文收益来自 torus 网络仿真，大消息下仍有其他算法胜出，不能直接当作 TPU 或 NCCL 实测。推算与采用范围见[集合通信与作业错峰](../case-studies/network-planning-and-collectives.md)。

### 6.4.4 通信库与设备资源

沿候选切分的一次 NCCL 调用追到 SM、显存和互联。用 AutoCCL（NSDI 2025）说明实现选择与资源分配为何要分开搜索，实际并发反馈怎样修正独占结果。给两个可重叠的 Qwen3 微批片段：通信独占耗时从 0.24 降到 0.18 ms，并发汇合却从 0.44 增到 0.62 ms；先找哪一段被挤慢，再算搜索成本能否摊薄。这是教学输入，论文基于 A40／NCCL 2.18.3 的结果另列条件；其通信优化目标不保证整步最优。[推算与版本范围](../case-studies/communication-tuning.md)

以 Qwen3-8B 的 BF16 输出归约为例，1／4／16 个 token 分别产生 8／32／128 KiB 输入；用 vLLM 从 2024 的 IPC custom AR 到当前多后端分派，说明形状、图缓冲、P2P 和拓扑怎样决定实际路径。类中列出的参与者数不等于每种操作都支持，超节点内的 MNNVL 与普通跨服务器网络也要分别核实。在 8 卡、每轮 2 μs、有效单向 50 GB/s 的 ring 教学条件下，单 token 的 72 次逐层归约约 2.04 ms，带宽翻倍只省约 10 μs，由此引出小消息的启动与融合优化。

### 6.4.5 通信卸载与专用单元

## 6.5 紧密协作范围的选择

拓扑、端口、介质和功率共同决定可行规模；大型同步域与更多副本使用同一任务比较。

### 6.5.1 直连、交换与分层拓扑

从端口和路径预算比较小规模直连、交换结构和更大型超节点。让同一组训练／推理通信经过不同拓扑，观察端点注入与共享链路如何限制性能。

**占位 D11-04：** 显式推算 radix、端口速率、端点多链路与交换容量怎样限制拓扑层级；区分芯片和整套 fabric 的端口预算、物理跳数与集合算法轮数，接到本节的拓扑实验。详见[端口与层级分析](../research/draft11-outline-audit/report.md#radix)。

再用四卡 PCIe 机器承接 Qwen3-8B 的 8 MiB AllReduce：逻辑发送量都是 48 MiB，把中转缓冲全放在一个 NUMA 节点或靠近发送 GPU，CPU 间互联的流量却不同。先逐段算字节，再以 TCCL 的作者材料和当前 NCCL 路径作对照，解释为什么拓扑、ring 次序与缓冲放置要一起考虑；具体假设与下界见[中转算例](../case-studies/pcie-staging-and-numa.md)。

### 6.5.2 互联介质、供电与物理规模

## 6.6 共享容量与远端访问

从局部不足、全局空闲的实际问题进入内存池，再分别检查冷状态和活跃数据的搬移频次。

### 6.6.1 局部容量不足与全局空闲

以作者早期 UB 内存池的设想进入：一台机器的计算已经很忙，内存却有剩余；另一台机器先被容量卡住。先判断借用容量能解决什么，再跟到后来的 KV cache 应用。

用四个节点各有 64 GiB 可用内存、同时需求为 80／48／32／32 GiB 的教学例子：总需求 192 GiB 小于总容量 256 GiB，仍有一个节点短缺 16 GiB。比较增加本地内存、迁移任务与从池中借用，区分容量节省、复制减少与实际访问成本；不把这个假设配置当成某款 GPU 的远程寻址能力。

### 6.6.2 内存借用与访问边界

按 UB OS 参考设计的内存导入、导出、借用与共享机制，画本地内存、远端内存和地址映射的关系。统一地址、可远程访问和缓存一致性分别解释；哪一方保留访问权、何时归还以及故障时怎样处理，回到具体机制。将容量与带宽分别算，不能把各节点标称内存带宽相加当成借用者可用带宽。

### 6.6.3 共享容量与 KV cache

承接作者“有了内存池以后，什么应用最值得用”的问题，比较冷前缀、等待恢复的会话与正在逐 token 使用的 KV。先按每次读取的字节和频率判断远端链路能否承受，第 9.5 节再展开共享 KV 池、PD 交接和前缀复用。

> **实验 6-9 ★〔延伸〕：内存池的容量收益与访问代价**
>
> 四台机器的总内存够用，为什么仍有任务放不下？ 四个 64 GiB 节点分别承接 80、48、32、32 GiB 的工作集；比较迁移任务、增加本地容量、借用 16 GiB。再把借用部分分为冷前缀与活跃 KV，扫描访问频次、带宽和延迟，判断容量收益能否转成服务收益。
>
> 条件：基础·手算／短脚本。

> 自绘 SVG；同一组节点画本地不足、借用容量和 KV 取回三种状态，远程路径标注访问频次；配实验 6-9。
