> 写作大纲 · 任务预算、状态放置与执行恢复六节重组 · 草案 22 · 2026-09-10

训练反复使用参数、激活和优化器状态，RL 又把生成、验证、学习与权重交接连接起来。本章沿“任务预算 → 状态放置 → 单步执行 → 持续运行 → RL 闭环 → 期限复核”推进，逐步计算按期取得并保留训练进展所需的资源。

**本章判断：** 省容量可能增加通信或重算；提高生成吞吐也可能改变样本选择。执行优化要同时保持所声明的更新语义、质量和有效进展。

**前置与交付：** 依赖第 3、6、7、9 章；沿用负载、并行切分和物理路径，新增梯度、优化器、反向依赖与恢复状态。交付训练方案、完成期限和 RL 阶段需求，第 11 章接着配置验证环境、资源池与任务恢复。

## 10.1 从训练任务到容量与时间预算

固定任务与质量条件，先建立容量和计算下界；效率假设由后续执行与恢复分析逐步校准。

### 10.1.1 任务、更新范围与完成目标

承接第 3 章，固定 Qwen3-8B 的领域继续训练为贯穿任务：100B 有效 token、30 天期限、混合精度 Adam 与全参数更新，以 8,192 token 序列为基线，声明质量验收和数据范围。全参数训练、LoRA 与低比特冻结参数的微调分别建账；改变更新范围后重新计算。

区分运行的 FLOPs、暂时完成的迭代与最终保存的进展。章首先给容量和计算下界，10.2–10.4 逐步补入状态搬移、等待与恢复，10.6 再复核期限；RL 在 10.5 增加有效样本和策略版本条件。

### 10.1.2 参数、梯度、优化器与激活

沿 Qwen3-8B 的混合精度 Adam 计算参数、梯度、主权重、优化器与激活。官方配置共有 8,190,735,360 参数：BF16 权重与梯度、FP32 主权重及 Adam 两个状态合计 16 byte／参数，持久状态约 131.052 GB（122.051 GiB）；梯度改为 FP32 则为 18 byte／参数，临时聚合与激活另加。单卡推理可驻留不会自动提供全参数训练容量；V4 的优化器和低精度状态按真实格式重算。

>

**计算＋实测结果（10-1）：** Qwen3-8B 推理只要 15.3 GiB 权重，全参数训练的未分片状态是 122.1 GiB——权重只占 1/8。4090（24 GB）上训练 8B 必须用到 ZeRO stage 3（15.3 GiB/rank），同一模型在 80 GB 卡上 stage 1 就够：分片阶段不是效率选择而是可行性选择。rank 数直接决定可行阶段——8B 在 4090 上 8 rank 需要 stage 3，64 rank 时 stage 2 即可。235B 在 8 rank 下任何阶段任何设备都放不下（stage 3 仍要 437.9 GiB/rank）。CPU FSDP2 实跑另给出 180 个张量重组与训练峰值 39.156／30.141 MiB 的实际对照。[逐阶段预算与三份实跑](../experiments/ch10/10-01/README.md)。

### 10.1.3 计算需求、MFU 与资源下界

接第三章的算法工作量，先明确本题采用完整工作还是矩阵子账。MFU 用相同计时窗口内的算法 FLOPs 除以卡数、对应精度峰值与时间的乘积；使用 30%／40%／50% 三档估计敏感性；50% 是较乐观情景，需要由对应模型与拓扑的训练步验证。稳态 MFU 若已包含重计算、通信与气泡，就不再把这些时间重复相加；日历完成时间另计区间之外的保存、故障、恢复和数据停顿。RL 按有效样本及质量进度核算，不把 rollout 与梯度计算硬合成一个 MFU。

> **实验 10-2 ★〔延伸〕：从训练任务反推资源**
>
> 按 Qwen3-8B 的具体矩阵求每 token 训练工作，再由 100B token／30 天推设备需求。先声明算法 FLOPs 的统计范围，再用 30%、40%、50% 效率作敏感性输入，与容量下界交叉检查；若只计矩阵子账，就以该子账定义效率，不能直接套用完整训练步口径的 MFU；换 235B MoE 或改变更新范围后重新计算。区分理想估算、实际训练步与全部日历时间。
>
> 条件：基础·手算／短脚本。

**计算结果（10-2）：** 先声明统计范围（训练矩阵子账，不含非矩阵、优化器、重计算与通信，效率按同一子账定义）。100B token／30 天下，Qwen3-8B 每 token 4.90e10 FLOPs，A100 需 13–21 张（效率 30–50% 拉开 1.6 倍），H100 需 4–7 张，全程由算力支配。Qwen3-235B 的支配项会翻转：A100＋30% 时算力支配（62 > 53 张），效率提到 40% 后容量接管，H100 与 B200 上全部由容量支配（6 张够算但 24 张才放得下）——卡越快，容量越早成为限制。[三种时间口径与敏感性](../experiments/ch10/10-02/README.md)。

## 10.2 训练状态的分片、重计算与卸载

回答状态放在哪里、何时需要取回，以及节省容量后增加了什么计算和搬移。

### 10.2.1 数据并行与 ZeRO／FSDP 状态分片

沿用第 6、7 章的 DP 分组，重点展开 ZeRO／FSDP 如何分片优化器、梯度与参数，以及何时重新收集。把节省的逐卡容量与新增访问放回既有拓扑，进一步选择训练状态的组织。

用同一参数张量画出持久分片、前向／反向前的临时聚合与更新后的归属，分别计算长期驻留和峰值。小模型 FSDP2 记录说明分片后的可见状态不能代表训练分配峰，完整数值与参考更新核对见扩写资料。

### 10.2.2 激活保存与选择性重计算

沿第 3 章的前向、反向与更新图及 10.1 的状态表，标出反向真正需要保留的张量及最后一次使用；比较保存全部激活、选择性重计算和整层重计算。先算少保存多少状态、增加多少 FLOPs 与临时工作区，再把它们交给 10.3 的微批时间轴。

以 Megatron Core 的细粒度重计算为具体实现，说明不同模块可采用不同策略。重计算、通信重叠和 CUDA Graph 有组合限制，收益需在同一执行方案中核对。

### 10.2.3 CPU／GPU 卸载与缓冲寿命

卸载继续第 5.2.3 的缓冲时序：节省的 HBM 要扣除取回暂存，主机还需为锁页池留容量。取回能否提前，由其他微批的可用计算窗口和缓冲复用点决定；异步提交后立即改写源张量会影响正确性。

再以 SuperOffload 引出转换位置的选择：同一 Qwen3-8B gate 梯度，BF16 为 96 MiB、FP32 为 192 MiB。先比较 CPU 转换加少量传输，与 GPU 转换加较多传输，再扣除暂存容量；互联变快后，较少字节未必给出较短完成时间。用 DeepSpeed ZeRO-3 的真实配置继续检查 CPU 更新和最晚就绪的梯度桶，[推算与实验条件](../case-studies/training-offload-and-casting.md)放入扩写资料。

同一 gate 形状的 CPUAdam 卸载记录中，CPU／GPU 转换分别传回 96／192 MiB 梯度，GPU 转换路径传输更多却完成更快，并占用更高的 GPU 峰值容量。用这一反例检查转换吞吐、链路与暂存是否改变选择；完整时长、数值检查和设备边界见扩写资料。

### 10.2.4 并行组合下的逐卡状态与拓扑映射

将第 6、7 章已有 TP／PP／DP／EP 候选加入梯度、优化器分片和激活策略，逐卡列出持久状态、临时聚合、通信缓冲与必要交换。分别记录容量下界和必须经过的 PCIe／NIC 路径，形成少量候选。

以 4090 集群启动实验 10-3：本节完成候选状态表，10.3 修正训练步时间，10.4 补入供数与恢复，10.6.2 才完成期限判断。长上下文与 MoE 的额外调度约束在 10.3.4 加入。

> **实验 10-3 ★〔核心〕：4090 集群的可行范围**
>
> 4090 集群的哪一项先不够？ 沿用 Qwen3-8B 的领域训练任务，再将模型换成 Qwen3-235B；对具体 4090 主机、PCIe、NIC 与 H100 系统计算逐卡容量、训练步通信和总时间。先排除无法达到期限的组合，再指出剩余候选最需要哪项实测。

**计算结果（10-3）：** 两个模型“先不够”的不是同一项：Qwen3-8B 上 4090 先不够算力（33 张对容量的 9 张），Qwen3-235B 上先不够容量（252 张对算力的 99 张，多出的 153 张纯为放状态）。升级 NIC 只解决通信：4090＋8B 从单 100 Gb 换到 4×200 Gb 使通信占比从 48.3% 降到 28.9%，天数从 57.5 降到 41.8，**仍然超期**。235B＋单 NIC 的通信占比高达 91.0%。只有 H100 系统达期限（22.7／21.2 天）。剩余候选最需要实测的是 4090 主机 PCIe 在 8 卡同时 all-reduce 时的实际有效带宽。[逐系统可行性与实测建议](../experiments/ch10/10-03/README.md)。

## 10.3 训练步的流水调度与通信重叠

在相同数学更新下，将前向、反向、通信和优化器排入时间轴，核对激活寿命、共享资源与暴露等待。

### 10.3.1 微批、梯度累积与更新边界

固定全局 batch、有效 token 加权与一次参数更新的边界，再改变微批数。区分微批大小、梯度累积次数和数据并行规模；长度不同时，按训练目标核对整步归一化分母，累计完成后再按约定裁剪和更新。

微批变化同时影响激活寿命、内核效率与流水填充。先保证不同候选完成同一数学更新，再比较步时；第 3 章定义的负载在这里落实为执行约束，RL 配方的 token-mean 特例在 10.5.1 展开。

### 10.3.2 流水线调度、气泡与激活寿命

比较简单填满排空与 1F1B 等时序，计算气泡、激活寿命和峰值容量。把 10.2 的重计算与卸载方案代回同一时间轴，检查计算窗口和缓冲复用；减少激活驻留不保证任何条件下都缩短步时。

基本时序仍有明确损失时，再以 DualPipe 比较双向流水的气泡、模型块放置和额外状态，说明增加调度复杂度的收益条件。官方 Megatron 无流水基线用于验证训练与生命周期记录，四阶段流水及多卡收益仍需对应实测，详见扩写资料。

### 10.3.3 反向依赖、梯度分桶与通信重叠

TP 的矩阵切法已在第 6 章推导，本节加入反向依赖、序列切分和通信就绪时间。按照第 7 章两级互联的实际代价，检查前向与反向哪些通信可以重叠、哪些暴露在关键路径。

沿第 6 章的同一 Qwen3 投影写出 `dX=dY Wᵀ` 与 `dW=Xᵀ dY`，核对前后向的驻留、归约与布局交接。MeshSlice 的启发式说明怎样先缩小候选范围；再用实际框架 trace 检查编译依赖与共享资源，不能把前向分块的预计收益直接乘成训练加速比。[前后向推算的衔接](../case-studies/mesh-shape-and-slicing.md)

检查梯度就绪、分桶和下一步依赖，比较理想重叠与共享资源下的实际情况。GPU、NPU 的具体执行记录用于说明相同想法怎样落地。沿第 6.4 的通信调优算例，重新标出训练中的并发汇合与暴露尾部：局部带宽收益必须回到整步时间，搜索成本按实际剩余训练长度摊薄。

用 MegaScale 按 DP／PP／TP 拆解依赖的案例承接第 7 章：参数收集和梯度分散的首尾仍可能暴露，发送与接收能否分离由计算依赖决定。其 175B、固定 batch 6144 的历史实验从 3072 卡的 23.66 s 到 12288 卡的 6.34 s，四倍设备约得到 3.73 倍步时加速；随后把当前贯穿模型代回同一方法。将固定任务扩展与改变模型、优化器、batch 的消融分开，不能把整套系统的 MFU 改善归给某个通信技巧。

### 10.3.4 MoE 与长上下文的调度变化

把第 2 章的模型变化加入训练：专家、上下文切分、通信倾斜和容量重新定价。近期 DeepSeek 报告作完整案例的一部分，而不是再列一套并行缩写。

用 FSMoE（ASPLOS 2025）解释为什么前向和反向需要分别选择切块：跨机 token 通信还要与已就绪梯度分享链路。沿[同一个 Qwen3 专家](../case-studies/expert-dispatch-and-resizing.md)，先算 72 MiB 梯度的归约时间，再判断三个 2 ms 空隙能否容纳分桶；额外启动会增加总通信，却可能减少暴露尾部。论文的修改版 GPT-2／Mixtral 与旧栈只作设计参照，新模型以实际反向图校准。

## 10.4 数据供给、检查点与故障恢复

先明确恢复所需状态及恢复点何时可用，再选择保存方式和周期，将稳态执行换算成持续运行成本。

### 10.4.1 数据读取、打包与预取

从一次设备空闲记录引出读取、预处理、长度打包与预取。计算每秒所需样本和字节，先定位最窄环节，再选择缓存或增加处理能力。

沿第 5.2.3 区分 CPU 准备、锁页暂存与 H2D：文本 token 输入和卸载激活的字节可能相差很大，先由真实张量决定是否值得预取；`pin_memory` 与异步提交的作用用实际流水记录解释。

> **实验 10-5 ★〔延伸〕：数据与检查点的带宽需求**
>

### 10.4.2 可恢复状态与布局变换

先定义恢复目标：保存参数、优化器、随机状态、数据消费位置与打包残留，才能核对恢复后的下一次更新。预取派发位置与已消费位置分别记录；只成功加载权重不足以验证训练续接。

用 ByteCheckpoint（NSDI 2025）串起恢复、改变并行布局与独立评估。沿 Qwen3-8B 的 `[12288,4096]` gate 矩阵，把 96 MiB BF16 权重从 TP=4 的四份 24 MiB，改为 TP=8 的八份 12 MiB；先根据全局坐标找文件片段，再加入 FP32 主权重与 Adam 两项状态，同一矩阵变成 672 MiB。说明逻辑张量、文件分片和框架融合布局的区别，恢复训练还需数据位置、token buffer 与随机状态。

真实文本流水的小模型恢复记录中，保留消费位置与打包残留后可与不中断训练一致；漏掉残留或错用预取派发位置会跳样并改变模型。布局变更、worker 数变化和下一步一致性的完整验证见扩写资料。

### 10.4.3 同步、异步保存与带宽竞争

### 10.5.3 异步供给、策略版本与长轨迹恢复

### 10.5.4 MoE Routing Replay 与训练一致性

先固定相同权重和 token，比较推理与训练引擎重算的专家选择及 logprob：不同精度、kernel 和 batch 形状产生的微小数值差异，可能翻转接近边界的 top-k，逐层积累成与策略更新无关的差异。由这个问题引出 Rollout Routing Replay／R3（2025），再用 NeMo RL 的 vLLM rollout＋Megatron 训练路径说明落地。

记录生成时每层、每 token 的专家 ID，在训练前向重放离散选择，同时以当前权重重新计算路由分数和专家输出，保留梯度。它不是重放旧输出，也不是省掉整个 router 计算；不能因此认为策略滞后、数值误差或 RL 收敛问题全部解决。与第 9 章 EPLB 区分：逻辑专家 ID 不随物理副本位置改变。

按 `有效 token 数 × MoE 层数 × top-k × ID 字节数` 先算路由记录，再加入多轮前缀、打包、上下文切分、传输与保存。例用 8,192 token、48 层、top-8、uint16 得 6 MiB；这是编码假设，真实后端若用 int32 则翻倍。缓存 KV 时要能找到同前缀的路由记录；采样、logprob、训练和激活重计算都要对齐 token 身份与权重版本。

> **实验 10-8 ★★〔延伸〕：Routing Replay 与训练一致性**
>
> 沿固定 NeMo RL 的 Qwen3-30B-A3B R3 配方或其配套 trace，关闭／开启 replay 比较专家集合不一致率、同权重 logprob 差异、记录容量与阶段时间，再比较相同任务下的训练曲线。加入多轮缓存命中、样本 packing 和缺失路由检查，验证 token 对齐；小批检查只证明被覆盖路径，不冒充完整收敛结论。

**记录结果（10-9）：** 取得 NVIDIA 官方 R3 验证报告的四对真实训练 history 共 808 行（可比较训练记录 800 行、每 run 100 步），逐步对齐并做离线分析。四种设置共用 seed 42，是一对一对照而非八个独立随机种子。结果：四种设置的日志级 logprob 误差中位数**均降低**，reward **无一致改善**，R3-on 的总步时中位数**均略长**。这些结论不替代逐 token 专家集合、缺失路由或 packing 的原始 trace 验证，也不是本机训练。[原始 history 分析与边界](../experiments/ch10/10-09/source-readiness/README.md)。

### 10.6.4 模型规模、数据量与期限的敏感性

用 A100、H100 与 B200 的明确形态和 dense 精度比较。先固定卡数、数据量与期限，反推可行规模；再分别固定预算或让数据量随参数增长，解释问题改变后答案为何不同。1T、5T、10T 作为明确标注的 Dense 扩展情景，真实 MoE 则按 V4-Pro／Kimi K3 的总状态与执行路径分别计算。

在 16,384 卡、20T token、BF16 dense、50% MFU 的教学条件下，1T Dense 的粗估为 A100 约 543 天、H100 约 171 天、B200 约 75 天；随后检查容量与通信能否支撑这一效率。读者应据此推算 5T／10T、90／180 天与不同集群规模，理解不存在脱离卡数、任务和期限的“A 卡／H 卡／B 卡参数上限”。
