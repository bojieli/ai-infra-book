# 第 10 章 训练系统

> 写作大纲 · 数据搬移主线与章节依赖修订 · 草案 22 · 2026-09-08

训练反复使用参数、激活和优化器状态，RL 又把生成、验证、学习与权重交接连接起来。本章以按期取得并保留的训练进展为目标，先算状态保存和搬移，再选择分片、重计算、流水与恢复。

**本章判断：** 省容量可能增加通信或重算；提高生成吞吐也可能改变样本选择。执行优化要同时保持所声明的更新语义、质量和有效进展。

**前置与交付：** 依赖第 3、6、7、9 章；交付训练期限和 RL 阶段需求。第 11 章接着配置验证环境、资源池与任务恢复。

**阅读安排：** 核心练习为实验 10-3、实验 10-8、实验 10-10；其余练习为延伸。每节的完整参数、实现版本与实验变体见对应[扩写资料](extensions/10-%E8%AE%AD%E7%BB%83%E7%B3%BB%E7%BB%9F.md)。章末更新[跨章设计决定](decision-record.md)。

## 10.1 有效训练进展与状态预算

先明确目标是按期完成且保留进展，MFU 用于诊断。再算权重、梯度、优化器与激活，为每种节省容量的办法计新增工作。

### 10.1.1 参数、梯度与优化器状态

章首先固定有效训练目标、质量和期限：运行的 FLOPs、暂时完成的迭代与最终保存的进展分别计量。MFU 解释稳态执行效率，日历时间还包括准备、数据停顿、检查点与故障；RL 则保留有效样本和策略条件。

再沿 Qwen3-8B 的混合精度 Adam 计算参数、梯度、主权重、优化器与激活。官方配置共有 8,190,735,360 参数：BF16 权重与梯度、FP32 主权重及 Adam 两个状态合计 16 byte／参数，持久状态约 131.052 GB（122.051 GiB）；梯度改为 FP32 则为 18 byte／参数，临时聚合与激活另加。单卡推理可驻留不会自动提供全参数训练容量；V4 的优化器和低精度状态按真实格式重算。

### 10.1.2 重计算、卸载与分片

以 PyTorch FSDP／DeepSpeed ZeRO 的具体配置承接容量预算，再用 Megatron Core（2026）的细粒度重计算和卸载说明不同模块不必采取同一种策略。分别算省下的激活、增加的 FLOPs 与主机传输；重计算、通信重叠和 CUDA Graph 有实现上的组合限制，不能把每项独立收益相乘。

卸载继续第 5.2.3 的缓冲时序：节省的 HBM 要扣除取回暂存，主机还需为锁页池留容量。取回能否提前，由其他微批的可用计算窗口和缓冲复用点决定；异步提交后立即改写源张量会影响正确性。

再以 SuperOffload 引出转换位置的选择：同一 Qwen3-8B gate 梯度，BF16 为 96 MiB、FP32 为 192 MiB。先比较 CPU 转换加少量传输，与 GPU 转换加较多传输，再扣除暂存容量；互联变快后，较少字节未必给出较短完成时间。用 DeepSpeed ZeRO-3 的真实配置继续检查 CPU 更新和最晚就绪的梯度桶，[推算与实验条件](../case-studies/training-offload-and-casting.md)放入扩写资料。

### 10.1.3 数据规模与完成期限

把 Qwen3-8B 的领域继续训练固定为 100B 有效 token、30 天期限的教学情景，先求每秒需要完成的 token 与算法 FLOPs，再检查候选设备数。数据准备、有效长度与全参数／LoRA 范围都写明；换训练预算后重算，不能把一个 SFT 项目的可运行配置当作预训练方案。

接第三章的算法工作量，先明确本题采用完整工作还是矩阵子账。MFU 用相同计时窗口内的算法 FLOPs 除以卡数、对应精度峰值与时间的乘积；使用 30%／40%／50% 三档估计敏感性；50% 是较乐观情景，需要由对应模型与拓扑的训练步验证。稳态 MFU 若已包含重计算、通信与气泡，就不再把这些时间重复相加；日历完成时间另计区间之外的保存、故障、恢复和数据停顿。RL 按有效样本及质量进度核算，不把 rollout 与梯度计算硬合成一个 MFU。

### 10.2.4 4090 集群的容量与通信限制

### 10.2.5 A100、A800 与 H20 的任务适配

同形态 A100／A800 先保持本地工作不变，把 NVLink 的变化代入已选 TP／PP／DP／EP 通信；HBM 带宽不随名称一并调低。比较单机少通信、TP 高频同步和 MoE 专家交换，观察互联差异在完成时间中放大或被隐藏的条件。

## 10.3 流水复用与暴露通信

从就绪时刻安排微批、梯度与重计算。减少暴露等待的同时核对激活寿命和共享链路。

### 10.3.1 微批安排与流水线气泡

[官方Megatron无流水GPU基线](../experiments/ch10/10-05/single-gpu-pipeline/README.md)中，36层小模型的8个微批输出和全部梯度与参考逐位一致，参数更新通过数值门槛；864个保存引用均释放，去重存储峰40KiB。该结果验证真实训练与生命周期记录，四阶段流水及多卡收益仍待实测。

比较简单填满排空与 1F1B 等时序，计算气泡、激活寿命和峰值容量。只在基本时序仍有明确损失时介绍更复杂的调度。

### 10.3.2 通信重叠与资源竞争

检查梯度就绪、分桶和下一步依赖，比较理想重叠与共享资源下的实际情况。GPU、NPU 的具体执行记录用于说明相同想法怎样落地。沿第 6.4 的通信调优算例，重新标出训练中的并发汇合与暴露尾部：局部带宽收益必须回到整步时间，搜索成本按实际剩余训练长度摊薄。

用 MegaScale 按 DP／PP／TP 拆解依赖的案例承接第 7 章：参数收集和梯度分散的首尾仍可能暴露，发送与接收能否分离由计算依赖决定。其 175B、固定 batch 6144 的历史实验从 3072 卡的 23.66 s 到 12288 卡的 6.34 s，四倍设备约得到 3.73 倍步时加速；随后把当前贯穿模型代回同一方法。将固定任务扩展与改变模型、优化器、batch 的消融分开，不能把整套系统的 MFU 改善归给某个通信技巧。

### 10.3.3 MoE、长上下文与并行组合

**占位 D14-03：** 补训练侧辅助损失与无辅助损失的均衡路线，用 DeepSeek-V3 的路由偏置和补充序列级损失说明具体边界；比较负载、通信、训练质量与稳定性，并区分第 9 章保持逻辑专家语义的推理 EPLB。详见[训练均衡的补回判断](../research/draft14-15-outline-audit/report.md#training-balance)。

用 FSMoE（ASPLOS 2025）解释为什么前向和反向需要分别选择切块：跨机 token 通信还要与已就绪梯度分享链路。沿[同一个 Qwen3 专家](../case-studies/expert-dispatch-and-resizing.md)，先算 72 MiB 梯度的归约时间，再判断三个 2 ms 空隙能否容纳分桶；额外启动会增加总通信，却可能减少暴露尾部。论文的修改版 GPT-2／Mixtral 与旧栈只作设计参照，新模型以实际反向图校准。

## 10.4 持续供给与可恢复状态

训练输入、检查点和恢复争用存储及主机资源；异步返回后仍要检查持久化供给是否跟得上。

### 10.4.1 数据读取与预处理

从一次设备空闲记录引出读取、预处理、长度打包与预取。计算每秒所需样本和字节，先定位最窄环节，再选择缓存或增加处理能力。

沿第 5.2.3 区分 CPU 准备、锁页暂存与 H2D：文本 token 输入和卸载激活的字节可能相差很大，先由真实张量决定是否值得预取；`pin_memory` 与异步提交的作用用实际流水记录解释。

> **实验 10-6 ★〔延伸〕：数据与检查点的带宽需求**
>
> 需要多快的数据与检查点通路？ 沿用当前模型的 token 目标、样本长度、检查点状态大小和周期，推每秒输入字节、预处理 CPU 与存储写入。扩大到 V4-Flash 后重算，检查写检查点是否挤占训练输入。
>
> 条件：基础·计算。

实验10-6补测：本机CPU上用PyTorch DCP将小模型检查点从2份行分片恢复为3份列分片及1份完整状态，参数、Adam与随机状态均一致，下一步训练与未中断基线逐位相同；漏掉Adam动量则不再一致。此结果验证恢复机制，不代表大模型存储带宽。[记录与边界](../experiments/ch10/10-06/README.md)。

### 10.4.2 故障规模与检查点周期

用设备数与单设备故障率估计一次中断的量级，解释保存频率、持久化和恢复的取舍。不要等到万卡实验才发现恢复成本不可接受。

在独立稀少故障、固定保存成本 c 的教学假设下，以间隔 τ 比较每单位时间约 `c/τ + λτ/2 + λr` 的损失，其中 λ 为作业中断率、r 为恢复时间。先估数量级，再检查相关故障和异步保存如何改变假设。

### 10.4.3 保存、恢复与存储带宽

比较同步保存、异步写出与分层保存，计入额外内存、存储带宽和恢复时间；恢复后能继续训练所需的数据与随机状态一起说明。

用 ByteCheckpoint（NSDI 2025）串起恢复、改变并行布局与独立评估。沿 Qwen3-8B 的 `[12288,4096]` gate 矩阵，把 96 MiB BF16 权重从 TP=4 的四份 24 MiB，改为 TP=8 的八份 12 MiB；先根据全局坐标找文件片段，再加入 FP32 主权重与 Adam 两项状态，同一矩阵变成 672 MiB。说明逻辑张量、文件分片和框架融合布局的区别，恢复训练还需数据位置、token buffer 与随机状态。

[真实文本流水恢复补测](../experiments/ch10/10-06/input-state-recovery/README.md)中，保留消费位置与打包残留的六次CPU恢复均与不中断训练完全一致；漏掉残留或错用预取派发位置则造成跳样并改变模型。已预取不等于已消费，恢复首步也不等于整个流水就绪。

从 PyTorch 2024 的后台线程，讲到 2025 的进程与计划缓存，再核对当前 staging／upload 完成事件。用取整 8B、112 GB 状态、全局有效 8 GB/s 存储算出 14 秒传输下界；若每 10 秒生成一份，异步队列仍会增长。API 暂停、后台对训练吞吐的影响和完整持久化时间分别计量；ByteCheckpoint 的 GPU states 与 full states、推算 ETTR 与实际训练进展也分别说明。[来源与算例](../case-studies/checkpoint-layout-and-loading.md)

## 10.5 RL：生成、验证与更新的闭环

先定义行为策略和有效样本，再选择阶段分工、权重交接与恢复；将数值和采样语义作为性能优化的约束。

### 10.5.1 Rollout、奖励与训练闭环

承接第 3 章的 RL 负载，组织 rollout、奖励／验证、样本缓冲与梯度更新，再把新权重交回采样端。DeepSeek-R1 交代推理训练路线，DeepSeek-V4 的 §5.2 作为系统主例；逐项计算生成、验证、训练、权重分发与数据组织的资源需求，代码与 Agent 任务连接第 11 章的 CPU 沙箱。

用[实验 10-8 的固定 verl 配方](../experiments/ch10/10-08/PROTOCOL.md)把这些角色接成一次真实更新：四个 prompt 各生成两条回答，沿同一批样本检查奖励、优势、训练微批，再追踪新权重进入 vLLM 后的下一次生成。先让读者看清每个阶段为什么存在、谁在等待谁；配置和源码留在配套材料。小模型验证流程，V4 承担规模与系统设计的推算，两者的证据分别说明；AReaL 只在下一节需要比较异步供给时引入。

这份配方还能说明切微批为什么必须保持训练目标：八条回答共 20 个有效 response token（含 EOS），每个微批沿同一个总分母累计梯度，全部完成后才裁剪并执行一次更新。计算经过的输入 token、回答条数和 loss 的归一化分母分别计数；不要在微批之外再多除一次批数。这里说明该配方的 token-mean 选择，不把它写成所有 RL 算法的统一规则。

### 10.5.2 长轨迹、抢占与采样恢复

依据 V4 的 token 级 WAL、抢占时 KV 保存及故障后重做 prefill，比较从断点继续与从头重采样。用长短轨迹的不同存活概率解释后者可能引入长度偏差，恢复同时影响系统成本与训练样本分布。同步／异步供给作为部署选择分析，只把报告明确披露的机制归于 V4。

再以 AReaL 的部分 rollout 区分“恢复同一策略”与“换权重后继续”：token、环境与行为 logprob 可以保留，新权重所需 KV 要重新验证或重建。给同一轨迹的不同段标出实际权重版本，比较版本滞后、暂停交接和有效样本供给；Qwen3-8B 的 8K KV 虽为 1.125 GiB，重建成本仍要回到 prefill 计算。沿[状态与版本算例](../case-studies/rl-state-and-reproducibility.md)解释扩大 rollout 池何时只会积压待验证或过期样本。

### 10.5.3 采样、教师与学习的资源配比

沿固定 verl 配方的 vLLM 权重交接，检查暂停、释放、同步与恢复各自在什么时候发生，再把同一阶段图扩展到 Qwen3-8B 的教学容量：训练和推理各自能放下，不代表交接峰值能放下。给定 64 GiB 可用预算，先恢复全部状态约需 83.26 GiB；先同步权重、释放训练状态再分配空 KV 池约需 59.26 GiB。后者是声明状态大小下的推算，不是小模型配方的实测峰值；保留地址也不能恢复已丢弃的数据。[条件与版本依据](../case-studies/weight-handoff.md)记录不同框架的实现范围。

随后改变一个条件：完整 actor、LoRA adapter 和 MTP 起草器分别需要保留哪些状态？沿实际支持的路径核对装载与后处理；跨 DP／EP 的交接还需所有相关 rank 就绪。SGLang 的历史路径在扩写中对照，不归作本次固定 vLLM 配方的执行结果。

分置时把第 6 章的模型切分继续算到权重分发。以 Qwen3-235B 的专家矩阵比较整份广播与按 EP 所需分片取回：423 GiB 专家权重在 EP16 下每 rank 只需 26.44 GiB，但瓶颈还可能在生产端网卡、训练侧重组和最大接收缓冲。用 vLLM 2026 的原生权重同步与 Sharded RDT 作案例，分别计入非专家权重、复制与量化；传输量缩小不能直接当作端到端加速倍数。

再借 RhymeRL 接回第 8 章的历史草稿：token 候选改变生成速度，历史长度帮助分组，但索引维护、验证接受率和每个副本的 batch 也会改变供给。分别在普通 decode 与历史起草下重算阶段配比，检查瓶颈是否转到奖励或学习；[案例](../case-studies/history-drafts-and-rollout.md)区分历史 token、旧 KV 与下一小节的路由记录。

固定教师的缓存选择也沿同一供给图推算：Qwen3-8B 的 8K token，BF16 最终 hidden 为 64 MiB，全 logits 约 2374 MiB。少存的数据要靠后续输出投影补算，复用次数会改变取舍；换教师版本后不能继续复用旧结果，完整算例留在扩写。

### 10.5.4 MoE 的 Routing Replay

先固定相同权重和 token，比较推理与训练引擎重算的专家选择及 logprob：不同精度、kernel 和 batch 形状产生的微小数值差异，可能翻转接近边界的 top-k，逐层积累成与策略更新无关的差异。由这个问题引出 Rollout Routing Replay／R3（2025），再用 NeMo RL 的 vLLM rollout＋Megatron 训练路径说明落地。

记录生成时每层、每 token 的专家 ID，在训练前向重放离散选择，同时以当前权重重新计算路由分数和专家输出，保留梯度。它不是重放旧输出，也不是省掉整个 router 计算；不能因此认为策略滞后、数值误差或 RL 收敛问题全部解决。与第 9 章 EPLB 区分：逻辑专家 ID 不随物理副本位置改变。

按 `有效 token 数 × MoE 层数 × top-k × ID 字节数` 先算路由记录，再加入多轮前缀、打包、上下文切分、传输与保存。例用 8,192 token、48 层、top-8、uint16 得 6 MiB；这是编码假设，真实后端若用 int32 则翻倍。缓存 KV 时要能找到同前缀的路由记录；采样、logprob、训练和激活重计算都要对齐 token 身份与权重版本。

> 沿固定 NeMo RL 的 Qwen3-30B-A3B R3 配方或其配套 trace，关闭／开启 replay 比较专家集合不一致率、同权重 logprob 差异、记录容量与阶段时间，再比较相同任务下的训练曲线。加入多轮缓存命中、样本 packing 和缺失路由检查，验证 token 对齐；小批检查只证明被覆盖路径，不冒充完整收敛结论。
>
> 条件：进阶·官方受支持配置／配套记录；完整训练作为可选扩展。

## 10.6 期限与资源投入的复核

### 10.6.1 有效训练进展与设备利用

沿前面的 MFU 预算，用 Google TPU 的 MPG 研究解释分配率为何不等于训练产出：沿具体训练记录，依次区分所有卡同时就绪、进展已保存的执行，以及同一数学工作的理想计算时间。100 张同型卡的一小时教学例中，单卡分配率可达 97.22%，最终计算基准对应的有效产出却只占容量的 33.33%；先算各段 GPU 时间，再给比例。聚合时统一分子分母，计算指标不能替代第 4 章的带宽瓶颈判断。[定义与复算](../case-studies/kernel-and-fleet-efficiency.md)。

### 10.6.2 模型规模、硬件代际与完成时间

用 A100、H100 与 B200 的明确形态和 dense 精度比较。先固定卡数、数据量与期限，反推可行规模；再分别固定预算或让数据量随参数增长，解释问题改变后答案为何不同。1T、5T、10T 作为明确标注的 Dense 扩展情景，真实 MoE 则按 V4-Pro／Kimi K3 的总状态与执行路径分别计算。
