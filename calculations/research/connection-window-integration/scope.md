# C68 finite ACK-window public boundary

This delivery connects a complete30MB upload, declared model processing and5MB final response through one global pair of full-duplex serialization resources. It preserves data packet identities, wire headers, reverse ACK traffic, sender-visible cumulative receive credit, separate unique outstanding credit, fixed ACK-driven growth and one selected timeout retransmission. File receipt, unique ACK completion and last protocol ACK/quiet are separate endpoints; cancelled timers do not extend the latter.

This is one explicitly declared finite teaching protocol, not TCP/QUIC/CUBIC/BBR. The initial design in connection-window-scope/README.md was a proposal. The implemented contract uses25KB segments,50KB initial window and1MB cap; admission irrevocably reserves unique credit before queued serialization. It does not reset the window after the selected loss. Those choices are visible in result assumptions and cannot be relabeled as RFC5681/6298 behavior.

RFC5681,6298 and8446 official original text is copied into sources/connection-window and registered in configs/sources.lock.json. Every call verifies the original hash/length via read_source; reference_sources identifies these as concept/implementation-boundary references. The numeric simulator is defined by its scenario and code, not derived from arbitrary RFC default values. Public results are candidate payload-identical except the public calculation identifier and the added verified reference records.

The independent review replays83 cases, including72 window/loss combinations,3 download loss positions,6 complete scenes and2 controlled duplicate injections. It reconstructs sender credit, ACK-visible prefix and physical FIFO resource conservation. Root additionally hand-checks4/4/2bytes stop/wait with input receiver27s, last uploadACK31s, shared-reverse response receiver33s and protocol quiet36s; timer100s never prolongs delivery. Same-time ACK/timeout and insufficient RTO cases are checked.

C68 remains open. Four sequential request reuse and retained/warm windows, actual TLS/QUIC new/resumed/reused/0RTT accepted/rejected/fallback contracts, fixed actual congestion controller behavior, speech/screenshot/media deadlines and figure12-4 are not delivered by this one-request finite protocol. Existing BDP, loopback and multistream records remain independent evidence. No protocol performance ranking or complete C68 claim follows from these tests.
