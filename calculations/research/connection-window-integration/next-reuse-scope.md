现有公共模型已经有真实方向串行器、ACK 返回推进、固定窗口增长、一次指定首发丢失、完整上传→模型→完整下载，以及有序握手消息图。它只运行一个请求，两方向均由同一个 `initial_window_bytes` 初始化；虽然结果已经输出各方向 `final_cwnd_bytes`，尚不能将不相等的两方向终值分别作为下一请求的初值。不能只将已有单请求时间乘四来宣称实现暖窗口。

当前源码准确边界优先于早期 scope 草案：段大小默认 25KB，队列 admission 即占唯一在途 credit，丢失后不重置窗口。早期草案的 1000B 分段、发送时占 credit、丢失重置均没有实现，不可在扩展中不说明便混用。

## 四请求扩展的第一验收用例与完整范围

复用公共单请求事件内核，增加单独序列计算入口或清晰的 sequence 模式；不要另写不相容的 B/W+RTT 近似器。固定四个相同 30MB 输入、5MB 输出请求，并增加同协议 64KiB 双向小文件对照，以覆盖原文大小请求差异。请求个数可作为受限整数输入，但冻结场景使用四个。相同有效链路/传播/分段/ACK/模型参数贯穿对照。

四种策略必须分别冻结：

1. 每轮四条声明消息后建立新连接，窗口每轮重置。
2. 每轮两条声明消息后建立新连接，窗口每轮重置；有效 ticket 是外部声明前置条件，不做免费恢复推论。
3. 第一次四条消息，其后三次复用连接，窗口每轮显式重置，隔离纯握手收益。
4. 第一次四条消息，其后三次复用连接，继承两个方向分别确认后的窗口，显示增量暖窗口收益。

默认图仍可用 c2s 400B/s2c 800B/c2s 400B/s2c 800B；两条消息图用前两条。名称和输出标明 custom message graph，不能直接命名成 TCP/TLS 或 QUIC 的精确结果。每条消息都依赖上一条到达，按方向计 wire bytes、序列化和传播，不能附加重复整体 RTT。

第一验收用例明确采用 ACK 排空后再提交：第 i+1 次到达等于第 i 次真实最后 ACK 时刻加声明非负 think time。默认 think time=0。该选择是受控串行工作负载；真实客户端可能在成片到达后就发下一轮，那种 ACK 未排空重叠必须另用共同事件引擎，不能借本 wrapper 声称覆盖。需要在输出中同时保存成片时刻、ACK 排空、下一次提交时刻与间隙。

**ACK 排空串行 wrapper 只完成第一验收用例，不证明整体请求复用完成。** 业务在完整成片到达后即可提交下一请求时，下一请求的上传可与上一请求的最后下载 ACK 竞争 client→server，窗口也只能继承提交当时已到达 ACK 造成的状态；后到 ACK 仍要更新同一连接的方向窗口。这个模式需要一个贯穿四轮的事件队列、方向串行器和连接级窗口，request_id 区分各请求文件前缀/ACK身份。不能在成片时把 final_cwnd（未来 ACK 后状态）提前借给下一轮，不能丢弃上轮 pending ACK，也不能重置链路可用时刻。完整复用交付必须包含该业务触发模式，或在原条目中继续明确它未完成。

## 必须维护的状态

- 连接层：connection_id、request_id、首次/新建/复用状态、所选显式握手图、提交/连接就绪绝对时刻。
- 窗口层：上行和下行独立 initial/final cwnd；继承仅取该方向最后确认后的值，不能取两方向 max 或把上行窗口赋给下行。分别验证正整数、可容纳最大实际段、初值不超 cap。
- 请求层：packet ID 与 offset 重新从零开始，但身份必须由 request_id+direction+packet 构成；received/acked 集合、累计前缀、唯一在途、重组、attempt 和计时器不得泄漏到下一请求。
- ACK 排空边界保证无真实在途数据、ACK、握手或预约，因此可以顺序调用同一内核、将相对时刻平移到全局时间。取消 timer 的未来 deadline 不表示真实在途；不能拿事件堆处理完的时间当提交门槛。若保存取消 timer 绝对时间，它可以落在下一请求区间，必须标记无物理资源意义并保留所属请求身份。
- 暖窗口无 idle decay 是显式假设；think time 不隐含窗口下降。新建连接必须重置；不得提供 new+preserve 的含混组合。建议将策略映射为明确 reset/preserve 规则，非法组合拒绝。
- 丢失位置必须带 request_id；每个单请求允许一次恢复不等于整个序列只能一次。冻结无丢失主对照，再单列第 2 请求指定一包首发丢失，以防四次无意都复用同一 loss 输入。是否全序列只允许一次应写入输入合同。
- packet/event 安全上限应同时约束总序列工作量，不能靠 per-request cap 绕过总规模限制。

## 输出与公平比较

每请求输出输入/输出 bytes、开始/结束窗口、握手 wire bytes、数据/头/ACK/重传 bytes、链路忙时、提交/握手就绪/完整上传/模型开始结束/完整成片/最后 ACK 的绝对时刻。每次请求逐事件日志仍可复现；字段说明相对还是绝对，避免嵌套结果里无声混用。

序列汇总分别给最后成片、最后 ACK、有效输入/输出 bytes、总物理 wire bytes、握手累计等待、请求响应时长之和和总墙钟跨度。响应时长从该请求提交到完整成片；不要把包含前轮等待的绝对完成时刻当该请求响应时长。相同 think time 与请求到达规则下比较策略。握手收益用策略 1 对 3；暖窗口增益用策略 3 对 4，不把两者合并成“协议升级加速”。

四请求上行唯一输入应为 120,000,000B，下行唯一输出 20,000,000B；重传不改变这些。默认四消息新建总握手 9600B、两消息新建 4800B、首次新建后三轮复用 2400B。这些是声明图字节，不包含未建模证书、票据签发/验证、加密 CPU 或真实协议额外消息。

## 可独立手算的验收 oracle

取输入 2B、输出 1B，段 1B，数据头与 ACK 均 0B；双向速率 8bit/s，每向传播 1s；IW=1B、cap=4B、rwnd=4B，每首次 ACK 增长 1B，model=0，固定 RTO=100s，不丢失，无 think time。

冷请求：上传第一段 0–1 发送、2 到达、3 ACK 返回；第二段 3–4 发送、5 到达、6 ACK 返回。模型在 5 完成，下载 5–6 发送、7 成片、8 最后 ACK。上传 cwnd 最终 3B，下行 2B，表明下一轮必须分别继承。未来取消 timer 到 101/104/106 等时刻不影响真实 quiet=8。

暖请求：上行初值 3B，两段可连续在 0–1、1–2 发送，于 2、3 到达、3、4 ACK 返回。下载 3–4 发送、5 成片、6 最后 ACK。本轮上行达到 cap4，下行变3；之后两轮此负载仍为成片5/quiet6，最终下行达到 cap4。每轮唯一载荷3B。

每条握手消息取 1B、方向交替，序列化 1s+传播1s，因此四条图耗8s，两条图耗4s。逐轮等真实最后 ACK 再提交：
