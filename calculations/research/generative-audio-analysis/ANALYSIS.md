# 音频生成：执行依赖、工作量和供给边界

本书落点是 AI Infra。以下信息服务于每步骤的矩阵/接口字节、执行次数、状态保留及供给计算，不作为大段架构介绍。

## 来源与稳定实现

本目录 `sources.lock.json` 固定九份小型官方实现：Transformers v4.57.1 的 Omni model/config；2026-09-09 审计时 current Omni model 作行为对照；Fish 官方仓库 slow/fast AR、推理、DAC/RVQ 与 codec YAML。锁包含 URL、revision、SHA256 与长度。未下载模型权重，配置使用项目既有官方归档。

新增 `topics/omni_audio.py` / `tests/test_omni_audio.py` 的第一阶段已经稳定，三个定向测试通过。当前是 Transformer 矩阵/KV 与码本循环账，不是完整音频请求总 FLOPs。`full_generation_flops/full_codec_flops/full_model_parameters/predicted_latency_seconds` 明确保留 null。

## Qwen3-Omni：两个外循环与一个帧内循环

输入文本和输出声学帧是独立轴，不能用文本 token 数乘固定系数得到音频帧数。

1. Thinker 处理文本/多模态输入并生成文本 token。每个文本位置的48层计算依赖之前文本位置；具体题例可以声明已在手的历史以及本次新位置，不计未执行的旧前向。
2. Thinker 的指定层 hidden 和 token embedding 分别经过两个 ResizeMLP。每个 MLP 的矩阵是2048→2048→1024，含偏置和SiLU。Talker 控制 token、speaker、tts pad 和文本对齐决定额外行数，不能悄悄当零。当前独立账只计调用者声明的文本行，其余是缺项。
3. Talker 沿声学时间轴执行20层 MoE，每帧输出主码。共享 FFN 宽768及其1024→1输出门也参与计算。
4. 每一帧主码产生后，CodePredictor 以“上一 Talker hidden + 主码 embedding”的两位置 prefill 开始，生成第一个残差码；随后14次单位置调用生成其余码。一次完整帧有15个残差输出，但处理16个位置、15次模型调用。当前官方 forward 对两个 prefill hidden 都计算第一个输出头，所以实际输出头行数也是16，不是15。
5. 16个码本 embedding 汇总并与该时间步文本 hidden/pad 相加，才能形成下一个 Talker 输入。这条依赖使同一请求的帧内预测不能当成15个完全独立任务。
6. Code2wav 对16码本 embedding 取均值，进入8层、窗口72的前置Transformer，再依次卷积上采样成波形。

**KV区别**：Thinker/Talker 沿各自时间轴增长；CodePredictor 每帧重建短缓存，最大16位置，不将容量乘总帧数。Code2wav 这里是整段块调用；不能把数学窗口72直接宣布为后端仅分配72条KV。当前记录其跨调用持久KV为0，并保留内部工作区未知。

## 默认入口并未把全部阶段做成实时流水

锁定 HF 顶层 `generate` 明确顺序调用：完整 `thinker.generate` → 完整 `talker.generate` → `code2wav.chunked_decode`。后者默认300帧/块、25帧左上下文，并最终拼接返回。框架或服务可以设计流式接口，但不能将这份源代码的架构潜力当作已经测得的流式首包时延。

因此，首音频关键路径必须选择一个真实接口协议：

- 固定 HF 整次调用：外部首次收到音频受完整 Thinker、完整 Talker/码本循环、所有 codec 块和返回影响。
- 假设新流式调度：必须明确第一块 F_c、Thinker最低可消费文本行、frame/codebook数据依赖、codec所需上下文和缓冲。其第一块工作至少覆盖 F_c 个 Talker 步与 F_c 个完整内循环，再加首块codec，不能仅报一次decode耗时。

## Code2wav名义步长与源实现长度必须区分

配置上采样乘积为 `2×2×8×5×4×3=1920`。官方模型卡写出24kHz输出，对应名义12.5帧/秒。

但两份已锁官方实现均使用：ConvTranspose无padding输出长度 `(L−1)s+k`，然后左右各裁掉`k−s`。两个前置 k=s 的倍率2层保持正常倍率；后面四层 k=2s，分别减少s个样本，逐层传播后最终长度为：

`1920F − (8×5×4×3 + 5×4×3 + 4×3 + 3) = 1920F − 555`。

这只是可直接审查的源实现张量几何，不冒充实际执行或擅自“修复”代码。独立测试按输入位置/卷积核位置枚举输出坐标与裁剪验证此式。每个chunk都会受到该差额；左上下文重复执行和裁除还需单独算总调用量。后续不能直接用名义帧率把输出块长度当成精确音频持续时间。

## Fish S2 Pro：fast不是九次执行

慢模型配置为 H2560、36层、32Q/8KV、head128、FFN9728。快模型同H/head/FFN，4层，无QK norm。使用源码的维度，不能将 head_dim 推为2560/32，也不能把“4B+400M”宣传数当精确参数。

每帧依赖：Slow AR输出主语义码及hidden → fast位置0用hidden预热 → fast位置1到9分别预测残差码 → 10码本音频embedding参与下一Slow输入。预热位置0照常执行四层、final norm与4096输出头，logits被丢弃；因此每帧是10次快模型计算、9次残差采样，逻辑因果pair数`1+...+10=55`。

快缓存位置0..9每帧覆盖重用，不能随音频秒数增长；慢缓存沿帧轴增长。源代码为快模型预分配十位置，实际注意力mask可保留矩形工作，其有效55pairs不等于所有backend指令数。当前模块只报有效工作。

codec YAML 的编码降采样 `2×4×8×8=512`，RVQ又降采样`2×2`，在44100Hz下名义码率精确为 `44100/2048=21.533203125` 帧/秒，不能当21。其语义码本4096，九残差码本各1024；Fast AR输出头4096仍是真实矩阵宽度。**RVQ.decode 明确 clamp 语义/残差索引到对应码本上限**，所以维度差不能通过缩小fast矩阵“纠正”，应增加clamp计量和码本读取。完整codec输出长度与卷积矩阵仍待实施。

## 接下来可直接实施的 Infra 账

当前模型几何的下一步是阶段执行DAG，不是再介绍模型：

- 每节点输出矩阵列表、有效FLOPs、执行次数、输入/权重/输出接口字节、固定和随时间增长的状态。专家矩阵执行行数按top-k，但一轮访问的专家并集须显式假设；不能把全部专家常驻容量当每步读取量。
- 拆分首次调用准备、文本外循环、声学外循环、码本内循环、codec块循环以及重复左上下文。每个循环给具体上下界/次数，首帧和后续帧单列。
- 输入有效矩阵供给、有效接口带宽和每调用固定开销，计算条件节点服务时间；节点间串行依赖沿DAG累加，独立请求共享服务池以每请求总工作算稳态上界。理论硬件峰值的精度、dense/sparse和执行单元必须匹配，不将scalar/codec成本混入Tensor FLOPs除法。
- 未计完整codec、输入前处理/采样和实际调度前，首音频ms和全请求吞吐保持未知；可以输出已覆盖工作对供给的必要下界，不把局部账标题写成全请求总成本。

推荐小例：Omni F=12/B1/Ttext16，与F=73的72窗口边界；Fish F=21与F=22展示“21Hz”取整误差；Omni单帧对照两位置prefill/14次调用；多请求B4展示共享供给与单请求依赖不可混同。
