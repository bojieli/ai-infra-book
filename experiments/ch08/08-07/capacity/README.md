# 8-5 容量分析：MacBook 上的 Qwen3-235B（本目录为实验 8-5 的容量部分）

对应正文 8.5。对 Qwen3-235B-A22B 的**实际量化文件逐片求和**，再用 M2 Max 96 GB 的可用内存、8K／32K 上下文与并发计算驻留，判断何时需要主存／磁盘换入。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py gguf-inventory
```

只需 Python 3.8+ 标准库。数据来自官方发布仓库 `unsloth/Qwen3-235B-A22B-GGUF`（固定 revision `09e11417…`）的分片清单与 LFS SHA256：树中 19 个完整变体、72 份完整 GGUF 文件，**逐片求和**而不是用标称参数量估算。

同一实验的**实跑记录**在上级目录：Mac 上 Qwen3-8B MLX 4-bit 的 14 次生成、8K 与 32K 上下文的实际槽位与 KV 占用。

## 结果

BF16 KV 每 token **192,512 B**；8K 上下文的一个独立请求要 **1.47 GiB**，32K 要 5.88 GiB。

**M2 Max 96 GB、8K 上下文、预留 8 GiB（可用 81.41 GiB）**

| 变体 | 分片 | 文件合计 | 装入后剩余 | 可容纳独立请求 |
| --- | ---: | ---: | ---: | ---: |
| **Q2_K** | 2 | **79.81 GiB** | **1.60 GiB** | **1** |
| UD-Q2_K_XL | 2 | 81.97 GiB | −0.56 GiB | 0 |
| Q3_K_S | 3 | 94.48 GiB | −13.07 GiB | 0 |
| Q4_K_M | 3 | 132.39 GiB | −50.98 GiB | 0 |
| Q8_0 | 6 | 232.77 GiB | −151.37 GiB | 0 |
| BF16 | 10 | 437.99 GiB | −356.59 GiB | 0 |

四条判断：

1. **只有 Q2_K 装得下，而且只剩 1.60 GiB**。UD-Q2_K_XL 只比它大 2.16 GiB 就已经溢出 0.56 GiB——**可行与不可行之间的间隔小于一个变体档位**。
2. **8K 与 32K 的差别是"能跑 1 路"与"一路都跑不了"**。同样是 Q2_K，8K 时剩下的 1.60 GiB 刚够一个 1.47 GiB 的 KV；32K 需要 5.88 GiB，直接放不下。**在 96 GB 的 Mac 上跑 235B，上下文长度而不是模型大小决定可行性。**
3. **预留 8 GiB 的假设决定结论**。不预留时（可用 89.41 GiB）Q2_K 能容纳 6 个请求、UD-Q2_K_XL 能容纳 5 个——从"勉强 1 路"变成"可用"。但操作系统、图形栈与应用本身确实要占内存，把预留设为 0 不是可部署的配置。**这一行的作用是说明结论对该假设有多敏感。**
4. **超过 Q3_K_S 之后必须主存／磁盘换入**。Q4_K_M 溢出 50.98 GiB，即使按 MoE 只换入激活专家，每步换入的字节也远超统一内存带宽能承受的量（对照实验 4-3：M2 Max 400 GB/s）。

M3 Ultra 192 GB 一档（结果文件第四组）可以装下 Q4_K_M 并留出余量——**这是"要不要买更大内存的 Mac"这个问题的量化答案**。

完整四组数值与逐片 SHA256 见 [results/capacity.md](results/capacity.md) 与 `results/inventory-*.json`。

## 限制

- 文件字节是发布仓库的实际大小，**不等于运行时驻留**：加载器的对齐、元数据与临时缓冲另计。
- KV 按 BF16、每请求独立计；实际引擎的分页与前缀共享会改变可容纳数（见实验 8-3、8-4）。
- 可用内存 = 标称容量 − 预留，是声明模型；macOS 的统一内存由 CPU/GPU/系统共享，实际可分配上限还受 `iogpu.wired_limit_mb` 等设置影响。
- 未按实测带宽预测速度；速度侧见上级目录的 MLX 实跑与实验 4-3 的带宽下界。
- R1 极低比特文件的对照未纳入本组（该仓库未在固定来源集中），保持为空。
