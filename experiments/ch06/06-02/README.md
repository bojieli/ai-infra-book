# 实验 6-2：Qwen3-8B 的并行组合

对应正文 6.2 的核心练习。在同一组八卡资源上比较副本、TP=1／2／4／8 与若干 TP×PP 组合：逐卡权重、KV、计算及每层通信，扫描 batch 和长度，给出各服务目标下的候选区间，再提出一项最值得补测的量。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py dense-placement|dense-communication
```

只需 Python 3.8+ 标准库。八卡、逐卡 80 GB；互联单向 450 GB/s、启动 3 μs 是**声明输入**。

本目录另有一份**实跑**：[jax-tp-sp/](jax-tp-sp/README.md) 在 M2 Max 的 CPU 逻辑设备上实际执行 Qwen3-8B FFN 形状的 TP 与 SP 两条路径，两批各 8 配置、40 个计时样本全部通过 FP64 参考检查，同 token 数与分片数的 TP/SP 四对输出**逐位相同**；每 rank 输出分配随 SP 切分从 512 降到 128 KiB。

## 逐卡收支扫描

| TP×PP×DP | 历史 | 每副本 batch | 全局并发 | 最忙卡驻留 | 逐卡矩阵 GFLOPs |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1×1×8（纯副本） | 8,192 | 8 | **64** | 26.26 GiB | 1,278.0 |
| 2×1×4 | 8,192 | 8 | 32 | 14.13 GiB | 639.0 |
| 4×1×2 | 8,192 | 8 | 16 | 8.06 GiB | 319.5 |
| 8×1×1 | 8,192 | 8 | 8 | **5.03 GiB** | **159.8** |
| 1×1×8 | 32,768 | 8 | 64 | **53.26 GiB** | 2,205.7 |
| 8×1×1 | 32,768 | 8 | 8 | 8.71 GiB | 275.7 |

八种组合在本组条件下**容量全部通过**——Qwen3-8B 太小，容量不是约束。真正的取舍在两端：

- **纯副本（1×1×8）**给出最高的全局并发（64），但每张卡要扛全部权重与自己那份 KV（32K 历史时 53.3 GiB），且每卡的矩阵工作最多。它服务**吞吐目标**。
- **TP=8** 把逐卡驻留压到 5.03 GiB、逐卡矩阵工作压到 1/8，单请求最快，但全局并发只有 8。它服务**延迟目标**。
- TP×PP 组合（2×4、4×2、2×2×2）的逐卡收支介于两者之间，代价是每步的通信操作数从 75 升到 77–79——**流水线段间交接是额外加进来的操作，不是免费的重排**。

## 每层通信

| TP×PP×DP | 每层激活 | 词表 logit 分片 | 非空通信操作 |
| --- | ---: | ---: | ---: |
| 1×1×8 | 8,192 B | 607.7 KB | 0 |
| 2×1×4 | 8,192 B | 303.9 KB | 75 |
| 8×1×1 | 8,192 B | **76.0 KB** | 75 |
| 2×4×1 | 8,192 B | 303.9 KB | **79** |

TP 增大不改变每层激活载荷（8 KB，只与 hidden 和 batch 有关），但把词表 logit 分片按 TP 均分。**decode 时每次通信只有几 KB——这正是实验 6-4 说的“小消息由启动时间决定”的区间**，因此 TP 的通信代价几乎全在 α（每次调用的启动开销）上，与带宽关系不大。

## 各服务目标下的候选区间

- **吞吐优先**：1×1×8 或 2×1×4（并发 64／32）。
- **延迟优先**：8×1×1（逐卡工作 1/8）。
- **长上下文**：TP≥4，否则 32K 历史下最忙卡驻留超过 50 GiB，留给工作区的余量太少。
- **中间地带**：4×1×2 在四项里都不是最差，是没有明确目标时的默认选择。

## 最值得补测的一项

**TP=8 时每层 all-reduce 的实际启动开销 α**。本表的通信项按声明 α 计算；实验 6-5 已经证明通信与计算共享资源时两者都会变慢（通信 36.92→45.21 ms，计算 11.03→12.88 ms），因此 α 的实测值会**同时**改变通信项与计算项，是唯一能翻转 TP=8 与 4×1×2 排序的量。

完整数值见 [results/parallel.md](results/parallel.md)。

## 限制

- 逐卡驻留不含分配器碎片与运行时临时量；容量通过不代表可用吞吐。
- 通信按声明 α 与带宽计算，未计入拥塞、重叠与实际集合通信库的算法切换。
- 四卡 SP×TP／完整 TP 的双模式切换按大纲安排放在第 9.6.2 节，沿用本题的固定切分。
