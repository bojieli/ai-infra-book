# 实验 6-9：内存池的容量收益与访问代价

对应正文 6.5。四台机器的总内存够用，为什么仍有任务放不下？四个 64 GiB 节点分别承接 80、48、32、32 GiB 的工作集，比较迁移任务、增加本地容量、向池借用 16 GiB 三条路径，再对同一份工作集只改变访问频次，求借用路径必须提供的能力。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py memory-pool-access
```

只需 Python 3.8+ 标准库。

## 容量：总量够，仍然放不下

| 节点 | 容量 | 任务需求 | 本地缺口 |
| ---: | ---: | ---: | ---: |
| 0 | 64 GiB | **80 GiB** | **16 GiB** |
| 1 | 64 GiB | 48 GiB | 0 |
| 2 | 64 GiB | 32 GiB | 0 |
| 3 | 64 GiB | 32 GiB | 0 |

总容量 256 GiB、总需求 192 GiB，**总量有 64 GiB 富余**，任务却放不下。三条路径的结论：

- **整任务迁移不可行**：80 GiB 的任务超过每一个 64 GiB 节点。总量富余分散在三台机器上，对这个不可切分的任务没有意义——池化要解决的正是这 **80 GiB 无法被使用的本地余量**。
- **增加本地容量**：只需给节点 0 加 16 GiB。最简单，但要改硬件配置，且富余仍然被锁在各自节点里。
- **向池借用 16 GiB**：唯一借用量正好等于缺口。容量问题解决了，但引入了**访问代价**——这是下一张表。

若任务可切分，迁走 16 GiB 的计算也是一种容量可行方案，但其运行时代价未知（切分是否合法、跨节点通信多少），本实验不填造。

## 访问频次决定借用路径必须提供什么

| 接口带宽 | 延迟 | 在途事务 | 读/秒 | 一次读取服务时间 | 负载 | 队列有界 |
| ---: | ---: | ---: | ---: | ---: | ---: | :---: |
| 10 GB/s | 2 μs | 128 | 0.0167 | 1.718 s | 0.029 | 是 |
| 10 GB/s | 2 μs | 128 | 1 | 1.718 s | 1.718 | **否** |
| 10 GB/s | 20 μs | 128 | 0.0167 | 10.486 s | 0.175 | 是 |
| 40 GB/s | 2 μs | 4096 | 1 | 0.430 s | 0.430 | 是 |
| 40 GB/s | 20 μs | 4096 | 1 | 0.430 s | 0.430 | 是 |
| 40 GB/s | 20 μs | 128 | 1 | 10.486 s | 10.486 | **否** |

24 个组合中 10 个可行、14 个不可行。三条判断：

1. **访问频次是决定性的**。同一条 10 GB/s、2 μs 的链路，每分钟读一次（0.0167 /s）负载只有 0.029，队列有界；每秒读一次就变成 1.718，立刻积压。借用同样 16 GiB，冷数据可行、热数据不可行。
2. **在途事务数比延迟更关键**。40 GB/s、20 μs、128 在途时服务时间 10.486 s；把在途提到 4096 后降到 0.430 s——**24 倍**。而在 4096 在途下，延迟 2 μs 与 20 μs 的服务时间完全相同（0.430 s），因为并发已经把延迟掩盖掉了。这条正是第 7 章“远程读取的在途并发”的先导。
3. **借用路径必须声明的能力是三元组**：带宽、延迟、在途事务数。只给带宽不足以判断可行——上表里 40 GB/s 的行既有可行也有不可行。

完整 24 行见 [results/pool.md](results/pool.md)。

## 限制

- 服务时间是确定性串行队列的条件值，不是排队论的期望值，也不是实测。
- 工作集按整块读取计；真实访问的局部性、缓存与预取都未计入，加入后可行区间会扩大。
- 池的故障域与副本依赖单列在结果 JSON 的 `failure_sets` 中；借用引入的新失效模式不由容量表回答。
- 第 9.5 节把这份固定工作集具体化为增长、失效与取回中的 KV，再算完整服务收益。
