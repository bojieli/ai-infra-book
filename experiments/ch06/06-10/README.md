# 实验 6-10：超节点规模与系统成本

对应正文 6.6 的核心练习。更大的超节点比更多的小型超节点划算吗？在同一组八卡资源上比较三种组织，改变模型、并发、延迟目标和故障恢复成本，给出选择改变的条件。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py supernode-cohort-cost
```

只需 Python 3.8+ 标准库。三种组织共用同样的 8 张卡：**tp8×1 副本**（一个大超节点）、**tp4×2**、**tp2×4**（多个小超节点）。费用、恢复时间与 SLO 门槛（3/4 请求达标）是声明输入。

## 结果

| 情形 | tp8×1 | tp4×2 | tp2×4 | 选中 |
| --- | --- | --- | --- | --- |
| 基线：4 并发、250 ms 目标 | 4 有效 / 0.496 | 4 / 0.400 | 4 / **0.320** | **tp2×4** |
| 延迟目标放宽到 500 ms | 4 / 0.496 | 4 / 0.400 | 4 / **0.320** | **tp2×4** |
| 输出 8→64 | 3 / 4.245 | 4 / 2.640 | 4 / **2.112** | **tp2×4** |
| 注入故障（恢复 200 ms） | **0 有效** | 2 / 2.300 | 3 / **1.427** | **tp2×4** |
| 恢复更贵（计费 ×5） | 0 有效 | 2 / 4.300 | 3 / **2.760** | **tp2×4** |
| **延迟目标收紧到 120 ms** | 1 / 1.984 | **2 / 0.800** | **0 有效** | 无一达标 |
| **换更大模型 Qwen3-32B** | 4 / 0.992 | 4 / **0.800** | **容量放不下** | **tp4×2** |

（格式：SLO 有效请求数 / 每有效请求费用）

**默认答案是“更多的小型超节点”**：在基线、放宽延迟、更长输出和故障注入四种情形下，tp2×4 的每有效请求费用都最低。原因是这组请求同时到达，多副本能并行服务，而单个大超节点只能排队——完成时间 160 ms 对 248 ms。故障时差距更大：tp8×1 的单一副本一挂就全军覆没（0 有效），tp2×4 只损失 1 个请求。

**选择改变的条件有两个，方向相反：**

1. **延迟目标收紧到 120 ms 时**，tp2×4 反而变成最差（0 有效）。它的单请求延迟是 160 ms，因为每个请求只用 2 张卡；tp4×2 用 4 张卡把单请求压到 100 ms，能救回 2 个。**并行度买的是单请求延迟，副本数买的是吞吐与容错，两者争同一份卡。**
2. **换成更大的模型时**，tp2×4 直接容量放不下，选择被迫回到 tp4×2。**容量是可行性前提，费用比较只在可行的候选之间进行。**

一句话：**超节点该做多大，由“单请求延迟目标”和“模型放得下”共同框定；在这个框内，副本越多越划算。**

完整逐情形数值见 [results/cohort.md](results/cohort.md)。

## 限制

- 请求同时到达、静态轮转、每副本一次服务一个请求；这里的并发是到达 cohort 大小，不是 tensor batch。
- 阶段时长是声明的教学值，全部 8 卡与全部副本始终预留至 cohort 完成，不含弹性伸缩。
- 费用是"声明信用"单位，不是货币；恢复计费与失败尝试单列在结果 JSON 的 `cost.subtotals_exact` 中。
- 未计入跨超节点的网络成本与运维复杂度——副本越多，路由与缓存亲和性越难（第 9 章）。
