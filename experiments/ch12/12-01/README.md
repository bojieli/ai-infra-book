# 实验 12-1：图片精修的传输与计算预算

对应正文 12.1。用原图和成片的实际字节计算上传、执行与回传；扫描上行带宽、处理速度和压缩开销，比较**减少字节、复用连接、加速模型**各省多少时间。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py image-request-budget
```

只需 Python 3.8+ 标准库。原图 30 MB、成片 5 MB；各阶段时间是声明输入，**不执行任何编解码或模型**。压缩变体在同一业务要求下把传输字节减半（15 MB），代价是 0.2 s 编码＋0.1 s 解码。

## 结果

| 情形 | 原图路径 | 压缩路径 | 压缩是否更好 |
| --- | ---: | ---: | :---: |
| 基线（20 Mb/s 上行） | 13.000 s | **7.300 s** | 是（−44%） |
| 上行 5 Mb/s | 49.000 s | **25.300 s** | 是（−48%） |
| 上行 100 Mb/s | 3.400 s | **2.500 s** | 是（−26%） |
| **上行 1 Gb/s** | **1.240 s** | 1.420 s | **否（+15%）** |
| 模型加速到 0.1 s | 12.800 s | 7.100 s | 是 |
| 模型变慢到 3 s | 15.700 s | 10.000 s | 是 |
| 压缩到 1/4（7.5 MB，编码 0.4 s） | 13.000 s | **4.500 s** | 是（−65%） |

三条判断：

1. **三种优化的收益差着量级**。基线上：减少字节省 5.7 s，加速模型（0.3→0.1 s）省 0.2 s，复用连接省 0.2 s。**上传占 13 秒里的 12 秒，其它两项加起来只有 3%。** 对这条路径，任何不减少上传字节的优化都是白费力气。
2. **压缩有交叉点**。上行到 1 Gb/s 时，传输只要 0.24 s，而压缩的编解码开销是 0.3 s——压缩反而**慢 15%**。交叉点出现在"传输节省 = 编解码开销"处；本例中约在 400–500 Mb/s 之间。**在快网络上压缩是负优化**，这正是端边云决策里最容易搞反的一条。
3. **模型变慢也改变不了主导项**。模型从 0.3 s 变到 3 s（10 倍），原图路径只从 13.0 涨到 15.7 s（+21%）。远端执行的延迟预算在慢上行下由传输而非计算决定——**"换更快的推理服务"解决不了这个问题**。

完整 16 行数值见 [results/budget.md](results/budget.md)。

## 限制

- 所有阶段串行：服务端等待完整输入，下载在成片编码之后；不假设分块或预览重叠。预览时间保持未知，早出预览不能替代完整成片。
- 文件字节是显式元数据，不由像素或 VAE 张量导出；同质量授权是调用方断言，不是实测的质量保证。
- `request_rtt` 只收一次，不按阶段累加；复用连接只去掉建连项，RTT 仍在。
- 本地处理时间（5 s）必须覆盖同一"原始输入到可用成片"的边界与质量要求才可比。
