# 实验 12-5：ACK 频率与空口效率

对应正文 12.3。减少 ACK 一定有利吗？按语音块与视觉帧的速率建立空口模型，扫描 ACK 频率，比较线上字节、等待与反馈延迟；改变编码码率后重算。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py transport-closed-loop
```

只需 Python 3.8+ 标准库。该实现逐包重放上下行链路、拥塞控制与 ACK 策略。上行 9,824 bps／下行 736 bps、单向传播各 1 单位是**声明输入**（上下行严重不对称，正是空口的典型形态）。

## 结果

| 媒体 | ACK 策略 | 线上/载荷 | 等待次数 | 最后应用事件 |
| --- | --- | ---: | ---: | ---: |
| 视觉帧（低码率） | 每包 ACK | 1.1341 | 1 | **37.04** |
| 视觉帧（低码率） | 每 2 包 | 1.0949 | 2 | 39.01 |
| 视觉帧（低码率） | 每 4 包 | 1.0765 | 2 | 50.01 |
| 视觉帧（低码率） | 每 8 包 | **1.0687** | 3 | **60.01** |
| 视觉帧（低码率） | 每 16 包 | 1.0687 | 3 | 63.01 |
| 视觉帧（低码率） | **每 8 包或 2 单位超时** | **1.0844** | 2 | **41.04** |
| 视觉帧（高码率） | 每包 ACK | 1.1313 | 1 | 127.04 |
| 视觉帧（高码率） | 每 16 包 | **1.0610** | 3 | **152.91** |
| 视觉帧（高码率） | 每 8 包或 2 单位超时 | 1.0794 | 2 | **131.04** |
| 语音块（低码率） | 每包 ACK | 1.1926 | 0 | 6.00 |
| 语音块（低码率） | 每 2 包及以上 | 1.1537 | 0 | 6.00 |

**答案是否定的：减少 ACK 省的是上行字节，代价是完成时间。**

1. **省字节确实有效**。视觉帧低码率下，从每包 ACK 到每 8 包，线上/载荷比从 1.1341 降到 1.0687——**上行开销减少一半**。在上下行严重不对称的空口上，这不是小数目：ACK 走的是那条只有 736 bps 的下行。
2. **但完成时间涨了 62%**（37.04 → 60.01）。ACK 变稀导致发送方的窗口推进变慢、等待次数从 1 次增到 3 次。**吞吐没变，反馈变慢了**——这对需要低延迟反馈的实时媒体是直接的伤害。
3. **"每 8 包或 2 单位超时"是这组里的最优解**：线上/载荷 1.0844（保住了 3/4 的字节节省），完成时间 41.04（只比每包 ACK 多 11%）。**计数与定时的组合策略同时拿到两边**——这也是真实协议普遍采用延迟 ACK＋超时兜底的原因。
4. **码率改变结论的幅度而非方向**。高码率视觉帧上，每 16 包 ACK 把完成推到 152.91（比每包 ACK 的 127.04 慢 20%），组合策略仍是 131.04。语音块因为太小（2,336 B），根本不触发窗口限制，六种策略的完成时间几乎相同——**小消息上调 ACK 频率不解决任何问题**。

完整 24 行数值见 [results/ack.md](results/ack.md)。

## 限制

- 链路速率、传播时延与初始窗口是声明输入，不是实测空口。真实无线还有调度周期、重传与信道波动。
- "最后应用事件"是本模型下的完成时刻，不是端到端播放延迟；播放停顿与输入过期的完整时序见实验 3-5。
- ACK 字节按固定开销计，不含协议头压缩与聚合。
- 不含丢包与重传；多路径下的重传成本见实验 7-9。
