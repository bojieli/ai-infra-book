# 实验 1-5：语音需求与专用化决策（配套延伸）

对应正文 1.4.1。用 TPU v1 论文里的历史需求锚点，算三个使用率下的增量容量，再比较通用扩容与专用加速两条路线，最后列出结论还依赖哪些没有数据的条件。

## 独立运行

只需 Python 3.8+ 标准库：

```bash
python3 run.py    # 写出 results/tpu-demand.json 与 .md
```

## 唯一的历史锚点

TPU v1 论文第 2 节记载：2013 年的预测认为，**若每人每天使用三分钟语音搜索，数据中心的计算需求将翻倍**。

论文没有给用户数，也没有给服务器台数。本实验因此把现有计算容量归一化为 1，把这条预测读成“再增加 1 个单位”。除此之外的每一步都是显式声明的线性外推，不是新的历史观察。原件见 [TPU v1](../../../references/files/papers/tpu-v1.pdf)。

## 结果

**三个使用率下的增量容量**

| 使用率 | 新增容量 | 总容量 |
| ---: | ---: | ---: |
| 1 分钟/人/天 | 0.333 单位 | 1.333 单位 |
| 3 分钟/人/天（论文锚点） | 1 单位 | 2 单位 |
| 6 分钟/人/天 | 2 单位 | 3 单位 |

**通用扩容与专用加速**

在 3 分钟锚点上，通用扩容要再建一整个数据中心的计算容量；若专用路线对这部分语音负载有声明的 10× 有效容量，新增只要 0.1 个单位，总容量 1.1；30× 时新增 0.033 个单位。使用率越高，两条路线的差距越大：6 分钟时通用要 +2 个单位，10× 专用只要 +0.2。

**单因子敏感性（固定 3 分钟）**：人口翻倍或峰值是均值的 2 倍，都把新增容量推到 2 个单位；模型变小使每秒音频工作量减半，则降到 0.5 个单位。三项同时发生（人口 ×2、工作量 ×0.5、峰值 ×2）回到 2 个单位——**互相抵消，不是互相独立**，这正是单因子敏感性必须逐项列出的原因。

完整数值见 [results/tpu-demand.md](results/tpu-demand.md)。

## 这个计算能回答什么、不能回答什么

能回答的是**需求侧的规模**：新增语音负载相当于现有容量的多少倍，以及有效容量倍数把它压到多少。这一条足以把问题从“要不要研发专用芯片”变成一个可比较的具体问题。

不能回答投入结论。它还依赖：

- **供数**：语音模型每秒音频要读多少权重与状态，专用芯片能否喂饱阵列。第 4 章展开。
- **成本**：单位容量的采购、供电与散热成本，以及研发投入需要多少台才摊得平。
- **交付**：从立项到上线的周期，是否赶得上需求增长的时间点。
- **负载稳定性**：模型结构在交付周期内会不会变，专用化会不会做完就过时。
- **延迟目标**：语音搜索的响应时限，决定能否靠排队提高利用率。
- **异构主机**：专用加速器仍需 CPU、内存与网络配套，这部分容量没有被替代。

## 限制

- 容量单位是同质归一化，不代表放置、功耗、延迟或加速器台数。用户数、服务器台数、实际加速器数量和成本论文都没有给，本实验保持为空，不填造。
- 有效容量倍数是可调输入。论文的 10× 性价比设计目标不是有效吞吐倍数，本实验不默认取用它。
- 线性外推是教学假设。真实使用率增长通常伴随请求分布和峰谷比的变化，第 3 章重新处理。
