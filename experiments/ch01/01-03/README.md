# 实验 1-3：什么改动能缩短生成时间

对应正文 1.3 的核心练习。沿同一教学模型（名义 70B、逐 token 生成、H100 SXM 资源卡）做四类改动，先检查容量，再算计算与读取两项下界，最后说明当前哪项改动有效、哪些新增成本还没算。

## 独立运行

只需 Python 3.8+ 标准库：

```bash
python3 run.py       # 写出 results/sensitivity.json 与 .md
python3 verify.py    # 与 calculations/ 的 decode-budget 场景交叉核对
```

## 固定输入

- 名义 70×10⁹ 参数，矩阵工作近似 `2 × N × batch` FLOPs。
- 权重每步整批共享读一次；每请求的历史状态另计。
- H100 SXM 标称资源卡：80 GB 容量、3.35 TB/s 显存带宽、989.4 TFLOPs/s（BF16 输入／FP32 累加／dense 张量峰值）。
- 资源时间下界取计算项与读取项的**最大值**，即假设两者完全重叠。

## 结果

| 改动 | 驻留 | 容量 | 计算下界 | 读取下界 | 资源下界 | 主导 | 吞吐 |
| --- | ---: | :---: | ---: | ---: | ---: | --- | ---: |
| 基线：8 bit，batch=1 | 70.0 GB | 通过 | 0.141 ms | 20.896 ms | 20.896 ms | 读取 | 48 tok/s |
| 翻倍算力 | 70.0 GB | 通过 | 0.071 ms | 20.896 ms | 20.896 ms | 读取 | 48 tok/s |
| 翻倍带宽 | 70.0 GB | 通过 | 0.141 ms | 10.448 ms | 10.448 ms | 读取 | 96 tok/s |
| 位宽 8→4 bit | 35.0 GB | 通过 | 0.141 ms | 10.448 ms | 10.448 ms | 读取 | 96 tok/s |
| 位宽 8→16 bit | 140.0 GB | **不通过** | 0.141 ms | 41.791 ms | — | — | — |
| batch=8 | 70.0 GB | 通过 | 1.132 ms | 20.896 ms | 20.896 ms | 读取 | 383 tok/s |
| batch=64 | 70.0 GB | 通过 | 9.056 ms | 20.896 ms | 20.896 ms | 读取 | 3,063 tok/s |
| batch=148 | 70.0 GB | 通过 | 20.942 ms | 20.896 ms | 20.942 ms | 计算 | 7,067 tok/s |
| batch=256 | 70.0 GB | 通过 | 36.224 ms | 20.896 ms | 36.224 ms | 计算 | 7,067 tok/s |
| batch=64 且每请求 128 MB KV | 78.2 GB | 通过 | 9.056 ms | 23.341 ms | 23.341 ms | 读取 | 2,742 tok/s |

四个判断：

1. **翻倍算力对这一步毫无作用**。计算项只有 0.141 ms，占资源下界的 0.7%；把它减半，下界一点不动。
2. **翻倍带宽把下界减半**，从 20.9 ms 到 10.4 ms，因为读取是当前的主导项。
3. **降位宽和加带宽在这一步等价**：8→4 bit 让每步读的字节减半，效果与带宽翻倍相同（10.4 ms）。但 8→16 bit 先在容量上就不成立——140 GB 装不进 80 GB，不必再比时间。位宽换来的时间不是免费的，质量必须单独评测。
4. **加 batch 不缩短单步时间，但提高吞吐**。batch 从 1 到 64，每步仍是 20.9 ms，吞吐却从 48 涨到 3,063 tok/s，因为同一次权重读取被 64 个输出分摊。到 batch=148 时计算与读取相等；再往上就变成计算主导，吞吐停在 7,067 tok/s 不再增长。

交叉点随每请求状态改变：无 KV 时是 **148**，每请求 128 MB KV 时推到 **203**，因为历史状态的读取也随 batch 增长，抵消了一部分复用收益。

完整数值见 [results/sensitivity.md](results/sensitivity.md) 与 [results/sensitivity.json](results/sensitivity.json)。

## 尚未计入的成本

- 历史状态（KV）的读取随 batch 与长度线性增长，基线里被设为 0；最后一行给出把它计入后的变化。
- 非矩阵操作（归一化、Softmax、激活、RoPE、采样）不在 `2N` 里。
- kernel 启动、调度与主机提交的串行等待没有计入，因此这是下界而不是预测。
- 低位宽存储需要反量化，可能增加计算和片上缓冲；**质量变化必须单独评测**，本实验不预设质量保持。
- 更大 batch 需要更多工作区与 KV 容量，可能先撞到容量而不是时间。
- 批内请求要等齐，单请求等待会变长。吞吐上升与单请求变快不是同一件事——实验 1-4 用实测给出这一分离。

## 交叉核对

`verify.py` 对基线、翻倍算力、翻倍带宽、4 bit 和 batch=64 五个场景，与 `calculations/` 中另一套独立实现逐项比对计算下界、读取下界与权重字节，15 项全部一致。这只说明两处算术没有分歧，不说明教学假设本身成立。
