# 实验 3-10：GPU 小时与系统预算

对应正文 3.5（进阶延伸）。核对 Llama 1/2/3.1、Qwen2.5/3/3.5、DeepSeek-V3/V4 的公开字段；对卡数已知的案例估算日历时间，对其他案例给条件区间；再把长期服务费用加入比较，说明哪些数据缺失会改变选择。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py，产物写入 results/
```

只需 Python 3.8+ 标准库。公开字段由 `calc.py training-history` 从固定原件抄录并做哈希校验；假设卡数（1,024–16,384）是本实验声明的教学档位，不是任何报告里的数字。

## 公开字段核对

13 个案例中，**只有 3 个同时公开了 GPU 小时和卡数**：

| 案例 | GPU 小时 | 卡数 | 条件日历时间 | 判定 |
| --- | ---: | ---: | ---: | --- |
| Llama-1 65B | 1,022,362 | 2,048 | 20.8 天 | 恒定卡数条件下 |
| Llama-3.1 405B | 30,840,000 | 16,384 | 78.4 天 | 用报告最大值取下界 |
| DeepSeek-V3 预训练 | 2,664,000 | 2,048 | 54.2 天 | 恒定卡数条件下 |

另有 4 个只公开 GPU 小时（Llama-1 7B、Llama-2 7B/70B、Llama-3.1 8B/70B），6 个两项都未公开（Qwen 全系、V4 两款）。

## 卡数未知时的条件区间

| 案例 | 1,024 卡 | 2,048 卡 | 4,096 卡 | 8,192 卡 | 16,384 卡 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Llama-2 70B | 70.0 天 | 35.0 天 | 17.5 天 | 8.8 天 | 4.4 天 |
| Llama-3.1 8B | 59.4 天 | 29.7 天 | 14.9 天 | 7.4 天 | 3.7 天 |
| Llama-3.1 70B | 284.8 天 | 142.4 天 | 71.2 天 | 35.6 天 | 17.8 天 |

**区间跨度是 16 倍**。这就是本实验最重要的一条：只给 GPU 小时而不给卡数，日历时间无法确定。反过来，只关心总投入时 GPU 小时就够了——两个问题需要的字段不同。

值得注意的是 Llama-3.1 8B（1.46M GPU 小时）比 Llama-2 70B（1.72M）少不了多少，尽管参数量差 8.75 倍：小模型用远多的数据训练，总投入追平了上一代的大模型（对照实验 3-9 的 D/N 表）。

## 哪些缺失数据会改变选择

- **GPU 小时是否与卡数覆盖同一范围**：若含预热、失败重跑或评测，日历时间会被高估。
- **卡数是否全程恒定**：真实作业有扩缩容与故障替换，恒定假设只给条件值，因此表里写的是“条件日历时间”而不是“训练用了多久”。
- **MFU**：同样的 GPU 小时在不同 MFU 下对应完全不同的有效计算。
- **是否含数据准备、tokenize 与检查点写入**。
- **推理侧的调用量与生命周期**：训练一次的成本能被多少次调用摊薄，决定训练与服务哪一侧主导总预算。一个被调用一亿次的模型，训练成本在总预算里可以忽略；只服务内部少量请求的模型则相反。
- **设备单价、电力与折旧年限**：GPU 小时不是货币。本实验不做货币换算，因为需要的输入全部未公开。

完整数值见 [results/budget.md](results/budget.md)。

## 限制

- `lower_bound_using_reported_maximum`：Llama-3.1 405B 报告的是最大卡数，因此 78.4 天只是日历时间的**下界**，不是实际用时。
- 未公开的字段一律保持“未公开”，不用同代模型推断。
- 长期服务费用的完整比较需要请求分布与设备供给，见第 8、9、11 章。
