# 实验 3-1：Prefill 与 Decode 的资源变化

对应正文 3.1。用第 2 章已有的需求表口径，比较输入较多与生成较多的两个时段。**保持每请求总 token 数不变**，只改变阶段组成，看资源需求是否仍会改变。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py forward|generate，产物写入 results/
```

只需 Python 3.8+ 标准库。不重复第 2 章的逐层矩阵推导，也不把峰值下界当成真实服务时间。

## 设定

- 时段 A（输入较多）：每请求 prompt 4,096 ＋ 输出 128。
- 时段 B（生成较多）：每请求 prompt 512 ＋ 输出 3,712。
- 两者每请求总计都是 **4,224 token**；batch 各扫 1／8／32；模型 Qwen3-8B。

## 结果

| 时段 | batch | prefill TFLOPs | decode TFLOPs | 合计 TFLOPs | prefill 权重读取 | decode 权重读取 | decode 历史读取 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 8 | 494.8 | 18.0 | **512.8** | 14.35 GiB | **1,804 GiB** | 585 GiB |
| B | 8 | 57.5 | 491.0 | **548.5** | 14.13 GiB | **52,329 GiB** | 9,655 GiB |
| A | 32 | 1,979.2 | 72.0 | 2,051.2 | 15.10 GiB | 1,804 GiB | 2,340 GiB |
| B | 32 | 230.1 | 1,963.9 | 2,194.0 | 14.22 GiB | 52,330 GiB | 38,620 GiB |
| A 命中 3072 前缀 | 8 | 131.1 | 18.0 | 149.1 | 14.16 GiB | 1,804 GiB | 585 GiB |

**这是本实验的核心结果：总 token 数相同、矩阵工作相差只有 7%（512.8 对 548.5 TFLOPs），权重读取却相差 29 倍（1,804 对 52,329 GiB）。**

原因很直接：decode 每一步都要把整份权重再读一遍，读的次数等于输出 token 数。时段 B 生成 3,712 个 token，就读 3,712 遍；时段 A 只读 128 遍。prefill 无论处理多少 token，权重都只读一遍（14 GiB 左右，三档 batch 几乎不变）。

由此得到两条判断：

1. **按 token 总量做容量规划会严重失真**。同样是每天 N 个 token，输出占比高的负载对显存带宽的需求可以高一个数量级。第 8、9 章的分离部署正是从这里出发。
2. **加 batch 对两个时段的意义不同**。batch 从 8 到 32，时段 A 的 prefill 工作按 4 倍线性增长（494.8→1,979.2 TFLOPs），decode 权重读取则完全不变（1,804 GiB）——被 32 个请求分摊。生成占比越高，batch 的边际收益越大。
3. **前缀命中省的是 prefill，不是 decode**。时段 A 命中 3,072 前缀后 prefill 从 494.8 降到 131.1 TFLOPs（降 73%），decode 的三项一个字节都没变。

结束时 KV 只与 batch 有关（0.58／4.64／18.56 GiB），与阶段组成无关——因为两个时段的最终序列长度相同。

完整数值见 [results/stages.md](results/stages.md)。

## 限制

- 这是资源下界与逻辑载荷，不是服务时间。重叠、调度、连续批处理与抢占都不在内。
- `decode 权重读取`按“每步每算子读一次”计，不含缓存命中；实际引擎会有部分权重驻留在 L2。
- 请求到达分布、排队和 p95 不在本实验范围，见实验 3-2。
