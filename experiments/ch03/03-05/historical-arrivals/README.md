# 3-5：既有语音到达记录分析（部分证据）

从 RTX 主工作树 `/home/ubuntu/OpenRealtime/.runtime/diagnostics/` 只读取得两份历史 transcript，共 163 个 `agent_audio` 块。与此前只检查的 `OpenRealtime-sidecar-voice-deadline` 工作树不同，这里确实保存了逐块到达记录。没有重跑模型、调用 API、改变服务或制造时间线。

这两份文件没有足够的运行身份、音频哈希和设备观测，不能算完成固定输入下改变模型、网络、缓冲的实验。文件名只用作标识，不据此认定用户意图、取消成功或模型配置。原件均保留 `trace endpoint returned 503 Service Unavailable`，不能把缺失执行证据抹去后当成完整复现。

## 可复算结果

首块延迟取记录中第一次 `user_speech_stopped` 到随后第一个 `agent_audio` 的到达差。间隔只取首次用户说话结束至第二次开始的半开窗口，避免把两次用户输入间的静默间隔混入；该窗口可能包含多个响应片段，不宣称单一 response 流的网络抖动。

第二次用户说话的记录窗口内，两份文件各还有 9 个音频块到达。没有 response ID、取消发出/确认、设备 flush/静音或计算退出事件，不能归因成取消延迟，也不能证明这些块属于应取消的响应。`response_done` 不能代替设备静音。

相邻到达间隔减前块时长是接收端时序差。它受到发送节奏、模型输出和传输等因素共同影响，既不是单独网络延迟，也不是设备 underrun。实际首次播放、取消确认、物理静音、计算退出均在结果中保持 `null`。`playback_ms` 不用于首播计算。

## 复算和证据

在本目录执行 `python3 analyze.py`，仅使用 Python 标准库。脚本先校验原件大小与 SHA-256、时间单调性、正音频时长以及两段用户语音顺序，再生成 `summary.json`。所有统计从原始事件得出，不执行教学时序计算。两份小表足以表达现有证据，未绘制容易被误解为实际播放的波形图。

- `sources/`：两份逐字节原始 JSON。
- `source-metadata.json`：读取时间、远端路径、大小、哈希和文件修改时间。当前仓库 HEAD 明确标为读取时 HEAD，**不是历史运行 revision**；文件修改时间也不是运行时间。
- `analyze.py` / `summary.json`：独立复算实现与完整未舍入结果。
- `manifest.json`：本目录封存文件哈希。

既有记录缺少原始输入音频关联、完整服务/模型身份、设备输出时钟和取消链。下一次实际语音运行需先补齐这些观测，再控制模型、网络、缓冲逐项比较。当前结果只能支持“记录中的首块接收时间与块到达节奏”，不能外推真实对话体验、比较两种模型或将第 3-5 项标记完成。
