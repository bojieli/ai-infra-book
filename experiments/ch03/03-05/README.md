# 实验 3-5：实时语音的响应预算

对应正文 3.2。对固定语音记录计算首次播放、块间抖动和打断响应；分别改变模型、网络与缓冲，判断哪一项能改善对话。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py audio-timing，产物写入 results/
```

只需 Python 3.8+ 标准库。固定记录为 8 个 20 ms 块、24 kHz 单声道 16 bit；模型、网络、发送、抖动缓冲、控制通路与设备量子的时间都是**明确标注的教学输入**，不是某个系统的实测值。本目录另有两个已交付的资料子目录：[historical-arrivals/](historical-arrivals/README.md)（历史到达记录）与 [source-contract/](source-contract/README.md)（来源核对）。

## 首次播放与块间抖动

| 场景 | 首次播放 | 采集到播放 | 欠载 | 累计停顿 | 播放结束 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线（模型 12 ms、网络 5 ms、缓冲 40 ms） | 78.0 ms | 58.0 ms | 0 | 0 | 238.0 ms |
| 网络第 3 块抖动到 50 ms | 78.0 ms | 58.0 ms | **1** | **5.0 ms** | 243.0 ms |
| 模型变慢到 25 ms/块 | 91.0 ms | 71.0 ms | 0 | 0 | 251.0 ms |
| 模型加速到 6 ms/块 | 72.0 ms | 52.0 ms | 0 | 0 | 232.0 ms |
| 缓冲取消（0 ms） | **38.0 ms** | 18.0 ms | 0 | 0 | 198.0 ms |
| 缓冲加大到 100 ms | **138.0 ms** | 118.0 ms | 0 | 0 | 298.0 ms |
| 网络整体降到 2 ms | 75.0 ms | 55.0 ms | 0 | 0 | 235.0 ms |
| 抖动 ＋ 缓冲 100 ms | 138.0 ms | 118.0 ms | **0** | **0** | 298.0 ms |

三项改动各改善不同的东西：

- **缓冲是唯一直接对抗抖动的手段**，但代价一比一记在首次播放上。缓冲 0→40→100 ms，首次播放 38→78→138 ms。抖动场景加大缓冲把欠载从 1 次降到 0 次，代价是首次播放多等 60 ms。
- **加速模型对首次播放的收益很小**。模型 12→6 ms 只把首次播放从 78 降到 72 ms（6 ms），因为首次播放主要由缓冲和一帧的采集时间决定，不是由模型决定。反过来模型变慢到 25 ms 会把首次播放推到 91 ms——**慢会伤，快不怎么帮**。
- **降低网络延迟同样只买回它自己那一份**（5→2 ms 时首次播放 78→75 ms），但它减少的是抖动的**幅度**，所以在抖动场景里比同等的模型加速更有价值。

## 打断响应

| 场景 | 静音生效 | 打断到静音 | 打断后仍可听见 |
| --- | ---: | ---: | ---: |
| 第 60 ms 打断（缓冲 40 ms） | 70.0 ms | 10.0 ms | 0 ms |
| 第 150 ms 打断（缓冲 40 ms） | 160.0 ms | 10.0 ms | 10.0 ms |
| 第 150 ms 打断（缓冲 0／100 ms） | 160.0 ms | 10.0 ms | 10.0 ms |

打断到静音固定为 10 ms，由控制通路延迟（5 ms）与设备量子（10 ms）共同决定，**与抖动缓冲无关**——因为静音作用在设备侧，不需要清空缓冲。这解释了为什么加大缓冲改善抗抖动而不损害打断体验：两者走的是不同路径。播放中打断时有 10 ms 已经进入设备的音频仍会被听见，这是设备量子的下界。

## 判断

对话质量由**三个不同的量**决定，各自的改善手段不同：首次播放看缓冲，抖动看网络与缓冲，打断看控制通路与设备量子。加速模型对三者都有帮助但都不是主导项。**在本组条件下，最有效的单项改动是把缓冲按实际抖动分布调到刚好够用**——多一分就一比一地加在首次播放上。

完整数值见 [results/voice.md](results/voice.md)。

## 限制

- 全部时序是声明的教学输入，不是端到端实测。真实的语音路径实测见第 12 章的 Queqiao 实验（12-07）。
- 本模型不含 VAD、端点检测、ASR 与 TTS 的分阶段延迟，也不含丢包重传。
- 欠载判定按“播放时刻是否有可用数据”，不含音频设备自身的重采样与混音开销。
