# 实验 9-4：PD 与 AF 的交接频次

对应正文 9.2 的核心练习。为什么同样带宽下 PD 和 AF 表现不同？固定同一教学 GQA 模型，先用相同总字节的控制比较隔离启动成本，再沿同一请求累计全部 decode 调用与 prefill 交接。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py pd-af-handoff
```

只需 Python 3.8+ 标准库。链路 25 GB/s、启动 5 μs 为声明输入。

## 结果

| 情形 | PD 快照 | AF 总字节 | AF 消息数 | PD 串行 | AF 串行 | 等时启动阈值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 基线：单步 decode | 1.000 GiB | 512 KiB | 64 | **42.955 ms** | **0.341 ms** | 681.4 μs |
| 累计 128 步 decode | 1.000 GiB | 65,536 KiB | 8,192 | 42.955 ms | **43.644 ms** | **4.9 μs** |
| 累计 1024 步（长输出） | 1.000 GiB | 524,288 KiB | 65,536 | 42.955 ms | **349.155 ms** | **0.3 μs** |
| α=1 μs | 1.000 GiB | 512 KiB | 64 | 42.951 ms | 0.085 ms | 681.4 μs |
| α=20 μs（跨机以太网） | 1.000 GiB | 512 KiB | 64 | 42.970 ms | 1.301 ms | 681.4 μs |
| 带宽减半 | 1.000 GiB | 512 KiB | 64 | **85.904 ms** | 0.362 ms | 1,362.8 μs |
| batch=64 一步 | 64.000 GiB | 32,768 KiB | 64 | 2,748.784 ms | 1.662 ms | 43,610.1 μs |

**为什么同样带宽下两者不同：它们花在两个不同的量上。**

- **PD 是一次大传输**：1 GiB 快照，时间几乎全是 `字节/带宽`。带宽减半，它就翻倍（42.955→85.904 ms）；启动时间从 1 μs 变到 20 μs，它只从 42.951 动到 42.970 ms（0.04%）——**PD 对启动完全不敏感**。
- **AF 是很多次小传输**：单步 64 条方向消息、每条 8 KiB，时间几乎全是 `消息数×α`。带宽减半只让它从 0.341 涨到 0.362 ms（6%），启动从 1 到 20 μs 却让它从 0.085 涨到 1.301 ms（**15 倍**）——**AF 对启动极度敏感**。

## 交接频次才是分界线

单步比较毫无意义（0.341 vs 42.955 ms，AF 快 126 倍），因为 PD 每请求只交接一次，AF 每步都交接。**沿同一请求累计**才是正确的口径：

- 128 步输出：AF 累计 43.644 ms，与 PD 的 42.955 ms **基本持平**；
- 1,024 步输出：AF 累计 349.155 ms，**是 PD 的 8.1 倍**。

"等时启动阈值"一列给出同一结论的另一种读法：单步时 α 要涨到 681 μs 两者才打平；累计 128 步时阈值降到 4.9 μs（已接近真实跨机 α）；1,024 步时降到 0.3 μs——**任何真实链路都达不到**。

**输出越长，PD 越有利；输出越短、KV 越大，AF 越有利。** batch=64 一行给出另一端：PD 快照涨到 64 GiB、2.75 秒，AF 只有 1.66 ms，等时阈值 43.6 ms——大 batch 下 PD 的一次性交接变得不可接受。

完整数值见 [results/handoff.md](results/handoff.md)。

## 限制

- 只算交接的字节与消息数，**两侧的计算与依赖等待未计入**；因此不能据此排名 PD 与 AF 的端到端性能。
- AF 的每层交接是教学模型（36 层间共 576 KiB、72 次方向消息的口径见正文），不是某个实现的实测。
- 链路按无拥塞、无竞争计；实测的远程调用分解见实验 7-4，真实 KTransformers 记录见实验 9-3。
