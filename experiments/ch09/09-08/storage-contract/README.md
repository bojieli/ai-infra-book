# 9-8 补测：损坏文件与缓存身份的后端行为

在RTX机器的实验专用SGLang 0.5.13.post1环境中，使用一页实际模型KV文件，对原生HiCacheFile执行七种独立调用。全部使用CPU张量，未启动模型，未修改原缓存或共享服务。

| 条件 | 原生调用的实际结果 |
|---|---|
| 完整文件 | 返回张量，内容与参考页逐位一致 |
| 文件缺失 | 返回None，目标保持全零 |
| 文件截短2字节 | 抛出OSError；此前字节已写入目标，末2字节保持零 |
| 同长度翻转1位 | 返回张量，损坏位被读入，没有内容校验异常 |
| 末尾追加5字节 | 返回张量，只读取目标长度；多余字节未触发异常 |
| 更换model_name | 原文件仍存在，但新命名空间exists为false、get返回None |
| 对已存在损坏文件再次set | 返回True，原损坏文件未改；随后get仍得到损坏内容 |

这是**后端原语的边界**：文件存在、get返回张量或set返回True，都不足以单独证明内容有效。截断异常也不保证目标张量未发生部分写入。这里只更换model_name，不测试真实权重更换、adapter、位置、dtype、布局及压缩版本等完整身份组合。

没有将损坏KV接入模型请求，也没有验证scheduler如何处理异常、是否重试或回退；不能从本表直接推断端到端可用性或质量。上一轮缺页回退已经单独实测，而内容损坏、写入中崩溃与格式不兼容的端到端路径仍待。原语数据不能替代容量、保存策略、V4压缩状态与远端比较，9-8保持partial。

输入page.bin为封存正常模型运行的一页2,359,296字节BF16 KV。results/保留全部实际文件、安装源码快照及原始记录；run.log保留日志。verify.py从原输入重建每种预期目标字节，检查原始记录中的目标哈希、实际磁盘文件和执行源码，不依赖状态标签判断通过。

离线验证（仓库根目录）：

```sh
python3 experiments/ch09/09-08/storage-contract/verify.py
python3 experiments/ch09/09-08/storage-contract/verify_manifest.py
```

独立重跑：复制本目录脚本和page.bin到一个没有results/的新目录，使用父实验ENVIRONMENT.md的专用SGLang环境执行run.py。输出目录存在即拒绝覆盖。此实验只需原生CPU张量操作，不占用GPU推理显存。结果仅对应记录中的固定包版本与源码哈希。
