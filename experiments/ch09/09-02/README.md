# 实验 9-2：A100＋H20 的 PD 分离

对应正文 9.1。分开 prefill 和 decode 的收益何时被抵消？以 A100 80GB SXM 做 prefill、H20 SXM5 96GB 做 decode，比较共置、同构 PD、异构 PD 与角色对换；沿同一 Qwen3-8B 扫描输入长度、输出长度、缓存命中、到达率与池规模。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py pd-pool
```

只需 Python 3.8+ 标准库。**每 worker 的服务速率是标明的假设**（A100 prefill 16,384 tok/s／decode 64 tok/s；H20 prefill 4,096／decode 256），不是实测记录；链路 25 GB/s。工具会在给定 worker 集合里自动选最优分工，因此“角色对换”与异构 PD 属同一次求解（最优分工一列给出它实际选了哪一侧），本实验把第四个布局换成“全 H20”作为另一端对照。

## 结果（节选）

| 布局 | 场景 | 每请求交接 | PD 上界 | 共置上界 | PD/共置 | 瓶颈 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 同构 A100 8 张 | 8K／128 | 1.125 GiB | 3.000 | 3.200 | **0.94×** | decode |
| 同构 A100 8 张 | 8K／1024 | 1.125 GiB | 0.438 | 0.485 | **0.90×** | decode |
| **异构 A100+H20** | 8K／128 | 1.125 GiB | **8.000** | 3.200 | **2.50×** | prefill、decode |
| 异构 A100+H20 | 8K／1024 | 1.125 GiB | 1.188 | 0.909 | **1.31×** | decode |
| 异构 A100+H20 | 2K／128 | 0.281 GiB | 9.000 | 5.882 | 1.53× | decode |
| 异构 A100+H20 | 32K／128 | 4.500 GiB | 2.250 | 1.471 | 1.53× | prefill |
| 全 H20 8 张 | 8K／128 | 1.125 GiB | 3.000 | 3.200 | 0.94× | prefill |

三条判断：

1. **同构 PD 反而更差（0.90–0.94×）**。把 8 张相同的卡分成 4＋4，两个池各自可能空闲，而共置时任何一张卡都能接任何工作。**分离本身不产生收益，收益来自异构**——只有当两类工作对资源的要求不同、且有两种不同的设备时，专用化才划算。这条与第 1 章 TPU 案例（专用化的门槛）是同一个道理。
2. **异构 PD 的收益随输出长度衰减**。8K／128 输出时 2.50×，8K／1,024 输出时只剩 1.31×。输出越长，decode 占比越高，整个系统重新被 decode 池限制，prefill 侧的富余帮不上忙。**"PD 分离能提速 2.5 倍"只在短输出场景成立。**
3. **收益被抵消的第一个条件是链路**。32K 输入时每请求要搬 4.5 GiB，25 GB/s 链路的容量只有 5.174 req/s，而 PD 上界是 2.250 req/s——尚未触顶但余量只有 2.3 倍。若输入再长或链路再慢，交接就会成为新瓶颈。8K 时链路容量 20.696 req/s 相对 8.000 的上界有 2.6 倍余量。
4. **前缀命中把 prefill 侧的压力移走**：8K 输入命中 6K 前缀后，异构 PD 从 8.000 升到 9.000 req/s，瓶颈从"prefill、decode"变成纯 decode。缓存越有效，PD 分离的收益越小——因为 prefill 本来就不忙了。

完整 24 组数值见 [results/pd.md](results/pd.md)。

## 限制

- 服务速率是声明假设，**不是 A100／H20 的实测**；结论的方向可靠，倍数需要实测校正。
- 只算稳态上界（吞吐），不含排队分布、首 token 与逐 token 延迟的尾部；SLO 判定见实验 8-9。
- 费用未计入：两种设备的单价与功耗需要另一组输入。
- 未含受支持 PD connector 的真实系统 trace 与时段尾延迟，这两项仍待。
