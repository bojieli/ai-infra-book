# 9-9 原生缓存亲和路由与显式清缓存

本项三轮因果序列完成，9-9整体仍为partial。原生SGLang Router0.3.2 cache_aware策略，两SGLang0.5.13.post1 Qwen3-8B BF16实例共享RTX PRO 6000。

## 方法

每轮重新启动路由器、清空两实例缓存，等待两个实例均健康注册。对实际Agent末轮3136-token输入先冷调用、再热调用；保持路由器运行，向两个实例实际POST /flush_cache后，再调用相同输入两次。每次强制1输出token，串行、没有在途请求。三轮共12次正式请求。使用相同文本逐token往返核验，原生worker请求日志按rid确认接收和完成，API响应记录实际缓存数。

三轮都保持同一实例归属，缓存数依次0→3135→0→3135；热请求、清除后和再次热请求中位分别31.281、163.616、30.809ms。两个后端各六条成功清除日志确认轮前及轮中操作。12个目标输出一致。这仅验证固定输入的一个输出token，不等于完整任务质量。清缓存API原始返回值、前后单调时钟及请求响应均保留；调用顺序由analyze.py校验。

这不是容量压力下的自然淘汰，也没有注入缓存事件丢失；相同路由归属不直接证明内部索引未更新。缓存亲和位置与物理KV命中必须分别核对。冷调用可能包含首次编译/预热，因果顺序固定且每阶段只有三次，延迟为本次观察，不报告稳定p95或纯重计算代价。未配置远端存储，不能给远端取回时间。

## 重现与证据

run.py包含固定本地权重、专用环境、完整worker和原生Router命令。专用环境安装与CUDA工具链参考上级README及9-8环境记录；参数disable-cuda-graph不关闭全部piecewise prefill图。确认31090/31091/31092/31099空闲，在独立副本且不存在results时，用专用SGLang环境Python执行run.py。脚本拒绝覆盖已有results，只清理自行新建进程组。清理退出码见execution.json，不把worker强制清理称正常服务退出。

离线 `python3 analyze.py` 核验源码哈希、注册健康、12次请求、原生日志归属及完成、清除时间顺序和输出，生成summary.json；`python3 write_report.py`重建本报告。results保存原始注册、请求、清缓存返回、原生日志及metrics；run.log保存执行状态。cleanup-check.json与gpu-after.txt用于核对退出及原服务，manifest.json保存SHA。
