# 4-6 昇腾公开算子记录

采用本书指定的 [CloudMatrix384 v2](https://arxiv.org/abs/2506.12708v2)，2025-06-18版本；原件为[归档PDF](../../../../references/files/papers/cloudmatrix384-v2.pdf)。第48–49页已渲染并逐表目视核对，`extract.py` 从同一PDF直接提取表8–10，`records.json` 保存来源哈希、页码、精度、硬件粒度与缺失字段。属于**作者公开测量记录分析**，没有在本地运行昇腾硬件。

| 作者记录 | H800 FlashMLA | 单个910C die的CANN MLA |
|---|---:|---:|
| 计算密集场景，BF16/FP16，算力利用率 | 66.7% | 65.4% |
| 访存密集场景，报告带宽 | 3000 GB/s | 1346 GB/s |
| 作者采用的带宽峰值 | 3350 GB/s | 1600 GB/s |
| 报告带宽利用率 | 89.6% | 84.1% |

表8与表9是不同瓶颈场景，不能把两行利用率视为一次调用同时达到的结果；百分比接近也不代表绝对速度接近。§5.5.2及这两张表没有完整的batch、头数、上下文形状、计数器字节定义或重复样本，相关字段保留未知。这里的1346 GB/s不可与本地预热复制“载荷/时间”作带宽排名，也不能用MLA替代普通attention的相同输入对照。

表10在**单个910C die**上使用INT8输入、BF16输出，tile为128×152，6组grouped GEMM覆盖M=2048/7168、N=4096/7168、K=4096/8192、groups=4/8（确切组合见records.json）。作者报告算力利用率77.4%–82.7%，带宽195–327 GB/s。较高算力利用率与较低外部带宽需求支持论文对这些大矩阵偏计算受限的解释；不能据此推断小batch decode或本地FP32矩阵也具有同一瓶颈。没有足够的测量协议来把这些百分比重建成独立验证过的延迟。

本记录支持第4章的限定结论：**同一硬件的带宽和算力利用率随算子与形状改变，必须核对精度、实现和分母。** 它不构成三家硬件的同条件排名，也不证明论文系统级吞吐收益仅来自单芯片架构。

在此目录运行：

```sh
python3 extract.py
python3 extract.py --verify
# 独立使用时，可传入同一版本的原件
python3 extract.py --pdf /path/to/cloudmatrix384-v2.pdf --verify
```

依赖标准Python和Poppler的pdftotext。源码锁定原件SHA256；验证重新提取8条算子记录，并检查表9百分比的舍入一致性。它能发现文件或提取结果变化，不能替代作者原始数据或硬件复现。`qa/` 为阅读时保存的原页渲染，不是新实验数据。原矩阵、复制、注意力测量均在上一级目录，互不覆盖。
