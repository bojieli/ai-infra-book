# 实验 5-7：形状特化的复用阈值

对应正文 5.3。为每种长度编译一份程序值不值？给定形状分布，比较通用、分桶与逐形状特化三种策略的“准备成本 ＋ 重复次数 × 每次执行成本”，再扫描复用阈值。

## 独立运行

```bash
python3 run.py    # 现场调用 calculations/calc.py shape-specialization，产物写入 results/
```

只需 Python 3.8+ 标准库。服务率与准备时间均为**教学输入**：形状分布 256×8、1536×1、2048×1；分桶 512／2048；编译成本 100／200／300 ms；执行速率 100／200／250 TFLOPs/s。

## 复用次数扫描（生命周期总时间，秒）

| 重复次数 | 通用 | 分桶 | 特化 | 最优 |
| ---: | ---: | ---: | ---: | --- |
| 1 | **0.117** | 0.412 | 0.907 | 通用 |
| 10 | **0.270** | 0.524 | 0.968 | 通用 |
| 40 | **0.780** | 0.895 | 1.172 | 通用 |
| **70** | 1.291 | **1.266** | 1.376 | **分桶** |
| **140** | 2.481 | 2.132 | **1.853** | **特化** |
| 400 | 6.903 | 5.348 | **3.621** | 特化 |
| 1000 | 17.108 | 12.770 | **7.703** | 特化 |

两个交点：**约 60 次复用时通用输给分桶，约 100 次时分桶输给特化**。在这条分布上，短寿命调用（几十次以内）根本来不及收回编译成本，通用程序反而最好；只有频繁复用才值得更深特化。

注意分桶在中间区间胜出的原因不是执行最快，而是**准备成本与执行成本都居中**：它编 2 份而不是 3 份，同时把 256 的调用 pad 到 512 执行。padding 是分桶的隐性代价（表中 256×8 的调用按 512 token 计算），复用次数足够多时这笔代价就压过了少编一份的收益。

## 变体：什么会移动阈值

| 情形 | 最优策略 |
| --- | --- |
| 基线（重复 70 次） | 分桶 |
| **编译成本翻倍** | **通用** |
| **特化产物已缓存** | **特化** |
| 长尾形状更分散 | 分桶 |

- **编译成本翻倍**把阈值整体右移，70 次时退回通用。这解释了为什么编译时间长的后端更倾向通用内核。
- **特化产物已缓存**（准备成本归零）让特化在同样 70 次时立刻胜出——**缓存把“为每种长度编译一份”从投资问题变成查表问题**，这是实际服务系统里最重要的一条杠杆。
- **形状更分散**（8 种长度各 1 次）时分桶仍最优：特化要编 8 份，每份只用 1 次，永远收不回来。

完整数值见 [results/specialization.md](results/specialization.md)。

## 限制

- 编译时间、执行速率与形状分布都是声明的教学输入，不是任何编译器或设备的实测。真实编译时间与形状分布见实验 5-5（编译代码与输入布局）和 5-8（图重放）。
- 只算准备与执行两项。产物占用的内存、缓存淘汰、首个请求的冷启动延迟和多版本管理成本都不在内。
- 分桶的 padding 按“执行到桶上界”计，没有考虑内核对尾块的特殊处理。
