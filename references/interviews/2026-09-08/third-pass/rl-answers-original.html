Vivek on X: "went through most of these. dumping my answers in case anyone studying rl finds it useful. Algo 1. pure value-based methods can't handle large or continuous action spaces well and only give you a greedy policy. pure policy gradient handles them but has high variance updates. actor critic keeps a direct policy and uses the critic to cut that variance. best of both. 2. ce(p,q) = kl(p,q) + entropy(p). minimizing any of them lands you in the same place. mle is just kl between data dist and model dist. 3. mostly depends on the env you're building. verifiable stuff (math, code) is much easier to reward than non-verifiable (writing) for obvious reasons. main thing is the env shouldn't be prone to reward hacking, there shouldn't be an easy path to optimizing the wrong solution. data and rewards have to be written carefully. 4. importance sampling is used in async rl to reuse off policy samples generated for an earlier policy of the trainer. rejection sampling is for data filtering, you can filter sft data or drop the too-easy/too-hard ones. broadly it's all monte carlo, estimating expectations from samples instead of computing them exactly. 5. ppo has a critic and a reward model. grpo drops both. its "critic" comes from doing multiple rollouts and taking the mean as baseline. the baseline reduces variance so not every rollout gets a positive push. kind of a zero sum thing within the group. std normalization isn't necessary, see dr.grpo. 6. rl is about embedding domain intelligence into the weights. test-time scaling is, given that intelligence, finding the best path to a solution and exploring different ones with more thinking tokens. one shapes the model weights while the other spends more on inference budget. 7. clipping is there because you don't want abrupt policy turns, the ratio variance across examples gets high. the min comes from trpo's trust-region idea, it keeps updates pessimistic so you only move when it's favourable. cispo is different, it clips the importance weight instead of the whole objective, so gradients still flow through all tokens and you keep more signal. 8. kl is there because you already have a good base model with intelligence you don't want to move too far from. but you also want to learn new domains via rl. it gets dropped because that same constraint stops you from moving far enough to actually learn, which you don't want. so removing kl helps stability and training in rlvr. 9. not sure i understand this question. 10. dpo has an implicit reward baked into the dataset, examples marked good vs bad, so no separate reward model needed like ppo. reward hacking still happens (as @willcb points out) because there's a backdoor to the solution you're chasing. it's an active problem with no single fix, env has to be stress-tested hard. you can catch it via signals like sudden reward jumps or rollout length blowups. 11. trainer-inference mismatch comes from a few things: different engine, different expert selection, different kernels, quantization, rounding. (see the thinking machines blog.) one fix is replaying expert selection so inference and trainer pick the same experts. broadly you're trying to make the rollout policy and the trained policy numerically identical, otherwise your importance weights are wrong. 12. group size is just more rollouts, more paths to learn from, 8/16 usually. lr is manageable, 1e-6 range. ppo epochs is usually 1, more epochs make the data more off-policy and destabilize things. generation length is purely task-dependent, hard to quantify without knowing the task. 13. all the algo are variants on grpo, mostly for better stability. at lab scale the choice barely matters but there are differences. dr.grpo: remove std. dapo: clip-higher, dynamic sampling, token-level loss, overlong filtering. gspo: sequence-level importance sampling instead of token-level, much better for moe. cispo: clip the weight not the objective. maxrl: solves diversity collapse. not sure about sapo/dppo (haven't read the paper). 14. trpo is constrained optimization, staying within a kl boundary. ppo does the same thing approximately with the clip. AReaL enforces it in the async setting by bounding staleness/off-policyness instead of a hard kl. 15. yeah, the papers suggest rl mostly sharpens abilities already in the base model rather than forming new ones. cool direction to push on though, with enough exploration and diversity i'm not fully sure it can't. 16. i haven't read the paper. 17. opd combines rl's on-policy exploration with sft's dense signal. rl's main weakness is sparse reward, opd fixes that by having a teacher score the student's own (on-policy) rollouts(important part). used for cheaply transferring capabilities, been on the trend lately. 18. not fully sure where reasoning emerges, but cot plays a big part. also pre-training for baseline intelligence and post-training for amplifying the intelligence using reasoning and test-time compute. 19. sorry, i don't remember the v4 stuff. Infra 1. it depends mostly on the algo and kl. for grpo with kl you need the training policy, reference policy for kl and the inference model. for memory optimization you can start by dropping kl, which removes the extra ref model. there are a couple of optimizations like nvfp4 quantization that save memory and properly distributed training helps a lot where fsdp, ep, tp split the model and optimizer states across gpus. you can also quantize the inference copy and shard optimizer states so each rank holds only a slice. 2. kv cache transfer matters for disaggregated prefill or decode. optimized via nvlink or layer-wise overlapped transfer of the kv/weights. multi-gpu depends on whether it's the same node or different node. generally tp helps a lot and you want to keep heavy kv movement within a node. 3. fp8 has more exponent bits which is better for training. int8 has more precision in a fixed range, better for inference weights. so fp8 for training, int8 for inference serving. 4. long-tail rollouts within a batch can be addressed with methods like pipelinerl or continuous batching or early truncation. mostly seen in async setups. 5. continuous batching mixes decoding for rollouts at different stages of next-token prediction. vllm uses paged-attention, sglang uses radixattention (prefix sharing). read the papers for more. the rl things here is aligning complete trajectories and logprobs when sequences finish at different times. 6. measured via throughput (tok/s), kv cache util and gpu util. for kv cache you watch occupancy. also watch for memory bound. also rollouts are getting kicked out. low gpu util usually means you're waiting on something (rollout sync or cpu) rather than compute-bound. both engines expose these scheduler/cache metrics. 7. same as normal backprop with a few tweaks, basically fsdp, ep and tp. for long context it's cp (context parallel). ideally no one uses pp, it's complex and not really necessary at most scales. 8. async rl frameworks like prime-rl, verl and trl. the bottleneck comes down to three things: staleness of the rollouts and how you manage it (importance sampling + staleness bounds), trainer-inference mismatch and token-in token-out. for the mismatch you fix it by making the rollout engine and trainer numerically consistent, replaying expert/router decisions and computing logprobs on the trainer side rather than trusting the inference engine. 9. not sure about AReaL but some methods preserve the old kv cache and some don't. i think there's no real perf difference between the two as such. 10. ep plays a big role for moe models, where a bunch of experts are placed on a node or set of gpus so each holds a subset. it raises throughput by parallelizing the expert ffns, but adds all-to-all communication to route tokens to the right expert. the actual gain is that all-to-all overlaps with compute and how balanced the expert load is. 11. parallelizing communication along with computation is the key. fsdp shards grads/params/optim, gathers them on demand, much simpler. megatron uses dp, pp and tp (3d parallelism) with more explicit comms. not too sure about megatron though, haven't used it much. 12. it needs reduction order, same kernels and batch invariant ops. refer the thinky blog for more. 13. i can talk about AReaL, it goes fully async with staleness control, decoupling rollout generation from training so the trainer never is waiting on the slowest rollout, then has ways of controlling the staleness using max off policy steps or like important sampling or removing samples like after threshold policies. not sure about Slime, need to read more on that. 14. staleness is the gap between the policy that generated the rollouts vs the policy you're training. the experiments i run are usually 1-4 steps behind. more staleness leads to instability in importance sampling since the ratios blow up. 15. again not sure about Slime. 16. none of them, use @PrimeIntellect. correct me if anything's off, happy to hear feedback"
