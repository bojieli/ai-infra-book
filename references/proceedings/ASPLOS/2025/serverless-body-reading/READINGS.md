# Dilu 与 Medusa：实例何时增加，增加以后还要等什么

这两篇论文适合放在第 11 章同一个资源调度问题中比较：请求突然增加时，先判断已有实例还有没有可用的执行余量；确实需要增加实例时，再拆开新实例达到可服务状态的等待时间。Dilu 主要改变前一个决策，Medusa 主要缩短后一个过程。论文没有给出两套实现共同运行的结果。

本次沿用已归档版本，新增摘要和 PDF 均为 0。Dilu 阅读 PDF 物理页 4、6–9、11–13；Medusa 阅读物理页 5–13，其中第 13 页主要是 artifact appendix。共读 17 个指定原文页，未通读两篇论文。实际查看了 Dilu 第 7、11、12、13 页以及 Medusa 第 6、7、10、11、12 页的图像。逐页内容与证据见 `reading-records.json`。

## Dilu：先使用已有实例的余量

[Dilu 论文](https://arxiv.org/pdf/2503.05130v1) 为 2025-03-07 的 arXiv v1，正式 DOI 为 `10.1145/3669940.3707251`。第 3.3、3.4 节把两个资源约束放在一起：共置实例的显存必须装得下，执行份额也必须足以满足各自的 QoS。这里的“资源份额”不能直接解释成给进程划出固定数量的物理 SM。

第 7–9 页说明了实际控制路径：容器中的拦截库截获 CUDA kernel launch，向 RCKM 请求令牌；控制器根据 request/limit、任务优先级和 kernel launching cycle 的变化，决定放行多少 kernel blocks。论文第 9 页明确指出，令牌和 kernel 的计量单位是 **CUDA kernel blocks**。第 7 页的“GPU time”是份额的解释，不能据此把每个令牌当成相同长度的微秒时间片，更不能误认成模型输出 token。5 ms 是示例控制周期，涉及的也不是容器启动或模型加载。

纵向调整让已有实例在突发到来时先获得更多执行机会，同时压低共置任务的机会；横向调整仍负责增加或减少实例。第 8 页的实现使用 40 s 滑动窗口，并按超过既有吞吐的观测数量决定是否扩实例。超过 20 个观测、以及缩实例时超过 30 个观测，是论文的具体设置，不能替代新业务的实测决策。实例仍驻留时，权重和其它显存状态仍占容量；空闲 SM 可重新分配不等于显存也同时归还。

第 11 页表 3 的突发负载中，Dilu 的冷启动次数为 7，FaST-GS+ 为 40，INFless+ 为 27；SLO 违约率分别为 1.79%、10.79%、6.28%。这支持的是“少触发冷启动并改善该 trace 的服务指标”，没有测出每次冷启动从若干秒变成若干毫秒。第 11–12 页的 3,200 个调度决策用时 1.12 s、实例 scaling overhead 小于 1 ms，必须与模型启动时长分开。不要拿不同 trace 的违约率直接相加，也不要把表 3 的计数降幅和摘要中其它实验的吞吐增益合成一个总加速比。

实测环境是 5 个 worker、每个 4 张 A100-40GB PCIe；模型包括 ResNet、BERT、GPT-2、Llama2-7B 和 ChatGLM3-6B。第 12–13 页的大规模结果另来自 1,000 节点、3,200 实例的模拟。第 9 页还将 LLM 的平均 time-per-output-token 作为延迟指标，因此这些结果不能自动证明现今大 MoE 服务的 TTFT/p99、长上下文或多租户隔离效果。第 13 页把更完整的弹性 LLM serving 和底层 sharing protection 留作后续工作。

## Medusa：缩短初始化，保留图重放

[Medusa 作者版 PDF](https://minhui-xie.github.io/papers/asplos25-medusa.pdf) 有 16 页，正式 DOI 为 `10.1145/3669940.3707285`。这里讨论的是 serverless 冷启动物化系统，与同名推测解码工作无关。

第 5–9 页将 loading phase 中的两项重复工作挪到离线阶段：一次 profiling forward 用来确定 KV 缓冲区可用的空闲显存量；不同 batch size 的 forward 用来构造 CUDA Graph。在线阶段复用前者的容量信息并恢复后者。它保存的不是用户 prompt 或历史对话的 KV 内容。第 8 页还解释，模型权重此前已经正常加载，不必在图恢复时再复制一份；临时 buffer 的内容也不需要全量持久化。

“保存图”不能写成原地址空间直接落盘再读回。图里的参数地址和 kernel 地址可能随进程变化。第 6–8 页将 buffer 指针转成分配序列的索引，在线重放分配/释放，再填入本次地址；匹配时还要考虑地址被释放后重新使用。cuBLAS 的部分 kernel 不能从常规符号表直接找到，因此要触发模块加载，再按 kernel 名称定位。第 8–9 页使用结构重复的第一层来触发相关 kernel，不是把整个模型的在线执行都消除。

第 10 页图 8 的 Qwen1.5-4B 例子很适合作为书中的小预算：权重体积 7.4 GB，普通 vLLM loading 为 2.85 s，单纯异步加载为 2.48 s，Medusa 为 1.67 s。KV 初始化从 0.50 s 降到 0.02 s；原 0.90 s 的 capture 工作被 0.31 s warm-up 与 0.26 s graph restoration 取代。最关键的变化还包括依赖顺序和重叠关系，不能只把两个缩短的阶段做减法。

第 9–12 页的边界同样要保留：基本实验在单张 A100-40GB SXM4 上进行，应用 trace 才使用 4 张 GPU；这不等于一个模型已支持跨 GPU graph restoration。第 12 页明确将多 GPU 图恢复留作 future work。当前实现只处理 host-side allocation 与 direct pointer；10 个模型、139,364 个图节点中未碰到 device-side allocation 或 indirect pointer，不构成对所有新 kernel 的支持保证。

第 10 页报告的是跨 10 个模型平均 loading latency 降低 42.5%，整体 cold-start latency 平均降低 34.9%。第 11–12 页的 53.0% 是 Qwen1.5-4B、RPS=2 对照图 10(b) 中的 p99 TTFT 改善，实验使用已载入用户代码和 Python 包的 warm execution environment，并以 ShareGPT 内容配合 Poisson 到达模式。它不是从零启动 VM、容器、依赖和模型的统一加速比例。请求率超出服务能力时，论文也观察到排队时间占主导。

## 一个可以手算并核验的关键路径

下列数值来自 Medusa 图 8 的四舍五入标注，计算由本次自行编写的 `calculations.json` 和 `verify.py` 独立重算；不是重新跑论文 benchmark。

- 普通加载：`0.85 + 0.39 + 0.21 + 0.50 + 0.90 = 2.85 s`。
- 单纯异步：`0.85 + max(0.47, 0.21 + 0.52) + 0.90 = 2.48 s`。权重支路未覆盖的 bubble 为 `0.21 + 0.52 - 0.47 = 0.26 s`；并发后权重加载自身还由 0.39 s 增至 0.47 s。
- Medusa：`0.85 + max(0.42, 0.23 + 0.02 + 0.31) + 0.26 = 1.67 s`。
- 相对普通加载，减少 `1.18 s`，即约 `41.4%`；相对异步版本减少约 `32.7%`。这是一台机器、一个模型的 loading phase，不能写成所有服务均加速 41.4%。

这个预算说明，先画依赖关系再求关键路径，才能知道哪段延迟还在。仅消除图 capture 仍留下 KV profiling；只有权重 I/O 变快，也不保证能把 tokenizer、KV 和 graph 初始化全部遮住。选择扩实例策略时，还要把控制决策、实例初始化、权重读取、服务队列与首 token 计算分别计时。

## 论文与公开框架实现之间的距离

Dilu 的主 README 固定在 commit `1134655a08e659db9a39f906acb76222d2c86c20`，明确称公开代码为 simplified reference implementation，依赖 PyTorch 1.11、CUDA 11.7 等历史环境。该 README 指向的 `adaptive_2D_scaling/vertical_scaling/README.md` 在同一 commit 返回 HTTP 404，响应已经保留。因此本次没有确认这条安装路径的可复现性，也没有检查 CUDA Graph launch 是否受到与普通 kernel launch 相同粒度的控制。

Medusa 主库固定在 commit `6581d2e5ec8fa4ecdabcdb50560982a78ea3ca89`；静态读取的 `vllm/__init__.py` 声明版本为 **0.3.1**。这只能证明该研究 fork 的版本字符串，不能认定它与上游 v0.3.1 完全一致。主 README 说明依赖修改过的 PyTorch 和 SPDK，并要求 CUDA 12.4、driver 550.54.14，理由是版本变化会改变 cuBLAS kernel 实现。README 没有固定所有依赖仓库的 commit；这些依赖实现本次未展开阅读、未构建。不得把这里的物化能力当作当前上游 vLLM、SGLang 或 Ollama 已有的默认功能。

两篇论文结合时还存在一个值得第 11 章保留的问题：Medusa 第 9 页复用“同模型、同 GPU 类型时空闲显存相同”的离线结果，而 Dilu 的动态共置会改变其它实例占用的显存。**本次推断**：要组合两者，至少需在恢复前核验实际可用容量，明确物化记录的配置与失效条件；仅按模型名和 GPU 名复用不能证明正确。图的分配序列、kernel 版本、batch/shape 配置发生变化也需要重新验证。这是从两篇设计前提推导出的待解决问题，不是论文已给出的集成方案。

正文可在既有资源调度实验中先让读者测量“已有实例增份额”与“创建新实例”的响应差，再用上面的时间线解释后者为何仍慢。保留现有章、节和实验编号，不增加系统名称罗列，也不把历史 Qwen1.5/Llama2 评估换名成新一代模型的实测结果。
