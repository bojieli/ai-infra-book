## POD-Attention：资源互补为何不等于自动重叠

本次完整读取作者 v2 的物理页 4–8，实际查看图页 5、6、7；首页另作摘要／身份核对。页 8 只提供评估设置及下一段的起始文字，本轮没有继续读主要评估结果，不能宣称完成全文或复现实验。

论文把几种“同时执行”分开：不同 CUDA stream 不保证同 SM 共驻；将 prefill 和 decode 的 warps 塞入同一 CTA，又可能受到慢 warp 和 CTA 同步的拖累。POD 在 CTA 已被硬件分配到 SM 后，再用该 SM 的计数器选择 prefill 或 decode 工作，让不同 CTA 独立完成。物理页 6 的伪代码与图 8、9支持这一描述。

更有用的判断在页 7–8：单独运行时，decode 内核的大 tile 所做的冗余计算未必影响带宽饱和；与 prefill 共驻后，这些计算会争用 tensor cores。反过来，chunked prefill 为增加并行度而过度切分 KV 维，也会多读 query，与 decode 争带宽。因而两个分别优化好的内核，合起来未必仍然合适。

这份 A100 实现将 decode 的 query tile 长度降到 16，按批次组成选择每 SM 2 或 4 个 CTA，并通过 virtual decode CTA 调整共享内存使用。对 prefill split 的限制是按实验选出的至多两波；这些是论文实现条件，不能写成通用硬件定律。这里的 wave quantization 指最后一波 CTA 留下空闲 SM，和 COMET 的数值量化不是同一件事。

一个可复算的例子来自页 5：108 个 SM、每个 decode 请求四个 CTA 时，batch 从 54 增到 55，只把工作块从 216 增到 220，却让一 CTA／SM 的简化波数从 2 变为 3，最后一波只有四个 SM 有工作。这个模型解释为何很小的 batch 变化也值得测，但不能据此预言实际延迟增加 50%；真实设备允许 CTA 并驻，单 CTA 时长和重叠条件也会变化。

再用独立教学数字说明互补的边界：prefill 对算力／带宽的归一化资源时间为 100／10，decode 为 10／100。忽略固定开销且各自能充分重叠内部资源时，串行理想时间为 200；同时执行的资源下界是 `max(100+10,10+100)=110`，不是 100。加入调度、依赖和资源容量限制只会使实际情况更复杂。数字不来自论文实测，不作为 POD 的加速比。
