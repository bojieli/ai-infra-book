Abstract
Modern NICs DMA packets directly to the LLC using tech-
nologies like DDIO, reducing access latencies for networking
applications. Prior work has observed several performance
issues with DDIO when the working set of packet buffers
does not fit into LLC. For example, the leaky DMA problem
arises when incoming packets evict older packets that have
not yet been processed by the application from LLC, causing
them to be fetched again from main memory. While using a
smaller pool of packet buffers that fits in cache is an obvious
solution, this may result in the NIC running out of buffers
to DMA packets into when a burst of packets arrives. This
paper proposes Toasty, a system that mitigates this tradeoff
between high throughput and resilience to packet loss that
arises when sizing the network packet buffer pool. While
prior work has proposed hardware-based solutions to this
problem, Toasty is a software-only solution that can be de-
ployed on commodity NIC hardware. Toasty manages the
packet buffer pool as a LIFO stack instead of a FIFO queue,
and adapts the number of buffers populated into the NIC
hardware RX ring based on incoming packet load and ap-
plication processing rate. Together, these changes enable
Toasty to recirculate a small working set of cache-warm
buffers in steady state, while falling back to a larger pool
of buffers during traffic bursts. We implement Toasty over
the AF_XDP kernel bypass framework, and our evaluation
shows that Toasty improves network throughput for a vari-
ety of network functions by up to 78% over the default buffer
pool implementation of AF_XDP. We also show that Toasty
matches the performance of a small buffer pool that fits in
cache, while being more resilient to traffic bursts.

1 Introduction
Innovation in chip manufacturing has led to an explosion
in the speeds at which computer networking is possible to-
day. However, CPU frequencies have not progressed at the
same pace, forcing networking software to play catch-up
in the ability to process packets over high-bandwidth links
efficiently [1, 5, 6, 17, 22–24, 29, 31]. Recently, kernel bypass
frameworks like DPDK [10] and AF_XDP [3, 15] deliver sig-
nificant improvements in software packet processing rates
by removing the kernel bottleneck from the network I/O data
path. To avoid dynamic buffer allocation and packet copy
overheads, these frameworks pre-allocate a large pool of
packet buffers in userspace memory, and the Network Inter-
face Card (NIC) receives pointers to these free buffers from
the device driver. When packets arrive over the network, the
NIC DMAs incoming packets into the free buffers, which are
directly processed by the application in a zero-copy manner,
and then recycled back into the free pool.
In addition to software frameworks, Direct Cache Access
(DCA) is a hardware technology to help applications process
packets faster, with Intel’s DDIO [11] leading the charge.
With the limited time budget available to process packets
with high-speed NICs, fetching every packet from memory
is no longer viable [7, 14, 18]. For this reason, DDIO enables
the NICs to DMA packets directly into the last-level cache

(LLC). This reduces the access latencies of packets and mem-
ory bandwidth usage for applications, and hence improves
network I/O performance. DDIO uses a limited number of
LLC ways (10% of LLC ways), to prevent network I/O traffic
from interfering with co-located applications.
Previous work [1, 5, 17, 23, 24, 30, 33, 35] has identified
several shortcomings with DDIO. If the size of the packet
buffer pool is larger than what can fit into the DDIO ways of
LLC, then network buffers contend for the limited available
space, and several problems result from this cache contention.
For example, if packets arrive faster than the application can
process them, newer packets may evict older packets from
the LLC even before the application has processed them.
This phenomenon is popularly known as the leaky DMA
problem [30], and causes the application to fetch most of
the packets from memory even with DDIO in place. A more
subtle problem arises in the case of packet buffers that have
been processed by the application and added back to the free
buffer pool. These free buffers continue to stay in various
levels of caches, with the data never being accessed again
(because the application is “done” with the packet), until they
are either evicted due to cache contention, or the NIC reuses
the buffers to DMA new packets. If free network buffers are
evicted from the cache before reuse by the NIC, their contents
will be written back to memory, because the cachelines would
be dirty. However, such writebacks are wasteful because the
packet content will be overwritten when the packet buffer is
reused for DMA in the future. This is called the unnecessary
writebacks problem [1, 32], and there is no way for hardware
to identify and avoid these writebacks.
The above problems seem to indicate that one must use a
small pool of free packet buffers, which fits snugly into LLC
DDIO ways, as proposed in prior work [17, 23, 24, 30]. A
small pool of buffers will significantly ameliorate the leaky
DMA problem, because packet buffers will not have to con-
tend for LLC space and evict other packet buffers, thereby im-
proving cache hit rates and application throughputs. A small
pool of packet buffers also ensures that processed buffers
that are added back to the free pool are reused quickly again
for DMA before being evicted from the cache. Such reuse of
cache-warm buffers for packet DMA avoids wasteful write-
back traffic to memory, because when the NIC tries to DMA a
packet into a buffer that is already present in the CPU cache,
the buffer is updated in place without accessing memory.
Our experiments with different types of network functions
over the AF_XDP kernel bypass framework (§2) show that
most network functions achieve optimal application (and
cache) performance with a small pool of buffers that fit in the
DDIO LLC ways. However, under highly variable or bursty
traffic conditions, we also see that a small buffer pool leads
to packet drops due to the exhaustion of packet buffers avail-
able to the NIC for DMA, a phenomenon observed in prior
research as well [1, 6, 17, 23, 24].
The goal of our work is to mitigate this tradeoff between
high network I/O throughput and resilience to packet loss
that one encounters when sizing the packet buffer pool. Prior
work has proposed solutions that either redesign the NIC-
CPU interface, or leverage advanced hardware features avail-
able in modern smart NICs, to better utilize the LLC space
available for network packets [17, 22–24, 28]. Our work seeks
to explore a solution that works on today’s commodity NICs,
for immediate deployment and impact.
To this end, this paper introduces Toasty, a software frame-
work that enables the reuse of a small working set of cache-
warm packet buffers in steady traffic conditions, while au-
tomatically adapting to a larger buffer pool to avoid packet
drops due to traffic bursts. Our work consists of two key
ideas. First, Toasty manages the pool of free packet buffers
as a Last-In-First-Out (LIFO) stack, rather than a First-In-
First-Out (FIFO) queue as is commonly done. This ensures
that network packet buffers that have been recently pro-
cessed and freed up by an application, and hence likely to
be warm (and toasty!) in caches, are reused for the DMA of
new packets immediately. However, using a LIFO stack for
the memory pool alone is not enough, because the hardware
RX ring (in which the NIC stores pointers to the free buffers)
still works as a queue, and changing its behavior from FIFO
to LIFO requires hardware changes. Therefore, the second
key idea of our work is to adaptively control the number of
packet descriptors that are filled in the hardware RX ring.
Under steady incoming load, the device driver refills the RX
ring with a small number of packet descriptors from the head
of the free pool, which, given our LIFO buffer pool design,
are likely to be warm in the cache. However, when the device
driver detects a high traffic rate that causes a rapid deple-
tion of free buffers available in the RX ring, it populates the
NIC RX ring with a larger number of buffers, temporarily
pulling in cold packet buffers from beyond the warm region
at the head of the buffer pool. This adaptive filling of the
hardware RX ring by the device driver ensures that we reuse
only cache-warm buffers in steady state, while effectively
handling traffic volatility. Toasty implements these ideas on
top of the AF_XDP kernel bypass framework, though our
ideas can be applied to other packet I/O frameworks as well.
Our evaluation of Toasty with a variety of network func-
tions shows that Toasty improves network function through-
put by up to 78% over the default AF_XDP implementation,
when both systems use a larger buffer pool that is resilient
to varying traffic conditions. Our gains are even more com-
pelling at up to 86% when there is increased contention in the
LLC from co-located applications. Further, the performance
of Toasty with a larger buffer pool matches the performance
of the default AF_XDP with an ideal throughput-maximizing
small buffer pool, while being a lot more resilient to bursty
