## 原理中值得保留的部分

论文把拓扑展开到时间维度，在各时刻为数据块选择可用链路，直到每个接收端取得要求的数据。相比仅选择 ring／tree，生成对象包含逐块路由与时序。搜索采用随机选择和逐步匹配；局部利用率高不是任意问题全局最优的证明。正文讨论通过反向 Broadcast／All-Gather 构造带归约的通信，再组合 All-Reduce。

链路用启动项与传输项建模。第 8 页明确未在本次生成中考虑 NPU 或内存性能；可以扩展成本模型不等于已经覆盖这些因素。交换机用固定 degree 展开为点对点连接，degree=d 时每条虚拟边的带宽为原来的 1/d；脚注说明没有覆盖所有连接组合或随时刻变化的连接。物理端口带宽不能在每条逻辑边上重复计算。

## 评估与实现边界

第 8–10 页的性能比较主要来自 ASTRA-sim 和作者增加的拥塞感知解析后端。第 9 页用 V100 八卡与 32 TPUv3 系统验证的是基线 All-Reduce 模拟，不能把该验证直接当作 TACOS 已在全部真实系统部署。TACCL 对照为作者在 TEN 上实现的 TACCL-like ILP 基线；C-Cube、MultiTree 因实现未公开采用论文报告数字。正文中的高效率相对于所设理论界，不等于训练 MFU。

本轮取得的作者 README 的 Constraints 明确写：点对点拓扑，交换机需预先展开；当前模式为 All-Gather；Reduce-Scatter／All-Reduce 尚在实现；不支持 All-to-All；当前输出是预计时间，MSCCL-XML 生成尚在进行。这是固定提交的文档声明，未用源码逐项证明不存在其他路径。不能从论文描述推断开源入口已支持全部 collective，更不能归为 vLLM／SGLang 自带功能。

README API 的链路带宽单位为 GiB/s，chunk 为 bytes，返回时间为微秒。示例将 1,048,576 bytes 标作 1 MB，书中统一写作 1 MiB；论文图里的 GB/s 与代码参数也不能不经换算直接互填。

## 采用决定

只在[现有通信调优案例](../../../../../case-studies/communication-tuning.md)增加一个对照：先求逐链路下界，再区分生成路由／时序、选择运行参数和实际执行。沿用第 6.4 的实验 6-5，工具选做可分析 All-Gather 的模型输入输出，但不要求替换真实 NCCL。原文算法、仿真评估和公开工具分别标注，不新增一节生成器教程。正文选读进入统一覆盖前，保留 `reading.json` 的待整合状态。
