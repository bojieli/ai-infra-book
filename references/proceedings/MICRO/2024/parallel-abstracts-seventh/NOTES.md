## 候选的具体问题

FloatAP 的摘要先指出一个限制：关联处理器可以让大量操作并行发生，但将浮点直接放入 bit-serial 路径，吞吐仍然不足。它利用位与分量并行的尾数对齐，以及既有 adder tree，改善浮点加法、归约、乘法和点积。这个问题适合第 4 章既有 PIM/精度讨论：**减少外部数据移动以后，内部操作次数、对齐和归约会不会成为主要代价？**

下一步如果补读，只围绕这一个问题核对机制与评估：各浮点格式的操作代价、数据与中间状态的容量限制、并行度，以及与 A100 的面积归一化、精度、吞吐和能效比较口径。摘要报告的是 area-equivalent A100 对照，FP32 与 bfloat16 的收益不同；不能把 2.7× 的 FP32 推理吞吐表述为每张现实部署设备对 A100 的通用优势。摘要声称支持 RISC-V V，并易于接入 DSL/ML 框架，但本批没有读取实现或集成测试，不能据此宣布已支持 PyTorch、vLLM 或当前大模型服务栈。

这最多为现有段落补一个经过核验的设计取舍，不要求增加新章节、独立案例目录或技术大全。

## 其余条目的取舍

SCALE 用共同的数据流结构组织 message-passing GNN 的图算子和神经算子，再结合度数/顶点感知调度处理不同粒度的负载不均衡。它与跨算子复用相关，可以留在第 4/5 章备查。摘要明确写的是 simulation results；在没有读取机制和配置之前，不把它的 all-reduce 或 workload balance 术语直接套用到多机 MoE 的 EP 调度，也不拿 1.82× 的结果作为生产框架表现。

Azul 以稀疏线性方程迭代求解器为对象，将数据保留在分布式片上 SRAM，提高跨迭代复用；同时仍需安排 PE 间的数据和计算，避免片内通信成为瓶颈。它与此前已读 Sparsepipe 有清楚的主题重叠，当前备查足够。摘要所列 GPU 和其他加速器的大倍数属于特定稀疏求解器评估，不能外推到 Transformer attention 或 MoE。首页虽包含正文与图，本轮只核对摘要和身份，没有分析那张图。

RTL2MµPATH 从 RTL 合成多个微架构执行路径，SynthLC 再以符号信息流分析验证 leakage contracts。它处理手工抽象与实现之间的形式验证缺口，但与本书当前模型、容量、带宽和系统吞吐的主线距离较远。不能将它视为 Agent sandbox 或租户隔离已经验证的证据；停止于摘要。
