1 Introduction


1.1 Purpose
This document describes the architecture, functionality, and external interfaces of UnifiedBus (UB)
Operating System (OS) Component. It is intended for application, driver, and OS developers, as well as
anyone interested in the software architecture of UB OS Component.


1.2 Scope




                                      Figure 1-1 UB system diagram

The preceding figure shows the UB system. UB OS Component extends the original OS framework of
memory management, communication, device management, and virtualization to better support UB. It
implements unified abstraction and decoupling of heterogeneous hardware, provides a unified memory
address space, supports global resource scheduling, dynamically combines and expands computing
resources, and accelerates communication between devices, thereby unleashing the potential of UB
hardware.

This document focuses on the architecture, functionality, and interfaces of UB OS Component.

           Architecture: software architecture and each layer of UB OS Component
           Functionality: functions at each layer and their relationships with existing OS components
           Interfaces: interface design and how to use these interfaces in typical scenarios

2 Architecture


The OS runs on the CPUs of compute nodes and provides a runtime environment for applications. The
following figure shows the software architecture of UB OS Component.




                           Figure 2-1 Software architecture of UB OS Component

UB OS Component enhances the original OS framework of memory management, communication,
device management, and virtualization to provide improved support for UB. The feature enhancements
include:

      ①    Device Mgmt: It provides UB device management capabilities, allowing hot plugging and
           configuration of UB devices on compute nodes. It consists of the following modules:

                UB Device Mgmt: Based on Linux's device management model (bus/device/driver), this
                 module provides extended management for UB devices. It manages UB drivers, UB
                 firmware interactions, and UB device hot plugging. In addition, it provides device driver
                 interfaces for developing UB device drivers.
                sysfs: UB Device Mgmt generates UB device, driver, and bus information in sysfs. Users
                 can view and use the information through sysfs.
                udev: UB Device Mgmt generates uevents. Users can use the udev tool to obtain the hot
                 plug status of UB devices and manage these devices accordingly.
                UB User Driver: It is the user-space driver for UB devices. It exposes UB devices to user
                 space, enabling applications and virtualization software to use these devices.
           For details, see 3 Device Mgmt.

      ②    Memory Mgmt: It enables memory-semantic access for memory borrowing and sharing
           across compute nodes and devices within UB Domain. It consists of the following modules:

                DMA/SVA Memory Mgmt: Based on Linux's direct memory access (DMA) and shared
                 virtual addressing (SVA) features, this module manages UB Memory Management Unit
                 (UMMU). Drivers and other components can register host memory with UB devices
                 using this module.
                Pooled Memory Mgmt: Its functions include exporting local memory, importing remote

                 release the borrowed memory using standard memory management interfaces such as
                 malloc, free, and numa_alloc_onnode provided by these common allocators, without
                 requiring any application modifications.
           For details, see 4 Memory Mgmt.

      ③    Communication: It implements communication and remote procedure calls (RPCs) across

                Connection Mgmt & Communication: They manage asynchronous communication

                 modules.
                UBComm Lib: It provides interfaces for enabling asynchronous communication and
                 Unified Remote Procedure Call (URPC) within UB. Applications can use these interfaces
                 to perform inter-node communication and function invocation within a SuperPoD.
                Socket: It is compatible with glibc and other libraries that provide socket interfaces.
                 Applications on different nodes can communicate with each other through socket
                 interfaces without modification or with minimal modification (see Note 2).
           For details, see 5 Communication.

                QEMU: It extends QEMU functions to virtualize UB Controller, UB devices, and UMMU.
                libvirt: It extends libvirt functions to support UB device creation and deletion.
                vfio-ub: It supports UB device virtualization based on Linux's Virtual Function I/O (VFIO)
                 framework.

3 Device Mgmt


3.1 Overview
UB device management involves UBus Driver, vfio-ub, and ubutils, which together provide a set of UB
device service management interfaces. These services include device discovery, device registration,
and interrupt enabling for UB device drivers; user-space passthrough to UB devices; and querying UB
device information and configurations. Various UB devices can be registered with UB to perform their
functions. In the OS, UB device management functions, such as device discovery, registration, and
driver loading, can be used in both single-server and cluster deployments.

          Single-server scenarios: Each server operates independently and exclusively manages its
           local UB devices. UBus Driver discovers and enables these devices, while vfio-ub enables
           user-space passthrough for direct device access.
          Cluster scenarios: In a SuperPoD, UBus Driver discovers and enables UB Entities allocated
           to compute nodes, supports the addition and removal of pooled devices, and works with vfio-
           ub to enable user-space passthrough for direct device access.

Note: UBPRM and UBFM work together to allocate UB Entities to compute nodes.

3.2 Functional Architecture

3.2.1 Device Management Architecture




                            Figure 3-1 UB device management architecture

         UBus Driver: It consists of ubfi, ubus, and vendor_ubus modules. ubfi parses the UBRT
          table reported by the BIOS, registers platform devices, and generates the required Bus
          Controller. ubus provides basic device services based on Bus Controller, including UB device
          enumeration, UB device creation, error handling, hot plugging, and interrupt handling.
          vendor_ubus is a vendor-specific implementation responsible for interacting with the vendor's
          hardware.
         vfio-ub: It enables user-space passthrough for UB devices.
         ubutils: It provides UB device management tools to support UB topology query,
          configuration space query, and device configuration.

The major device management functions are as follows:

         UB device information parsing: ubfi parses the UBRT table reported by the BIOS. This table
          contains SoC information related to UB components, including register addresses,
          associations of UB devices with the interrupt controller and with the UMMU, and system
          resources that can be allocated by UB. After obtaining information from the UBRT table, the
          OS parses the table entries, creates and registers device nodes such as Bus Controller and
          UMMU, scans for the Bus Controller ports, completes UB Entity enumeration, and
          establishes the topology relationships.


unifiedbus.com                                                                                      12
3 Device Mgmt


         Device enumeration: UBus Driver enumerates UB devices within a single server without
          repetition or omission. Device enumeration requires using Neighbor Discovery Protocol,
          enumeration management messages, and configuration access messages. This process
          includes topology scanning, network address allocation, routing table setup, Entity Identifier
          (EID) assignment, and initialization of discovered UB Entities for registration on UB.
         Device resource space management: The host obtains device resource space information
          and allocates its address spaces to devices. The host driver accesses the device resource
          space using the host-side address. The CPUs allocate an address window to each UB Entity.
          UBus Driver manages the address resource, allocates an address space to each device
          when UB Entities are enabled, and releases the address space after the device is removed.
          UB devices support hot plugging and UB Entities are created on demand. Therefore,
          dynamic resource allocation and release shall be supported.
         Device configuration space access: UB Entities support configuration space registers, which
          store capability description and configuration interfaces for device management. According to
          the UB protocol, configuration access messages are used to read from and write to
          configuration space registers. Bus Controller acts as the initiator of configuration access
          messages, while the device serves as the responder. Bus Controller also has its own
          configuration space register and functions as both the initiator and the responder. UBus
          Driver accesses configuration space registers using hardware and software interfaces
          (Message Queue) provided by Bus Controller.
         Bus device driver: The UB device driver framework leverages the Linux kernel's driver model
          to enable unified management of UB devices and complies with the bus/device/driver
          architecture of that model. It provides a unified abstraction of UB Entities and standardized
          programming interfaces that allow vendor drivers to manage devices. It also manages UB
          services and offers common service registration and deregistration interfaces for UB
          components, such as Reliability, Availability, and Serviceability (RAS) and hot plugging.
         Device interrupts: UB interrupts adopt a message-based mechanism to establish interrupt
          paths between UB devices and the system. They handle access to the interrupt controller
          and manage UB device interrupt requests and releases.
         Port management: UBus Driver allows querying and configuring information related to port
          link establishment and neighboring devices. These operations can be initiated by either the
          driver software or the user.
         Error detection and reporting: UBus Driver supports the error detection, correction, and
          reporting mechanisms defined in the UnifiedBusTM (UB) Base Specification 2.0. These
          mechanisms enable efficient error handling and enhance overall system robustness and
          reliability.
         UB device information query and configuration: UB provides the lsub and setub tools to view
          the UB network topology and device configuration spaces, as well as to modify a specified
          device configuration space. It exposes UB subsystem information to user space through
          sysfs and grants the write permission on certain modules, allowing the kernel to be triggered
          to execute related tasks.

3.3 Usage Process

3.3.1 Device Drivers
The UB driver is registered with the system by calling ub_register_driver, which is generally
implemented in the init function of the driver module. Once UB detects a UB device and matches it with
a driver, the driver generally performs the following initialization process (generally implemented in the
probe function of the driver):

      1.   Call ub_set_user_info to set host information, such as an EID.
      2.   Call ub_entity_enable to enable UB Entities.
      3.   Call ub_iomap to map a resource space.
      4.   Access the device configuration space to initialize the device.
      5.   Call request_irq to register the interrupt request (IRQ) handler.
      6.   Register the UB Entities with other subsystems (such as NVMe or netdev).

When the device is no longer used, the driver needs to remove the device (generally implemented in
the remove function of the driver):

      1.   Deregister the UB Entities from other subsystems (such as NVMe or netdev).
      2.   Disable the IRQs generated by the device and call free_irq to release them.



unifiedbus.com                                                                                           16
3 Device Mgmt


       3.   Call ub_iounmap to release the resource space.
       4.   Call ub_entity_enable to disable the device.
       5.   Call ub_unset_user_info to clear the host information.

When the entire driver module needs to be removed, call ub_unregister_driver to deregister the device
driver (generally implemented in the exit function).

Note: Not all drivers require the preceding steps. Driver developers can adjust the initialization and removal steps based
on the device functions and design.



3.3.2 Device Service Driver
The process of developing and using a device service driver is as follows:

       1.   The UB service driver registers with the system through ub_service_driver_register.
       2.   After the UB component device is detected, ub_service_bus_type matches the service ID
            with a registered driver. Once matched, it calls the probe function of the corresponding
            driver to initialize the service.
       3.   ub_service_bus_type calls the remove function of the corresponding driver to remove the
            UB component device.
       4.   To remove the entire driver module, ub_service_driver_unregister is called to unregister the
            driver.

4 Memory Mgmt


4.1 Overview
This chapter describes the software architecture and interfaces that enable memory access within the
UB interconnect topology.

In general, existing bus architectures follow a host-device model, where the host (CPU) manages each
device and three independent memory access paths exist: host-to-device, device-to-host, and device-
to-device. UB streamlines this model. It categorizes UB nodes as Users and Homes in the memory
access model. Users can access the memory resources of Homes either synchronously (via load/store)
or asynchronously (via DMA).


4.2 Functional Architecture




                  Figure 4-1 UB Memory Management (UBMM) software architecture

         libummu: It provides APIs for allocating and releasing token IDs in user space, and
          maintains the permission table defined in the UnifiedBusTM (UB) Base Specification 2.0.
         ummu-core: It provides basic token ID management, as well as configuration and
          management of advanced capabilities defined in the UnifiedBusTM (UB) Base Specification 2.0.




unifiedbus.com                                                                                         18
4 Memory Mgmt


           ummu driver: It interacts with the UMMU hardware, implements the underlying capabilities
            defined by ummu-core, and ensures memory paths on the Home side.
           libobmm/OBMM: It provides memory borrowing interfaces (EXPORT and IMPORT), as well
            as memory consistency maintenance interfaces (used only for memory sharing).
           UB Decoder driver: It configures the UB Decoder hardware to ensure proper operation of
            load/store paths on the User side.

Note: ummu driver and UB Decoder driver are used to configure memory paths on the Home side and User side,
respectively. In addition, links between Homes and Users can be established only after the correct route information is
configured in UBFM.



4.2.1 Memory Access Target (Home)
As described in the UnifiedBusTM (UB) Base Specification 2.0, a memory access target needs to
register local memory resources with UMMU and generate a memory access credential tuple {EID,
TokenID, UBA}. The OS provides four types of interfaces to perform these operations:

           User Shared Virtual Address (USVA): It exports the specified VA segments of a user-space
            process to other devices or nodes. USVA uses a permission table to restrict device access to
            specified VA segments in user space.
           Kernel Shared Virtual Address (KSVA): It exports the specified VA segments in kernel space
            to other devices or nodes. KSVA uses a permission table to restrict device access to the
            allowed VA range in kernel space.
           DMA: It maps the specified physical memory as UB addresses in kernel space and exports
            them to other devices or nodes.
           EXPORT: It exports local memory resources of a specified size to other devices or nodes.


4.2.2 Memory Access Initiator (User)
A memory access initiator uses an access credential to initiate memory access through multiple
methods.

           Asynchronous access: The User employs an access credential tuple provided by the Home
            to initiate asynchronous DMA operations through the DMA or Unified Remote Memory
            Access (URMA) engine.
           Synchronous load/store access: The User calls the IMPORT interface to configure the
            access credential tuple into UB Decoder. Afterward, all load/store access requests to a
            specified physical address are directed to the Home through UB.

The IMPORT interface takes the memory resources exported by the EXPORT interface as input
parameters, and uses them in either of the following methods:

           After memory resources are bound to the NUMA nodes of the local OS, they are assigned to
            user-space processes through a standard memory allocation interface (for example,
            malloc/free in glibc or jemalloc).


unifiedbus.com                                                                                                            19
4 Memory Mgmt


          After memory resources are bound to character devices, user-space processes can access
           them by mapping them into their address spaces using mmap.


4.3 Usage Process

4.3.1 EXPORT/IMPORT
The EXPORT and IMPORT interfaces are used to export and import memory during memory borrowing.
In a SuperPoD, the memory resources of nodes with ample memory can be exported, and then
imported to nodes that have insufficient memory or need additional memory for higher performance.

UBPRM makes a memory borrowing decision. To do so, it needs to obtain the EIDs on the Home side,
the EIDs on the User side, and the size of the memory to be borrowed. The following figure illustrates
the memory borrowing process:




                                 Figure 4-2 Memory borrowing process

      1.   Home: It calls the obmm_export API, specifies the EID and memory size, and generates the
           UBA and token ID information in mem desc. The tuple {dest EID, UBA, TokenID} describes
           the memory lending information on the Home side.
      2.   UBPRM: It populates {src EID, scna, dcna} and private information implemented by different
           vendors in mem desc.



unifiedbus.com                                                                                           20
4 Memory Mgmt


      3.   User: It calls the obmm_import interface to import mem desc into the OS.
      4.   User: To bind memory resources to NUMA nodes, it calls the standard memory APIs (such
           as malloc, mbind, numa_alloc_onnode, and move_pages) to allocate and use memory.
      5.   User: To bind memory resources to character devices, it calls the mmap interface to map
           them as address spaces.


4.3.2 OWNERSHIP
When multiple nodes need to share data for reading and writing, one node may export a memory
segment, while other nodes import and use that segment, thereby enabling memory sharing within a
SuperPoD. If the hardware between nodes does not maintain cache coherence, there is a risk of data
inconsistency when multiple applications read or write data simultaneously. In this case, a hardware-
software collaboration mechanism is required to ensure data consistency.

OWNERSHIP is used to manage the holding status of a memory segment. Each node has an
independent local OWNERSHIP state for each memory segment. OWNERSHIP has three states:

          Invalid: This node cannot read from or write to the memory.
          Write: This local node can read from and write to the memory.
          Read: This node can read from the memory.

The application needs to proactively transition the OWNERSHIP state based on memory read/write
requirements to ensure that software operations on memory comply with the definitions of these
OWNERSHIP states. OWNERSHIP state transitions involve the following operations:

          Clean: Dirty cachelines are written back to memory and retained.
          Invalidate: Specified cachelines are invalidated, and subsequent CPU accesses read them
           directly from memory.




                                Figure 4-3 OWNERSHIP state transitions

OWNERSHIP state transition operations:

          Write -> Invalid: The Clean and Invalidate operations ensure that the modified data is
           written back to memory and the corresponding cachelines are invalidated.




unifiedbus.com                                                                                          21
4 Memory Mgmt


          Write -> Read: The Clean operation ensures that the modified data is written back to
           memory and the corresponding cachelines are retained to accelerate subsequent read
           operations.
          Read -> Invalid: The Invalidate operation ensures that the corresponding cachelines
           become invalid while memory data is not affected.
          Others ("NA" state transitions marked in Figure 4-3): No action is required.

OBMM provides the obmm_set_ownership interface to implement the OWNERSHIP mechanism. When
using shared memory, ensure that only one application performs write operations at a time. In addition,
call the obmm_set_ownership interface to maintain data consistency before and after reading or writing
a memory segment.

The process for memory sharing on the Home side is the same as that for memory borrowing. On the

4.5 UBTurbo

4.5.1 Overview
UBTurbo provides performance acceleration capabilities for the OS.

          Remote memory access has higher latency than local memory access. Therefore, careful
           planning of remote memory usage is essential to prevent significant performance
           fluctuations. UBTurbo provides the SMAP component as a reference for migrating data
           between remote and local memory. The core idea is to migrate page data based on the local


unifiedbus.com                                                                                       24
4 Memory Mgmt


          spatiotemporal characteristics of application access patterns, combined with the hardware-
          assisted hot and cold data identification capabilities provided by the chip (the chip shall
          support hot and cold data identification for remote memory). Hot data is stored in local
          memory while cold data is placed in remote memory, thereby delivering end-to-end
          performance acceleration for applications.
         In a hierarchical memory scenario, the access latency of remote memory is higher than that
          of local memory. Therefore, the location and proportion of remote memory need to be
          carefully planned. UBTurbo provides a remote-to-local memory ratio adjustment feature. It
          can dynamically modify this ratio based on memory latency sensitivity and the distribution of
          hot and cold data.

5.3 URMA

5.3.1 Overview
In the servers, racks, and clusters of the UB peer-to-peer architecture, compute units such as CPUs,
GPUs, and NPUs have their own advantages in processing different tasks. To fully leverage
heterogeneous computing power and efficiently complete computing tasks, the following communication
requirements arise:

         Direct communication among heterogeneous compute units for higher system performance:
          Peer-to-peer heterogeneous compute units scale out horizontally, where all components can
          directly communicate with each other and mutually invoke computing power, supporting fine-
          grained parallel processing or invocation.
         Large-scale high-performance computing and communication: The communication efficiency
          within and between nodes should be improved to support large-scale high-performance
          computing and communication.
         Flexible routing for enhanced network utilization and real-time performance: Multipath out-of-
          order transmission and efficient congestion control jointly unleash data center bandwidth
          capacity, improve network utilization, meet real-time service requirements, and enhance the
          overall efficiency of computing clusters.

URMA is designed to implement communication between two UB Entities, including one-sided DMA
access and two-sided message sending and receiving. URMA has the following features:

         Peer-to-peer access: Any two heterogeneous computing devices can communicate directly
          via URMA, bypassing CPUs.
         Connectionless communications: URMA reuses the reliable services provided at the UB
          transport layer between applications, eliminating the need to establish end-to-end
          connections between applications and thus significantly cutting down on communication
          overhead.
         Relaxed transaction ordering and multipath transmission: URMA communication components
          allow applications to specify transaction ordering modes and support out-of-order transaction
          execution and completion, thereby avoiding transaction head-of-line blocking, enabling
          underlay multipath transmission, and significantly improving execution efficiency.

5.3.3.1 Jetty Management

URMA performs resource management through Jetties. Jetties are used to receive and send
messages, and deliver memory semantics commands. They can be classified into Jetty for Sending
(JFS), Jetty for Receiving (JFR), Jetty for Completion (JFC), and Jetty for Completion event (JFCE)
based on their functions. Necessary Jetty resources shall be created before performing subsequent
operations, including read, write, send, and receive.

Jetty access is controlled through a token mechanism. On the management plane, the TokenValue is
specified when creating the Jetty and exchanged with the sender via an application's secure channel.
The sender configures the TokenValue on the hardware UB device when importing the Jetty. The UB
device carries the TokenValue when sending messages on the data plane, and the receiver validates
the token upon receiving access requests, granting access only if validation succeeds.




                                      Figure 5-4 Jetty management

The overall process is as follows:

      1.   Call urma_create_jetty to create a local Jetty.
      2.   Call urma_import_jetty to import a remote Jetty.

5 Communication


5.3.3.2 Segment Management

Each segment is a contiguous VA space mapped to a physical memory region.

The token mechanism is used to protect memory security during one-sided operations (for details, see
Section 5.3.3.4). When registering a segment, the management plane specifies the token value and
exchanges the token value with the sender through a secure channel. The sender configures the token
value to the UB device when importing the segment. When a UB device performs one-sided data-plane
access, it carries a TokenValue. The receiver validates the token in the incoming one-sided request and
proceeds with memory operations only after the validation passes.

The usage process is as follows:

      1.   Use local memory: Allocate a VA, and then register the segment via urma_register_seg.
      2.   Release local memory: Deregister the segment via urma_unregister_seg.
      3.   Use remote memory: Import remote memory via urma_import_seg to obtain target_Segment
           and UBA.
      4.   Release remote memory: Deregister the remote segment via urma_unimport_seg.

5.3.3.3 Two-sided Operations

Message semantics provide a two-sided messaging service. Message semantics are asynchronous
and non-blocking, the receiver shall receive messages proactively and read them before further
processing. UMDK supports one-to-many message semantics. Messages can be sent from the same
Jetty to different Jetties, which may be located on different remote nodes or processes. Two-sided
operations support both contiguous and non-contiguous memory on the local and remote sides.

      1.   The send procedure is as follows:
           (1) Call urma_post_jetty_send_wr to submit a send request through the JFS.
           (2) Call urma_poll_jfc to poll for send requests. Only after the polling is complete can the
                 send message buffer be reused (modified or released).
      2.   The receive procedure is as follows:
           (1) Call urma_post_jetty_recv_wr to submit a receive request, adding the local receive
                 buffer to the JFR.




unifiedbus.com                                                                                            32
5 Communication


            (2) Call urma_poll_jfc to poll for receive requests. Only after the polling is complete can the
                 message content be read from the receive buffer.

Note: To increase the throughput, the server can batch submit multiple receive requests. After a message is received, a
new receive request is added to the JFR. Alternatively, when the number of receive requests in the JFR is less than the
threshold, a new receive request is added to the JFR.


5.3.3.4 One-sided Operations

One-sided operations provide read and write semantics. These operations require knowledge of both
local and remote memory addresses. During one-sided operations, only the local process performs the
operation. No involvement or awareness is needed from the remote application. Two-sided operations
are used to transmit control messages, while one-sided operations are used to transmit a large amount
of data for data migration. One-sided operation buffers support local contiguous memory, local non-
contiguous memory, and remote contiguous memory.

The read and write process is as follows:

       1.   Call urma_post_jetty_send_wr to submit a read or write request to a JFS that has been
            registered.
       2.   Call urma_poll_jfc to poll the JFC to check whether a CQE arrives. If the return value of
            urma_poll_jfc is greater than 0, a CQE has arrived, indicating that the read operation is
            complete. Only after the request is complete can the send message be reused (modified or
            released).


5.3.3.5 Atomic Operations

Atomic operations provide compare-and-swap (CAS) and fetch-and-add (FAA) semantics. These
operations require knowledge of both local and remote memory addresses.

CAS atomic operations compare the original value of the remote address with the comparison value. If
they are equal, the data at the remote address is updated to the new value; otherwise, the value
remains unchanged.

FAA operations update the value at the remote address by adding the specified value to the original
one, and return the original value.

The atomic operation process is the same as that described in Section 5.3.3.4.


5.3.3.6 Completion Records

All one-sided, two-sided, and atomic operations in UMDK are non-blocking. A success returned from an
operation only indicates that the command has been placed into the send or receive queue. It does not
necessarily mean that the operation has been completed. A completion record is used to describe the
operation completion information. After the operation is complete, the hardware writes the completion
record to the JFC completion queue. When the application polls the JFC, the hardware reads the




unifiedbus.com                                                                                                        33
5 Communication


completion record from the completion queue and returns it to the application. URMA supports two
modes for determining whether an operation is complete: polling and interrupt.

         Polling mode is used in low-latency scenarios. In this mode, the application proactively
          checks completion records to determine the execution status of operations and proceed
          accordingly. The application calls urma_poll_jfc to query completion records in polling mode.
          Polling is a non-blocking method for checking completion; if the completion queue is empty,
          no completion record will be returned.
          Note 1: The application determines whether an operation is complete by checking the status fields of the
          completion records. If a fault occurs, the status field indicates the cause of the failure.

          Note 2: The completion_len field represents the length of data successfully processed (such as the number
          of bytes sent or received). This field is only valid on the receive side, such as in URMA_OPC_READ or
          URMA_OPC_RECV operations.

          Note 3: If the completion record is of the JFS type, data has been successfully sent, and the application can
          then modify or release the associated local buffer.

          Note 4: If the completion record is of the JFR type, the application can read messages from the receive
          buffer.

          Note 5: If notify_data is enabled, the completion record also carries the immediate data.

          Note 6: The application associates a specific operation with its completion record through the user_ctx
          parameter (for example, the user_ctx parameter in the urma_read API).
         Interrupt mode is used in scenarios where communication is not frequent. In this mode,
          application threads remain in the sleep state while waiting for completion events, minimizing
          CPU overhead. The URMA wakes threads when a completion event arrives.
          The interrupt process is as follows:
          (1) Enable the completion event by calling urma_rearm_jfc.
          (2) Submit the send operations (one-sided, two-sided, or atomic operations).
          (3) Call urma_wait_jfc to block and wait for a completion event. This function returns the
                 JFC that generated the event and automatically disables it by default.
          (4) Repeatedly call urma_poll_jfc to retrieve all available completion records until none
                 remain.
          (5) Go back to step (1) to re-enable the event.

6.1 Overview
This chapter describes the virtualization implementation of UB, UB Entity, Bus Controller, and UMMU. In
cloud computing scenarios, hardware resources on a physical machine are isolated and provisioned to
VMs through virtualization, significantly enhancing resource utilization. As a next-generation high-speed
interconnect, UB natively supports virtualization.

Mainstream device virtualization technologies are as follows:




                          Figure 6-1 Mainstream device virtualization technologies

Under traditional architectures, each server connects to the Top of Rack (TOR) switch through its own
NIC, meaning its maximum supported bandwidth is fixed. This can lead to several issues in real-world
applications, as illustrated below.




                          Figure 6-2 NIC traffic diagram in traditional architectures

           Low bandwidth utilization during off-peak periods: Service deployment typically estimates a
            theoretical peak bandwidth requirement, but in practice, workloads often remain far below
            this threshold. The bandwidth usage increases only during peak hours. This results in

6 Virtualization


            underutilized bandwidth and wasted reserved capacity. To address this, public cloud vendors
            apply virtualization and bandwidth oversubscription techniques to improve overall physical
            bandwidth utilization.
           Bandwidth bottleneck during peak periods: Under heavy workloads, bandwidth pressure

            scenarios, the total committed bandwidth across all VMs exceeds the maximum bandwidth

           Uneven bandwidth pressure across servers: Since each server has a fixed NIC bandwidth,
            variations in workload distribution can cause imbalanced network pressure across servers.
            This makes it difficult to ensure consistent network service quality.

A UB Entity acts as an isolated functional unit within a UB device. Virtualization in UB supports direct
device assignment to VMs, delivering native-level performance. Compared to traditional hardware-

7.1 Overview
This chapter describes the Reliability, Availability, and Serviceability (RAS) features of the OS within
UB, covering the detection, isolation, and recovery capabilities for UB faults, as well as handling
recommendations for related components such as applications, UBFM, UBPRM, and UBMM.

                                             Table 7-1 RAS features

 isolation and recovery

 prevention and                 capability.

Note 1: Local RAS faults in the UBPU hardware modules are handled in the traditional single-node manner and reported
by the BIOS to BMC and the OS. These faults are not elaborated in this document.

Note 2: In Section 10.6.2 of UnifiedBusTM (UB) Base Specification 2.0, errors are classified into three types:

       In the case of a class-A error, the physical topology of the UB Fabric remains intact. The error can be traced to a
       specific transaction and does not affect the execution of other transactions.

       In the case of a class-B error, the physical topology of the UB Fabric remains intact. The error can be traced to a
       specific UB Entity, TP channel, or Jetty (UB Entity-level, TP channel-level, or Jetty-level error) rather than a
       particular transaction. All resources of the error unit need to be processed.

       Class-C errors occur on device- or port-level public resources.

7.2 Functional Architecture




                                      Figure 7-1 UB RAS framework

The components and their functions are as follows:

         Hardware and firmware
          −   UB Memory, Bus Controller, and UB Entity: Errors in these hardware components may
              occur during operation. The hardware reports the corresponding error to UB Firmware.
          −   UB Entity: If a service error (class-A or class-B) occurs, the error is directly reported to
              the corresponding UB Entity driver.
          −   UB Firmware: It receives hardware error events and forwards them to the OS.
         OS components
          −   ACPI Platform Error Interfaces (APEI) driver: Hardware faults are reported according to
              the APEI specification and processed by the APEI driver.
          −   traceevent: The kernel uses this mechanism to record various events. When a hardware
              error occurs, the hardware reports the non_standard_event event through the APEI driver.
          −   rasdaemon: It listens to events reported by EDAC and traceevent, records related logs,
              and provides the logs for upper-layer services to monitor and process.
         UB components
          −      UBus Driver: It receives class-C errors reported by UB Firmware through APEI and
                 notifies the corresponding module for processing.




unifiedbus.com                                                                                               50
7 RAS


           −     sysSentry/sysSentry Service: When emergency events such as OOM, panic, or
                 reboot occur, it blocks the corresponding events and reports them to UBPRM to prevent
                 data loss or service interruption. It is also responsible for unified management of UB
                 event reports.
           −     OBMM: It handles memory-related errors. When a memory fault occurs on the Home
                 side, OBMM marks the faulty memory to prevent further access or reuse.
           −     UVB: When a fault occurs on the Home-side node, it broadcasts the fault information to
                 other nodes for coordinated handling.
           −     vfio-ub: When the interrupt soft notification mechanism is used, if a device fault occurs,

          Vendor components
           −     FMA: It serves as the memory fault isolation notification chain. Services can use this
                 chain to bypass the OS's default memory fault isolation logic and perform customized
                 fault handling as needed.
           −     UB Entity driver: It handles various UB driver faults and can implement customized
                 handling logic based on specific service requirements.


7.3 Fault Detection

7.3.1 UB Device Fault Detection
UB device faults refer to faults of UB Entities, Bus Controllers, and other devices. The fault handling
methods vary according to the device type.




unifiedbus.com                                                                                            51
7 RAS




                                Figure 7-2 UB device fault detection framework

UB device errors are classified into two types:

         Class-A and class-B errors
          (1) For UB Entity service faults, UB Entity driver obtains the fault status by querying the
                 status registers in the UB Entity's configuration space. The corresponding component
                 using the UB Entity then passes the fault information to the service layer.
          (2) In virtualization scenarios, when a UB Entity interrupt is passed through to a VM, the UB
                 Entity driver inside the VM receives it. If the UB Entity interrupt requires host
                 participation for soft notification, the interrupt is first received by vfio-ub on the host,
                 which then notifies the VM through KVM.
         Class-C errors
          (1) UB Firmware triggers the FHI/ERI interrupts.
          (2) The OS kernel reports traceevent error events through the APEI driver and notifies UBus
                 Driver.
          (3) The OS kernel reports the fault to rasdaemon using traceevent.

7.3.2 Remote Memory Fault Detection




                         Figure 7-3 Remote memory fault detection framework

In scenarios involving borrowed or shared memory, faults shall be detected and reported by both the
User and Home sides. The process is divided into the following cases:

         Home-side memory fault reporting
          (1) The Home memory controller reports the memory fault to UB Firmware.
          (2) UB Firmware reports the fault to the OS.
          (3) The APEI driver in the OS kernel notifies traceevent and OBMM.
         User-side read fault on remote memory
          (1) UB Firmware triggers SEA/SEI interrupts.
          (2) The OS kernel APEI driver reports the fault to traceevent.
         User-side write fault on remote memory
          (1) UB Firmware reports the fault as a UB event to UBus Driver.
          (2) UBus Driver reports the fault to sysSentry.
          (3) sysSentry forwards the message to sysSentry Service.
          (4) sysSentry Service reports the fault information to UBPRM and the O&M service.

7.3.4 OOM Detection
In memory borrowing scenarios, UBPRM periodically monitors memory watermarks. This watermark is
configurable and can trigger memory reclamation or memory borrowing. However, if memory usage
spikes rapidly within a short period, the UBPRM detection mechanism may not catch the change in
time, potentially causing processes on service nodes to be stopped or nodes to restart, leading to
service interruptions. The OOM prevention mechanism addresses this by reporting OOM events to
UBPRM, triggering emergency borrowing. The OOM prevention progress is as follows:

      1.   The node where the OOM fault occurs reports the event to sysSentry via the OOM event
           notification chain.
      2.   sysSentry reports the OOM event to sysSentry Service.
      3.   sysSentry Service reports the OOM event to UBPRM or the O&M service for handling.


7.3.5 Node Fault Detection
When a Home-side node experiences a panic or reboot, the memory it has lent becomes inaccessible,
which may impact application processes on the User side. In this situation, the data stored in the Home-
side memory shall be migrated to ensure service continuity.




unifiedbus.com                                                                                       55
7 RAS




                                Figure 7-7 Node fault detection framework

The notification process is as follows:

      1.   During the Home-side node kernel fault process (for example, a panic, reboot, or shutdown),
           sysSentry is notified of the imminent reset and restart.
      2.   sysSentry broadcasts the fault event through the URMA/UVB channels.
      3.   The fault event is transmitted from the Home-side node's URMA/UVB channels to the
           URMA/UVB channels of the management node.
      4.   sysSentry on the management node receives the fault event information and notifies the
           management node UBPRM through sysSentry Service.


7.4 Fault Isolation and Recovery

7.4.1 UB Device Fault Isolation and Recovery
      1.   For class-A and class-B faults, the corresponding driver or service process handles the fault
           directly, for example, by releasing affected resources or retrying operations.
      2.   For correctable class-C errors, they can recover automatically, and UBus Driver only logs the
           event without further action. For uncorrectable errors, the corresponding UB Entity driver is
           informed to take appropriate measures, for example, resetting a faulty port and logging the
           event.
      3.   UBPRM subscribes to non_standard_event events through system traceevent and
           processes the fault events.
      4.   The O&M platform monitors and handles faults by checking logs of events reported by
           rasdaemon.




unifiedbus.com                                                                                             56
7 RAS


7.4.2 Remote Memory Fault Isolation and Recovery
    Applications or UBPRM can subscribe to sysSentry remote memory access failure events, receive
    the corresponding fault information, and isolate the faulty memory or restore the applications based
    on the received fault information.

         Home-side memory fault isolation and recovery
          (1) The APEI driver isolates the faulty memory.
          (2) OBMM marks the faulty memory as unavailable for borrowing.
         User-side remote memory read fault isolation and recovery
          (1) When remote memory is bound to a NUMA node, faulty memory is isolated by the APEI
                 driver, which sends SIGBUS to the application processes that are using the memory.
          (2) When remote memory is bound to a character device, sysSentry Service notifies
                 subscribers—including UBPRM, O&M service, and application processes—via events.
                 Subscribers can take appropriate actions, such as isolating the memory or reallocating it.
          (3) The O&M service and UBPRM monitor rasdaemon logs and perform necessary fault
                 handling.
         User-side remote memory write fault isolation and recovery
          (1) sysSentry sends SIGBUS to application processes that are using the memory.
          (2) sysSentry Service notifies subscribers—including UBPRM, O&M service, and
                 application processes—via events. Subscribers can take appropriate actions, such as
                 isolating the memory or requesting memory again.


7.4.3 Communication Fault Isolation and Recovery
         Communication control-plane fault recovery
          (1) Applications call the urma_get_async_event interface to obtain exception events.
          (2) Applications classify and handle the events based on the event type (see
                 urma_async_event_type), for example, printing the logs.
          (3) Applications call the urma_ack_async_event interface to notify URMA that the exception
                 event has been processed.
         Communication data-plane fault recovery
          (1) Applications call the urma_poll_jfc interface to retrieve anomaly status.
          (2) Applications classify and handle the events based on the event type (see
                 urma_cr_status), for example, printing the logs.


7.4.4 OOM Prevention, Isolation, and Recovery
UBPRM can subscribe to OOM-type events from sysSentry. When an OOM event occurs, UBPRM
receives the notification from the sysSentry service and performs corresponding handling. The
recommended handling procedure is as follows:



unifiedbus.com                                                                                            57
7 RAS


      1.   UBPRM borrows memory from other nodes and imports it to the OS of the affected service
           node.
      2.   The OS attempts to allocate memory during an OOM event; if successful, it returns memory
           to the corresponding application; otherwise, the application is terminated. If OOM occurs
           during a kernel-space allocation, the system enters a panic flow and reboots.


7.4.5 Node Fault Isolation and Recovery
UBPRM can configure sysSentry via sentryctl to intercept panic/reboot events and set necessary
parameters for cross-node communication. It subscribes to OS panic and reboot events to monitor such
events.

Upon receiving a fault notification from the sysSentry Service, UBPRM performs isolation and recovery
measures, for example, migrating Home-side memory to other nodes and releasing the borrowed
memory from the faulty node to ensure service continuity for services that are using pooled memory.

After handling the fault, the system recovers according to the following procedure:

      1.   UBPRM notifies sysSentry Service of the fault handling result.
      2.   UBPRM transmits the result through sysSentry and URMA/UVB channels to the URMA/UVB
           channels of the Home-side node.
      3.   Home-side sysSentry receives the fault handling result via URMA/UVB channels.
      4.   The Home-side node proceeds with the kernel fault handling operation and continues
           rebooting.
      5.   If the Home-side node does not receive the notification from UBPRM within a specified time,
           it also reboots.
