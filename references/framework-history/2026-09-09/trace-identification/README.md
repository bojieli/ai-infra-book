# 重复片段的身份与等待

2026-09-09。围绕第 5.4.4 节／实验 5-8 补读 Apophenia：[物理页 2–12、16–17](../../../proceedings/ASPLOS/2025/apophenia-reading.json)，共十三页，其中六页已查看图像。另归档三份原始响应、一份从 ZIP 精确提取的源码，复用四份文件；九个[读取范围](reading.json)分开记录。没有编译或执行下载代码，也未重跑本书已有 GPU 实验。

## 论文解决的开销

Apophenia 位于应用与 Legion 依赖分析之间，识别重复的任务流，再调用既有 trace 引擎记录和重放分析结果。它处理的是任务及 region 使用方式；源代码中同一个循环、同样的算子名称，可能因交替分配的 region 产生两种序列。数据内容可以更新，影响依赖的身份和使用方式则要满足相应条件。

论文用异步历史分析寻找候选，再根据完整匹配决定重放；没有预测尚未出现的任务。收齐片段的等待，在应用生成任务远快于后续分析时容易隐藏，任务粒度和资源配比变化后要重新检查。长 trace 能摊薄固定开销，FlexFlow 强扩展部分却显示短 trace 可以减少暴露的重放发起延迟；不能只最大化覆盖率或 trace 长度。

分布式版本还要使各节点在相同的操作计数处接收异步分析结果，避免控制流分歧。本文采用这一约束，未审计完整分布式实现。其科学计算弱扩展与 CANDLE／FlexFlow 强扩展分开；后者因当时工程限制仅使用 DP，不能称为现代 MoE 混合并行测试。Eos 的 H100 80 GB 与 Perlmutter 的 A100 40 GB 对应不同应用及网络，论文也明确不作跨机器性能比较。

第 6.3 节的 7／12 微秒是任务发起时间，100 微秒是另一阶段的单任务 trace 重放开销；这些数不能相加或用作 CUDA kernel 启动常数。稳态吞吐前用了 30–300 次应用迭代预热，短生命周期服务仍须单独计算发现和准备成本。

## 公开工件与框架的边界

[Zenodo 元数据](zenodo-record.json)将该版工件标为 2024-10-07 发布，早于论文的正式 2025 出版日期；[原始 ZIP](legion-artifact.zip)的大小和 MD5 与元数据一致。附录明确多数评估无法通过这份代码完整重现，TorchSWE 的当时依赖包含未公开组件，FlexFlow 的命令也带有特定集群参数。

所读 [Legion 源码](legion_auto_trace.cc.txt)把任务、region、字段及访问权限等纳入 hash，并保留待提交操作，匹配后在 trace begin/end 内转交执行。部分字段被显式略过，AllReduce 的 hash 还留有 TODO；完整 tracing 引擎可能另有检查，不能仅凭本文件证明普适正确性，也不据此宣告已发现运行错误。本文未审计候选挖掘算法、所有 flush 调用点或完整工作负载。

vLLM v0.6.0 的[既有 runner](../../2026-09-08/graph-selection/vllm-060-model-runner.py)在重放前更新固定输入及元数据缓冲。对照固定于 `537af2c3a4ba7462ddc9bc94ec7a4ea496da6d2e`（2026-09-07 提交）的[完整图封装源码](vllm-cuda-graph.py.txt)，新封装按外部提供的 batch descriptor 和模式捕获／重放，缓冲和输入复制由外部负责。DEBUG 检查只收集顶层位置参数里的 Tensor 地址；形状分派和这项检查不能替代完整的依赖与生命周期约束。

这补充了已有 2024 decode→2025 分段图→2026 模式分派的演进记录，没有发现将 Apophenia 自动任务匹配接入 vLLM 的证据。Legion 的自动识别、CUDA Graph 重放和动态请求调度各有自己的执行边界。
