# 从分片策略到实际通信：PartIR 与 Shardy

2026-09-09。本次只采用一个判断：分片表达、策略选择、集合通信生成和实际执行时间，需要分别检查。放在第 6.2.2 已有 Qwen3 张量并行例子里，不新增编译器专题或核心实验。

## 论文怎样把切分讲清楚

PartIR 的扩展预印本物理页 3–5 用两次矩阵乘法逐步引入 batch parallelism、model parallelism 和参数完全分片。原始形状为 `X[256,8] W1[8,16] W2[16,8]`，mesh 为 B=4、M=2，元素为 FP32。

先沿 B 切输入，局部 X 变为 `[64,8]`。再沿 M 切 W1 的输出维、W2 的收缩维，两份局部权重均为 `[8,8]`。第二次乘法产生 `[64,8]` 的部分和，须沿 M 归约，才能恢复输出语义。进一步沿 B 切参数，常驻权重变为 `[2,8]` 与 `[8,2]`，但使用前需要各自 AllGather 回 `[8,8]`。

独立复算得到：全局两次乘法为 131072 FLOPs；B×M 切分后每卡为 16384 FLOPs。只做 B 切分时，每卡权重 1024 字节；加入 M 后为 512 字节；再沿 B 分片后常驻权重为 128 字节。最后一个数字不包含临时聚合缓冲区，不能当作峰值显存。

若教学上指定无重传的常规 ring，M=2 的 AllReduce 对 2048 字节输出，每卡发送和接收各 2048 字节；B=4 的两次权重 AllGather，每卡接收共 384 字节，发送也为 384 字节。这些是逻辑载荷估算，不含协议开销、梯度、优化器状态或反向过程，也不是论文实测。小到这个程度的矩阵不能用于论证实际 GPU 加速收益；它只帮助核对局部形状和通信语义，再将方法用回书中 Qwen3 的真实规模。

物理页 5 明确将 `AutomaticPartition` 定义为可接入优化算法的接口，论文实现采用 Monte Carlo tree search 和时间成本模型。它和手动策略调用相同的低层变换动作。因而“有自动策略接口”与“已经为任意模型、硬件找到全局最优策略”是不同的结论。论文栈中的时序变换、SPMD lowering 与成本建模也处在不同阶段。

## 公开实现比概览文字多了什么

Shardy 固定源码为 `a72dc82ce730c55be36a409945f4224181d050fc`，提交时间 2026-09-09T01:31:51Z。原始响应与检索时间在 [sources.json](sources.json)。官方概览说明它结合 GSPMD 的传播和 PartIR 的增量分区；README 与概览仍把新 SPMD partitioner 写成计划。

所读 `src-export-export_pipeline.cc` 已包含受选项控制的 `runShardyPartitioner`：先检查未归约轴、插入显式 reshard，再根据选项进入逐指令分区或 reshard-to-collectives 路径，并优化集合通信。文件注释还指出 AllReduce 与后续切片可能融合成 ReduceScatter。配套测试文件前 28 行明确给出 ReduceScatter，以及先切片再 AllGather 的预期 IR。

这证明固定分支具有这些转换路径，不能证明所有上层框架默认启用它们，也不能仅凭静态测试文本确认真实设备上的速度。这里没有构建或运行 Shardy 测试。

另读 `src-propagation-auto_partitioner_registry.cc`：它保存、注册和调用自动分区 callback，未注册时报告错误。这是扩展入口；仅凭这个文件不能断言仓库提供了某种全局成本优化器，也不能断言仓库没有其他优化器。

归档的 JAX 迁移文档称，传播顺序或冲突处理差异可能改变布局，导致性能回退甚至 OOM；建议用更明确的约束和 IR dump 检查。文档同时保留了“2026 年 3 月完成迁移”的时间表。本次不把这段计划文字当作已核实的实际发行状态，也不推荐读者照搬过渡期开关。精确 JAX 版本的迁移完成情况仍需另查发行记录。

## 怎样放回已有实验

第 6.2.2 的 Qwen3 算例已经让读者逐卡计算权重、激活和通信。只再加一次核对：将相同的分片约束交给固定版本编译器，检查输出布局、归约组和集合载荷是否与纸笔计算一致；不一致时先查传播和重分片，再测运行时间。可以用 Shardy 的 IR 检查做扩展，但不把 PartIR 的论文 API 写成当前 JAX 的直接用法。
