  "body": "\r\n\r\n\r\n## Purpose\r\n\r\nThis PR is the first, intentionally small, step toward fine-grained prefix cache hits for hybrid models.\r\n\r\nHybrid full-attention + Mamba models often need the full-attention cache block size to align with the Mamba state block size. Since vLLM prefix-cache matching is block-size granular today, this makes the effective cache-hit granularity much coarser than what full attention can otherwise support. The larger project is to allow prefix-cache matching at a smaller hash granularity while keeping cache block ownership and GPU memory allocation unchanged.\r\n\r\nThis PR only adds the core primitives needed by later PRs:\r\n\r\n- prefix-chain block hashes computed at `hash_block_size`;\r\n- coarser cache-group block views derived from that same prefix chain;\r\n- block-pool partial entry registration so one cache block can be looked up by a fine-grained prefix-boundary hash key;\r\n- cleanup/replacement/promotion semantics for partial entries;\r\n- tests covering partial-entry lifecycle and partial-to-full promotion.\r\n\r\nThis PR does not expose a public CLI flag, implement scheduler splitting, implement backend checkpointing, or enable full end-to-end partial cache hits by itself.\r\n\r\n## Design\r\n\r\n### Prefix-chain boundary hashes\r\n\r\n`Request.block_hashes` remains the request's list of prefix-cache hashes at `hash_block_size` granularity. Each entry is a chained boundary hash for the full prefix ending at that boundary:\r\n\r\n```text\r\nH2  = hash(parent=None, tokens[0:2])\r\nH4  = hash(parent=H2,   tokens[2:4])\r\nH6  = hash(parent=H4,   tokens[4:6])\r\nH8  = hash(parent=H6,   tokens[6:8])\r\nH10 = hash(parent=H8,   tokens[8:10])\r\n```\r\n\r\nBecause every entry already represents the whole prefix up to that boundary, a larger cache-group block view can reuse the boundary hash at the end of the larger block. For example, with `hash_block_size=2` and a cache group `block_size=6`, the full-block key for tokens `[0, 6)` is `H6`, not a concatenation of `H2`, `H4`, and `H6`.\r\n\r\nThis keeps full-block matching and partial-boundary matching on the same hash chain. It also removes the need for request-side block-size recomputation helpers.\r\n\r\n### BlockHashListWithBlockSize\r\n\r\n`BlockHashListWithBlockSize` is the compatibility wrapper that exposes a coarser block view over the fine-grained prefix-chain list.\r\n\r\nWhen `target_block_size` is a multiple of `hash_block_size`, each target block key is the fine-grained boundary hash at the end of that target block. This preserves the existing API shape for code that expects block hashes at a group's cache block size, while avoiding a second hash calculation path.\r\n\r\nExample:\r\n\r\n```text\r\nhash_block_size  = 2\r\ntarget_block_size = 6\r\n\r\ncoarse[0] = request.block_hashes[2]  # H6\r\ncoarse[1] = request.block_hashes[5]  # H12\r\n```\r\n\r\n### KVCacheBlock hash token length\r\n\r\n`KVCacheBlock` now tracks the prefix length covered by its registered hash via `block_hash_num_tokens`.\r\n\r\nThis is needed because the same cache block can first be registered at a partial prefix boundary and later become a full cache block. The block pool must know whether the current key is shorter than a newly registered key so it can replace the old partial entry instead of leaving both keys alive.\r\n\r\n### Partial entries in BlockPool\r\n\r\n`BlockPool.cache_partial_block()` registers a partial prefix-cache entry for an existing block. The lookup direction remains hash-to-block, but cleanup also needs the reverse direction:\r\n\r\n```python\r\ncached_block_hashes_by_block: dict[int, set[BlockHashWithGroupId]]\r\n```\r\n\r\nThe cache block remains the reference-counted resource. The partial-entry map is only lookup metadata attached to that resource. Eviction, reset, and promotion remove every partial entry recorded for the block so stale hash keys cannot point at freed or repurposed blocks.\r\n\r\nPartial-entry lifecycle:\r\n\r\n1. A block may be registered under a partial-tail boundary hash.\r\n2. If the same block later reaches a longer partial boundary, the old partial entry is removed and the new boundary entry is registered.\r\n3. If the same block later becomes full, the partial entry is removed and the full-block key is registered.\r\n4. Eviction/reset removes both the primary hash and all partial entries.\r\n\r\nKV-cache events are emitted for partial-entry store/remove operations using the partial token range. For a partial tail inside a larger cache block, the event describes the tail boundary rather than the whole cache block.\r\n\r\n### Scope of this PR\r\n\r\nThis PR deliberately stops at memory/block/prefix-cache primitives. Later PRs can decide where to probe partial entries and where to create Mamba state checkpoints. In particular, this PR does not change scheduler behavior, does not force chunk splits, and does not add model-backend logic for materializing partial recurrent states.\r\n\r\n\r\n---\r\n<details>\r\n<summary> Essential Elements of an Effective PR Description Checklist </summary>\r\n\r\n- [ ] The purpose of the PR, such as \"Fix some issue (link existing issues this PR will resolve)\".\r\n- [ ] The test plan, such as providing test command.\r\n- [ ] The test results, such as pasting the results comparison before and after, or e2e results\r\n- [ ] (Optional) The necessary documentation update, such as updating `supported_models.md` and `examples` for a new model.\r\n</details>\r\n\r\n"
