### 2. Context Engineering／Harness 系列：让输入组织进入缓存模型

主来源：[从提示工程到上下文工程：写好 Agent 的秘诀](/Users/boj/ring0.me/source/_posts/context-engineering.md)，2025-07-30。补充：[从 Claude Code 看 Harness Engineering](/Users/boj/ring0.me/source/_posts/claude-code-harness-genai-2026.md)，2026-04-21。

**落点：8.2.4 Chat 与 Agent 的前缀复用；3.1.3 只定义相应请求变体。**

现有大纲已说明公共前缀、工具定义、复用间隔及状态占用。增量在于解释应用怎样主动制造或破坏这些前缀：稳定内容放在前部、动态内容后置、确定性序列化、历史追加、工具输出落盘后按需取回，以及子 Agent 的独立上下文与共享上下文之间的取舍。

建议补入大纲的内容：

> 固定同一任务，对比稳定前缀、前部插入动态字段、追加更正、工具输出外置四种请求组织。测新增输入、可复用前缀、缓存驻留、文件读取及任务质量；再比较独立子任务上下文与继承父历史，检查节省 prefill 是否抵得上额外模型调用和汇总工作。

输入压缩另计摘要调用、缓存失效和后续补读，不能把“文件仍在磁盘”当作模型一定能无损使用。2026 Harness 文章的内部标记、调用者数量、失败计数和具体阈值属于其源码分析叙述，未经独立核对不作为当前 Claude Code 的实现保证。

《一场泄露看懂 Claude Code》《Claude 的 Context Engineering 秘籍》与这组重叠，不各增一项；提示词写法、Skills 教程、权限产品流程、组织管理不进入本书。

### 4. 《Groq 推理芯片：用空间换时间的把戏》：补完整的容量反例

原文：[groq.md](/Users/boj/ring0.me/source/_posts/groq.md)，2024-02-22。

**落点：4.6.4–4.6.5 的容量与专用化；13.3.1 复用此算例。**

Groq 架构与原始论文已经在资料库，不能再新增“Groq 芯片介绍”。这篇有用的是连续推导：权重放入片上 SRAM 后，长上下文和 batch 增加 KV 容量需求；增加设备容纳状态又改变切分、通信、成本与有效吞吐。

建议补入大纲的内容：

> 对固定模型分别算权重、每请求 KV、激活与工作区，改变上下文和并发数，求能容纳它们的设备数下界；随后加入实际切分与互联约束，区分最低单请求时延、SLO 内吞吐与单位产出成本。

**明确去重：** 文章中的 MSRA／FPGA 空间计算经历已经出现在《H100／4090》中，《MSRA 读博五年（二）》又是同一故事，不另算新增。

博客售价是推测，batch 增加后的吞吐有理想化外推，不能沿用为实测；“容量放得下”不保证可按比例提高吞吐。型号、精度、GB／GiB 和输入输出工作量需重新统一，既有 Groq 官方资料用于后续核对。

### 5. 《全球算力能支撑多少数字员工？》：适合作为假设审查题

原文：[digital-worker.md](/Users/boj/ring0.me/source/_posts/digital-worker.md)，2026-03-09。

**落点：13.5.2 有条件的预测与复核；可引用 11.1、11.4 已有预算。**

价值是把一条 Agent 轨迹外推到服务人数，再分别用设备、功率和费用检查。现有大纲已有资源和成本计算，这篇提供一个容易理解、也值得质疑的完整估算对象。

建议补入大纲的内容：

> 从“一名数字员工每周工作 40 小时”的假设出发，区分活跃生成、工具等待、峰值同时在线和月累计服务时长；加入 prefill、KV 驻留、环境资源及失败重做，分别求设备与供电约束下的容量区间。揭示假设改变后哪个约束先成为瓶颈。

不建议把“680 万数字员工”或 2030／2035 预测直接作为本书结论。尤其要重做输入成本近零、100 token/s 持续生成、服务利用率与工作占空比的口径；收入对应市场需求，不能与硬件产能当成同一种独立测量。长期利润率、供应链预测和社会结论不搬入正文。

### 6. FastWake 项目页：补主机等待的具体取舍

原文：[FastWake: Revisiting Host Network Stack for Interrupt-mode RDMA](/Users/boj/ring0.me/source/_posts/projects/FastWake/index.md)，2023-06-14。它位于用户指定的 `_posts/projects` 目录。

**落点：7.3.2 并发访问与延迟隐藏，作为已有轮询／事件通知段的短例。**

现有大纲提到了轮询和通知，但还可以补一个作者自己的具体实现：每核 dispatcher 轮询多个完成队列，与中断亲和性优化两种方案。比较的对象是完成发现、线程唤醒、CPU 占用和功耗，适合解释链路时延低之后谁仍在等待。

建议补入大纲的内容：

> 用 FastWake 比较忙轮询、普通中断和共享 dispatcher。给定活跃线程数、完成事件到达率及功率约束，判断何时值得占用 CPU 换唤醒时延；再标出 AI 通信路径中哪些完成由主机等待，哪些由设备侧消费。

项目页已给出论文与原 x86／ARM 实验条件；书稿若使用加速比例，应回读论文。不能把传统应用 RDMA 的收益直接套到 NCCL／GPU 发起路径。本次没有发现它在当前章内或资料对应表中已有独立落点。
