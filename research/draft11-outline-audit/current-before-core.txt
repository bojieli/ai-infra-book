# 第 1 章 初识 AI Infra
本章从云数据中心到 AI 数据中心的变化开始：大模型成为上层应用的可编程接口，系统抽象边界随之上移，底层设计围绕模型执行重新组织。再从集群向芯片逐层展开，把容量、算力、带宽和延迟变成可以计算的约束，解释模型的变化怎样沿执行、存储和互联传到整个数据中心。
在掌握基本估算之后，回看 Google TPU、作者参与的可编程网卡研究，以及 Unified Bus 的设计经历。每个案例都从当时的需求与可用条件出发，解释一个设计为何出现、它改变了什么，以及还留下了什么问题。

### 1.1.1 可编程性与系统抽象边界上移
**占位 AB-01：** 从 OSDI／SOSP 名称中的 Operating Systems 引出 OS 的通用编程抽象，再讲应用如何通过指令、上下文与工具调用组织大模型能力，使可编程性（programmability）的主要表达层和系统抽象边界上移。由此解释设计重心从通用执行、多租户与虚拟化，转向模型计算、状态与多卡协作；第 12 章接回通用工具环境。详见[系统抽象边界调研](../research/system-abstraction-boundary/report.md#opening)。
### 1.1.2 集群、芯片与软件全栈

继续放大到主机与芯片：CPU／主存、GPU／HBM、网卡和本地存储怎样连接；GPU 内部又有哪些计算单元、寄存器、片上存储与数据通路。图上明确画出 CPU—GPU、GPU—GPU 和超节点之间的实际路径。此处先建立资源与距离的直觉，第 4–7 章再展开内部机制。

## 1.3 纸笔估算与推算实验
### 1.3.1 从设计问题建立简化模型
用“H100 与 4090 应怎样选择”说明 back-of-the-envelope computation 的用途。先确定模型、输入输出、batch、质量与延迟目标，再沿物理图计算：权重、KV／递推状态和工作区能否逐卡放下；每阶段有多少 FLOPs；权重、历史状态和新状态分别经过哪些存储与通信接口。驻留字节是容量需求，读写字节是一次执行的流量，二者分别记录。
第一章就给出计算方法：容量先检验 `M_weight + M_state + M_workspace ≤ M_available`；单段计算时间至少为 `FLOPs / F_precision`，HBM 服务时间至少为 `(读字节 + 写字节) / B_HBM`，通信按算法的消息与轮次估为 `nα + V_link / B_link`。对可能并行且不争用同一资源的工作取最大值，对必须先后执行的阶段沿依赖相加；总显存与总线速不能绕过局部瓶颈。
### 1.3.2 解码的计算与读取下界
完成一个可跟算的示范：假设 70B 权重按每参数 1 byte 驻留，低并发解码每步读一次权重，70 GB ÷ H100 SXM 的 3.35 TB/s 标称 HBM 带宽约为 20.9 ms。再用运算量／计算上限估另一项时间，下界至少取必要资源时间与依赖路径中的最大值；各阶段能否重叠仍需具体判断。由此比较加算力、加带宽、降低字宽和增加复用。

### 1.3.3 从第一次估算到有效预测
在前一例直接引入 Roofline：算术强度 `I=FLOPs/V_HBM`，可达吞吐上界为 `min(F_precision, B_HBM×I)`；拐点 `F_precision/B_HBM` 说明何时增加计算单元才可能有用。再在两卡交接中数每条链路的实际流量，求最慢一段和同步轮次的时间，建立最窄链路与关键路径的分析方法。

# 第 2 章 模型架构
第一章已经建立物理层次和资源约束，本章练习怎样从模型算出这些约束的输入。先沿 Qwen3-8B Dense 走完一层，再以 **DeepSeek-V4 与 Kimi K3** 为主要比较对象，解释压缩历史、选择性访问、有限状态和专家稀疏分别改变了什么。V4 先用 Flash 配置跟算，再按 Pro 的真实配置扩展，不能按总参数量等比例换算。
每种结构都分别计算 prefill 和 decode：本次处理多少 token、完成多少 FLOPs、常驻权重与状态多少字节、每步实际读取哪些权重与历史、更新哪些状态。计算形状和最低必要流量先算清，再说明融合、分块与缓存会怎样改变实际 HBM 访问；容量与访问量分别成列。正文展开代表层与一个完整请求，完整逐层清单交给实验，最后把结果放回 Chat 与 Agent 的使用条件。
## 2.1 序列模型与 Transformer
### 2.1.1 递归状态与序列依赖
从四个 token、三层的小计算图开始，横轴画序列位置，纵轴画网络深度。RNN 在时间方向将历史压入固定宽度的状态 `h_t=f(x_t,h_(t−1))`；下一位置必须等前一位置的状态。先数每步矩阵乘、状态大小与依赖，再问长历史的哪些信息还能被后续位置直接取回。
### 2.1.2 注意力与并行序列计算
用“将时间方向的递推转向网络深度”作直观引子，讨论把 Transformer 想成转了 90 度的 RNN，哪些地方能帮助理解。Transformer 的第 l 层从上一层各位置的表示取信息，已知输入时，同层各位置不必串行等待彼此；深度方向仍逐层推进。
在同一张图上补出注意力跨位置的边，说明这不只是旋转原图：通常各层参数不同、跨位置交互采用内容相关的加权访问，状态也没有被压成同一个固定宽度向量。用 `QKᵀ` 和 `AV` 的小矩阵计算这些新增工作，比较依赖缩短与历史保留的代价。2017 年的 encoder–decoder 背景简述后转入现代因果模型。
### 2.1.3 从序列训练到逐 token 生成
已知整段输入时可以并行处理多个位置，生成下一个未知 token 仍依赖先前输出。用同一图说明缓存 KV 后，Transformer 也可按 token 递推执行，但全历史注意力的状态随长度增长；采用特定线性注意力才能改为固定大小的统计状态，不把两者当成同一个代数等式。这个区别为后面的 Kimi K3 KDA、V4 压缩历史和 prefill／decode 的不同执行方式铺垫。

## 2.2 Qwen3 Dense：一层模型的完整计算
### 2.2.1 模型配置与张量尺寸
固定 Qwen3-8B 的官方配置：36 层、隐藏维度 4096、32 个 Q 头、8 个 KV 头、头维度 128、FFN 中间维度 12288。用 B 表示请求数、S 表示已有历史、P 表示每条请求本次输入的 token 数：prefill 的投影输入为 `X[BP,4096]`，每序列生成一个 token 的 decode 为 `X[B,4096]`。从 B=1、S=0、P=8192 的完整 prefill 开始，再算已有 8192 历史后的单步 decode。
### 2.2.2 Q、K、V 与注意力输出
按数学右乘记号列 `Wq[4096,4096]`、`Wk/Wv[4096,1024]`、`Wo[4096,4096]`，对照代码权重的转置存储。把投影结果拆成 32 个 Q 头和 8 组 K、V，说明每个 KV 头服务 4 个 Q 头；接着计算 QKᵀ、Softmax、乘 V 与输出投影。QK Norm、RoPE 和 mask 放到实际位置，算 FLOPs 时区分完整矩形计算与利用因果三角的实现。
### 2.2.3 前馈网络与单层工作量
展开 SwiGLU 的两次升维与一次降维：`[m,4096]×[4096,12288]` 两路，经 SiLU 与逐元素乘后，再乘 `[12288,4096]`。三组权重共 150,994,944 个参数，矩阵乘约 `301,989,888m` FLOPs；比较注意力投影、序列交互和 FFN，观察上下文变长时占比如何变化。残差与 RMSNorm 的计算和流量单列。
### 2.2.4 从一层到完整模型
将 36 层与词嵌入、输出头连接起来，分别列常驻权重、状态容量、prefill FLOPs、decode FLOPs，以及对应的权重／状态读写。投影与 FFN 每层约 `385875968×BP` FLOPs；因果注意力有效位置对数为 `B×[PS+P(P+1)/2]`，QK 与 AV 合计每对约 `4×32×128` FLOPs。prefill 是否计算全部位置的输出头、内核是否跳过因果上三角分别说明，不能把所有后端写成同一执行量。
对权重读取先按一轮理想复用计量，再加入实际分块与缓存假设；prefill 不等于每个输入 token 都从 HBM 独立重读整份权重。对注意力区分逻辑上的历史参与次数与物理读写：分块融合会改变历史重读及中间矩阵写回，具体实现留到第 5 章验证。用同一张简洁计算表贯穿各模型，完整算式另附[资源计算笔记](../case-studies/model-resource-accounting.md)。

## 2.3 注意力状态：共享与压缩
### 2.3.1 KV cache 与历史复用
从不保存历史的逐步生成计算出重复工作，再得到 KV cache。Qwen3-8B 的 BF16 KV 每个历史 token 占 `2×36×8×128×2=147456 bytes`，即 144 KiB；8192-token 历史占约 1.125 GiB。一次普通全历史 decode 至少需要逻辑上访问这份历史，并新增 144 KiB 状态；是否全部从 HBM 读取、KV 头间能否有效复用，取决于缓存层次与内核路径。
接着区分“存多少”和“累计读多少”：生成 G 个 token 时，历史读取项按 `144 KiB×[G×S+G(G−1)/2]` 累加，新 token 当步访问与写入另计。batch 无前缀共享时各序列状态相加，理想权重复用则可能由整个批次分摊；不能把状态大小或每 token 的数字直接当成整项任务流量。
### 2.3.2 MHA、MQA 与 GQA
在相同隐藏维度与上下文下改变 KV 头数，比较状态容量、读取字节与模型质量。共享 KV 头减少状态宽度，但 Q 头仍要完成各自的序列交互，不能直接用缓存缩减倍数代表全部注意力计算缩减倍数。
### 2.3.3 Kimi K3：MLA 的潜变量与全局访问
直接用 Kimi K3 的 Gated MLA 层：按报告、配置与参考代码画 512 维潜变量、Q 投影、上投影／权重吸收和输出门控。MLA 使用 NoPE，但当前参考代码仍保留参与 QK 的 64 维额外分支，只是不做旋转位置编码；不能仅由 NoPE 推断缓存少了这 64 维。先把必要表示保存量算出来，再比较吸收式与显式展开式执行的矩阵工作及中间读取。
按保留潜变量与额外分支的紧凑 BF16 教学路径，24 层历史为 `24×S×(512+64)×2` bytes；8192 历史约 216 MiB。已归档的 Hugging Face 参考代码实际上缓存展开后的 K／V，同样输入约 11.25 GiB，不能把紧凑路径的数值当成这份代码的分配量或生产测量。这些都只算 MLA，KDA、短卷积、前缀检查点和工作区随后补齐。全局层仍访问全部潜在历史，容量压缩没有消除随长度增长的读取。

## 2.4 注意力计算：稀疏化与混合结构
### 2.4.1 局部窗口与选择性访问
沿长上下文中被读取的历史位置，区分局部窗口、显式稀疏选择与压缩历史。用 V4 的窗口、压缩条目与索引器引出三种工作，分别计算保存、选择和读取；全局历史缩小、实际读取变少与新增索引工作需要同时计量。
### 2.4.2 DeepSeek-V4-Flash：CSA 与 HCA
采用正式名称 DeepSeek-V4-Flash，固定 43 层、隐藏维度 4096、64 个注意力头、每头 512 维。逐段展开 Q 的 `[m,4096]→[m,1024]→[m,64,512]`、共享 KV 的 `[m,4096]→[m,512]`，以及分 8 组的低秩输出投影；与上一节 K3 MLA 的潜变量、全局访问及门控分别比较。
沿配置逐层比较窗口 128、压缩比 4 的 CSA 与压缩比 128 的 HCA。主干为 2 层纯窗口、21 层 CSA、20 层 HCA，MTP 另计。以 BF16 参考缓存为例，一层 CSA 保存窗口与 `floor(S/4)` 个 512 维压缩条目，另存同数量的 128 维索引条目；每步主注意力最多取窗口加 512 个压缩条目，索引打分仍需扫描压缩索引历史。HCA 保存并访问窗口加 `floor(S/128)` 个压缩条目；尚未完成的压缩块与滑动状态另计。
分别计算 prefill 的各位置、decode 的当前查询、压缩器与索引器 FLOPs，列状态的常驻、读取和更新量。参考实现模拟量化但以 BF16 保存的缓存，与真实压缩存储格式分别核算；不能用最终 top-k 条目数代替全部访存，也不能用保存量直接代替每步读取量。V4 的节省来自哪些项、在哪些上下文和 batch 下出现，由计算结果说明。

## 2.5 参数稀疏化：混合专家模型
### 2.5.1 从稠密 FFN 到专家路由
以 Qwen3 的稠密 SwiGLU 为起点，将容量分给多个专家，再为每个 token 选择少数专家。沿 V4 与 K3 的路由、共享专家和负载分布，解释总参数决定权重驻留，激活参数只近似反映部分计算；批内访问的不同专家集合决定必要权重读取，路由与跨设备交换另算。
### 2.5.2 DeepSeek-V4-Flash 的专家计算
固定每层 256 个路由专家、每 token 选择 6 个，以及 1 个共享专家；专家中间维度为 2048。逐个专家展开两次 `[t_e,4096]×[4096,2048]` 和一次 `[t_e,2048]×[2048,4096]`，其中 `t_e` 是该专家实际收到的 token 数。用同一批 token 比较稠密大矩阵与多个不等长专家矩阵，计算约 25.17M 参数／专家及激活计算；前三层哈希路由与后续评分路由分开。全模型约 284B 总参数、13B 激活参数采用报告定义，不能仅以专家矩阵求和冒充精确总量。
### 2.5.3 状态、专家与系统协作
**占位 TC-03：** 补 MoE、GQA／MLA 与稀疏状态分别减少的资源及相互代价。 详见[成本下降调研](../research/token-cost-2023-2026/report.md#architecture)。

## 2.6 模型规模与使用条件
### 2.6.1 参数规模与设备容量
**占位 TC-02：** 补能力密度提升及“小模型接近旧大模型”的有条件对照。 详见[成本下降调研](../research/token-cost-2023-2026/report.md#density)。
从常见的 7–8B、约 30B、70B 与 235B 出发，判断它们在什么硬件和业务条件下形成部署上的“甜点”。先按精度计算权重，再扣除 KV、工作区、并行复制与运行余量：约 8B 的 BF16 权重约 16 GB，适合讨论 24 GB 卡的单实例空间；约 30–32B 的 BF16 权重为 60–64 GB，理想 4-bit 权重为 15–16 GB；70B 的 BF16 权重约 140 GB，8-bit 约 70 GB。每种情况都要加回量化元数据、较高精度部分和状态，才能判断一张或几张卡是否适合。
用 Qwen3-235B-A22B 与八张 80 GB 卡计算：名义 BF16 权重约 470 GB，均分约 58.75 GB／卡；剩余容量还要承担状态、工作区和复制。再换为八张 24 GB 卡或不同精度，解释为什么“八卡甜点”必须带上卡型、格式、上下文与并发。Qwen3 的约 30B 型号是 MoE，32B 是 Dense；总参数用于驻留，激活参数用于部分计算，不能仅看数字接近就视为同一任务。
部署可行点、满足延迟和吞吐的经济点、模型团队实际选择该规模的原因分别讨论。Llama 1 明确考虑训练与推理预算，Qwen3 展示多个规模；这些资料不证明“7B 是为 4090 设计”或“235B 唯一由八卡显存决定”。结合能力目标、训练数据、预算和服务范围，把硬件容量作为设计约束之一。
### 2.6.2 层数、宽度与专家划分
固定近似总参数预算，分别改变深度、隐藏宽度、FFN 比例、注意力头和专家数量。更深的模型增加逐层依赖与 KV 层数，更宽的矩阵改变分块与 Tensor Core 利用，更多更小的专家改变每专家 token 数、路由和 EP 的通信；较少激活专家也会改变能力和训练行为，不能只追求最小 FLOPs。
沿 Qwen3-8B 和 235B 的实际配置手算候选：128 个专家可以均匀分到八卡，但四个 KV 头不能在 TP=8 时继续无复制地均分为完整 KV 头，常见实现需要复制或改并行组合。整数可分只是起点，再用第 1 章方法比较逐卡峰值、矩阵形状、带宽、延迟与质量；完整 TP／PP／EP 方案在第 6 章展开。

# 第 3 章 推理与训练负载
第二章算清了模型一次执行的矩阵与状态，本章继续问这些执行怎样组成实际工作。先看较容易理解的推理：prefill、decode，以及 Chat、Agentic、Real-time 三类请求；reasoning 改变的是其中的计算预算、长度与依赖。
理解生成之后，再讲训练：预训练与中期训练持续从数据学习，SFT 调整目标行为，RL 则把生成、环境反馈和梯度更新接成循环。训练部分再结合 Llama、Qwen 与 DeepSeek 的公开训练资料，比较规模、数据和使用时计算的分配，解释 scaling law 怎样帮助作出设计判断。
## 3.1 推理负载
先算一次模型执行，再比较 Chat、Agentic 与 Real-time 的请求和依赖。输入输出不仅包括文本；图像、音频和视频还需统计像素、帧、块与实际传输字节。
### 3.1.1 Prefill 与 Decode
沿 Qwen3-8B 和 V4-Flash 的第二章算例，把整段输入代入实际矩阵，计算 prefill 的投影、注意力与专家工作。前缀命中后只处理未缓存部分，但仍可能读取既有状态；最大上下文长度与真实新输入长度分别统计。
对比单 token decode 与批量输入的矩阵形状。低并发下，一次读取权重只服务少量 token；增加 batch 可以摊薄权重读取，随后 KV、容量、专家分布与等待又可能成为限制。prefill 常偏计算密集、decode 常偏带宽密集，是可由形状检验的起点。
分别计算输入处理、生成、排队与状态寿命。定义首 token 时间、逐 token 时间与完整请求时间；reasoning 服务还需区分首个内部 token、首个对用户有用的输出。将各阶段换成同一请求分布下的需求，为第 9、10 章的批处理和 PD 分离准备输入。

# 第 4 章 加速器架构
第 3 章已经给出了具体推理与训练负载，这一章把同样的矩阵、字节和并发放到芯片上。沿计算单元、存储层次和数据通路逐层比较 NVIDIA、昇腾与 Apple，解释不同资源配比在什么条件下有利。
NVIDIA、昇腾、Apple 在每一层同时出现；代际变化也在这一层解释。每项设计先给当时的代表负载及旧资源限制，再分析新增单元或通路怎样改变计算、数据移动和同步，最后计算面积、功耗、精度或软件复杂度的代价。Ampere、Hopper、Blackwell、Rubin 沿同一问题比较，昇腾与 Apple 也采用这一顺序。厂商明确披露的设计动机与本书的约束推断分别注明。

本章切分的是同一芯片内的计算与数据：沿真实矩阵选择分块、布局和融合，减少寄存器、片上存储与 HBM 之间的搬移。第 6 章将同一推算扩到卡间，第 7 章再扩到超节点之间。贯穿对象包括矩阵乘—Softmax—矩阵乘，以及第 2 章的 Qwen3／V4 代表链。CUDA／Triton、Ascend C 与 Metal 在同一问题上对照，读者最后应能解释一次优化为什么有效，以及移到另一种硬件上需要重新考虑什么。

## 5.3 算子编译器与编程抽象
### 5.3.1 手工优化与融合组合
从前一节已经调好的独立算子出发，加入归一化、激活、残差和量化转换，观察原有接口与中间写回怎样阻碍进一步融合。单算子做成高效内核以后，跨算子分块、布局、生命周期和融合边界仍需共同选择；这是引出作者 AKG 工作与算子编译器的主要问题。
用含 k 个算子的线性链说明，仅相邻融合边界就有 `2^(k−1)` 种形式划分，尚未加入 tile、布局和动态形状。合法性与硬件约束会排除许多组合，但手工枚举和维护仍迅速变得昂贵。编译器负责表达依赖、选择可行组合并生成代码，不能许诺自动得到全局最优。
用 Korch 的历史子图说明另一层选择：InstanceNorm 拆开后再与 ReLU、Pad 组合，kernel 从三个变四个，整条链仍可能更快。由此区分算子的数学边界、并行与访存特点，以及真正的 kernel 边界；候选的串行实测时间、切图与后端限制一起决定结论。[案例与适用条件](../case-studies/kernel-orchestration-and-quantization.md)
### 5.3.2 典型模型的算子与融合机会
安排一张“模型—算子—形状—融合机会”表：小尺寸序列模型、Qwen3-8B Dense、Qwen3 MoE、DeepSeek-V3／V4-Flash、Kimi K3。每行沿真实计算路径列投影、归一化、位置编码、注意力、FFN／专家、路由、状态更新和残差；给典型输入尺寸、逻辑算子数、可融合边界与主要中间张量字节。新模型带来的压缩器、索引器、线性状态和 mHC 等算子由这张表自然引出。
Qwen3 以固定 vLLM 提交核对，V4-Flash 以官方参考实现核对；V4／K3 的服务侧缓存与执行再接到已公开的 SGLang 实现，扩写时固定对应提交并补实际 trace，不把早先归档提交的覆盖范围当作引擎当前的支持范围。模型层逻辑算子、框架节点、库调用与实际 GPU kernel launch 分开计数，静态代码不能证明启动次数。完整清单和追踪放入实验材料，正文只展开两条代表链。
### 5.3.3 图变换、分块与自动调优
沿 Qwen3 的 QKV 投影—QK Norm—RoPE—注意力，以及 V4 的压缩／索引或 MoE 链，讲依赖、融合合法性、布局和分块怎样共同决定代码。用一个具体变换引入多面体与 isl，再比较 AKG、TVM／TensorIR、TileLang 等表达与搜索方式；计算编译调优成本在多少次执行后才能摊薄。
区分三个问题：多面体／isl 表达迭代域、访问和依赖，用来判断变换是否保持语义；硬件与成本模型估计候选运行得怎样；实际 profiling 校准缓存、寄存器溢出、并发和流水损失。性能预测失准不等于依赖分析失效，MFU 不到 100% 也不能直接证明是哪一个模型错了。
以 TVM 的规则 schedule 作起点，再比较固定模板参数搜索、Ansor／MetaSchedule 的结构与参数搜索，以及让 LLM 修改 schedule 或算法实现。MetaSchedule 本身已经通过真实硬件测量更新成本模型；不能把“传统编译器没有反馈”作为 Agent 的优势。固定空间较容易控制合法性和搜索成本，但可能漏掉新融合与算法；开放生成空间更大，验证与调优成本也更高。
接回当前 vLLM 的 SiLU+Mul→量化路径：从 v0.6.0 的手工激活算子，走到编译 pass 对跨算子模式的匹配。以 Qwen3 的 `[1024,24576]` gate-up 输出计算省掉的 48 MiB 中间读写，再单独推算活动张量峰值。编译器可见的表达也可能被 Inductor 自行融合，因此比较实际图和 trace；禁用某个自定义融合 pass 不等于恢复了两个独立 kernel。

# 第 6 章 超节点
第 5 章在芯片内部切分矩阵，以片上复用减少访存。本章将同样的思路扩到多张卡：给定真实模型、请求与一组硬件，权重、KV、激活和计算应该怎样分配，切开以后需要交换什么。
用 Qwen3-8B、Qwen3-235B-A22B、DeepSeek-V4-Flash，再到 V4-Pro 与 Kimi K3 反复推算。每次都先算逐卡容量、每步权重与 KV 读取、运算和通信，再找出限制，决定采用 TP、PP、DP、EP 或其组合。超节点硬件在解决这些具体限制时出现。
## 6.1 从单卡负载到多卡方案
### 6.1.1 贯穿本章的模型与硬件
复用第 2、3 章配置：Qwen3-8B Dense；235B／22B 激活的 Qwen3 MoE 与 284B／13B 激活的 V4-Flash；约 1.6T／49B 激活的 V4-Pro 与 2.8T／104B 激活的 Kimi K3。DeepSeek-V3 的 671B 总参数作为历史过渡。它们代表不同规模与结构，不能写成参数量完全相同的模型。
从单卡、八卡服务器到更大超节点，固定 GPU 可用显存、有效矩阵性能、HBM 带宽、卡间单向带宽与小消息延迟；模型、精度、请求长度和并发共同构成实验输入。先用一组条件完成推算，再换硬件检验原选择是否仍然成立。
### 6.1.2 容量、带宽与执行时间
逐卡检查 `权重＋KV／递推状态＋激活＋工作区 ≤ 可用内存`。分别数每步实际激活专家的权重读取、所有活跃序列的 KV 读取、算子 FLOPs，以及每条必要链路的字节和启动次数；总参数、激活参数、实际读取字节不能相互替代。
给出第一遍时间下界：本地计算 `F/P`、本地读取 `(W_read+KV_read)/B_mem`、路径传输 `V/B_link` 与必要同步；共享链路合并流量，串行依赖沿实际时序累加。以最忙的设备或链路定位瓶颈，再决定该减少哪项工作。
### 6.1.3 Prefill、Decode 与训练的不同切分
同一模型分别代入一段 prefill、一次 decode 和一轮训练。低并发 decode 的小消息与逐层依赖，不能按大矩阵 prefill 的带宽效率估计；训练另有梯度、优化器和反向通信。增加副本主要改变吞吐，把一次计算分到多卡可能改变容量与单请求延迟，两者从计算结果比较。

## 6.2 Dense 模型：TP、PP 与 DP 的选择
### 6.2.1 Qwen3-8B 的副本与数据并行

### 6.2.2 张量并行与层内数据交换

### 6.2.3 流水线并行与组合方案

## 6.3 MoE 模型：EP 与混合并行
### 6.3.1 两个 200 多 B 模型的逐项比较
固定 Qwen3-235B-A22B 的 94 层、4096 隐藏维度、128 选 8 路由专家、1536 专家中间维度，以及 V4-Flash 的 43 层、4096 隐藏维度、256 选 6 加共享专家、2048 专家维度。Qwen 的 GQA 与 V4 的混合压缩注意力分别核算 KV，不能由接近的总参数量推断相近的状态与通信。

### 6.3.2 专家并行与路由流量
把专家分配到不同卡，计算每个专家收到的 token 数、局部矩阵、共享专家工作以及 dispatch／combine。按 token 实际选择的远端设备计流量：同一设备承接多个被选专家时可以复用或合并传输，不能直接把 top-k 当成 k 个不同目的地。接着比较 EP、专家内部 TP、attention TP 和服务副本的组合，明确各通信组的成员与数据所有权。
以 Qwen3-235B 的单专家 BF16 权重 36 MiB 为起点，区分总驻留、每 token 选中的专家和批内独立活跃专家。8 个输入 token 若都选同 8 个专家，理想一次读取涉及 288 MiB；均匀独立路由的期望则约为 1.815 GiB。再用真实路由重算逐卡读取与每专家矩阵：decode 的复用收益与 prefill 的计算长尾可能指向不同放置，不能仅按激活参数或平均 FLOPs 决定 EP。
### 6.3.3 万亿参数模型的结构差异
V4-Pro 与 Kimi K3 分别沿自己的层数、注意力状态和专家结构推算。K3 的 896 选 16 路由专家在 3584 维潜空间工作，另有 2 个全宽共享专家，首个 dense 层和 MTP 单独计数；路由激活应按实际跨卡表示计量，不能直接套 7168 维全宽传输。总权重、实际激活矩阵、专家粒度、状态和同步次数一起决定放置。

### 6.4.3 环与树的通信代价

以 p 个参与者、每个输入 M 字节的简化 ring all-reduce 为例，写出 `T ≈ 2(p−1)α + 2(p−1)M/(pB)`，说明轮次项与传输项从哪里来。先用小例子比较消息大小改变后的选择，再由实际拓扑和归约成本修正；公式不替代所有集合算法。

### 7.3.2 并发访问与延迟隐藏

## 8.1 从数据中心到端到端交互
从作者参与过的图片精修、ASR／TTS 传输与 Agent 交互进入，每条路径都从提交输入画到获得可用结果；找出值得优化的等待。
### 8.1.1 图片精修与语音服务的输入输出
图片精修需要保留更多原始信息用于后期调整，因此输入可能是几十 MB 的 RAW，成片回传又有数 MB。背景在这里一笔带过，随即标出上传、云端处理与下载的字节和时间；具体文件大小由输入记录提供。

### 8.1.2 图片精修的传输与计算
先用明确标注的教学条件计算：30 MB 输入、5 MB 成片、上行 20 Mbit/s、下行 100 Mbit/s、RTT 100 ms、云端处理 0.3 s。连接已可用且服务收齐原图再处理时，上传与下载的串行发送时间分别约 12 s、0.4 s；单次请求的简化时间预算约 12.8 s，另加排队、协议与未计入的本地处理。上行瓶颈下，把模型处理从 0.3 s 降到 0.03 s，只省下约 0.27 s。
随后改变上行速度、无损压缩的实得比例与编解码开销、分块能力和输出质量，比较减少字节、提前处理与增加算力的收益。先返回预览与完整精修成片分别计时；只有模型依赖允许时，才把上传与分块处理重叠，不能把预览提前等同于成片完成。

# 第 9 章 单实例推理
第 2、3 章算清了模型与请求，第 4–8 章说明了设备和传输条件。第 6、7 章已确定实例可能使用的多卡切分，本章在给定实例资源上进一步组织请求：用权重复用推导批处理，用 KV 容量与寿命推导分页和缓存，再把 Chat、Agentic 与 Real-time 的不同约束放回服务选择。
贯穿主例采用 Qwen3-8B：先在 RTX 4090、H100 和作者 M2 Max 的对应精度下估计，再改变请求而保持模型不变。长状态与专家问题用 Qwen3-235B-A22B／V4-Flash 复算；H20 加入阶段与设备选择。输入与来源见[业务推算笔记](../case-studies/inference-training-scenarios.md)。单实例可以包含多张设备，本章关注一套引擎内部的组织。
## 9.1 批处理与请求调度
### 9.1.1 请求执行时间与状态占用

### 9.1.2 batch 与权重复用
从权重复用和矩阵形状解释 batching，计算它节省的读取；随后加入等待凑批、请求长度差异和显存容量，看到吞吐与延迟的取舍。

### 9.1.3 从固定批次到连续批处理
让短请求先结束、长请求继续，观察空槽位，再介绍 Orca 等系统的迭代级安排。比较旧批次和新请求如何交接。
实际入口使用 vLLM 或 SGLang：它们负责模型执行、请求批处理、KV 管理与服务接口，分别沿调度日志看新请求怎样进入下一步。Ollama 的本地模型管理与 runner 在 9.4 出现；TensorRT-LLM 是面向 NVIDIA 的 LLM 推理栈，在图执行和内核选择处对照。TensorRT 则是更通用的网络优化与执行工具，图像编码器可以使用它，不将二者当作同一产品的两个简称。

从 Agent 生成一份文件读取参数引入 XGrammar：把可预先判断的 token 缓存下来，仅对依赖完整语法栈的部分做运行时检查，再与 GPU 前向重叠。沿 SGLang 2024 集成、vLLM 2025 的 logit processor 与当前语法管理路径，比较冷 schema、编译等待和每步掩码；Ollama 的本地 JSON schema 入口作对照。有效格式与参数含义、任务成功分别评价。
用 Qwen3-8B 的 151,936 词表和 64 请求算一批约 1.159 MiB 的位掩码，再给 CPU 每行工作与 GPU 前向时间，找采样前的汇合点。字节不多不代表 CPU 开销可忽略；当前填充路径也不总按线程数并行。实验 9-2 用实际 trace 校准，[计算与版本条件](../case-studies/structured-generation.md)供扩写查用。
连续批处理还会改变同一请求遇到的矩阵形状和归约切分。接回第 5 章的数值对照，用 SGLang 的确定性路径和 vLLM batch invariance 说明为何温度设零仍未必复现；固定归约、请求种子与兼容后端各解决什么问题，又牺牲哪些执行选择。比较[历史与当前版本](../case-studies/rl-state-and-reproducibility.md)，完整实验放在 11-9，与跨引擎 logprob 和 Routing Replay 连起来。
### 9.1.4 Prefill 干扰与分块执行
用长 prefill 插入 decode 的时间线引出 Sarathi-Serve 的分块安排。把 Qwen3-8B 的 8K 输入切成 512-token 块，首块与末块分别有 131,328 和 4,063,488 个有效注意力配对：新 token 数相同，历史工作不同。沿[推算笔记](../case-studies/chunking-and-state-transfer.md)比较等待、矩阵效率、提交频次与历史读取；配对数不直接等于耗时或 HBM 访问倍数，固定 token 预算需要按实际执行时间校准。
用 NanoFlow（OSDI 2025）的算子级 nano-batch 流水说明如何重叠不同请求的计算、访存与通信。Qwen3-8B 一层 BF16 FFN 权重为 288 MiB，256-token batch 切成两个 128-token 微批后，若没有跨微批缓存命中，逻辑权重读取增至 576 MiB，数学工作不变。沿[时序算例](../case-studies/resource-sharing-and-placement.md)比较仅切分、理想重叠与实际争用；论文的高吞吐分析不能直接外推到 batch=1 或长 reasoning。第 10 章再改变阶段放置，同一请求未就绪的 KV 依赖始终保留。
接第 8 章的截图：视觉编码时间不能只用语言 token 预算约束。用 TriInfer 的 image／token 两种预算，对照 vLLM／SGLang 的实际调度，先测独占 E、独占 D，再看同卡并发是否超过 decode 步间隔；多个 stream 仍可能争用同一芯片。第 10 章才比较独立编码资源，原请求的 E→P 依赖保持。
### 9.1.5 动态批次与图重放
承接第 5 章，把图分桶、padding、分段和回退放进同一调度过程。图缓冲会与 KV 竞争容量，最终用服务结果比较。

### 9.2.4 Chat 与 Agent 的前缀复用

### 10.2.1 Prefill 与 Decode 的资源冲突

实验入口采用 SGLang 的 PD 服务与实际 KV 传输后端，或固定 vLLM 的分离式 prefill connector。推理引擎安排请求，Mooncake／NIXL 等承担相应数据通路，不能把传输库当成完整服务。先检查两端模型、KV 格式和设备支持，再选择能运行的组合；A100＋H20 的硬件推算与特定版本是否支持这一部署分别记录。

再把第 8 章的视觉输入接到 PD 之前：用 vLLM 2025 EPD 与 SGLang 2026 EPD 比较编码共置、独立 E→PD、E→P→D。沿同一 Qwen3-VL-4B 截图算 EC 交接及其后产生的 KV；编码阶段可独立选择并行方式，单图与多图、缓存命中和视觉突发分别判断。公开 4／5／6 卡成绩保留资源差异，不能把额外卡数的收益全部归给分离。
### 10.2.2 A100 与 H20 的阶段分工
案例采用 A100 80 GB SXM 做 prefill、H20 SXM5 96 GB 做 decode。先分别看两卡在相同模型、精度和请求形状下的两个阶段，再决定是否这样分工；两池都执行 attention 和 FFN，也都需要相应模型权重。比较共置、同构 PD、A100→H20 异构 PD 与角色互换。先用 Qwen3-8B 的实际 KV 与两个阶段工作量计算，再换 Qwen3-235B／V4-Flash 的状态和专家路径；增加前缀命中、reasoning 输出或 batch 后重新选择角色与池规模。H20 未取得的精确规格保留未知，阶段效率用相应 GEMM 与请求测量校准。
### 10.2.3 KV 交接与收益边界
**占位 TC-14：** 补 PD 分离、专家通信与异构资源对成本的影响及交接代价。 详见[成本下降调研](../research/token-cost-2023-2026/report.md#serving)。
把实际模型的 KV 大小、传输路径、格式转换、双份暂存与两侧排队纳入完整请求。Qwen3-8B 在 8K 长度的 BF16 KV 为 1.125 GiB；原有 1 GiB 教学算例用于检查算术，随后全部代入模型值。按请求吞吐求池配比，画出分离开始值得的位置。
先沿案例算一笔 KV：同构 GQA 的 32 层、8,192 token、8 个 KV 头、128 维、每元素 2 byte，得到 1 GiB。人为给定有效单向带宽 25 GB/s，仅载荷传输约 42.95 ms；再加格式转换、接收缓冲与排队。这是条件式计算，不能标成 A100／H20 的实测。沿真实 PCIe／NIC／RDMA 或 host staging 路径计算，不能假定跨代设备直接通过 NVLink 互联。
两侧能力都换成相同请求分布下的 requests/s，检查 `到达率 < min(P 池服务率, D 池服务率, 共享链路带宽 / 每请求平均 KV 字节)`，再扫描池配比与延迟。不能拿两种 token/s 直接相除当设备配比。首 token 的产生位置、后续间隔和完整请求时间分别比较，部分 KV 与计算重叠时只累加暴露的等待。
将 Qwen3 的 1.125 GiB KV 代入假设有效单向带宽 11 GB/s：独占传输下界约 110 ms，8 requests/s 需约 9.66 GB/s，16 requests/s 则需约 19.33 GB/s。前者满足平均速率条件也不表示没有可见等待，后者即使两池有空闲算力仍会积压；接收完成前的双端状态也要占用容量。

## 10.3 AF 分离：KTransformers 的异构执行
AF 指 attention／FFN 的分工。本节从 KTransformers 的同机 CPU／GPU MoE 执行讲起，再推到跨机 AF 池化；每一步都先确定哪些算子与状态在哪里，再算需要来回交接多少次。
### 10.3.1 专家驻留与算子放置
从 MoE 总参数与激活差异进入 KTransformers：对照“把专家权重搬到 GPU”和“让 CPU 使用本地 DRAM 就地计算专家”。画清 attention、路由、共享／路由专家、其余 dense 层与 KV 的放置；热点专家可能驻留 GPU，prefill 与 decode 也可能采用不同配置。由此解释 AF 的切分位置，不能把一个项目概括为所有 attention 永远在 GPU、所有 FFN 永远在 CPU。
结合 SGLang 2025 年的 KT 集成预览与当前 wrapper，把框架分工落实为提交 CPU 专家、并行执行 GPU 专家、同步合并结果。它与第 9 章的 GPU 权重预取分别计算；CPU 专家使用的格式、线程和物理专家映射也进入记录。[执行路径与算例](../case-studies/weight-offload-execution.md)连接容量和实际服务能力。

## 10.4 专家放置与负载均衡
### 10.4.1 路由倾斜与设备负载
分别使用 Qwen3-235B 和 V4-Flash 的路由记录，把 top-k、专家宽度、共享专家及批内复用代入每卡和每链路工作。相同请求数下找最忙的设备，解释平均激活参数为何不足以预测完成时间。

### 10.4.2 专家复制与 token 迁移
比较专家复制、放置、迁移和调度，计入额外权重与更新成本。将负载变化放进同一实验，看静态最佳安排何时失效。
以 vLLM／SGLang 的 EPLB 连接路由统计、逻辑专家到物理副本的映射，以及热点专家复制。保持模型的逻辑 top-k 语义；复制相同权重的专家与修改模型路由规则不是一回事。负载观察窗口过短可能频繁迁移，过长又跟不上变化。
用 CRAFT（MLSys 2026）引出逐层副本预算：不同层的倾斜程度和复制收益不同，新增专家又会挤占 KV。Qwen3-235B 若每卡每层多放一个 BF16 专家，94 层合计约 3.305 GiB／卡；把预算集中给少数层后，是否能达到相同服务目标，要用路由和时间记录判断。论文基于 SGLang v0.4.8 的 R1／Kimi K2 实验作历史对照，当前引擎支持的放置能力单独核对。
再区分已有副本间的分派与权重重排。用 SGLang 2026 的 LPLB／Waterfill 说明当前 batch 的均衡自由度：同一个 Qwen3 单层练习，最忙设备从 640 行降到 512 行，究竟腾出多少时间给统计、求解和额外通信？共享专家另按 V4 路径计量。随后用 288 MiB 的迁移预算判断热点持续多久才值得重排；[完整推算与版本边界](../case-studies/expert-dispatch-and-resizing.md)保留在实验材料。
### 10.4.3 Grouped GEMM 与计算通信重叠
沿一次 MoE 层展开路由、排列、dispatch、grouped GEMM 和 combine，按每专家 token 数算矩阵形状。举八个本地专家分别收到 32、16、8、4、2、1、1、0 个 token 的教学输入：实际 64 个专家 token，全部补齐到 32 则执行 256 行。由此比较 padding、变长分组和 persistent 调度；合成一个 kernel 能减少提交，但不能自动消除长尾专家或 tile 的浪费。
同一输入若只对非空专家按 32 行块补齐，则为 224 行。把后端的实际补齐规则放回第 5 章的算力和访存估算，比较有效工作与执行工作，不把 grouped GEMM 当作已经消除 padding 的保证。
用 vLLM DBO、SGLang TBO／SBO 和 DeepEP 的真实执行图，比较两微批交错、共享专家与通信重叠。沿 SGLang 从 H100 多机到 GB200 NVL72 的[历史选择](../case-studies/resource-sharing-and-placement.md)，解释通信缩短后为何需要重新权衡切分损失与更细粒度的重叠。当前 Qwen3 MoE 的 prefill 与 decode／验证也有不同操作顺序和资源预算；图模式、后端及缓冲一起核实，不能只按独占时间的 max 承诺收益。

## 10.5 多级 KV 缓存与共享内存池
接着作者 UB 文章中“先设想内存池，后来遇到 KV cache 应用”的经历，把第 6 章的容量借用、第 7 章的远程访问落实到推理服务。Mooncake／LMCache 提供软件 KV 池的实例，UB 提供另一类访问和资源管理机制，分别分析各自路径。
### 10.5.1 缓存层次与访问方式
以 SGLang HiCache 与 LMCache 的真实后端作为 HBM、主机和外部存储的实验入口：分别记录写入、预取、命中和淘汰，而不是仅画一个内存池方框。2026 年 Unified Radix Cache 把混合模型状态接到这些层次；沿 V4 的压缩／窗口与 K3 的循环状态重新核算有效边界。
沿 HiCache 从 2025 公告到当前实现，明确单实例私有的 host 层与按后端配置共享的存储层。再用 vLLM 从异步 connector、CPU offload 到当前多级后端作对照；其原生路径先经过 CPU，不能由“远端存储”推断 GPU 直读。缓存容量、共享范围和数据通路分别落到实际部署。
用 HiSparse（2026）的 DSA 案例补充另一种问题：本步选中的 KV 很少，完整历史容量却仍然很大。比较按需从主机取回与 HBM 热缓冲，计算低并发时的额外 IO 和高并发时释放容量的收益；这是其已披露 DSA 路径，不能直接假定适用于 V4 的全部压缩层或 K3 的状态。
沿 Qwen3-8B／235B 的两个实例反复处理同一 Agent 前缀，比较本地 HBM、主机 DRAM、本地 SSD 和远端缓存池。逐层计算容量、访问带宽、启动延迟、块大小与排队；热的活跃 KV 与等待复用的冷前缀采取不同放置。Mooncake／LMCache 提供软件层次与共享实例，UB 的硬件访问语义另行对应。
沿用 1 GiB 前缀和 25 GB/s 条件式算例：取回一次的纯传输下界为 42.95 ms；假定每个 decode 步都要从远端读取这份不变前缀，生成 100 token 至少累计约 4.295 s 的链路服务时间，另计增长中的 KV。与一次本地 prefill 重算和搬回本地继续生成比较，解释远端容量能否成为活跃 KV 的供数来源；有重叠或分片时按每条链路和依赖重算。
接回第五章的布局：Qwen3-8B 的 16-token BF16 块，按声明布局可拆成 72 个 32 KiB 连续段，也可组织成一个 2.25 MiB 连续块。有效载荷相同，再比较 DMA、搬运 kernel、布局转换与并发计算争用；[完整推算](../case-studies/cache-tiers-and-routing.md)与实验使用同一配置。
> **实验 10-7 ★：共享 KV 池的命中收益**
视觉变体用 SGLang 的全局 embedding cache 说明另一类状态：命中 EC 可以省 ViT，仍可能要取回并发送完整特征，再执行语言 prefill。当前指南将 encoder 传输后端和全局 EC 缓存分开配置；沿内容、预处理、模型版本与前缀位置检查 EC／KV 的不同身份，不能把两种命中收益重复相加。
### 10.5.2 缓存亲和性与负载路由
从两次同前缀请求引出缓存亲和与负载均衡的冲突，比较原实例排队、新实例重算和跨池取回的完成时间。Preble、SGLang 与 Mooncake 作设计对照；命中率、复用间隔和正在占用的显存决定选择。
用同一 Qwen3 的 8K 前缀给出具体选择：在声明的队列与串行取回假设下，原实例 HBM 命中约 260 ms，空闲实例重算约 200 ms；远端有效带宽从 5 改为 20 GB/s，取回方案从约 310 降到 129 ms。先画状态就绪与 GPU 等待的依赖，再增加共享链路负载，说明单请求的选择何时失效。数字是教学输入，[算例](../case-studies/cache-tiers-and-routing.md)不冒充框架成绩。
对照 SGLang 2024 的近似缓存树与固定当前 Model Gateway：已读策略依据文本匹配和负载阈值，并未直接预测上述完成时间。区分 router 预计命中、worker 的实际 token 命中和 KV 所在层级，实验检查过期信息怎样改变选择。
再沿 vLLM 的 KV events、SGLang HiCache 与 Dynamo 的实际集成，解释缓存怎样成为路由依据：拷贝完成才报告新位置，GPU 淘汰后 CPU 副本可能仍在，事件缺失则需恢复索引。用同一前缀把 A 的队列改为 80 ms，计算有效命中时的 90 ms 与全部失效后的 260 ms；即使平均值优于 B 的 200 ms，尾延迟也可能不合格。由此区分缓存层级的评分权重、命中概率和实际取回时间。Agent 并发分支还会先于缓存发布到达，短期预测可帮助聚集请求，但不能保证前缀已经可用；[扩写依据](../case-studies/cache-events-and-routing.md)保留版本与计算条件。

### 10.5.4 持久化与多级命中

## 10.6 服务恢复与部署选择
### 10.6.1 流式输出与部分故障
区分普通交互、Agent 续接与 RL rollout 的恢复目标。依据 DeepSeek-V4 的 token 级 WAL 与 KV 保存机制，比较继续 decode、用已生成 token 重做 prefill，以及重新采样的差别；最后一种会改变输出和采样分布。计算不同故障下的重做工作、缓存访问和已经交付结果的处理，第 11 章再分析训练影响。

## 11.5 RL 系统：Rollout 与梯度更新
### 11.5.1 Rollout、奖励与训练闭环
承接第 3 章的 RL 负载，组织 rollout、奖励／验证、样本缓冲与梯度更新，再把新权重交回采样端。DeepSeek-R1 交代推理训练路线，DeepSeek-V4 的 §5.2 作为系统主例；逐项计算生成、验证、训练、权重分发与数据组织的资源需求，代码与 Agent 任务连接第 12 章的 CPU 沙箱。
以 verl 的实际数据流对应这些角色：rollout 可调用 vLLM／SGLang，梯度更新由 FSDP／Megatron 等后端执行，verl 组织样本、奖励与权重交接。用小模型配套实验贯通真实流程，再将 V4 教学预算代入，不能用开源实验反推 V4 未公开部署。AReaL 用于异步供给的对照。
### 11.5.2 长轨迹、抢占与采样恢复
依据 V4 的 token 级 WAL、抢占时 KV 保存及故障后重做 prefill，比较从断点继续与从头重采样。用长短轨迹的不同存活概率解释后者可能引入长度偏差，恢复同时影响系统成本与训练样本分布。同步／异步供给作为部署选择分析，只把报告明确披露的机制归于 V4。
再以 AReaL 的部分 rollout 区分“恢复同一策略”与“换权重后继续”：token、环境与行为 logprob 可以保留，新权重所需 KV 要重新验证或重建。给同一轨迹的不同段标出实际权重版本，比较版本滞后、暂停交接和有效样本供给；Qwen3-8B 的 8K KV 虽为 1.125 GiB，重建成本仍要回到 prefill 计算。沿[状态与版本算例](../case-studies/rl-state-and-reproducibility.md)解释扩大 rollout 池何时只会积压待验证或过期样本。
用 RobustRL（OSDI 2026）的 verl＋vLLM 路径补一次 trainer 故障：先判断已生成轨迹、环境、训练检查点分别在哪里，再决定重做多少。沿[恢复算例](../case-studies/rl-scheduling-and-recovery.md)，300 秒 rollout 后更新失败，保留轨迹可把教学完成时间从 790 秒减至 490 秒。讲清按角色恢复的边界、检查点版本及尚未持久化的状态；正常等待工具不能判为 GPU 故障。
以 RollPacker（NSDI 2026）的长短轮次补充主动取消：多启动回答、保留先完成的组，可以缩短等待，也可能改变入选分布。沿[两次采样的算例](../case-studies/rollout-tail-and-sampling.md)，固定权重下长回答入选概率仍可由 1/2 降至 1/4。分开核算 prompt 覆盖、回答选择、额外生成与验证质量；公开实现的完成组还受奖励与过滤时间影响。
### 11.5.3 采样、教师与学习的资源配比
用 vLLM Sleep Mode 具体展示阶段切换：保留到 CPU 的权重、丢弃 KV、释放显存及装入新权重分别计时。不同 sleep 级别保留内容不同；唤醒推理进程不表示旧 KV 已恢复。将主机容量、权重版本与重新 prefill 加进共置 RL 的预算。
统一生成、验证和学习的有效样本单位，再决定 GPU、CPU 与环境池配比。以 V4 的多教师 OPD 为例，比较保存全词表 logits 与保存末层 hidden state、使用时重算输出头的容量和计算代价；加入教师权重按需读取、分组调度与异步传输。把第 10 章的分离与缓存方案代入这一循环，比较分置、共置和阶段切换的收益边界。
再用 Weave（OSDI 2026）的 H20／H800 双池案例引向第 12 章：保持每个作业采样后更新，用其他作业填等待。收益取决于阶段互补、主机状态驻留和切换时间；省下设备与单作业变快分别核算。RobustRL 借 rollout 机器恢复 trainer 还要求同型资源，不能直接套到异构双池。

### 11.5.4 MoE 的 Routing Replay
先固定相同权重和 token，比较推理与训练引擎重算的专家选择及 logprob：不同精度、kernel 和 batch 形状产生的微小数值差异，可能翻转接近边界的 top-k，逐层积累成与策略更新无关的差异。由这个问题引出 Rollout Routing Replay／R3（2025），再用 NeMo RL 的 vLLM rollout＋Megatron 训练路径说明落地。
记录生成时每层、每 token 的专家 ID，在训练前向重放离散选择，同时以当前权重重新计算路由分数和专家输出，保留梯度。它不是重放旧输出，也不是省掉整个 router 计算；不能因此认为策略滞后、数值误差或 RL 收敛问题全部解决。与第 10 章 EPLB 区分：逻辑专家 ID 不随物理副本位置改变。
先对齐 rollout logprob 的定义：vLLM V1 的 raw 与经过温度等处理的概率有区别，请求 prompt logprob 也可能改变前缀缓存路径。没有对齐这些条件时，不能把所有差异归因于 MoE router；后端返回的缺失路由与回退必须进入实验记录。
分别标明行为策略、更新前训练策略与当前策略。教学例中正确比值为 1，若把 `−3` 的行为 logprob 错换成 `−3.25`，比值就变为约 1.284，越过题设的 1.2 上界。先验证引擎内部的 batch invariance，再检查跨引擎与路由差异；可重复的 rollout 不自动等于 on-policy，训练端重算也不能不加说明地覆盖行为概率。
按 `有效 token 数 × MoE 层数 × top-k × ID 字节数` 先算路由记录，再加入多轮前缀、打包、上下文切分、传输与保存。例用 8,192 token、48 层、top-8、uint16 得 6 MiB；这是编码假设，真实后端若用 int32 则翻倍。缓存 KV 时要能找到同前缀的路由记录；采样、logprob、训练和激活重计算都要对齐 token 身份与权重版本。

## 11.6 训练效率与完成成本
### 11.6.1 有效训练进展与设备利用
先说明 MFU 的算法 FLOPs、精度峰值、卡数与计时边界，使用 30%／40%／50% 三档估计敏感性；50% 是较乐观情景，需要由对应模型与拓扑的训练步验证。稳态 MFU 若已包含重计算、通信与气泡，就不再把这些时间重复相加；日历完成时间另计区间之外的保存、故障、恢复和数据停顿。RL 按有效样本及质量进度核算，不把 rollout 与梯度计算硬合成一个 MFU。

承接第一章的系统抽象边界上移，前面三章已经算过模型怎样在 GPU 上推理和训练，本章回到调用模型的任务及其通用运行环境。代码 Agent 需要等待模型、运行测试、保存文件，再继续下一轮；RL 也要采样、验证、更新。GPU 的速度只是其中一个条件，CPU、环境内存、模型服务和任务状态需要一起安排。

## 12.1 Agent 任务与 CPU 资源
### 12.1.1 模型调用之外的任务执行
跟随代码任务经历排队、环境准备、模型调用、代码执行和结果保存。承接第 3 章的 Agent 负载和第 8 章的 Computer Use，把一轮内部依赖与多轮累计等待画出来，找出改善模型速度之后仍在关键路径上的部分。
用 Ollama 2025 年流式工具调用说明首段文本、完整工具参数与可开始执行的时刻并不相同。流式返回可以减少部分等待，但参数未完整或操作未确定时不能提前执行有副作用的工具；预热环境则可按第 12.2 节另算。
接回第 9 章结构化生成的记录：输出符合 schema、参数已收齐和任务语义正确是三项判断。把语法准备造成的模型等待与工具本身的 CPU 工作分开，避免增加环境 CPU 后仍未改善推理侧的关键路径。
### 12.1.2 共享平台与并发需求
对稳定任务流先用 `平均环境数 = 到达率 × 平均驻留时间`，再乘每环境内存；CPU 核时按实际执行另算，预热池和突发余量另加。代码执行、浏览器和 RL 验证的资源组合由具体任务决定。
例如每秒进入 10 项任务、每项驻留 30 秒、每环境占 2 GiB，则平均需要约 300 个环境和 600 GiB 内存；若每项只执行 3 核秒，平均 CPU 工作量约为 30 核。用这个差距引出等待模型时暂停环境的收益与恢复代价。数值为教学输入，平均值不能直接当作满足 P99 的配置。

## 12.2 AI 作业与环境调度
### 12.2.1 异构设备、成组分配与资源碎片
接回第 6、7 章算出的并行方案：一个作业需要的不是任意若干张卡，还包括卡型、主机内存、CPU 和网络位置。用 ASI 的生产集群研究（OSDI 2026）解释空闲设备为何仍分配不出去，再比较打包放置、迁移整理和跨交换机放置，权衡等待完整一组设备与立即开跑之后的通信代价。

承接 Elastic EP 的组规模变化，区分引擎提供的重配置机制与平台何时触发它的策略。先比较热点预计持续时间和搬移回本时间，再看切换期间的队列与缩容后的 KV；保持 GPU 数不变的专家分派和新增 GPU 不能用同一个收益口径。
接回实验 3-2／10-2 的请求组成变化：QPS 没有增加，decode 池仍可能积压。沿[同一算例](../case-studies/workload-and-provisioning.md)比较预留 D 热副本、将 P 改成 D 和等待突发结束；只有新角色在需要它的时段内准备好，重配才能缓解这次等待。
用 Rubick（MLSys 2025）补充另一种选择：沿前章推算，为同一训练作业保留几种并行、重计算和卸载方案，再根据 GPU、CPU 与互联余量选择。比较多给一张卡与多给 CPU 的实际收益；少量测点校准各阶段及重叠，预测有偏差时更新。保证相同训练目标并计入检查点和重启成本，避免把缩放卡数视为无代价操作。

## 12.3 模型路由服务
### 12.3.1 订阅产品与按量 API
从同一位开发者的月度代码任务出发，比较订阅内使用与自建 Agent 调用 API 的费用和限制。扩写时安排一张小表，以 Claude 与 Gemini 的官方方案为例，列订阅费、使用入口与额度、超额计费、API 输入／输出价格、缓存费用及速率限制，保留日期、地区和档位。
解释订阅费怎样摊到实际完成的任务，API 费用又怎样随上下文、思考长度和重复调用增长。消息或计算额度、特定应用积分与 API token 不是同一单位；有无开发者额度逐项核对。比较同类任务的实际账单，不能由月费推出订阅相当于 API 的固定几折，也不能把使用上限当作无限供给。
### 12.3.2 中转服务与后端选择
沿“Agent → 中转入口 → 上游服务 → 流式返回”说明鉴权、接口适配、后端选择、限流、回退与计量，这是模型中转服务的基本请求路径。比较上游按量 API、购买或自建的推理容量，以及通过产品允许的入口使用订阅额度：来源不同，价格、并发和可持续供给也不同。不能把所有中转服务都解释成订阅与 API 的价差。
从上游与下游两张账单计算服务收入、容量及运维成本，再加额外网络跳转和排队。模型名称相同仍要核对实际版本、量化、上下文、reasoning 设置和缓存支持；中转层若改变这些条件，输出 token 单价就不足以说明服务是否等价。

### 12.3.3 任务质量与思考预算
用“一个模型思考 100 个 token，另一个需要 1,000 个”引出选择。固定任务和质量门槛，比较实际 reasoning token、可见输出、工具调用次数与成功率；区分配置预算、实际用量和预算截断。少思考却经常失败的模型未必经济，隐藏思考不能用可见摘要长度估算。
先做等单价教学算例：输入 10,000 token、可见输出 200 token，输入／生成价格分别为每百万 2／10 美元。实际思考从 1,000 减为 100 token，单次费用由 0.032 降为 0.023 美元；思考部分缩为十分之一，总费用并没有缩为十分之一。换模型时重新代入各自 tokenizer、计费项与速率；reasoning 若已含在 output usage 中，不再加一次。
再比较首段可用结果与任务结束时间。思考与可见输出速率、排队、prefill 和工具等待共同决定延迟；每秒输出更多 token 的模型，可能因为生成更长而更晚完成。先用分阶段预算解释，再用任务记录检查延迟和质量分布。
### 12.3.4 前缀缓存的成本与延迟
把第 9、10 章的 KV 复用接到 API 选择：重复系统提示、工具定义、仓库内容和多轮历史能命中多少前缀，多久再次访问，换后端会丢掉多少复用。分别计算未缓存输入、缓存创建、命中读取和按时长计费的存储；比较请求命中率与 token 加权命中率。
安排 10 轮代码 Agent 算例，固定公共前缀，再改变新增上下文、命中比例、轮间间隔和 TTL，算缓存费用的交点。结合最低缓存长度、前缀变化与工作区边界解释命中条件。API 缓存 token 是计费和复用证据，不能直接反推出 KV 在哪级存储或读取多少字节；资源模型回到第 2、10 章。
命中主要改变前缀处理，不意味着 decode 或 reasoning 自动免费、加速。比较“命中但排队”与“空闲但要重算”，把缓存亲和性、传输和容量压力放进预计完成时间；更换模型或供应商通常不能延续原缓存。
### 12.3.5 质量、成本与完成时间的联合选择
**占位 TC-16：** 补价格竞争、模型路由与能力价格前沿，区分 API 售价和生产成本。 详见[成本下降调研](../research/token-cost-2023-2026/report.md#economics)。
将候选写成“模型版本＋服务商／副本＋思考预算＋缓存条件”，先排除不满足质量、上下文和功能的选项，再比较完成时间和成功任务成本。限流区分请求数、输入／生成 token 及并发槽位；长 reasoning 会占用更久的槽位，也可能降低有效请求吞吐。
