# 从云数据中心到 AI 数据中心：可编程性与系统抽象边界上移

> 独立调研与写作报告 · 2026-09-08。大纲只保留论点占位、叙述顺序与配图计划，扩写时使用本报告。

本专题恢复原始 skeleton 第一章的一条核心论证：**传统系统以操作系统为关键编程抽象，承接各种应用；大模型成为新的可编程接口之后，应用的多样性可以在模型之上表达，模型之下的系统则围绕相对集中的计算形态协同设计。** 这为解释云数据中心向 AI 数据中心的变化提供了开篇主线，也解释本书为什么先集中讨论模型执行，再在第 12 章展开通用运行环境。

这里采用作者本轮明确的术语 **programmability（可编程性）**。系统抽象边界描述应用如何向系统表达工作，以及底层要提供怎样的执行契约；不能将这条论证改成不同平台之间的可移植性问题。全文的整体判断是本书的分析视角，下列资料分别支持其中的历史来源、机制与适用范围，不将其包装为某篇外部论文已经证明的统一定律。

## 2. 第一章的论证应怎样展开

**先说明操作系统为什么是传统系统的重要抽象边界。** 程序通过进程、地址空间、文件、网络等抽象使用计算资源。系统不预先知道应用的全部算法与用途，必须提供能够承载多种程序的通用执行环境。云计算把这种环境组织成可分配、共享和隔离的服务，虚拟机、容器与网络虚拟化因此成为理解通用云数据中心的重要入口。

作者提出的 OSDI／SOSP 是合适的历史引子：OSDI 的全称是 *Operating Systems Design and Implementation*，SOSP 是 *Symposium on Operating Systems Principles*。两者名称中的 Operating Systems 可以带出这段学科背景；会议今天的研究范围已覆盖广泛系统软件，不能由名称推断全部论文都以 OS 为唯一边界。[OSDI 官方说明](https://www.usenix.org/conference/osdi26)、[SOSP 官方说明](https://sigops.org/s/conferences/sosp/2026/)

**再说明大模型怎样承接应用的可编程性。** 对话、信息提取、代码生成等任务可以共享模型能力，通过指令、示例、上下文、输出要求和工具调用组织不同的行为。对于调用模型的应用开发者，工作表达的重心上移到了这一层。Stanford CRFM 的基础模型报告以同一基础模型适应广泛下游任务、自然语言提示适配和模型基础的趋同为背景，支持这一观察。[CRFM 报告介绍与引言](https://crfm.stanford.edu/report.html)

**随后解释边界下方获得了什么设计空间。** 上层任务可以很不同，但对同一模型的一批调用，会进入共同的模型执行路径。系统可以围绕张量计算、权重和中间状态的访问、批处理及多设备协作组织硬件和软件。应用的差异不必全部变成底层要分别支持的一套通用程序，因此从模型、算子、运行时到存储与互联的联合设计有了共同对象。

“只需服务好大模型这一应用”适合作为章首直觉，正式论述应明确其观察范围是模型执行部分。这里的“一种”指相对集中的工作负载形态；不同模型架构、训练与推理阶段、上下文长度及并发需求仍会改变执行。内核与编译器也仍然需要可编程性。不同模型的接口、tokenizer、能力和行为并未因此成为统一标准，模型输出也不能直接等同于具有确定语义的 OS 系统调用。

**最后落到本书为什么这样组织。** 第 2、3 章先刻画这个共同对象的结构与负载，第 4–11 章分析执行它的设备、互联和系统，第 12 章接回应用调用工具时需要的通用环境，第 13 章综合设计取舍。抽象边界上移由此成为后续章节顺序的原因，而不只是开头的一句判断。

## 3. 数据中心变化的六个观察面

下表是本书用于组织材料的对照。左侧以承载多种客户程序的通用云为参照，右侧聚焦大模型训练与推理的执行部分；实际数据中心可以同时包含两类资源池，表格不表示所有部署都完成了同样的替换。

| 观察面 | 通用云数据中心的典型设计出发点 | 大模型执行部分的设计重心 | 后续章节 |
|---|---|---|---|
| 应用怎样表达工作 | 通过 OS、语言运行时和服务接口部署多样程序 | 上层通过模型能力组织任务，底层承担共同模型执行 | 1、2、3 |
| 计算怎样组织 | 管理不同程序的执行与资源需求 | 围绕张量与阶段形态批量执行，并在多设备间切分 | 4、5、6、9、11 |
| 状态怎样管理 | 进程内存、文件和服务状态 | 显式核算权重、激活、KV 或递推状态、优化器与检查点 | 2、5、9、10、11 |
| 网络承担什么 | 服务通信、存储访问、租户网络与隔离 | 模型分片协作、集合通信、专家分发和阶段状态交接 | 6、7、10、11 |
| 调度优化什么 | 各类客户程序的资源供给、共享、公平性与服务目标 | 模型阶段、批量、拓扑、成组分配及有效训练／推理产出 | 9、10、11、12 |
| 隔离放在哪里 | 客户程序与其机器、网络和存储环境 | 分清模型请求、GPU 作业和工具环境的隔离对象 | 9、10、12 |

这一组织方法也能接上第一章已有历史案例。SmartNIC 的网络虚拟化案例说明通用云为何需要花费 CPU 处理转发、封装和隔离；TPU 说明共同模型计算怎样支持专用加速；UB 说明模型规模扩大后，多设备协作怎样进入整体设计。三者分别提供历史条件下的证据，不能只凭年代把它们写成前者被后者全面替代。具体经历与推算沿用[可编程网卡案例](../../case-studies/programmable-nic.md)和作者的[UB 原文](../../references/files/documents/ub-reflection.html)。

模型执行效率也不能只由 GPU 峰值衡量。边界下方的共同计算要进一步转换为可计算的容量、访问量、带宽、同步和关键路径，才能解释哪些优化值得做。因此恢复这条主线之后，第一章仍应尽早给出已有的纸笔估算方法，并在 1.1.3 用[固定能力的成本下降报告](../token-cost-2023-2026/report.md#findings)连接全栈协同的结果。

## 4. 多租户与虚拟化怎样衔接第 12 章

本书应将这个变化写成**设计重心与隔离对象的迁移**。对于集中执行大模型的计算部分，如何让模型高效运行是主要分析问题，逐个租户复制完整通用机器环境不再是解释所有机制的起点。对于代码 Agent 和 RL 验证，系统再次面对不同来源的程序、依赖、文件和外部连接，通用环境交付与隔离就成为直接问题。

这里有三个需要分开的对象：

1. **模型请求与应用的共享。** 多个用户或应用可以调用同一模型服务。请求状态、数据访问、配额和延迟要求仍然需要管理；共用模型不会自动消除租户边界。
2. **GPU 作业和设备资源的隔离。** 不同作业可以共享集群，部分负载也可以共享单卡资源。NVIDIA MIG 官方文档明确讨论多用户 GPU 实例、资源分区及云服务商的多租户场景，说明这类需求仍存在。是否适合采用，要根据实际卡型、作业规模及资源需求判断。[NVIDIA MIG 说明](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/introduction.html)
3. **工具代码与运行环境的隔离。** 同一模型可能为不同用户编写并执行完全不同的程序，环境必须管理文件、进程、资源限额和生命周期。Firecracker 的公开设计就是面向多租户函数与容器服务的 microVM 技术，并利用 Linux KVM 创建虚拟机；这一机制适合承接第 12.4 节的讨论。[Firecracker 官方说明](https://firecracker-microvm.github.io/)

因此，第 12 章可以用一条完整路径回扣第一章：应用在模型层表达任务，模型通过工具接口请求执行，代码进入通用 OS 环境，运行结果再返回模型上下文。模型抽象边界上移和 OS 持续承担工具执行可以同时成立。第 9、10 章仍保留服务共享与状态管理，第 12 章集中展开通用代码的多租户环境、容器／microVM、预热、快照与恢复。
