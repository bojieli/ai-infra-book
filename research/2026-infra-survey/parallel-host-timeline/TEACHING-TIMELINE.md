# 同一请求的四次 decode 迭代

沿用 Qwen3-8B 的请求，假定 prefill 已结束，当前批次保持不变，再执行四次普通单 token decode 前向。这是四次迭代，不能与“请求总共输出四个 token”混用。仅为观察主机依赖，给每次准备 P、GPU 工作 G、主机结果处理 H 分别假设 **4τ、10τ、2τ**；τ 是教学时间单位，没有对应某张显卡的微秒数。必要的设备输入接续已计入 G，忽略额外争用和协议开销，并假定四次都不会提前停止。

| 执行安排 | CPU 总工作 | GPU 总工作 | 第四次结果处理完成 |
| --- | ---: | ---: | ---: |
| 每步 P → G → H | 24τ | 40τ | 64τ |
| 四步共用一次 P，GPU 逐步执行，末尾统一处理四份 H | 12τ | 40τ | 52τ |
| 每步仍做 P／H，但准备提前、结果处理延后，与 GPU 重叠 | 24τ | 40τ | 46τ |

第二行只演示摊销调度；真实多步 runner 仍有逐步元数据工作，所以把 P 全部摊销只是显式的教学假设。第三行只演示重叠，CPU 一点也没有少做。这是同一基线的两种改动，不能把各自加速比相乘；CUDA Graph 的提交节省也不能再次重复扣减同一块 P。

第三行的一种可行时间安排：

```text
GPU:           G1[4,14]   G2[14,24]   G3[24,34]   G4[34,44]
CPU准备: P1[0,4] P2[4,8]      P3[16,20]   P4[26,30]
CPU结果:                     H1[14,16]   H2[24,26]   H3[34,36] H4[44,46]
```

GPU 上仍然 G1 → G2 → G3 → G4。能提前的是主机准备，不是凭空提前知道上一步 token：旧 SGLang 的 future token、vLLM 多步的 GPU 输入推进、当前的设备状态传递，就是为了在设备真正消费输入时接到上一轮结果。这个例子要求下一轮 P 不依赖前轮 H，且 P+H 不超过可用 GPU 窗口。若必须先做 H 才能准备下一步，第三行会退回串行的 64τ；有多个 CPU 线程、不同队列或争用时必须重画时间线。

多步窗口还有服务代价：例中 5τ 到达的新请求不能插进已经决定的这四步，至少要等到 44τ 的 GPU 窗口结束再考虑准入；这不是生产实现的精确 TTFT。异步结束检测也可能让后续工作已经提交，因此延迟、额外算量和 KV 回收安全点应分别观察。

把同一请求切到推测执行时，不再把每轮当作固定加一。若两轮验证的序列推进增量分别为 Δ₁=3、Δ₂=1，长度依次是 L → L+3 → L+4。调度器可以先准备可提前确定的部分，但需要新长度、真实 token 或 grammar 状态的操作仍要等对应结果。在当前 EAGLE V2 路径中可画成：

```text
设备本轮: draft → target verify → accepted-state / new-length publish → draft extend
主机下轮:                  等消费者所需的 publish ──────→ 准备 / 必要的长度镜像
主机输出: 上轮停止检查与状态处理可重叠本轮设备工作；grammar mask 要等对应已提交 token
```

这里 Δ 是代码中的序列推进增量，不是接受率，也不承诺等于应用最终显示的 token 数。只有不需要 CPU 长度镜像的后端才可跳过该 D2H；受约束生成可能先发起前向，再等待状态后采样。沿真实 trace 找出这种等待，才知道某一处优化是在减少工作还是改变工作的先后顺序。
