# 从同一份 Qwen235 所有权记录接通容量与通信

2026-09-09。只设计一个教学情景，接回已有实验 6-3→7-3／7-10→9-1；不增章节或核心实验。所有模型数字来自仓库已经锁定的 Qwen3-235B-A22B 配置，本轮没有联网、运行模型、调用下载代码或改动共享计算程序。

**采用建议：值得接入现有连接练习。** 它新增的判断是：容量表里采用怎样的请求与状态复制，决定随后需要哪种通信。不能先按“EP”算一张容量表，再任取另一个 EP 实现的 All-to-All 字节。这里有意沿用既有容量表的同一 cohort 组织，因此输入不需要再次跨 EP 派发，专家结果却要跨 TP／EP 汇合；少搬输入的代价是重复 attention、KV 和非专家权重。

本情景是对已有容量假设补全数学上可执行的数据流，**不宣称它是 vLLM／SGLang 的默认部署，也不宣称它最优**。自然模型路由、浮点一致性与具体引擎实现仍需另核。

## 固定任务与布局

取一个请求：先从空缓存 prefill 8192 个输入位置，再执行第一次 decode。prefill 产生第一个输出；第一次 decode 处理这个尚未进入 KV 的输出 token，产生第二个输出，步末状态由 8192 增至 8193。这里只核算层内矩阵／状态与声明的集合通信，不把未计输出头和采样的子账称为完整请求时间。

使用 **DP1、PP1、TP2、EP4，共 8 个 rank**。DP1 表示一个独立请求 cohort，不把 EP4 算成四个服务副本。94 层均驻留，每层 128 个路由专家、top-8；没有额外共享专家。BF16 权重、激活与 KV，归约的线格式显式设为 FP32。每卡名义容量 80,000,000,000 bytes，工作区预留 2 GiB，沿用既有容量表；预留值不是已测峰值。

记 rank 为 `r=2e+t`，`e∈[0,4)`、`t∈[0,2)`。为接入第 7 章，将 8 张卡映射到两个各含 4 张卡的教学服务器：A 放 rank 0–3，B 放 4–7。这里只声明服务器边界与下列有向 ring，不虚构某款网卡、交换机或物理带宽。

| ranks | 服务器 | EP 专家范围，左闭右开 | TP 内专家中间维 | 查询／KV 头 |
| --- | --- | --- | --- | --- |
| 0、1 | A | [0,32) | rank 0 为 [0,768)，1 为 [768,1536) | 偶数 rank 为 Q[0,32)、KV[0,2)；奇数为 Q[32,64)、KV[2,4) |
| 2、3 | A | [32,64) | 同上，按偶／奇 rank | 同上 |
| 4、5 | B | [64,96) | 同上 | 同上 |
| 6、7 | B | [96,128) | 同上 | 同上 |

TP 组是 `(0,1)、(2,3)、(4,5)、(6,7)`；EP 组是 `(0,2,4,6)` 和 `(1,3,5,7)`。每个 EP 组中的同一 TP 坐标保存相同请求、相同 KV 头；只有专家所有权不同。专家 gate/up 为局部 `[768,4096]`，down 为 `[4096,768]`；两个 TP 分片合成一个完整专家。

本例给定相同的逻辑路由记录：位置 `s` 的 8 个专家为 `(8s+k) mod 128, k=0…7`，每层沿用该规则。它保证 top-8 不重复，供算术与负载对比使用，不是 Qwen 模型真实路由统计。路由概率与 token 顺序在各 rank 一致；如何取得和验证这些记录、实际 router 的数值一致性均不由本算例证明。

## 逐卡容量来自同一张参数表

每卡的物理参数副本数为 32,410,709,504，BF16 权重为 **64,821,419,008 bytes**。分项如下，8 个 rank 数量相同，但专家、查询头和词表切片身份不同。

| 94 层及首尾合计 | 每卡参数数 | 每卡 BF16 bytes |
| --- | ---: | ---: |
| embedding＋输出头，TP 切词表、沿 EP 复制 | 622329856 | 1244659712 |
| attention 投影，TP 切分、沿 EP 复制 | 3351248896 | 6702497792 |
| 本地专家，EP 分专家、TP 切中间维 | 28387049472 | 56774098944 |
| router，沿 TP／EP 复制 | 49283072 | 98566144 |
| norm | 798208 | 1596416 |

全模型唯一参数仍为 **235,093,634,560**，唯一 BF16 权重为 470,187,269,120 bytes；8 卡物理权重合计 **518,571,352,064 bytes**。差额来自所选复制方式，不能用逻辑权重除 8 代替逐卡表。

每卡每个缓存位置的全 94 层 KV 为 `2×94×2×128×2=96256 bytes`。prefill 后每卡 **788,529,152 bytes（752 MiB）**；第一次 decode 再写 96,256 bytes，步末 **788,625,408 bytes**。8 卡在 8192 个位置共占 **5.875 GiB**，是单份逻辑 GQA KV 的 4 倍。容量预算在两个时刻分别为每卡 67,757,431,808／67,757,528,064 bytes，已加权重与声明的 2 GiB 预留；没有据此保证实际运行可行。

独立脚本按配置重新计算这些参数，并逐 rank 对照[现有容量结果](inputs/capacity.json)的 BF16 行。没有执行现有容量模块或导入其 Python 代码。

## 输入为什么不需要 All-to-All，结果又怎样返回

1. 各 EP 副本对同一批位置计算 attention。每个 TP 组先归约 attention 输出，得到同一份完整宽度 hidden；因此 MoE 入口的每个 rank 都已有这些输入位置。
2. 各 rank 按给定 top-8 只挑选本 EP 拥有的专家。本地排列／gather 可以产生逻辑 assignment 输入，但 **跨 EP 的输入 dispatch 发送与接收均为 0**。这不表示本地 gather、router 或内存访问免费，也不表示其他 EP 布局的 dispatch 为 0。
3. 两个 TP rank 分别计算专家中间宽度的两个分片，按路由概率形成本 EP 对每个位置的部分输出。先在 TP2 中求和，再在同一 TP 坐标的 EP4 中求和；所有 rank 得到一份相同的逻辑 MoE 输出，继续下层。未收到专家任务的 EP 仍贡献零张量并参与声明的固定集合调用。

这里的 combine 是部分结果的归约与复制，不是把每个专家结果独立发回一个唯一 token 源。汇合 TP 后，只在 EP4 中求和；如果误将两个相同 TP 结果再次放进一个全 8 卡求和，会把结果重复计算。脚本用 7 个位置的整数贡献验证两级汇合恰好还原一个逻辑结果；这只检查身份与代数守恒，不证明浮点逐位一致。

## 同一路由规则在 prefill 与 decode 中的不同负载

以下专家数字均为**单层**。KV 则保留上节的**全模型**口径，结果 JSON 也明确标记。

| 项目 | 8192-token prefill | 第一次 decode，处理位置 8192 |
| --- | ---: | ---: |
| 逻辑 token—专家任务 | 65536 | 8 |
| 每 EP 的任务 | 每组 16384 | EP0 为 8，其余 0 |
| 每个 TP rank 的任务行 | 16384，计算不同中间维分片 | rank 0／1 各 8，其余 0 |
| 活跃本地专家 | 每 rank 32 个 | rank 0／1 各 8 个，其余 0 |
| 理想独立专家权重读取 | 每 rank 576 MiB | rank 0／1 各 144 MiB，其余 0 |
| 本地逐 assignment 的 BF16 输入逻辑载荷 | 每 rank 128 MiB | rank 0／1 各 64 KiB，其余 0 |
| 专家矩阵 FLOPs | 每 rank 309237645312 | rank 0／1 各 150994944，其余 0 |

两个 TP rank 都执行任务行，但其专家中间宽度互不重叠。全 8 卡专家矩阵 FLOPs 的和仍等于一次逻辑 MoE 工作，不能把任务行副本误认为重复完整专家计算。attention 则不同：EP4 重复了完整 attention 的数学工作。prefill 每 rank 的 attention 投影＋有效因果 QK/PV 为 1,133,938,475,008 FLOPs，decode 为 205,537,280 FLOPs；都不含 softmax、norm 等非矩阵算术。

权重“理想只读一次”仍是逻辑复用上限，实际 HBM 要看 tile、缓存和执行。decode 的全模型旧 KV 读取，在每 rank 只读一遍且共享 GQA 头的假设下为 788,529,152 bytes，再写新的 96,256 bytes；prefill 的 KV HBM 读取保留未知，不能用状态容量或注意力配对数直接替代。

这解释了同一布局的两项限制：prefill 的独立专家工作均衡，attention 却有四份物理工作；decode 的专家工作只在一对 TP rank 上，其他 rank 仍占权重／KV 并参加固定通信。没有测得的时间，不能仅由这两点宣称另一方案更快。

## 每个源与目的的通信载荷

所有归约使用显式的 FP32 线格式，张量大小 `M=new_tokens×4096×4`：prefill **128 MiB**，decode **16 KiB**。采用未重叠的简化 ring reduce-scatter＋all-gather 计消息，TP2 为 2 轮、每轮每 rank 发送 `M/2`；EP4 为 6 轮、每轮发送 `M/4`。没有为已知零贡献添加跳过或压缩优化。

| 阶段 | 有向源→目的 | 每条边累计发送 | prefill | decode |
| --- | --- | ---: | ---: | ---: |
| attention TP 汇合 | 0↔1、2↔3、4↔5、6↔7，各方向分别计 | M | 128 MiB | 16 KiB |
| expert TP 汇合 | 同上，是另一次调用 | M | 128 MiB | 16 KiB |
| expert EP 汇合 | 0→2→4→6→0，1→3→5→7→1 | 1.5M | 192 MiB | 24 KiB |

输入 dispatch 的源—目的矩阵全部为零；本地 assignment 载荷在上一表单列。每个 rank 的总发送分别为 **448 MiB／56 KiB**，总接收相同。网络物理发送只累加一次，不把接收再加成两倍流量；包含三项集合调用的全网单层发送为 **3.5 GiB／448 KiB**。

穿过 A/B 边界的边只有 `2→4、3→5、6→0、7→1`。prefill 单层 A→B 与 B→A 各 **384 MiB**，两向合计 **768 MiB**；decode 各 **48 KiB**，合计 **96 KiB**。同一规则经过 94 层后，两向总发送分别 **70.5 GiB／8.8125 MiB**。这里只将逻辑 ring 的边映射到服务器割集，没有把它当交换机全部物理跳数流量。

若两服务器分别可提供有效单向出口 `B_A`、`B_B`，则这部分单层传输至少受 `max(3M/B_A,3M/B_B)` 限制；有共同资源时先合并相应方向载荷。再按实际集合轮次、就绪与计算依赖修正。首尾 embedding、词表头、采样、入口 token 复制、路由记录准备、控制协议和分配器等尚未计入，以上不能当完整迭代时间。

完整逐轮 **80 条消息／阶段负载形状**、逐源／目的汇总、8 rank 的状态和矩阵工作均在 [results.json](results.json)。这里的两个阶段是同一请求的 prefill 与首次 decode，不是两个部署情景。

## 怎样接回已有子账与书稿

保留现有[独立源 token 的 All-to-All 结果](inputs/independent-source-communication.json)作为另一种 token 所有权条件下的案例；它的 8 个专家 rank、每源 64 个 token 和 29,360,128 bytes dispatch 不贴到本表。本情景与它的差异来自请求和计算分工，不来自一个更快的通信算法。

在实验 6-3 增加一个连接步骤即可：要求读者把已选容量表的请求身份与 TP／EP 成员写到矩阵图上，再推导需要 dispatch 还是部分结果归约。实验 7-3 将同一组成员映射到两个服务器，按有向边汇总割集；实验 7-10 用后续实测的有效链路与就绪时间检查这份布局。第 9 章把整个 DP1／TP2／EP4 组作为一个服务实例，再谈增加独立副本或 P/D 实例；不要把 EP4 当 4 个独立请求池。

第 10 章若进一步训练，需要显式添加相同参数的梯度同步及训练 DP／优化器分片，本推理案例不自动给出那套分组。没有新增未经核对的训练状态计数。

若之后决定使用 attention 侧分配不同请求的组织，就应同时重算 KV 所有权、非专家工作和源—目的派发，不保留本例的同 cohort KV 复制再借用另一组织的吞吐收益。这个改动作为后续已有练习的条件变化；本交付不再扩展第二情景。
