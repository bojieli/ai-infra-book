# SGLang 权重更新：结果汇总与恢复采样

本次固定 SGLang `c99d906effa8bd05573995127f0d4a0984c5a96a`，补读 `tokenizer_manager.py` 的磁盘权重更新路径。来源与原始字节见 `sources.json`，实际阅读范围见 `reading-proof.json`。这里只做静态阅读；没有执行框架、故障注入或测量恢复时间。

承接[下层安装与成功边界](../root-weight-update-boundary.md)，本次补齐一个重要区别：**磁盘更新的控制层已有多 worker 成功结果汇总，但汇总成功与完整恢复协议仍是不同的事情。** 不能把下层局部返回的观察扩大为“框架没有全体成功判断”。

## 普通磁盘更新的调用关系

| 阶段 | 所读实现 | 可据此说明的边界 |
|---|---|---|
| 请求进入 | 生成请求先等待暂停条件，再持有 reader lock 处理请求与响应 | 存在本地请求与更新协调；不是分布式事务证明 |
| 暂停 | 设置 `is_pause`；非 abort 模式异步发送暂停消息，abort 模式反复中止并检查锁 | 发出暂停消息不等于在本函数里收到全部 scheduler 的暂停确认 |
| 提交更新 | 未暂停时取得 writer lock，已暂停时使用空上下文；建立结果 future 后发消息 | 已暂停路径依赖外层暂停流程，不能只根据布尔值推出设备已经静止 |
| 汇总结果 | 预期数量来自 `elastic_worker_count`，初始值为 DP size；单 worker 直接返回，多 worker 收齐后取 `all(r.success)` | 不能把这里的 worker 数直接写成全部 TP／EP rank 数；下层如何汇总还需分别核对 |
| 发布管理层信息 | 成功才更新模型路径；成功且给定版本才更新 tokenizer 的版本信息 | 失败不发布新版本，并不证明所有已经修改的权重自动回滚 |
| 恢复 | `continue_generation` 清除暂停标志、发送继续消息并唤醒等待者 | 这个方法内没有检查上一次更新结果；更新方法也不自动调用它 |

响应处理函数按预期数量收集返回结果。所读函数没有显示逐响应的唯一 worker／事务版本核验；不能据此断言其他层没有检查，也不能据此报告重复响应漏洞。本次不覆盖弹性扩缩期间的并发更新。

## 如何用于第 10 章

仍使用已有阶段交接选做，不新增实验。让读者在时间线上分别标出：暂停完成、传输完成、各接收方安装结果、缓存处理、版本发布、恢复调用、首个有效 token。先记录成功路径，再给一个接收方失败的教学情景。

例如四个预期响应为成功、成功、失败、成功，聚合结果为失败。这个布尔运算可以确定，但不能推断前两个接收方保留旧权重。若系统原来已经暂停，调用方应先确认可恢复的一致状态，再允许继续；具体采用重载、重建还是其他恢复机制，需要相应调用方实现或实验作证，不能从此文件虚构。

对教学预算而言，四个响应的汇总等待由最晚到达的响应约束；恢复时间还包括必要的重载、缓存重建与首 token 工作。既不能把四个并行接收时间简单相加，也不能把最后一个响应到达当成服务已经恢复。这里不给未经测量的毫秒数。

本次已足以支撑提纲对责任边界的表述。RL 调用方的完整故障恢复、弹性更新、进程失联超时以及各后端的事务保证仍未验证；不把它们写成已经支持的能力。
