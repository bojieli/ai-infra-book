# DSpark：预算、紧凑窗口与执行图的三本账

## 已补足的接口证据

`local_verify_tier_num_tokens` 把每请求至少一个位置计入 floor，再加预算，并以完整窗口上限截断。因此这里的预算不是目标模型全部输入行数。`dp_global_verify_tier_num_tokens` 对有效需求取最大值；只要某参与项是负的 sentinel，就返回无共同预算限制的状态。调用方是否进入该模式仍取决于配置和工作阶段。

`schedule_layout` 区分 static、compact 和 verify-all 路径；紧凑路径还检查捕获槽位和最大档位。存在捕获档位时向上取整得到 `graph_num_tokens`，不是把逻辑总长直接当执行图大小。超出捕获范围返回 None；不能将这种返回解释成所有情况下仍运行同一紧凑图。

`_budget_aligned_to_graph_tier` 另有默认关闭的选项：把图向上取整和跨 rank 最大需求留下的预算余量，交给真实草稿位置。它不改变布局的档位算法，也不证明额外位置必然提高整体收益。是否启用必须与实验配置一并记录。

`run_compact` 将 layout 传入 `BuildRaggedVerifyWindow`，再经 `_run_ragged` 构造带 ragged layout 的目标验证输入。返回结果可以来自图内 epilogue，也可能要显式 scatter 回 strided 表示。因此紧凑输入并不意味着所有输出与中间缓冲都同步缩到相同长度。本轮没有读 BuildRaggedVerifyWindow 的 kernel 或完整 worker dispatch，不能据此宣称已核验全部实际内存访问。

## 接回已有四请求算例

第 8 章已有窗口为 7／3／2／2，包含每请求一个已有位置，合计14行。教学设定最大窗口7、每请求最少1、图档位8／16／32，则预算是14−4=10，执行档位为16。另一个 rank 需求25时，共同档位仍为32。自写整数推算见 `budget.json`，不调用下载函数。

启用上述可选余量填充时，本地16行档可把预算上限从10补到12；若共同档位32，本地四请求完整窗口最多28行，预算上限为24。这里说明的是预算容量，不能由上限反推 top-k 一定选择了某组窗口，更不代表所有多余验证都被接受。

两份上游测试文件的静态断言与这一区分相符：无预算 sentinel 会阻止独立降档；混合窗口8／1／3合计12，在 floor24与8／16／32／64档位下得到32行。padding 可以分布到多个槽，也可以扩展现有槽，测试还区分真实请求数与乘过草稿宽度的 token 数。这里只阅读预期断言，没有运行测试，不能报告上游测试通过或 GPU 路径通过。

## 采用与停止边界

只补现有第8.3节的动态验证变体：同时记录预算、真实窗口、图档位、DP共同需求及余量填充开关。判断逻辑窗口缩短是否转化为少做矩阵工作，再扣除规划、重排、草稿及状态维护的代价；不新增一种推测算法小节。

此次从原先仅有成本表的证据推进到了 planner→layout→verify 接口。仍待核的是 worker 的模式分派、布局物化与窗口构建 kernel；本轮不把这一缺口标为全部关闭。源码只能说明路径和条件，真实耗时仍需匹配模型、后端与配置的实验。原论文性能、官方文章表现和这个固定实现也仍分别记账。
